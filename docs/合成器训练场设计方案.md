# 合成器训练场设计方案

> 状态：**R-S1–R-S4 已实施**（2026-11-22），单元测试通过，mod 编译通过，待游戏内按 §6 验收。审阅结论：R1–R12 按建议执行；R11 的文案按审阅意见去掉了“每个放了材料的格子正好 n 个”。实施时补充的地方见 §7。
>
> 分析后已经确定的方向：
> - 判定用原版的配方匹配：合成器预览出的产物是目标，并且所有空格都已禁用。不比对固定格位，平移、镜像都算对；
> - 放 n 份：每个放了材料的格子正好 n 个，每种材料多发一些余量。n 不超过材料的堆叠上限；
> - 配方池是全部配方，先按形状分组抽，再抽配方；
> - 判定时机和酿造台一样，要求先关掉界面；
> - 只做 named 模式；
> - 场地 `crafter` 设在 `(10000, 120, 10360)`，每轮换一台新的合成器。
>
> 本方案沿用《工作台训练场设计方案》（下称"工作台方案"）和《酿造台训练场设计方案》（下称"酿造台方案"）的架构，下面只写不同的部分。

## 1. 用户原始流程

1. agent 传送到对应的训练场地中，正前方放一台合成器，视角对着它，直接右键就能打开
2. 清空 agent 身上的所有物品
3. 开始计时，发布和 3×3 工作台一样的任务，但有三点不同：
   1. 不需要合成出产物，只要把物品放到合成器对应的位置；
   2. 配方范围从 3×3 配方改为所有配方；
   3. 要求 agent 把配方中空余的位置禁用（用户原话是"上锁"，游戏里叫"禁用"）
4. 检测到合成器里正好是指定的物品（不多也不少）时，停止计时并记录

第 3 步的"对应位置"和第 4 步的"不多也不少"按 R2、R4 落实。

## 2. 已核实的事实

| # | 事实 | 对方案的影响 |
|---|------|------------|
| C1 | 合成器界面（`CrafterMenu`）：0–8 是合成格，9–35 是背包，36–44 是快捷栏，产物格是 `NonInteractiveResultSlot`（现在落在 45），只用来预览，拿不走也放不进。产物由服务端用 `CrafterBlock.getPotentialResults` 加 `assemble` 算好后同步给客户端 | 预览本身就是"合成器会做出什么"的原版答案，判定直接用同一个方法（R2） |
| C2 | 合成器只有被红石触发才真正合成，然后把产物吐出去 | "只放料、不合成"天然成立。场地里不放红石（R10） |
| C3 | 每个合成格都有禁用开关，存在方块实体的数据槽 0–8，数据槽 9 是"是否通电"。只有空格能禁用（服务端 `slotCanBeDisabled`）；禁用的格子放不进物品（客户端 `CrafterSlot.mayPlace`、服务端 `canPlaceItem` 都会挡）；用数字键把物品换进禁用格时，会先自动解除禁用 | 被禁用的格子一定是空的，"空格都禁用"这个条件不会和"放了材料"冲突 |
| C4 | mod 已经能读写禁用状态（v2.49）：<br>• `container/get` 返回 `disabledSlots`、`powered`、`result`；<br>• `container/click` 点空格时照原版 `CrafterScreen.slotClicked` 切换禁用，并发 `ServerboundContainerSlotStateChangedPacket`；<br>• 服务端通过数据槽把状态同步回客户端 | 不用新增任何界面 API |
| C5 | 原版的有序配方可以**平移**，也可以**左右镜像**；无序配方放在哪些格都行 | "对应位置"不唯一，不能比对固定格位（R2） |
| C6 | 合成器方块实体会存档格子里的东西、禁用状态和通电状态 | 每轮要换一台新的（R10） |
| C7 | Shift 点背包里的物品时，会按格子顺序 0–8 先补进已有的同种堆，再整堆放进第一个没禁用的空格 | 多发余量（R4）以后，整组塞进去会放多 |
| C8 | `recipes.json` 一共 1026 条配方（有序 706、无序 320），全部能放进 3×3，按形状归成 **88 种**。占比最大的是：两种材料的无序配方 183 条，单材料的无序配方 83 条，`AA/AA` 68 条，`AAA/ABA/AAA` 66 条，`AAA` 64 条 | 按配方等概率抽，近一半轮次会集中在少数几种形状上（R3） |
| C9 | 按配方占用的格数：1 格 83 条，2 格 252 条，3 格 105 条，4 格 114 条，5 格 51 条，6 格 205 条，7 格 48 条，8 格 24 条，9 格 144 条。占满 9 格的配方不需要禁用任何格子 | 报告按格数分组，能直接看出"要禁用几格"对成绩的影响（R9） |
| C10 | 按材料的最小堆叠上限：64 的 971 条；16 的 5 条（末影之眼、蜂蜜块、南瓜派、雪块、蜂蜜瓶做糖）；1 的 50 条（蛋糕、带箱子的船、床和挽具染色、发射器等） | 每格放 n 个，n 不能超过所有材料堆叠上限中最小的那个（R4） |
| C11 | `item-props.json` 已经覆盖 `recipes.json` 里出现的全部材料 | 不用重新提取数据 |
| C12 | 合成器是整格方块 | 工作台方案 W2 的俯角公式和 `aimOk` 自检可以直接用 |

## 3. 总体设计

```
/bt train crafter [n=a-b] [extra=a-b] [item=<id>] [runs] [seed]
  插件 crafter 题型：按形状抽配方 → 抽 n → 抽每种材料的余量 → 拆堆、打乱格位
  → arena/prepare { station: crafter, items, expect: { crafter: {...} } }
       mod：换一台新合成器、发物品、对准视角、用服务器配方核对产物
  → 发任务 → 轮询 arena/status（mod 在 tick 里记第一次到达的时刻）
  → 任务结束 → arena/status 拿最终状态 → 判定、写记录 → arena/finish
```

和酿造台场地的分工一样：**插件出题、判定，mod 负责场地、计数、核对配方和到达检测**。新增题型文件 `src/training/crafter.js`，其余复用训练器。

## 4. 决策点

### R1　场地、工作站和视角

- 场地 `crafter` 设在 `(10000, 120, 10360)`，和酿造台场地间隔 30 格。场外平台、告示牌、屏障墙沿用现有逻辑。
- 工作站 `crafter` 对应 `Blocks.CRAFTER`，位置和工作台一样在 `(ox, oy+1, oz+2)`。朝向用默认值，不影响交互。
- 视角、`aimOk` 自检、等 100 ms 再发任务，全部沿用工作台方案 W2（C12）。
- `opensStation` 认 `CrafterMenu`，记录第一次打开界面的时刻 `openedMs`。

**建议：采用。**

### R2　判定依据：按原版配方匹配，不比对格位

| 方案 | 做法 | 问题 |
|------|------|------|
| 固定格位 | 出题时定好每格放什么，逐格比对 | 平移、镜像后的摆法和无序配方的任意摆法也都合法（C5），却会被判错。"空格"跟着出题时的位置走，和 agent 实际摆的位置对不上 |
| **配方匹配** | **mod 用合成器预览产物的同一个方法（`getPotentialResults` + `assemble`，C1）算出产物；产物是目标，并且所有空格都已禁用** | 无 |

"空格"指 agent 实际没放材料的格子，跟着 agent 的摆法走。

**建议：配方匹配。**

### R3　配方池与抽样

- **配方池**：`recipes.json` 里的全部配方（C8），减去场地配置 `exclude`，默认不排除。sampler 的候选函数加一个"不排除更小格子"的选项，现有的 `craft2x2`、`craft3x3` 场地不受影响。
- **按形状分组抽**：先在 88 种形状里等概率抽一种，再在这种形状里等概率抽一条配方。形状的算法沿用工作台方案 W4（`shapeOf`）。用 `item=` 固定目标时不分组，直接在这个产物的配方里抽。
- **材料**：同一符号用同一种物品，沿用工作台方案 W3。

**建议：采用。**

### R4　数量：放 n 份，多发余量

| 物品 | 发多少 | 要放多少 |
|------|-------|---------|
| 配方里的每种材料 | 一份里用到的个数 × n，再加这种材料的余量 e。e 在 `extra` 里抽（缺省 `0-16`），每种材料各抽一次 | 每个放材料的格子正好 n 个。这种材料一共要放"一份里的个数 × n"个，余量全部留在物品栏 |

- `n` 在命令行写 `n=`（选项名 `portions`，和合成、酿造场地一致），缺省 `1-16`，上限 64。实际取值不超过本配方材料的最小堆叠上限（C10）：不可堆叠的配方只能 n=1，堆叠上限 16 的最多 16。如果 `n` 的下限超过了上限，就换一条配方，最多换 20 次，还不行就报错（沿用工作台方案的 `MAX_REDRAWS`）。
- 余量 e 不超过这种材料的堆叠上限，所以不可堆叠的材料最多多发 1 个。e 可以抽到 0；所有材料都抽到 0 时，"全部放进去"就是正确答案，这也是一种合法题型。
- 余量的选项叫 `extra`，不叫 `spare`：`spare` 已经被织布机和制图台使用，取值是 0–3，含义也不同。
- **拆堆**：每种材料按工作台方案 T14 的拆堆算法拆成若干堆，不给产物预留格位；再在 36 格里随机摆放，由种子决定。物品栏最多占用：5 种材料 × ⌈(9 × 16 + 16) / 64⌉ = 15 格，放得下。

**随机数的抽取顺序**（同一种子出同一道题）：形状 → 配方 → 材料 → n → 每种材料的 e（按材料顺序）→ 拆堆 → 打乱格位。

**建议：采用。**

### R5　计数和守恒

材料都是不带组件的普通物品，按物品 id 计数。mod 分别统计物品栏、光标、合成器 9 格、场内地上的数量。

**守恒**：每种材料都满足"物品栏 + 光标 + 合成格 + 地上 = 发放数"，不满足就说明有东西被扔出了场外。合成器不会真的合成（C2），所以不会有物品消耗。

### R6　判定

任务结束时，按最终状态判定，判定顺序沿用酿造台方案 P6：

| 顺序 | 结果 | 条件 |
|------|------|------|
| 1 | `aborted` | 手动停止；`prepare` 失败（包括 R8 核对不过） |
| 2 | `lost` | 合成器被挖掉；场内地上有物品；或者不守恒（R5） |
| 3 | `timeout` | 超时 |
| 4 | `success` / `false_success` / `failed` | 任务以完成结束时，到达条件（R7）成立就是 `success`，否则是 `false_success`；其余情况是 `failed` |

- 放多了可以再拿回来，所以不设 `overshoot`。
- 合成器只放了指定的材料，不会出现"放错格"的独立结果；放错格会表现为产物不对。

**失败原因 `faults`**：结果不是 `success` 时，记录里列出最终状态不满足的条件，可以同时有多条：

| 原因 | 条件 |
|------|------|
| `recipe` | 预览产物不是目标（包括没有产物） |
| `count` | 有放了材料的格子数量不是 n |
| `unlocked` | 有空格没有禁用 |
| `leftover` | 物品栏剩下的数量不对（放少了、放多了，或者混进了别的物品） |
| `open` | 界面没关，或者光标上还有东西 |

**建议：采用。**

### R7　到达条件

mod 在服务器 tick 里检测，记下第一次到达的时刻 `reachedAtMs`，不打断 agent。`Expect` 增加合成器写法：

```
expect: { crafter: { target, portions: n, held: { 材料 id: 应剩个数, … } } }
```

同时满足下面几条就算到达：

1. 容器界面已经关闭，光标为空；
2. 物品栏里每种材料恰好剩 `held` 里的数，没有别的东西；
3. 合成器每个非空格正好 `portions` 个；
4. 每个空格都已禁用；
5. 用合成器当前 9 格算出的产物 id 是 `target`。

满足 2–5 时，守恒已经保证合成格里一共放了"一份 × n"的材料。

**建议：采用。**

### R8　mod：换新、核对配方、`status`

**换新**：每轮 `prepare` 先把这个位置设成空气，再放一台新的合成器。这样格子里的东西、禁用状态、通电状态都会清掉（C6）。

**核对配方**：`prepare` 收到 `expect.crafter` 以后，用插件给的规范摆法验证产物：

- 有序配方把图案放在左上角；
- 无序配方按顺序放进 0 号格往后。

然后用 `getPotentialResults` 算产物。产物不是 `target` 就报错，插件记 `aborted` 并停止整组，提示"配方数据过期（重跑提取脚本），或者这条配方和别的配方冲突（加进 `exclude`）"。核对通过时，`prepare` 返回 `crafter: { product }`。

规范摆法由插件随 `expect.crafter.layout` 传过去（9 个元素，物品 id 或 null），mod 不用自己解析配方。

**`status`**：合成器工作站另外返回下面几项。都只读，`finish` 的顺序不用改。

- `held`、`carried`、`dropped`：按物品 id 计数；
- `crafter: { grid: [{ id, count } | null ×9], disabled: [格号…], result: id | null, powered }`；
- `containerOpen`；
- `stationIntact`。

**建议：采用。**

### R9　记录与报告

记录在工作台场地的公共字段之外增加：

| 字段 | 含义 |
|------|------|
| `recipe`、`shape`、`target` | 抽到的配方、形状、产物 |
| `cells` | 配方占几格（1–9）。要禁用的格数是 9 − `cells` |
| `portions` | n |
| `extra` | 每种材料多发的个数 `{ id: e }` |
| `items`、`slots` | 一份的材料、实际发放的格位 |
| `grid`、`disabled`、`result` | 结束时合成器的 9 格、禁用的格号、预览产物 |
| `faults` | R6 的失败原因 |
| `openedMs`、`reachedMs` | 第一次打开界面、第一次到达的用时 |
| `stationIntact`、`powered` | 合成器是否还在、是否通过电（正常应为 false） |

**报告**：

- 分组方式加 `cells`、`shape`、`portions`。`crafter` 场地默认按 `cells` 分组：88 种形状太散，格数直接反映要禁用几格。
- 失败原因按 `faults` 分别计数。

**建议：采用。**

### R10　超时、场地安全、合成器被挖、胶囊库

- **超时**：场地配置单独设 `timeoutSec`，默认 **900 秒**，和 3×3 工作台一样。最多要放 9 格、禁用 8 格。
- **红石**：场地里只有地板和屏障，合成器周围不放任何红石元件，也不发红石相关的物品。`powered` 进记录，用来兜底检查。
- **合成器被挖**：沿用工作台方案 W8：每轮换新，轮次进行中不补放，记 `stationIntact`，判 `lost`。
- **胶囊库**：不做特殊处理。合成器的格号和工作台不同（C1），工作台训练出的胶囊能不能迁移过来，正好在这里检验。

**建议：采用。**

### R11　任务文案

只写目标状态，不写做法。不提"右键打开"，也不提"点空格禁用"：怎么禁用由 agent 自己从 `command_docs` 和 `container/get` 的 `disabledSlots` 里查。用词和接口一致，用"禁用"，不用"上锁"。

模板 `prompts/training/crafter.md`：

```
你正前方有一台合成器（minecraft:crafter），视角已经对准它。你的物品栏里有合成 {{target}} 的材料。
请把材料放进合成器的合成格，让它合成出 {{target}}，并且材料正好够它合成 {{n}} 次，没放材料的格子全部禁用。放好以后关掉它的界面。用不完的材料留在物品栏里，不要动其他物品。
```

**审阅结论**：只写“材料正好够它合成 n 次”，不写“每个放了材料的格子正好 n 个”。合成器每次合成从每个非空格各取 1 个，“正好够 n 次、不剩料”就等于每格正好 n 个，判定（R7）不变，只是换算交给 agent。

### R12　暂不做的部分

- **hidden 模式**：没有"做出来"这一步，产物格又会直接显示结果，不说目标就没法出题。
- **真的触发合成**：不接红石，不考察产物吐出的方向和取产物。以后要练"自动合成线"再另做。
- **混入干扰物品**：物品栏里只有本配方的材料。需要时再加。
- **特殊配方**（烟花、地图复制、盔甲染色等）：`recipes.json` 里本来就没有，不出。

## 6. 验收清单（实施后）

1. `/arena crafter` 能传送到场外平台；`/bt train crafter runs=1` 进场后，第一次右键就能打开合成器，`aimOk=true`。
2. `container/get` 能看到 `disabledSlots`、`result`、`powered=false`；点空格能切换禁用，再开界面状态还在。
3. 有序配方放在非左上角的位置、或者左右镜像后，判 `success`。
4. 无序配方随意摆放，判 `success`。
5. 漏禁用一个空格，判 `false_success`，`faults` 含 `unlocked`。
6. 某格多放 1 个，判 `false_success`，`faults` 含 `count` 和 `leftover`。
7. 没关界面就宣布完成，`faults` 含 `open`。
8. 往地上丢一个材料，判 `lost`。
9. 挖掉合成器，判 `lost`，`stationIntact=false`。
10. 下一轮开始时，合成器是空的，也没有禁用格。
11. 不可堆叠材料的配方（例如蛋糕）只出 n=1，余量最多 1 个。
12. `training-report` 能按 `cells` 分组，并列出失败原因计数。

**补充**
- **失败原因多了 `foreign`**：出现材料以外的物品，例如在物品栏的 2×2 里用材料做了别的东西。这时材料变少不判 `lost`，按任务结束方式判 `false_success` 或 `failed`，`faults` 里记 `foreign`，记录的 `foreign` 字段列出这些物品。R6 原来没覆盖这种情况。
- **核对失败的提示**：插件提示"请重新运行 npm run extract-recipes，或把配方加进 exclude"（R8）。
- **测试**：插件 309 条、根目录 311 条测试通过。用真实的 `recipes.json` 抽 3000 个种子：
  - 发放总数守恒，没有超过堆叠上限的堆；
  - 蛋糕只出 n=1；
  - 物品栏最多占满 36 格（沿用 T14 拆堆，总堆数在 [最少堆数, 36] 里均匀抽）。

**2026-11-23 补充：手动停止的轮次也算失败原因**
- 之前 `judgeCrafter` 遇到手动停止（`/bt train stop`）直接返回，记录里的 `faults` 为空。现在只要拿到了最终状态，就照常计算失败原因、守恒和 `foreign`。结果仍判 `aborted`，手动停止优先于 `lost`。
- 这样复盘时能看出 agent 停在哪一步。报告里各失败原因的计数也包括这些中止轮次。
