## 0. 一句话与范围

**P2 让慢树在任务中途修自己，P3 让快树从经历里长出新反射；P4 让任务结束后把这次用得好的子树和代码存进胶囊库，下一次同类任务直接引用。**

| 在 P4 里 | 不在 P4 里 |
|---|---|
| 任务结束后的 `reflect` 请求：触发、会话、证据（§2、§3） | 胶囊准入（多图验证、测试图成绩，算法层 §8.8.2）——P6 训练 |
| `bt_inspect` 补"树的版本链"（原 `bt_history` 的后一半，§3.3） | 胶囊的 GC（§8.6）与淘汰 / 合并（§8.7） |
| `capsule_save` 工具：存子树、草稿转正、同名新版本（§4） | 按任务类型分片装载胶囊摘要（§8.7，库还小，全量进提示词） |
| 保存时查写死的值（集成方案 §5.4 第 5 条，§5） | `fact_write` / `fact_search` / `mc_source_*`（P5） |
| `bt_reflect_done`、提醒与重试、提示词（§6） | 胶囊的人工审查流程（集成方案 §5.1.0"审查方案将来落在转正这一步"） |
| 下一次规划能找到胶囊（§7） | 改执行器里 SubTree 的语义（P0+ 已实现，不动） |

**验收**（集成方案 §10）：跑完一次任务后存出一个胶囊；下一次同类任务的大纲直接引用它。§10 细化成可执行的场景。

## 2. 触发与会话

### 2.1 什么时候复盘【P4-D1】

| 结局 | 复盘？ | 理由 |
|---|---|---|
| `done`（根 SUCCESS） | **是** | 主要来源：整棵树跑通了 |
| `failed`：大模型 `bt_abort_task` | **是** | 失败的任务里也可能有跑通的部分（例如"找到工作台并打开"成功了，合成失败了）；T9 定的是"可判定的结局，不限于成功" |
| `failed`：同一请求 3 次不合法、展开 / 修复用尽、死后重生失败 | **是** | 同上 |
| `failed`：人 `/bt abort` | **否** | 集成方案 §7.3 已定"放弃当前任务，不进反思"。人想复盘可以手动 `/bt reflect`（§9） |
| `failed`：会话消失 / 被关 | **否** | 没有会话可发（集成方案审阅点 6） |

实现：`finishTask(state, reason, { by })`，`by ∈ { 'tree', 'agent', 'user', 'session', 'executor' }`，进 `task/failed` 事件和 `taskSummary`。`bridge.onTask` 按上表决定发 `reflect` 请求还是只发原来的 `task_end` 通知。配置 `reflect.enabled = false` 时全部退回只发通知。

### 2.2 在哪个会话里复盘【P4-D2】

**倾向：在任务所属的会话里**（集成方案 §7.2"一个任务属于发起它的会话"），用 `followup` 叫醒，和 `expand` / `failed` 一样是一个请求（`requestId` 形如 `r<N>`）。

| | 原任务会话（倾向） | 单开会话（像快树） |
|---|---|---|
| 大模型知道这棵树为什么这样写 | 知道（大纲、展开、修复都在上下文里） | 不知道，只能从版本链反推 |
| KV 缓存 | 前缀连续，便宜 | 新会话从头算 |
| 人看得到 | 在同一个对话里看到复盘过程与结果 | 要去会话列表里找 |
| 上下文变长 | 是。长任务的会话本来就长，复盘只多一回合 | 否 |

快树单开会话是因为它没有"所属任务会话"（P3-D7）。慢树有，就用它。

### 2.3 状态机：复盘不是执行器状态【P4-D3】

集成方案 §7.1 画的是 `done / failed → reflecting → idle`。**倾向：`reflecting` 只是 bridge 里一个在飞的 `reflect` 请求，执行器的任务状态停在 `done` / `failed`，不加新状态，也不挡新任务。**

- 执行器不需要知道复盘在不在进行：快树照跑，任务树已冻结
- 人在复盘期间 `/bt task` 新任务：允许。同一会话里回合是串行的，新任务的规划请求会排在复盘回合之后，所以第二次任务的大纲**天然能看到**刚存的胶囊（§10 场景 2 依赖这一点）
- 不挡新任务意味着复盘的证据不能放在 `executor.task` 上（新任务会把它换掉），见 §2.4
- `/bt status` 显示在飞的复盘请求；集成方案 §7.1 的图改成注明"reflecting = 在飞的 reflect 请求"

### 2.4 证据保留到复盘结束

| 证据 | 现在的寿命 | P4 |
|---|---|---|
| 任务对象（节点状态、黑板、快照缓冲、内存事件） | 到下一个 `startTask` 为止 | `reflect` 请求**持有这个任务对象的引用**；`bt_inspect` / `bt_view` 在复盘回合里读它，不读 `executor.task` |
| 代码草稿 | `endDrafts` 后不可引用 | 请求创建时把草稿表**拷一份**进请求（`req.drafts`）；`capsule_get task/…` 与 `capsule_save from: task/…` 在复盘回合里读这份。草稿区本身照旧在任务结束时关掉——新任务的 `beginDrafts` 不受影响 |
| 树版本链 | 磁盘上永久 | 不变 |
| 事件日志 | 磁盘上永久 | 不变 |

请求关闭（`bt_reflect_done`、放弃、会话消失）就丢掉引用。**进程重启时在飞的复盘直接丢弃**，不像快树那样重放：快照只在内存里，重放出来的复盘缺最重要的证据。

## 3. 复盘请求的消息：目录

沿用 P2 §4 的做法：消息只推一份目录，内容由大模型用 `bt_inspect` 自己取（不给的东西也不该塞进消息，I13 的理由同样适用于胶囊：值进了上下文就容易被抄成字面量）。

### 3.1 消息正文（`prompts/requests/reflect.md`）

```text
# 复盘请求 c1（任务 task-…-1，已结束：done，根 SUCCESS，用时 145 s）

任务：做一把木镐
结果：<task.result>

## 目录
树版本：v1 大纲 · v2 展开 n1.2 · v3 展开 n1.3 · v4 修复（failed @ n1.3.2）· v5 展开 n1.4
节点：共 23 个；SUCCESS 19 · FAILURE 2（n1.3.2 ×1，已修复）· 未执行 2
快照：before@n1.1 … after@n1.4.3（共 18 个）· interrupt · episode-end
事件：412 条（node 380 · request 6 · patch 1 · fast 3 …）
黑板键：recipe.pickaxe · plan.click · …（只列键名）
代码草稿：task/plan-grid@1a2b3c4d（被 n1.3.4、n1.4.2 引用，执行 3 次全部成功）· task/has-table@…（被 n1.2.1 引用，从未执行）

## 最终的树
<renderTree(最新版，带各节点最终状态)>

请按「任务复盘」决定要不要把这次任务里的子树 / 代码存进胶囊库：用 capsule_save 保存（可以多次），最后用 bt_reflect_done 结束（requestId: "c1"）。什么都不存也要用 bt_reflect_done 结束，并写明理由。

{{skill}}
```

目录里的每一项都是从任务对象和事件日志里**数**出来的，不含快照内容和黑板值。"草稿被谁引用、执行几次成功几次"让大模型不用逐个查就知道哪些草稿真的被用过。

### 3.2 准入的工具【P4-D4】

| 类 | 工具 |
|---|---|
| 查知识 | `command_docs` · `data_shapes` · `capsule_search` · `capsule_get` |
| 看树 / 看证据 | `bt_view` · `bt_inspect`（**不含 `live`**） |
| 提交 | `capsule_save` · `bt_reflect_done` |

- `bt_submit_*` / `bt_abort_task` 不准入：任务已结束，没有树可改
- **`bt_inspect live` 不准入**：任务结束后的现场和这次任务无关，却会把此刻的格子号、坐标带进上下文——而复盘的产物是要复用的树。快照（任务过程中的状态）照给：判断"哪一步做了什么"离不开它，和 P2 §4.5 同一个取舍
- `capsule_save` / `bt_reflect_done` **只在复盘回合准入**（guard 按回合绑定的请求类型放行，和 `bt_submit_patch` 只在修复回合可用一样）
- P5 之后加 `fact_*` / `mc_source_*`（集成方案 §5.1.2 的表）

### 3.3 `bt_inspect` 补树版本链【P4-D5】

原 `bt_history` 的"树版本链"部分（集成方案 §5.1 表，留 P4 再定）。**倾向：并进 `bt_inspect`，新增 `what: 'tree'`**，不单做工具：P2 已经把"看事件"并进了 `bt_inspect`，再拆一个工具只会让大模型多猜一次该用哪个。

| 参数 | 返回 |
|---|---|
| `{ what: 'tree' }` | 版本表：`[{ version, origin, at, nodes }]`，`origin` 是 `plan` / `expand <节点 id>` / `patch <请求类型> @ <节点 id>` |
| `{ what: 'tree', version: 3 }` | 第 3 版，渲染成和 `bt_view` 相同的带 id 文本（节点状态只在最新版上有意义，旧版不带状态） |
| `{ what: 'tree', version: 4, against: 3 }` | 两版之差：按节点 id 列出新增 / 删除 / 改动（改动给字段级差异：`ref`、`params`、`writes`……） |

- 名字用 `tree` 而不是 `versions`：`versions` 已经是查询数据源的版本（P2-D17），保持不变
- `origin` 从事件日志拼：`task/start` → v1、展开事件带节点 id 与新版本号、补丁事件带请求类型与节点 id。实施前核对这几种事件确实带了版本号（§11 #1）
- 两版之差在 `bt/diff.js`（按 id 对齐）。快树仍用 P3 的 `diffTrees`（按 arm 名字对齐，见 §10.1）
- 修复请求（`failed` 等）也能用 `tree`：P2 里大模型就常想知道"上一版补丁改了什么"

## 4. `capsule_save`

### 4.1 参数【P4-D6】

```text
capsule_save({
  requestId,                    // 当前 reflect 请求
  folder: 'code' | 'trees',
  name,                         // 库内名字（小写、点分），如 "craft.wooden-pickaxe"
  description,                  // 必填：一句话说清楚"做什么、在什么前提下"——它就是 manifest 里给规划看的那一行
  from?,                        // 出处：trees 写任务树里的节点 id（"n1.3"），code 写草稿（"task/plan-grid"）
  signature?, body?,            // code 从草稿转正时可省略（沿用草稿的）；trees 必填（编写格式）
  preconditions?,
  replaces?,                    // 库里已有同名条目时必填：被替换的那一版的 hash（§4.3）
  keepLiterals?                 // §5：确认保留的字面量，每条带理由
})
```

**子树由大模型自己写（编写格式），`from` 只记出处，不做自动提取。** 理由：

- 任务树里的子树读写的是**任务帧**里的黑板键（`$recipe.pickaxe`），胶囊不能读调用方的任务帧（行为树 §8.2）：哪些键变成 `inputs`、哪些写出变成 `outputs`、哪些字面量要提成参数，这正是复盘要做的判断，自动提取做不了
- 执行格式 → 编写格式的反编译要单独写一套，收益只是省大模型抄一遍
- 大模型写的 body 照常过 `saveCapsule` 的全部校验（编译、钉引用、以 `inputs` 为初始键过校验器），写错了按错误原文改

`from` 的用处：记进事件日志（§4.5）；§5 的字面量检查优先拿这个节点执行时的快照和黑板值做比对。`from` 写错（树里没有这个 id）就报错，不写也可以。

**不设"只能存跑成功过的子树"的门槛**：存什么、存得好不好由 agent 自己学（`agent-learns-not-taught`），准入门槛是 P6 训练的事（算法层 §8.8.2）。工具结果里**如实报告** `from` 节点的执行记录（执行 N 次、成功 M 次），给它判断用。

### 4.2 草稿转正

```text
capsule_save({ requestId, folder: 'code', name: 'craft.plan-grid', description: '…', from: 'task/plan-grid' })
```

- 省略 `signature` / `body` = 原样沿用草稿；给了就用给的（转正时顺手改名改参数）
- 草稿从请求里的那份拷贝取（§2.4），引用写 `task/plan-grid` 取这个任务里该草稿的最新版，也可以带 `@hash`
- `code/` 的名字和草稿名字可以不同（草稿名只在任务内有意义）

**子树里的 `task/…` 引用自动换成转正后的 `code/…`**【P4-D7】：现在 `saveCapsule` 一律拒绝 `task/` 引用（"save the draft as code/ first"）。大模型最自然的做法是照着任务树抄子树，里面全是 `task/…`。倾向：同一次复盘里，某个草稿（按 hash）已经转正过，存子树时把对它的引用自动改写成那个 `code/…@hash`，结果里列出改写了哪些；没转正过的照旧拒绝，错误信息写"先用 capsule_save 把 task/x 存成 code/"。

### 4.3 同名：新版本还是另存【P4-D8】

库本身已经支持"同名 = 新版本，manifest 指最新版，老版本原样留着、已钉住的树照用"。要定的是怎么避免**无意中**把一个不相干的同名胶囊顶掉：

- 名字在库里不存在：直接存
- 已存在：**必须写 `replaces: <当前最新版的 hash>`**，否则拒绝，错误里附上那个条目的说明和 signature，让大模型决定是"改进它"（带上 `replaces` 重交）还是"另起一个名字"
- `replaces` 不是最新版的 hash：拒绝（和快树补丁的 `base` 同一思路：在过期的版本上改要先看新版）
- signature 变了也允许作为新版本：老调用点钉的是老 hash，不受影响；新的规划按新契约写
- `locked` 条目不能被替换（人手放的基础条目）；`core.*` 内置名字本来就写不进去

大纲引用胶囊时可以省略 `@hash`，装载时钉到当前最新版（P0+ 已实现，不变）。所以"改进已有胶囊"立刻对下一次规划生效，而已经存下的任务树不受影响。

### 4.4 校验的顺序

1. 请求检查：`requestId` 是在飞的 `reflect` 请求、属于本会话
2. `name` / `description` / `from` / `replaces`（§4.1、§4.3）
3. 草稿转正：取草稿（§4.2）
4. `saveCapsule` 的现有校验；trees 先做 §4.2 的 `task/` 改写
5. **子树丢了 `read`**（trees 且给了 `from`；2026-10-26 游戏内验收后加，§10.3）：出处子树里调用某段代码的节点带着 `read`，胶囊里调用同一段代码（按名字认，草稿看它转正成了谁）的节点少了其中的来源 → 拒绝，指出原节点用的 `read`
6. **字面量检查**（§5）
7. 写库

任何一步失败都返回逐条错误、不写库；**不计入"不合法次数"**：复盘不改树，反复存不对没有副作用，回合结束时还没 `bt_reflect_done` 由提醒兜住（§6.2）。

### 4.5 落盘与记录

- 写库：`library.write`（manifest 更新，系统提示词的胶囊清单下一回合就变，§7.1）
- 任务事件日志记一条 `capsule/saved { requestId, ref, folder, from, replaces?, created, keptLiterals? }`
- **胶囊条目里不记出处**：算法层 §8.2 已定"没有 `origin` 字段"，要追溯出处看事件日志（`ref` → 任务 id → 那次的树和快照）
- 工具结果：`{ ref, created, rewritten?: [...], from?: { runs, successes } }`

## 5. 保存时查写死的值【P4-D9】

集成方案 §5.4 第 5 条：P2 / P3 的证据里有具体值，"不写死"最终的关口在保存胶囊时。

### 5.1 比对什么

**对象**：要保存的条目里的字面量——trees 是编译后每个节点 `params` 里不是 `$` 引用的值（含 `steps` 里的命令参数），code 是 `body` 源码里的**字符串**字面量（2026-10-26 起不比数字，§10.3；扫源码，不做语义分析）。

**和谁比**：这次任务里**观察到**的值（2026-10-26 前是"树自己读到或算出来"的，§10.3）——

| 证据 | 取哪些值 |
|---|---|
| 任务结束时的黑板 | 观察来的键的全部叶子值：初始黑板、`core.*` 查询与动作写下的。**不取**大模型自己的 Compute 代码写下的键、ForEach 的 `as` / `indexAs` |
| 快照（`from` 给了就只取那个节点执行期间的，否则全部） | 背包的格子号与物品 id、`container` 的格子号、坐标（`x/y/z` 取整）、朝向（取整） |

**不比**：布尔、`-1..2` 的整数、空串、长度 ≤ 2 的字符串；命令注册表里该参数是枚举的（如按键名）；`wait` 的 tick 数。这些重合大多是巧合。

### 5.2 命中了怎么办

**倾向：拒绝，但可以显式保留。** 返回每一处命中：

```text
n.2.params.slot = 36   与 before@n1.3.4 的 inventory 里 oak_log 所在格子号相同
n.4.params.item = "minecraft:oak_planks"   与黑板 recipe.pickaxe.ingredients[0].item 相同
→ 改成参数（signature.inputs + "$名字"）或读取节点；确实是常量就写进 keepLiterals：
  { "n.4.params.item": "这个胶囊就是做木板的，物品固定" }
```

重交时 `keepLiterals` 里的每一处都要带理由，理由记进 `capsule/saved` 事件。

| | 拒绝 + 可保留（倾向） | 只警告 | 一律拒绝 |
|---|---|---|---|
| 抄格子号这种真错误 | 挡住 | 存进去了，工具结果里一句话很容易被忽略 | 挡住 |
| "做木板的胶囊里写 oak_planks"这种合理常量 | 写一句理由就能过 | 能过 | 过不去，只能硬改成参数 |
| 多一回合 | 命中时多一次 | 不多 | 命中时多一次 |

这是**保存关口的硬规则**，不是教写法：它只说"这个值和那次任务里读到的值一样"，改成参数还是读取节点、还是声明保留，由大模型判断。

### 5.3 已知漏洞

- 换个表达就躲过去（写 `35 + 1`、拼字符串）：P4 不防。这类绕过要靠 P6 的多图准入（换张图就失效）
- 只比这一次任务的证据：抄了别的任务里的值查不出来

## 6. `bt_reflect_done`、提醒、提示词

### 6.1 `bt_reflect_done`

```text
bt_reflect_done({ requestId, summary })
```

- `summary` 必填：存了什么、为什么；什么都没存就写为什么没有值得存的（和 `fast_skip` 必须写理由同理）
- 结束请求：丢掉任务对象和草稿拷贝的引用（§2.4）；记 `reflect/done { requestId, saved: [refs], summary }`（`saved` 由工具自己统计，不靠大模型报）
- 之后再调 `capsule_save` → 请求已关闭

### 6.2 回合结束没交 / 回合出错【P4-D10】

复用 P1 的提醒与重试：

- 回合结束还没 `bt_reflect_done` → `steer` 提醒一次（`requests/reflect_reminder.md`，列出本请求已经存了哪些）
- 提醒后的回合仍没交 → 请求按 `abandoned` 关闭，**已经存进库的胶囊保留**（每次 `capsule_save` 都是独立生效的）
- 回合出错 → 自动重试（同 P1，最多 3 次），用尽按 `abandoned` 关闭
- 关闭后给会话发原来的 `task_end` 通知吗？**不发**：复盘请求本身已经告诉过会话任务结局

### 6.3 提示词

| 文件 | 内容 |
|---|---|
| `prompts/requests/reflect.md` | §3.1 的消息 |
| `prompts/requests/reflect_reminder.md` | 提醒 |
| `prompts/requests/reflect_retry.md` | 回合出错后的重试（通用的 `retry.md` 叫人用 `bt_abort_task`，复盘里没有这个工具） |
| `prompts/skills/review.md` | 「任务复盘」skill |

「任务复盘」只讲**机制和规则**，不讲"该存哪些"（`agent-learns-not-taught`）：

- 胶囊是什么：下一次规划能直接 `use: trees/…` / `compute code/…` 的条目；规划时看到的是 `name` + `description`
- 胶囊不能读调用方的任务帧：用到的外部值要成为 `signature.inputs`，调用点用 `params` 传入；写出的值是 `outputs`
- 子树、草稿怎么存（`capsule_save` 的参数、`from`、`replaces`、`keepLiterals`）；用 `bt_inspect tree` 看版本链
- 字面量检查会拒绝什么、怎么处理
- 什么都不存是合法的结局

**不写**：哪类子树值得存、粒度该多大、名字怎么起、参数该提几个。这些是训练里要学的。

现有的 `skills/reflect.md`（「慢树反思（任务中）」，`failed` 请求用）不改。

## 7. 下一次规划能找到胶囊

### 7.1 系统提示词里的清单（已有）

`catalog.js` 每次组装提示词时把库里每个条目列成"名字（种类）：说明"。存了新胶囊，**下一个回合**的系统提示词里就有它。代价：库变了，系统提示词的这一段变，KV 缓存从这里失效一次——只在保存胶囊时发生，可以接受（集成方案 §6.3）。

### 7.2 `capsule_search`【P4-D11】

现在是"整串子串匹配引用名或说明"。规划时大模型多半会搜任务里的词（"木镐"、"合成"），整串匹配容易落空。倾向：**按空白拆成多个词，任一命中即返回，按命中词数排序**；不做分词和语义检索——库现在只有个位数条目，清单已经全量在系统提示词里，搜索只是补充。库大到清单放不下时（算法层 §8.7 分片），再一起重做。

`skills/outline.md` 第一步已经是"`capsule_search` 看有没有做过的同类子树或代码"，**不改**：要不要用、怎么用胶囊是规划时自己判断的。

## 10. 实施顺序与验收

**顺序**：

1. **P4a 证据**：`finishTask.by`、`reflect` 请求的创建 / 持有任务对象 / 草稿拷贝、复盘目录、`bt_inspect tree` 与 `bt/diff.js`
2. **P4b 保存**：`capsule_save`（转正、`task/` 改写、`replaces`）、字面量检查
3. **P4c 结束**：`bt_reflect_done`、提醒与重试、guard、提示词
4. **P4d 收尾**：`/bt reflect`、`capsule_search` 多词、文档（集成方案 §5.1 表、§7.1 图、§10 行；`已实现内容.md`；插件 README）

每步带单元测试（假的 mod + 假的会话，同 P2 / P3）。

### 10.1 实现中定下的细节

- **请求 id 用 `c<N>`**：执行器自己的请求是 `r<N>`，复盘请求由 bridge 发，另起前缀免得撞号
- **`finishTask` 的 `by`**：`tree`（根 SUCCESS）/ `agent`（`bt_abort_task`）/ `user`（`/bt abort`，`abortTask` 的缺省）/ `session`（会话没了）/ `executor`（其余：展开 / 修复次数用尽、重生失败、本地应答器放弃）。进 `task/failed` 事件和任务摘要
- **版本链存在任务对象里**（`task.versions`，每版带 `origin` 与 spec），同时照旧落盘。不从事件日志拼：`runtimeDir` 为 null（测试）时也有版本链；`origin` 在写版本时就知道
- **快树的差异没有并进 `bt/diff.js`**（与 §3.3 原写的不同）：快树补丁按 arm 名字寻址（P3-D8），按名字对齐才对得上"改了哪条反射"；任务树按 id 对齐。两者不是同一种差异
- **`bt_inspect tree` 的 `against` 是字符串**（`"3"`）：和 `snapshot` 共用同一个参数，那边是快照名
- **复盘回合里 `eval` 也要给 `at`**：不给就是用现在的状态求值，和 `live` 同理
- **`capsule_save` 只在复盘回合可用**：guard 对 `capsule_save` / `bt_reflect_done` 单独检查回合绑定的请求（`REFLECT_ONLY_TOOLS`）；bridge 再按 `requestId` 查一遍
- **复盘回合认会话不认回合**：`bt_inspect` / `bt_view` / `capsule_get task/…` 只要本会话有在飞的复盘请求就看它持有的任务。同一会话的回合是串行的，复盘回合结束（交了或被关闭）之前不会有别的回合
- **`capsule_save` 的字面量证据**：trees 给了 `from` 就只取那个节点及其子节点的快照，code 取全部快照；黑板取观察来的键（§5.1）
- **字面量被拒时附一份 `keepLiterals` 模板**：键是命中的原样位置、值是占位，大模型删掉改成参数的、其余填理由（§10.3）

### 10.2 游戏内验收

| # | 场景 | 通过的标准 |
|---|---|---|
| 1 | `/bt task 做一把木镐`，跑到 `done` | 自动发出复盘请求；大模型至少存下一个胶囊（子树或转正的草稿），`bt_reflect_done` 结束；`src/capsules/manifest.json` 里出现新条目；事件日志里有 `capsule/saved` |
| 2 | 清掉木镐（材料恢复到场景 1 开始时），再 `/bt task 做一把木镐` | 大纲里出现 `use: trees/…` 或 `compute code/…` 引用场景 1 存的条目，任务 `done` |
| 3 | 换一种起始条件（材料放在别的格子 / 工作台换个位置），再做一次 | 同一个胶囊仍然能用（检验没有写死格子号、坐标）；不能用就看复盘是否改进了它（`replaces`） |
| 4 | 做一件当前做不到的事（比如没有铁却要铁镐），大模型 `bt_abort_task` | 仍然发复盘请求；结局可以是什么都不存（`summary` 写了理由） |
| 5 | 任务进行中 `/bt abort` | 不发复盘请求，只有通知；随后 `/bt reflect` 能手动发 |
| 6 | 复盘回合里调 `bt_inspect live`、`bt_submit_patch` | 被 guard 拒绝 |

场景 2 是集成方案 §10 的验收标准本身；场景 3 是"可复用"的最低检验（P6 的多图准入是它的正式版）。字面量检查（§5）是否在场景 1 里被触发取决于大模型怎么写，单元测试覆盖它；游戏里触发了就记录结果。

### 10.3 第一轮游戏内验收（2026-10-26）

| # | 结果 |

| 1 | **通过**。`做木镐`（`task-20261026123953-1`）一次跑通（170 s），复盘 c1 存了 4 条代码（草稿转正）+ 1 棵子树 `trees/crafting.put-recipe-and-take` |
| 2 | **通过**（同类任务换成木斧）。`做木斧`（`task-20261026124806-2`）的规划先 `capsule_search`，大纲直接引用 `code/container.is-type`、`code/inventory.wood-materials`，两次展开用了 `trees/crafting.put-recipe-and-take` |
| 3 | **一半**：换了产物，没有专门换格子 / 工作台位置。胶囊在木斧任务里第一次用就失败（见下），P2 修复后任务 `done`（210 s）；复盘 c2 用 `replaces` 换掉了出错的子树与点击计划代码，老版本留着 |

**发现的两个问题与改动**（同日改完，单元测试 119 个通过）：

1. **子树胶囊丢了 `read`**：c1 重写子树时把两个 Compute 节点的 `read` 漏了（任务树里原节点有 `read: ["container"]` / `["container","inventory"]`；会话日志里 `capsule_save` 的参数就没有），保存时看不出来，木斧任务里 `state` 是 undefined。
   → §4.4 第 5 步：对照 `from` 子树查 `read`。用 c1 当时的数据重放：两处都报出；c2 修好的版本不报
2. **字面量检查零真命中、十次误报**：c1 两条代码被拒一次；c2 四条代码被拒，又因 `keepLiterals` 的键写成 `body:L27`（少了字面量后缀）再被拒一次。被拒的全是合成格号 9 / 4、"1 原木 → 4 木板"的 4、match 词表 `planks` / `stick`——和**它自己的代码算出来**的黑板值（循环下标、`recipe-cells` 算出的格位）相同。
   → 证据只取观察来的黑板键；代码只比字符串；被拒时附 `keepLiterals` 模板（§5.1、§10.1）。按新规则这十次都不会命中（推断：黑板值当时没落盘，不能重放）

| # | 位置 | 问题 | 倾向 |
|---|---|---|---|
| **P4-D1** | §2.1 | 哪些结局复盘 | **已定**：`done` 与大模型 / 执行器判定的 `failed` 都复盘；人 `/bt abort`、会话消失不复盘（可手动 `/bt reflect`） |
| **P4-D2** | §2.2 | 在哪个会话复盘 | **已定**：任务所属的会话，`followup` 叫醒，作为一个 `reflect` 请求 |
| **P4-D3** | §2.3 | `reflecting` 是不是执行器状态 | **已定**：不是：只是一个在飞请求；不挡新任务；证据由请求持有 |
| **P4-D4** | §3.2 | 复盘回合准入哪些工具 | **已定**：查知识四个 + `bt_view` + `bt_inspect`（不含 `live`）+ `capsule_save` + `bt_reflect_done` |
| **P4-D5** | §3.3 | 树版本链放哪 | **已定**：并进 `bt_inspect`，新增 `what: 'tree'`（版本表 / 某一版 / 两版之差）；修复请求也能用 |
| **P4-D6** | §4.1 | 子树怎么来 | **已定**：大模型按编写格式自己写，`from` 只记出处；不做自动提取；不设"跑成功过"门槛，只报告执行记录 |

| **P4-D10** | §6.2 | 没交 / 出错 | **已定**：提醒一次，再没交按 `abandoned` 关闭；已存的胶囊保留；出错重试同 P1 |
