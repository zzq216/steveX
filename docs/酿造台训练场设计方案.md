# 酿造台训练场设计方案

> 状态：**P-S1–P-S4 已实施**（2026-11-22），单元测试通过，待游戏内按 §6 验收。审阅结论：P1–P14 全部按建议执行。实施时补充、改动的地方见 §7。
>
> 分析后已经确定的方向：
> - 题型只做"放置"，模仿熔炉场地：只练把指定数量的烈焰粉、酿造材料、药水放进对应的格子，不要求酿出产物；
> - 判定看物品栏少了多少，不盯酿造台格子里的数量；
> - 每轮换一台新的酿造台；龙息用完剩下的玻璃瓶不算丢失；
> - 抽题先抽材料、再抽配方，配方由 mod 核对；
> - 材料是烈焰粉的配方排除；海龟壳按堆叠上限只发 1 个；
> - 换瓶子的配方（火药、龙息）和喷溅、滞留药水的配方都出；
> - 场地 `brewing` 设在 `(10000, 120, 10330)`。
>
> 另外定了要生成酿造配方的 json 文件（P10）。
>
> 本方案沿用《熔炉训练场设计方案》（下称"熔炉方案"）第二版的做法：只练放置；按物品栏少了多少判定；放好以后关掉界面才算完成；炉子按原版速度工作，不加速。整体架构同前几个方案：插件主控，mod 以服务器身份操作场地；每轮一个新会话；记录写进 jsonl；"恰好达到"的时刻由 mod 在 tick 里检测。下面只写和熔炉方案不同的部分。
>
> 目标：在已有场地旁边另建一块场地，场内正前方放一台酿造台。训练 agent 把指定数量的烈焰粉放进燃料格、把指定数量的酿造材料放进材料格、把指定几瓶药水放进药水格，然后关掉界面。以后再练"想酿某种药水，该往哪些格子放什么"时，这里练出的放置能力可以直接用上。

## 1. 用户原始流程

1. agent 传送到对应的训练场地中。正前方放一台酿造台，agent 的视角对着它，直接点右键就能打开
2. 清空 agent 身上的所有物品
3. 开始计时，并发布任务：从酿造台配方中随机选 1 个，给 agent 1 格烈焰粉和 1 格配方里的酿造材料，数量都在 32–64 之间随机；再给 n 瓶配方里要放进去的药水（n 在 1–3 之间随机）。要求 agent 把 1–32 个烈焰粉放进燃料格，把 1–32 个酿造材料放进材料格，把 1–n 瓶药水放进药水格
4. 检测到酿造台里恰好是目标物品（不多也不少）时，停止计时并记录

第 1–3 步保留，数量范围照用（P3、P4）。第 4 步改成看物品栏少了多少，再加上关掉界面的要求（P5、P6）：

- 烈焰粉一放进燃料格就会被吃掉 1 个（F3）；
- 酿造会自己开始，20 秒后药水变了、材料少了（F4）。

所以"酿造台里恰好是目标"这个状态，要么永远不出现，要么只在一段时间里成立。

## 2. 已核实的事实

依据 `1.21.11_src` 的 `BrewingStandBlockEntity`、`BrewingStandMenu`、`BrewingStandBlock`、`PotionBrewing`、`Potions`、`Items`、`VanillaItemTagsProvider`，以及 mod 现有的 `InventoryApi`、`ContainerApi`、`ArenaManager`。

| # | 事实 | 对方案的影响 |
|---|------|------------|
| F1 | 酿造台有 5 格：<br>• 0–2 是药水格，只收药水、喷溅药水、滞留药水、玻璃瓶，每格最多 1 个；<br>• 3 是材料格，只收 `isIngredient` 为真的物品；<br>• 4 是燃料格，只收 `brewing_fuel` 标签的物品（1.21.11 里只有烈焰粉）。<br>菜单里 5–31 是背包，32–40 是快捷栏 | n 瓶药水要放进 n 个药水格，"1–n 瓶"可行 |
| F2 | 药水、喷溅药水、滞留药水都是一个一叠。同一种瓶子的药水 id 相同，区别在 `potion_contents` 组件 | 计数要按"id + 药水种类"区分（P7） |
| F3 | **烈焰粉一放进燃料格就被吃掉 1 个**：每个 tick，只要燃料值 ≤ 0、燃料格里有烈焰粉，就把烈焰粉扣 1 个、燃料值设成 20（`FUEL_USES`），不管有没有在酿造 | 放进 k 个，格子里马上只剩 k−1 个，看格子数判定不成立（P5）。被吃掉的这 1 个要算作"放进去了" |
| F4 | **满足条件就自动开始酿造**：燃料值 > 0，并且材料格里的材料对任一药水格的药水有配方。400 tick（20 秒）后，每个药水格都变成配方的产物，材料扣 1 个；燃料值每开始一次酿造扣 1 | 放好以后酿造台里的东西还会变。判定不能看材料格的数量和药水的种类（P5、P6） |
| F5 | 材料用掉后如果有剩余物（龙息剩玻璃瓶）：材料格空了，玻璃瓶就放回材料格；材料格还有材料，玻璃瓶就**掉在酿造台旁边的地上** | 地上的这种玻璃瓶不算丢失，材料格里的这种玻璃瓶也不算放错（P6） |
| F6 | Shift 点烈焰粉时先往燃料格放，燃料格满了就**接着放进材料格**（烈焰粉也是材料：粗制药水 + 烈焰粉 → 力量药水）。Shift 点药水时依次填进空的药水格 | 会放错格。材料是烈焰粉的配方要排除，否则燃料和材料是同一种物品，只看物品栏分不清各放了多少（P3） |
| F7 | 酿造台的方块实体会保留燃料值、格子里的东西和酿造进度 | 每轮要清空并换一台新的，同熔炉方案 K12（P11） |
| F8 | 配方写在代码里，不在 jar 的 json 里（`PotionBrewing.addVanillaMixes`）：<br>• `addMix(药水 A, 材料, 药水 B)` 41 条；<br>• `addStartMix(材料, 药水 B)` 11 条，每条展开成"水瓶 + 材料 → 平凡的药水"和"粗制的药水 + 材料 → B"两条；<br>• `addContainerRecipe` 2 条：普通 + 火药 → 喷溅，喷溅 + 龙息 → 滞留；<br>• `addContainer` 3 种瓶子。<br>药水配方对三种瓶子都成立（`hasPotionMix` 只看药水种类，不看瓶子）；换瓶子的配方保留药水种类。46 种药水都没有特性开关限制 | 出题和 agent 查配方都要用到这份表（P3、P10） |
| F9 | 材料严重扎堆：红石出现 14 次、发酵蛛眼 12 次、荧石粉 10 次，其余 16 种材料各 1 次（另有火药、龙息） | 按配方等概率抽，大约一半题的材料是这 3 种。要先抽材料再抽配方（P3） |
| F10 | 海龟壳是材料，但一叠只能放 1 个；其余材料、烈焰粉都是 64 个一叠 | "1 格 32–64 个"对海龟壳做不到，按堆叠上限只发 1 个（P4） |
| F11 | `PotionBrewing` 有公开的 `isIngredient`、`hasMix`、`mix` 方法，服务器通过 `level.potionBrewing()` 拿到 | mod 能直接用服务器的配方核对题目、算出产物，不用写 mixin（P8） |
| F12 | `slotItem` 从 v2.48 起给出 `potionContents { potion, effects }`；`container/get` 的酿造台分支给出 `fuel`（剩余可酿次数，0–20）和 `brewingTicks`（剩余酿造 tick） | agent 这边的观察已经够用，不用补字段 |
| F13 | 2×2 合成里，4 个荧石粉能合成荧石，其余材料在 2×2 里都合不成东西（红石块、金胡萝卜等要 3×3） | 合出荧石就出现了开局没有的物品，判为放错（P6） |
| F14 | 酿造台的方块形状是一根 2 像素宽的立柱（高 2–14 像素）加一块薄底座，不是整格方块 | 现有俯角公式对准方块中心，正好落在立柱上，`aimOk` 自检照常做（P1）；游戏内要确认第一次右键就能打开 |

## 3. 总体设计

流程和熔炉方案相同：

1. 插件出题；
2. `arena/prepare` 换一台新的酿造台、发材料、对准视角、核对配方、登记目标；
3. 发布任务，轮询 `arena/status`；
4. 任务结束后调用 `arena/finish`，判定并写记录。

插件侧新增训练题型 `brew`，实现放在新文件 `src/training/brew.js` 里，接口和 `cook.js` 相同。训练器、记录、报告、每轮新会话都直接复用。

mod 侧的改动：

1. 增加工作站 `brewing_stand`、场地 `brewing`，每轮换新；
2. `prepare` 能发指定种类的药水（`items[].potion`）；
3. 酿造台工作站的 `status` 按签名计数物品栏、光标、酿造台五格、地上；
4. `Expect` 增加"酿造台"写法；
5. 记录本轮酿造了几次（P9）。

数据：生成 `data/brewing.json`，出题用，也开放给 agent 查（P10）。

## 4. 决策点

### P1　场地、工作站和视角

- 新增场地 `brewing`，origin 设在 `(10000, 120, 10330)`，在制图台场地 `(10000, 120, 10300)` 之后，间隔 30 格。场地的搭建、清场、屏障墙、告示牌逻辑原样复用。
- 酿造台放在 `(ox, oy+1, oz+2)`。酿造台没有朝向属性；三个药水瓶位置的方块状态由酿造台自己更新。
- 俯角用现有公式对准方块中心，射线落在中间的立柱上（F14），`aimOk` 自检照常做。
- `/arena brewing` 传送到场外平台，`/bt train brewing` 开始训练。

**建议：采用。**

### P2　题型：只做放置

模仿熔炉场地，只练"把指定数量的东西放进对应的格子，然后关掉界面"：

- 不要求等酿造完成，也不要求把产物拿回物品栏；
- 不加速酿造台，按原版速度工作；
- 文案里写明放什么、放几个，所以这一轮里 agent 用不着自己查配方（P12）。

"想酿某种药水该放什么"留到以后的题型（P14），那时 agent 要用到配方数据（P10）。

**建议：采用。**

### P3　配方池与抽样

**配方池**：从 `data/brewing.json`（P10）展开成"开局药水 + 材料 → 产物"三元组：

- 药水配方 × 三种瓶子：`{ 瓶子, 药水 A } + 材料 → { 同一种瓶子, 药水 B }`；
- 换瓶子的配方：
  - 火药：`{ potion, 任意药水 } → { splash_potion, 同一种药水 }`；
  - 龙息：`{ splash_potion, 任意药水 } → { lingering_potion, 同一种药水 }`。

  这里的"任意药水"取配方表里出现过的药水（含水瓶），不出酿不出来的药水。

去掉下面几类：

1. 材料是烈焰粉的（F6）；
2. `exclude` 里的材料、药水 id。

**抽样**：先在材料里等概率抽一种，再在用这种材料的配方里等概率抽一条（F9）。

| 方案 | 做法 | 效果 |
|------|------|------|
| A | 按配方等概率抽 | 红石、发酵蛛眼、荧石粉三种材料约占一半 |
| **B** | **先抽材料，再在材料内抽配方** | 每种材料的机会相同；红石这类材料内部仍然覆盖不同的药水和瓶子 |

`input=<材料 id>` 固定材料，这时跳过材料抽样；固定的材料被排除了，就直接报错。

**建议：B。**

### P4　数量

| 物品 | 发多少 | 要放多少 |
|------|-------|---------|
| 烈焰粉 | 1 格，F 个，在 `fuel` 里抽（缺省 `32-64`） | m 个放进燃料格，在 `m` 里抽（缺省 `1-32`），不超过 F |
| 酿造材料 | 1 格，R 个，在 `raw` 里抽（缺省 `32-64`），不超过它的堆叠上限（海龟壳只发 1 个，F10） | n 个放进材料格，在 `n` 里抽（缺省 `1-32`），不超过 R |
| 开局药水 | b 瓶同一种，b 在 `bottles` 里抽（缺省 `1-3`） | p 瓶放进药水格，p 在 [1, b] 里随机 |

- 选项名和熔炉场地对齐：`raw` / `fuel` 是发的总数，`n` / `m` 是要放的个数（`n` 对应材料格，`m` 对应燃料格），`input` 固定材料。另加 `bottles`。
- 3 种物品各占格子，在 36 格里随机摆放（药水一瓶一格），由种子决定。

**随机数的抽取顺序**（同一种子出同一道题）：材料 → 配方 → F → R → b → m → n → p → 打乱格位。

**建议：采用。**

### P5　放料怎么判：看物品栏少了多少

和熔炉方案 K4 同理。F3、F4 说明酿造台格子里的数量和药水种类都会自己变，所以按物品栏、光标、酿造台五格、场内地上分别计数，判定看物品栏：

- 物品栏里烈焰粉恰好剩 F − m，材料恰好剩 R − n，开局药水恰好剩 b − p；
- 放完以后，不管酿造台怎么吃燃料、怎么酿，这个状态都保持不变，检测时刻是确定的。

药水格另外检查一条：三个药水格里一共恰好 p 瓶，每一瓶都是开局药水或它的产物。酿造是一瓶换一瓶，所以这个数不会变。这一条防的是"把药水放进去又拿出来一瓶"或"药水放到了别处"。

| 方案 | 做法 | 问题 |
|------|------|------|
| 用户原案 | 看酿造台里的数量和种类 | 燃料部分永远不成立（F3）；酿造完药水和材料都会变（F4） |
| **A** | **看物品栏少了多少，药水格只数瓶数** | 无 |
| B | 冻结酿造台：放对之前不让它吃燃料、不让它酿 | 要改原版行为（mixin），agent 看到的酿造台和源码不符；熔炉方案已经否了这条路 |

**建议：A。**

### P6　判定

任务结束时按 P5 的几处计数，判定顺序沿用熔炉方案 K7：

| 顺序 | 结果 | 条件 |
|------|------|------|
| 1 | `aborted` | 手动停止 |
| 2 | `lost` | 酿造台被挖掉；场内地上有物品（龙息剩下的玻璃瓶除外，F5）；或者不守恒（见下） |
| 3 | `overshoot` | 吃掉的烈焰粉 > m，或者用掉的材料 > n。吃掉、用掉的拿不回来 |
| 4 | `misplaced` | 燃料格里有烈焰粉以外的东西；材料格里有本题材料以外的东西（Shift 溢出进来的烈焰粉，F6；龙息剩下的玻璃瓶除外）；药水格里有开局药水和产物以外的东西；或者出现了开局没有的物品（2×2 合出的荧石，F13） |
| 5 | `timeout` | 超时 |
| 6 | `success` / `false_success` / `failed` | 任务以完成结束时，到达条件（P8）成立就是 `success`，否则是 `false_success`（包括放对了但没关界面）；其余情况是 `failed` |

**守恒**：

- 药水：物品栏 + 光标 + 药水格 + 地上的药水（开局药水和产物都算）= b；
- 烈焰粉：吃掉的 = F − 物品栏 − 光标 − 燃料格 − 材料格 − 地上，只能是 0 或 1。燃料值有 20 次，一轮里用不完，不会吃第二个；
- 材料：用掉的 = R − 物品栏 − 光标 − 材料格 − 地上，应该等于本轮酿造的次数（P9）。

少了就是有东西被扔出场外。

- 放进去还没被吃掉、用掉的多余物品可以再拿回来，所以只在最后看物品栏是否恰好剩 F − m、R − n、b − p。
- 酿没酿完、产物拿没拿都不判。
- 中文名：`overshoot` 沿用"放多"，`misplaced` 沿用"放错"。

**建议：采用。**

### P7　药水的计数签名

药水按"瓶子 id + 药水种类"计数：`minecraft:splash_potion#minecraft:awkward`。

- 药水种类取 `potion_contents` 里的药水注册名，和 `slotItem` 给的 `potionContents.potion` 一致（F12）；
- 没有药水内容的瓶子（玻璃瓶）就是 id；
- 其他物品就是 id。

**建议：采用。**

### P8　mod：发药水、核对配方、"恰好达到"的检测

**发药水**：`arena/prepare` 的 `items` 允许 `{ slot, id: "minecraft:potion" | "minecraft:splash_potion" | "minecraft:lingering_potion", count: 1, potion: "minecraft:awkward" }`，mod 用 `PotionContents.createItemStack` 做出这瓶药水。

**核对配方**：`prepare` 用服务器的 `PotionBrewing`（F11）核对两件事：

- 这条配方确实能酿（`hasMix`）；
- 产物（`mix`）和插件从 `brewing.json` 算出的一致。

核对不过就报错。插件记 `aborted`，停止整组，并提示"数据过期，请重跑提取脚本"，同熔炉方案 K8。`prepare` 返回服务器算出的产物签名。

**到达检测**：沿用熔炉方案 K8，mod 在服务器 tick 里检测，记下第一次达到的时刻 `reachedAtMs`，不打断 agent。`Expect` 增加酿造台写法：

```
expect: { brew: { fuel, fuelLeft, ingredient, ingredientLeft, potion, potionLeft, placed, products: [签名…] } }
```

同时满足下面几条就算到达：

1. 容器界面已关闭，光标为空；
2. 物品栏里 `fuel` 恰好 `fuelLeft` 个、`ingredient` 恰好 `ingredientLeft` 个、`potion`（签名）恰好 `potionLeft` 瓶；物品栏里没有这三种以外的东西；
3. 燃料格为空或只有 `fuel`；材料格为空、只有 `ingredient`，或者只有它的剩余物（龙息的玻璃瓶）；
4. 药水格里恰好 `placed` 瓶，每瓶的签名是 `potion` 或 `products` 之一。

**`status`**：酿造台工作站另外返回下面几项。都只读，不改动状态，`finish` 的顺序不用改。

- `held`、`carried`、`dropped`：按签名计数；
- `stand: { potions: [签名 | null ×3], ingredient: {签名: n}, fuel: {签名: n}, fuelCharges, brewTicks }`；
- `containerOpen`；
- `brews`（P9）。

**建议：采用。**

### P9　记录酿造次数

| 方案 | 做法 | 说明 |
|------|------|------|
| **A** | 加一个 mixin，在 `BrewingStandBlockEntity.doBrew` 里给本轮的酿造台记一次，`status` 给 `brews` | 和信标、铁砧、锻造台的 mixin 同类。材料守恒（P6）能严格核对；记录里能看出放好以后有没有酿起来 |
| B | 不记 | 材料只能查"地上有没有"，扔出场外的材料查不出来 |

**建议：A。**

### P10　要不要生成酿造配方的 json 文件

要。理由有三：

1. **出题要用**：配方池（P3）要有一张完整的配方表；
2. **agent 以后要用**：你的目标是让 agent 学会"想酿某种药水，该往哪些格子放什么"，这需要查配方。配方写在代码里（F8），agent 现在只能读 `PotionBrewing.java`，而"一条起始配方展开成两条""药水配方对三种瓶子都成立"这些规则在代码里是隐含的，容易读错。锻造台方案 M9 也是因为同样的原因补了 `smithing.json`；
3. **和服务器核对**：数据过期时，P8 的核对能当场发现。

| 方案 | 做法 | 说明 |
|------|------|------|
| **A** | **从源码提取**：`extract-item-props.js` 解析 `PotionBrewing.addVanillaMixes` 里的 `addContainer` / `addContainerRecipe` / `addMix` / `addStartMix`，`Potions.X` 按 `Potions.java` 查注册名，`Items.X` 按 `Items.java`（方块物品按 `Blocks.java`）查注册名，燃料按 jar 里的 `brewing_fuel` 标签展开。认不出的写法报错退出，不猜 | 和 `FuelValues`（熔炉方案 K10 的 A）同一种做法；P8 的核对兜底 |
| B | mod 加接口 `arena/brewing-catalog`，出题时从游戏里读；不生成文件 | 和织布机一样准确，但 agent 查不到配方 |
| C | mod 导出文件 | 每次更新数据都要先开游戏 |

**格式**（`data/brewing.json`）：

```
{
  source,
  fuel: [{ id: "minecraft:blaze_powder", charges: 20 }],    // brewing_fuel 标签；charges 是一个燃料能开始几次酿造（FUEL_USES）
  containers: [{ id: "minecraft:potion" }, { id: "minecraft:splash_potion" }, { id: "minecraft:lingering_potion" }],
  potionMixes: [{ from: "minecraft:water", ingredient: "minecraft:nether_wart", to: "minecraft:awkward", time: 400 }, …],
  containerMixes: [{ from: "minecraft:potion", ingredient: "minecraft:gunpowder", to: "minecraft:splash_potion", time: 400 }, …]
}
```

（实施时改的格式，见 §7 补充 ①：`core.json.query` 只能取数组，单个数值放进记录里。）

- `addStartMix` 在提取时就展开成两条 `potionMixes`，数据里不留"起始配方"这个概念；
- `from` / `to` 在 `potionMixes` 里是药水注册名（和 `potionContents.potion` 一致），在 `containerMixes` 里是瓶子的物品 id。

**开放给 agent**：

- `jsonSources` 增加 `brewing`；
- 数据源说明（`JSON_NOTES`）只描述数据本身，不说怎么用：药水配方对三种瓶子都成立；换瓶子时药水种类不变；`charges`、`time` 的含义；
- `items.json` 的覆盖范围扩大到酿造材料、烈焰粉和三种瓶子，出题用它查堆叠上限（F10）。

**建议：A。**

### P11　超时、每轮换新、酿造台被挖、胶囊库

- **超时**：三种物品要放，药水要一瓶一瓶放，比熔炉多一点。`timeoutSec` 为 **600 秒**。
- **每轮换新**（F7）：`prepare` 先清空酿造台的五格，再把那一格换成空气，然后放一台新的，和熔炉方案 K12 相同。燃料值、酿造进度跟着清掉。
- **酿造台被挖**：轮次中被挖掉不补放，记录 `stationIntact=false`，判为 `lost`。
- **胶囊库**：原样带进训练。熔炉训练里"往原料格、燃料格放恰好 n、m 个，再关界面"的子树，可能会被迁移过来，这正是想观察的。药水格一格只能放 1 个，是新情况。训练前先备份 `src/capsules/`。

**建议：全部采用。**

### P12　任务文案

和熔炉方案 K11 一样，文案只说现状和要求，不提右键、Shift 点击、怎么拆分物品堆，不说格子编号，也不说物品栏里各有多少。药水写清种类，因为同一种瓶子的药水 id 相同（F2）。

模板 `prompts/training/brew.md`：

```
你正前方有一台酿造台（minecraft:brewing_stand），视角已经对准它。
你的物品栏里有 {{fuel}}、{{ingredient}} 和 {{bottles}} 瓶 {{potion}}。请把 {{m}} 个 {{fuel}} 放进它的燃料格，{{n}} 个 {{ingredient}} 放进它的材料格，{{p}} 瓶 {{potion}} 放进它的药水格，放好以后关掉它的界面。不要多放，也不要动其他物品。
```

- `{{potion}}` 写成"瓶子 id（药水种类）"，例如 `minecraft:splash_potion（minecraft:awkward）`，和 `slotItem` 的 `id`、`potionContents.potion` 对应；
- 不提产物，也不说要不要等它酿完（P2）。

**建议：采用。**

### P13　记录与报告

### P14　暂不做的部分

以下内容等放置训练稳定后再考虑，现在不做：

- **"酿出 k 瓶 X"的题型**：只给目标药水，agent 自己查 `json.brewing` 决定放什么材料、放几瓶，等酿完再把产物取回来。这就是"想要某种药水该往哪些格子放什么"的训练，数据（P10）这一版就准备好
- 多步酿造（水瓶 → 粗制 → 目标）、发多种材料作干扰
- 药水格里放玻璃瓶、用水瓶装水
- 材料是烈焰粉的配方（P3 排除的那条）

## 6. 验收清单（实施后）

1. `npm run extract-item-props` 生成 `brewing.json`：
   - `potionMixes` 条数 = `addMix` 条数 + 2 × `addStartMix` 条数（41 + 22 = 63），`containerMixes` 2 条，燃料只有烈焰粉；
   - 重新生成后其他数据文件逐字节不变。
2. `/arena brewing` 能传送到新场地的场外平台；其他场地和它们的训练不受影响。
3. `/bt train brewing runs=3`：每轮开始时，正前方是一台新的酿造台（燃料值 0、格子全空），`aimOk=true`；物品栏里只有本轮的烈焰粉、材料和药水；第一次右键就能打开酿造台。
4. 抽题检查（单元测试，抽几千道）：
   - 各种材料出现的次数大致相同，不出烈焰粉材料；
   - 海龟壳只发 1 个；
   - m ≤ F、n ≤ R、p ≤ b；
   - 同一种子出同一道题。
5. 在游戏里手动验证：
   - 放对、关界面时 `reachedMs` 有值，判为 `success`；放对了但没关界面，判为 `false_success`；
   - 放进 k 个烈焰粉后，燃料格只剩 k − 1 个，仍然判为放对了；
   - 放好以后酿造完成（药水变成产物、材料少 1 个），判定结果不变，`brews` = 1；
   - Shift 把烈焰粉溢出到材料格，判为 `misplaced`；
   - 龙息题酿造后地上掉了玻璃瓶，不判 `lost`；
   - 在 2×2 里合出荧石，判为 `misplaced`；
   - 把一瓶药水扔出场外，判为 `lost`。
6. 轮次中把酿造台挖掉后，记录里 `stationIntact=false`；下一轮开始时酿造台已经补回。
7. `training-report` 能按 `ingredient` / `bottle` / `kind` 汇总，并显示"酿起来了"一列。
