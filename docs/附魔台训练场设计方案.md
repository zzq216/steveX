# 附魔台训练场设计方案

> 状态：**N-S1–N-S4 已实施**（2026-11-20），单元测试通过，待游戏内按 §6 验收。审阅结论：N1–N12 全部采纳建议。实施时有两处和方案不同（记录里目标附魔的字段名、物品属性表扩大的影响），见 §7。
>
> 本方案沿用《工作台训练场设计方案》（下称"3×3 方案"）、《箱子训练场设计方案》（下称"箱子方案"）、《切石机训练场设计方案》（下称"切石机方案"）和《熔炉训练场设计方案》（下称"熔炉方案"）的整体架构：
> - 插件主控，mod 以服务器身份操作场地；
> - 每轮一个新会话，记录写进 jsonl；
> - "恰好达到"的时刻由 mod 在 tick 里检测。
>
> 下面只写和它们不同的部分。
>
> 目标：另建一块场地，场内正前方放一台附魔台，周围摆书架。训练 agent 读附魔台界面上三档显示的附魔，选出带有指定附魔的那一档，把物品附魔好，然后关掉界面。

## 1. 用户原始流程

1. agent 传送到对应的训练场地中。正前方放一个附魔台，agent 的视角对着它，直接点右键就能打开
2. 清空 agent 身上的所有物品
3. 开始计时，并发布任务：
   - 从所有能附魔的物品里随机选一个作为原材料，给 agent 一个；同时给 1 组青金石，把经验设成 216 级
   - 读出这件物品放进附魔台后，三档会显示的附魔信息，随机选一种附魔
   - 要求 agent 把原材料在附魔台上附魔成第 n 档、等级为 m 的 p 附魔，然后把物品放回物品栏
4. 读出"把这件物品放进附魔台、选第 n 档"会得到的附魔结果。检测到物品栏里有附魔和它一致的物品时，停止计时并记录

本方案保留这个流程的主体，按 §2 的事实做了几处调整：

- 任务只说附魔 p 和等级 m，不说第几档，要 agent 自己读界面、找出对应的那一档（N6）；
- 附魔台周围固定摆书架，否则附魔很单调、还常有档位不可用（N2）；
- 经验每轮设成 30 级，够用任何一档（N4）；
- 每轮按出题种子重设玩家的附魔种子，三档内容由插件事先预览出来再出题（N4、N5）；
- 和熔炉方案一致，要求附魔好后关掉界面才算完成（关界面时物品自动回到物品栏，"放回物品栏"就自然满足了，N7）。

## 2. 已核实的事实

数据来源：`1.21.11_src` 里的 `EnchantmentMenu`、`EnchantmentHelper`、`Enchantment`、`Player`、`ItemStack`、`EnchantingTableBlock`、`Item`、`ToolMaterial`、`Items`；游戏 jar 里 `data/minecraft/enchantment/*.json`、`data/minecraft/tags/enchantment/in_enchanting_table.json` 和物品标签。

| # | 事实 | 对方案的影响 |
|---|------|------------|
| E1 | **三档内容是确定的**：只取决于玩家的附魔种子（存档里叫 `XpSeed`）、附魔台周围的有效书架数、放进去的物品。每档的门槛等级、界面上露出的提示附魔、实际会得到的附魔，都是用这三样算出来的（`EnchantmentMenu.slotsChanged` 86–123 行、`getEnchantmentList` 185–198 行） | mod 可以在 agent 看到界面之前，用原版的同一套计算把三档全部算出来（N5） |
| E2 | 附魔种子只在**成功附魔一次后**才换成新的随机数。放进、取出、再放进物品，三档内容都不变（`Player.onEnchantmentPerformed` 1528–1537 行） | agent 可以反复放进取出查看，不影响题目 |
| E3 | **界面上每档只露出一个附魔**作为提示：从这一档的实际结果里随机挑一个（115–117 行）。实际结果可能有好几个附魔；不同档的实际结果里也可能含有同一个附魔 | 出题时要保证目标附魔只出现在一档的结果里（N5） |
| E4 | 附魔书：结果多于一个附魔时随机去掉一个（193–195 行）；附魔后书变成附魔书（153–156 行），附魔存在"存储的附魔"里，不在普通的附魔字段 | 检测时附魔书要读另一个字段（N8） |
| E5 | 界面上显示的等级数只是**门槛**，玩家等级要不低于它，也不低于档号。实际扣掉的是档号那么多级经验和那么多个青金石：第 1 档扣 1，第 3 档扣 3（`clickMenuButton` 135–162 行） | 经验只要不低于最高门槛就够（N4）；青金石、经验各少了多少，就知道用的是哪一档（N9） |
| E6 | 门槛算法（`EnchantmentHelper.getEnchantmentCost` 496–511 行）：k = 随机 1–8 + ⌊书架数 / 2⌋ + 随机 0–书架数，书架数最多算 15。<br>第 1 档 = max(⌊k / 3⌋, 1)，第 2 档 = ⌊k × 2 / 3⌋ + 1，第 3 档 = max(k, 书架数 × 2)；门槛小于档号时这一档不可用（106–108 行）。<br>**没有书架**：k 是 1–8，三档最多约 2、6、8 级，k = 1 时第 2、3 档都不可用。**15 个书架**：k 是 8–30，三档分别是 2–10、6–21、30 级，三档一定都可用 | 不摆书架时附魔很单调、还常缺档；摆满 15 个，最高门槛正好 30 级（N2、N4） |
| E7 | 书架要在附魔台外圈两格的位置（以附魔台为中心 5×5 的外圈，附魔台同层或高一层，共 32 个位置），并且它和附魔台之间那一格要是空的（`EnchantingTableBlock.isValidBookShelf` 47–50 行） | 书架怎么摆见 N1 |
| E8 | 关掉附魔台界面时，物品格和青金石格里的东西**自动退回物品栏**（`EnchantmentMenu.removed` 210–213 行） | "放回物品栏"只要关掉界面就满足（N7） |
| E9 | 物品要有"可附魔"属性、而且身上还没有附魔，才能上附魔台（`ItemStack.isEnchantable` 989–996 行）。附魔过一次就不能再附魔 | 每轮只有一次机会，附魔错了没法重来（N7） |
| E10 | 附魔台能出的附魔有 36 种（`in_enchanting_table` 标签）。只有当某个附魔把这件物品列为"主要物品"时，才会出现在这件物品的三档里；书例外，所有这些附魔都可能出现（`EnchantmentHelper.getAvailableEnchantmentResults` 584–598 行） | 物品池要按这条过滤（N3） |
| E11 | 有"可附魔"属性的物品共 **77 种**：<br>- 工具 35 种：剑、镐、斧、锹、锄 × 7 种材质；<br>- 矛 7 种；<br>- 盔甲 29 种：头盔、胸甲、护腿、靴子 × 7 种材质，加海龟壳；<br>- 弓、弩、三叉戟、重锤、钓鱼竿、书。<br>它们每一种都至少有一个附魔台附魔适用（按 E10 用 jar 数据核对过）。<br>鞘翅、盾牌、剪刀、刷子、打火石、胡萝卜钓竿、诡异菌钓竿虽然有适用的附魔（耐久等），但没有"可附魔"属性，**不能上附魔台** | 物品池是这 77 种，按 16 类分组（N3） |
| E12 | 可附魔程度（`enchantable` 的数值）随材质不同，比如金比铁高，越高越容易出多个附魔、高等级附魔（`selectEnchantment` 546 行） | 先抽类别再抽材质，让各材质都能练到（N3） |
| E13 | `container/get` 对附魔台已经给出每档的门槛（`costs`）、提示附魔的注册名（`enchantName`）、提示等级（`levelClue`）、书架数（`bookshelves`）。附魔台格子：0 = 物品格，1 = 青金石格 | agent 这边不需要新接口 |
| E14 | 玩家的附魔种子是 `Player` 的受保护字段，只在成功附魔时由 `onEnchantmentPerformed` 改写。mod 已经有 mixin 访问器（`LivingEntityAccessor` 等） | 加一个访问器就能设种子（N4） |

## 3. 总体设计

流程比前几个场地多一步"预览"：

1. 插件出题：抽物品和附魔种子；
2. **`arena/enchant-preview`**（新，只读）：mod 按物品、附魔种子、书架数，用原版的计算算出三档的门槛、提示和实际结果；
3. 插件按预览结果选目标（N5）。选不出来就换一件物品，回到第 1 步；
4. `arena/prepare`：摆好附魔台和书架、发物品、设经验和附魔种子、对准视角、登记目标。mod 再用真实的附魔台菜单算一遍三档，和预览核对；
5. 发布任务，轮询 `arena/status`；
6. 任务结束后调用 `arena/finish`，判定并写记录。

插件侧新增题型 `enchant`，在新文件 `src/training/enchant.js` 里实现。训练器的公共流程只多一个可选钩子：在 `prepare` 之前调用题型的 `preview`。

mod 侧的改动：

1. 增加工作站 `enchanting_table`（附魔台加书架）；
2. 新接口 `arena/enchant-preview`；
3. `prepare` 设经验等级和附魔种子，返回真实菜单算出的三档；
4. 附魔台工作站的 `status` 返回物品栏、光标、附魔台两格、地上的计数，以及界面开没开、经验等级；
5. 增加一种"附魔"写法的到达检测。

## 4. 决策点

### N1　场地、附魔台和书架

- 新增场地 `enchanting`，origin 设在 `(10000, 120, 10150)`，和熔炉场地间隔 30 格。场地的搭建、清场、屏障墙、告示牌逻辑原样复用。
- 附魔台放在 `(ox, oy+1, oz+2)`。玩家站在 `(ox, oy+1, oz)`，朝 +z，现有的俯角公式和 `aimOk` 自检照用。附魔台高 12/16 格，实施时确认准星落在方块上。
- **书架**：放在附魔台同一层的外圈。以附魔台为中心，外圈有 16 个位置，去掉玩家站的那一格（附魔台正前方两格），正好 15 个。
  - 这 15 个位置和附魔台之间的格子（附魔台周围一圈 8 格）全是空气，满足 E7。玩家和附魔台之间那一格也是空的，不挡视线。
  - 书架算作工作站的一部分，和漏斗下面的红石块一样记进 `stationBlocks`。轮次中被挖掉任何一个，`stationIntact=false`，判"丢失"（`lost`），因为书架数一变，三档内容就变了。
- `/arena enchanting` 传送到场外平台，`/bt train enchanting` 开始训练。

**建议：采用。**

### N2　书架数量

| 方案 | 做法 | 效果 |
|------|------|------|
| A | 不摆书架 | 三档门槛最多约 2、6、8 级，附魔等级低、种类少；k = 1 时第 2、3 档不可用（E6） |
| **B** | **固定 15 个** | 三档一定都可用，门槛 2–10、6–21、30 级；能出现锋利 IV、效率 V 这类高等级附魔，以及多附魔的结果 |
| C | 参数 `bookshelves`（0–15），缺省 15 | 灵活，但少于 15 个时会缺档，选目标要跳过不可用的档 |

**建议：B，同时预留 C。** 场地配置里留 `bookshelves` 这个参数（缺省 15）；少于 15 个时，按固定顺序只摆前几个位置。出题逻辑（N5）本来就只在可用的档里选，所以不用额外处理。

### N3　物品池与抽样

物品池：E11 的 77 种，去掉 `exclude` 里的。按类别分成 16 组：

- 剑、镐、斧、锹、锄、矛（各 7 种材质）；
- 头盔（8 种，含海龟壳）、胸甲、护腿、靴子（各 7 种材质）；
- 弓、弩、三叉戟、重锤、钓鱼竿、书（各 1 种）。

| 方案 | 做法 | 效果 |
|------|------|------|
| A | 77 种物品平均抽 | 工具和盔甲约占 92%，弓、弩、三叉戟、重锤、钓鱼竿、书合计不到 8% |
| **B** | **先在 16 类里等概率抽一类，再在类里抽材质** | 每类机会相同；类内覆盖不同材质（可附魔程度不同，E12） |

`item=<id>` 固定物品，这时跳过分组抽样。

**建议：B。**

### N4　经验、青金石、附魔种子

- **经验**：每轮把等级设成 `xpLevel`（缺省 **30**）、经验进度清零。30 级正好够用 15 个书架时最高的门槛（E6）；用掉一档后剩下的等级对这一轮没有影响。
  - 你原案的 216 级也能用，但没有必要。数值可以在场地配置里调。
  - 现在的 `prepare` 不动经验，要新增这一步。
- **青金石**：每轮 1 组（64 个），放在随机的一格。
- **附魔种子**：每轮由出题种子算出一个附魔种子，`prepare` 时写给玩家（E14：mod 加一个 `Player` 的 mixin 访问器）。
  - 这样同一个出题种子永远出同一道题，也不受上一轮附魔的影响（E2）。
  - 种子写在玩家身上，训练结束后保留在存档里，对正常游戏没有影响。

**建议：全部采用。**

### N5　出题：先预览三档，再选目标

`arena/enchant-preview { item, enchantSeed, bookshelves }` 是一个只读的纯计算接口。mod 用原版的同一套方法算出三档，返回：

```
{ enchantable, offers: [{ slot, cost, clue: { enchantment, level } | null, result: [{ enchantment, level }] }] }
```

- 计算方法逐行照搬 `slotsChanged` 和 `getEnchantmentList`：同一种随机数源（`RandomSource.create()` 后 `setSeed`）、同样的调用顺序，书照样去掉一个附魔；
- `prepare` 摆好书架、设好种子以后，还会用**真实的附魔台菜单**算一遍（在服务器上临时建一个附魔台菜单，放进物品的副本，读出三档），和预览逐项核对。不一致就终止本轮，报"预览和附魔台不一致"。

插件拿到预览后选目标：

1. 候选：可用的档（门槛 > 0、提示不为空）里，提示附魔 (p, m) 满足：**三档的实际结果里，只有这一档含有 (p, m)**（E3）；
2. 从候选里随机选一档，作为目标档 n，目标就是 (p, m)；
3. 没有候选时（比如三档提示一样），用下一个子种子换一件物品重新预览，最多 10 次，还不行就本轮 `aborted`。

这样"物品附魔后含有 (p, m)"就等价于"用的是第 n 档"，判定不用知道 agent 点了哪个按钮（N7）。

**随机数抽取顺序**（同一种子出同一道题）：物品类别 → 材质 → 附魔种子 → 青金石格位、物品格位 →（预览后）目标档。换物品重试时用 `seed + 重试次数` 重新抽。

**建议：采用。**

### N6　任务文案

和前几个场地一样，文案只说现状和要求，不提右键、按钮、第几档、青金石怎么用。

模板 `prompts/training/enchant.md`：

```
你正前方有一个附魔台，视角已经对准它。你的物品栏里有一个 {{item}} 和一些青金石。
把这个 {{item}} 放进附魔台后，界面上的三档里会有一档显示 {{enchantment}} {{level}} 级。
请用附魔台把它附魔成带有这个附魔的物品，附魔好后关掉它的界面。不要动其他物品。
```

- `{{enchantment}}` 用注册名（如 `minecraft:sharpness`），`{{level}}` 是数字，和 `container/get` 的 `enchantName`、`levelClue` 一致；
- "带有"是要求：实际结果可能还有别的附魔（E3），不影响成功；
- 不说第几档。要 agent 读三档的提示、找出对应的那一档，这正是这项训练要练的；
- **第二句是这一轮的事实，不是做法**（2026-11-20 补充）：出题时已经保证目标就是某一档的提示（N5）。不说的话，agent 无法区分"目标在某档的提示里"和"目标藏在某档没露出的结果里、或者三档都没有"，会为后两种走不到的情况写分支（赌一档、等待，甚至挖书架改三档，后者会判 `lost`）。说了以后，树可以写成"读三档 → 找提示等于目标的那一档 → 附魔 → 关界面"，找不到就明确报错。
  - "放进附魔台后"这个前提要保留：不放物品时三档是空的；
  - 这个保证只在训练场成立，依赖它的树在真实任务里遇到"没有这档"会直接报错，而不是想办法；
  - 以后加"做不到的题"（N12）时，这句不能再无条件出现，要另用一个模板，和箱子题 `rel=gt` 的做法一样。

**建议：采用。** 如果你希望降低难度，可以另加一种只说"用第 n 档附魔"的模式，作为对照。

### N7　判定

任务结束时，按以下几处计数：

- 物品栏（不含光标）；
- 光标；
- 附魔台的物品格、青金石格（界面还开着时）；
- 场内地上。

设：**结果物品** = 物品栏里那件由原材料变来的物品（id 是原材料，或者原材料是书时为附魔书）；**消耗的青金石** = 64 − 上面几处青金石的合计。

| 顺序 | 结果 | 条件 |
|------|------|------|
| 1 | `aborted` | 手动停止 |
| 2 | `lost` | 附魔台或任何一个书架被挖掉；场内地上有物品；原材料（或它变成的物品）哪里都找不到 |
| 3 | `misenchanted` | 物品附魔了，但附魔里没有 (p, m)。附魔没法重来（E9），一旦附错就失败 |
| 4 | `timeout` | 超时 |
| 5 | `success` / `false_success` / `failed` | 任务以完成结束时，如果到达条件（N8）成立就是 `success`，否则是 `false_success`（比如还没附魔、界面没关）；其余情况是 `failed` |

- 中文名：`misenchanted` 是"附错"。
- 消耗的青金石、经验只记录、不判定；它们应该都等于 n（E5），作为核对。
- 实际得到的附魔和预览的第 n 档结果做比对，记成 `matchedPreview`。不一致说明预览算错了，不是 agent 的问题，报告里单独列出来。

**建议：采用。**

### N8　"恰好达到"的检测（mod）

沿用箱子方案 C9：mod 在服务器 tick 里检测，记下第一次达到的时刻 `reachedAtMs`，不打断 agent。

`Expect` 增加一种附魔写法：`expect: { enchant: { item, result, enchantment, level } }`。`result` 是附魔后的物品 id（书变附魔书，其余同 `item`）。同时满足下面几条就算到达：

1. 容器界面已关闭（和熔炉方案 C9 相同；关闭时物品格、青金石格的东西会退回物品栏，E8）；
2. 物品栏里恰好有一件 `result`，它的附魔里有 `enchantment` 且等级是 `level`；附魔书读"存储的附魔"（E4），统一用 `EnchantmentHelper.getEnchantmentsForCrafting` 读；
3. 物品栏里除了这件物品和青金石，没有别的东西。

**`status`**：附魔台工作站返回下面几项。只读计数，不改动状态。

- `held`、`carried`、`dropped`；
- `table: { item, lapis }`：附魔台界面开着时两格里的东西；
- `containerOpen`；
- `xpLevel`：当前经验等级；
- `enchantments`：物品栏里那件结果物品的全部附魔 `[{ enchantment, level }]`，供插件记录、比对预览。

**`prepare`** 新参数 `enchantSeed`、`xpLevel`、`bookshelves`。返回值多一项 `offers`：真实菜单算出的三档（格式同预览），以及实际数到的书架数。

**建议：采用。**

### N9　记录与报告

每轮记录在通用字段之外，增加：

| 字段 | 含义 |

### N10　数据

插件出题需要知道 77 种可附魔物品和它们的类别、材质。

| 方案 | 做法 | 说明 |
|------|------|------|
| **A** | **扩展 `extract-item-props.js`**：给有"可附魔"属性的物品记 `enchantable`（数值）。来源：`.enchantable(n)`、工具和剑的 `applyCommonProperties`、矛、`humanoidArmor`。覆盖范围加上这 77 种物品（下界合金装备、锁链盔甲这些不在配方表里的也要加进来）。再用 jar 里的附魔数据核对：每种至少有一个附魔台附魔适用 | 和现有提取脚本"规则只在源码里、认不出就报错"的做法一致；`preview` 的 `enchantable` 字段会当场核对 |
| B | mod 加一个接口，训练开始时从游戏里取可附魔物品清单 | 最准确，但出题要等游戏连上，单元测试也得造假数据 |

agent 不需要新数据：三档内容从 `container/get` 读（E13）。

**建议：A。**

### N11　超时、被挖、胶囊库

- **超时**：只有一件物品要附魔，加上读界面、选档、关界面。`timeoutSec` 建议为 **600 秒**，和箱子、熔炉场地一样。
- **每轮重置**：`prepare` 补回附魔台和书架，清空物品栏，设经验和附魔种子。附魔台没有方块实体里的物品（关界面时会退回），不用额外清空。
- **被挖**：同 3×3 方案 W8 的 A。轮次中附魔台或书架被挖掉不补放，记录 `stationIntact=false`，判"丢失"（`lost`）。
- **胶囊库**：原样带进训练。合成、切石机训练里学到的"读界面列表、按编号选"的能力，可能会迁移过来。训练前先备份 `src/capsules/`。

**建议：全部采用。**

### N12　暂不做的部分

以下内容等基本训练稳定后再考虑，现在不做：

- 只说"用第 n 档"的对照模式（N6）
- 要求结果附魔和第 n 档**完全一致**（现在只要求含有目标附魔，由 N5 保证两者等价）
- 一轮附魔多件物品、物品栏里放干扰物品、青金石或经验不够的题
- 铁砧、砂轮

## 6. 验收清单（实施后）

1. `/arena enchanting` 能传送到新场地的场外平台；其他场地和它们的训练不受影响。
2. `/bt train enchanting runs=3`：
   - 每轮正前方是附魔台，`aimOk=true`，第一次右键就能打开；
   - `container/get` 的 `bookshelves` 是 15；
   - 物品栏里只有一件原材料和 64 个青金石；经验是 30 级。
3. 抽题检查（单元测试）：
   - 只出 77 种可附魔物品，16 类各约 1/16；
   - 目标附魔只出现在目标档的实际结果里；
   - 同一种子出同一道题。
4. 预览核对：在游戏里抽几十道题，`preview` 的三档和真实附魔台菜单（`prepare` 的 `offers`、`container/get` 的 `costs` / `enchantName` / `levelClue`）完全一致；附魔后的实际结果和预览的那一档一致（`matchedPreview=true`）。
5. 在游戏里手动验证：
   - 选对档、附魔、关界面后，`reachedMs` 有值，报完成后判为 `success`；
   - 附魔好了但没关界面就报完成，判为 `false_success`；
   - 选错档，判为 `misenchanted`；
   - 附魔书：结果是附魔书，按存储的附魔判定；
   - 丢出物品，判为 `lost`；挖掉一个书架，判为 `lost`。
6. 同一种子跑两次，两次的三档内容完全一样；上一轮附魔过，不影响下一轮的题。
7. `training-report` 能按 `kind` / `slot` / `enchantment` 汇总，`misenchanted` 显示为"附错"，并列出"预览不一致"的轮数。
