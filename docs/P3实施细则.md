## 0. 一句话与范围

**P2 让慢树在被打断、走不通、死了之后能回头改自己；P3 让快树从"自己没认出来、或认出来却没处理好"的经历里长出新反射、改掉坏反射。**

| 在 P3 里 | 不在 P3 里 |
|---|---|
| 快树能感知到"受伤 / 死亡"（§2，含一处 mod 改动） | 近处实体感知（僵尸、苦力怕）——另立设计（§2.3，P3-D3） |
| 没有任务时的死亡与重生（§2.4） | 路由层的"快树指导意见"（人用自然语言改快树，已定排除） |
| 快树事件流：分级、合并、全量落盘（§3） | 信息量的精细度量、置信度 / 淘汰 / 探索配额（T9 待定项，要实测数据） |
| 批量、触发、限流（§4） | 快树回归测试（训练用，P6） |
| 快树反思会话、`fast_*` 工具、提示词（§5、§6） | 跨 agent 的版本合并（T4 已推迟） |
| 补丁格式、校验、版本冲突、自动落盘、生效时机、回滚（§7、§8） | 慢树反思与 `capsule_save`（P4） |
| `/bt fast status / log / rollback / reflect`（§9） | |

**验收**（集成方案 §10，按 §2.3 修订）：用命令构造环境危险（放水、岩浆 / 火），让 agent 在 `otherwise` 下受伤；一批事件触发反思，补丁自动落盘；下次同样的场景由新 arm 处理；`/bt fast rollback` 能回到旧版本。§11 细化成可执行的场景。

## 2. 感知：快树能看到什么

快树进化的原料是"在 `otherwise` 下受了伤"。这句话要成立，快树得先**一直**知道生命值，反思时得能看出**是什么伤的**，新写的 arm 得能**认出**那种局面。现在三样都不全。

### 2.1 `player` 一直轮询【P3-D1】

现在只有任务存在期间才轮询 `player`（P2 为了死亡检测加的）。没任务时，空快树不读任何来源，轮询集合是空的——站在岩浆里烧死也没有任何记录。

**倾向**：`player` 无条件留在轮询集合里（`statePollMs` 200 ms 一次，一次本地 mod 调用）。代价是空闲时每秒 5 次调用；换来的是"受伤 / 死亡"在任何时候都看得见。

### 2.2 `player` 补字段（mod 改动）【P3-D2】

判据是"人在屏幕上看得到的才给"（与 [观察边界](观察边界与物品可见性设计方案.md) 一致）：

| 新字段 | 人怎么看到的 | 用途 |
|---|---|---|
| `flags.onFire` | 屏幕上的火焰 | 着火反射的 `when` |
| `flags.inLava` | 屏幕变橙、看得见岩浆 | 岩浆反射的 `when` |
| `flags.inPowderSnow` / `vitals.frozenTicks` | 屏幕结霜 | 冻伤 |
| `lastDamage: { type, ticksAgo } \| null` | 受伤时的红闪、方向性抖动、伤害音效；死亡信息里也有 | **反思的证据**：这次掉血是什么伤的（`minecraft:drown` / `lava` / `on_fire` / `fall` / `mob_attack`……） |

**核查（2026-10-26）：已有的"着火"在哪里，能不能直接用**

| 已有 | 能否给快树用 |
|---|---|
| `vision/snapshot` 的活体实体摘要里有 `onFire`（仅真时出现），判据是 `entity.displayFireAnimation()`，也就是火焰渲染用的 `isOnFire() && !isSpectator()`（`LivingSummary.java:176/244`，[实体属性观测面设计方案](实体属性观测面设计方案.md) §3）。落盘后 `core.nbt.query` 的 `entities.living.onFire` 能查到 | **不能**。① 它描述的是**别的实体**：本地玩家第一人称下不进快照，只有第三人称或睡眠相机时才会被采进去（`EntityPresenceCorrector.java` 注释）。② `vision/snapshot` 是会写记忆文件的重量级采集（首次约 15 s），不能每 200 ms 轮询；查询 NBT 也不是 `local_cached`，快树的 `when` 读不了 |
| `player` 的 `flags` | 只有 `onGround` / `inWater` / `sprinting` / `sneaking`，**没有着火** |

所以 `player` 上仍要补 `flags.onFire`，判据直接沿用 `displayFireAnimation()`，字段名也叫 `onFire`，和实体摘要保持一致。改动量和 P2 加 `dead` 字段相当。

`lastDamage` 来自客户端 `LivingEntity.getLastDamageSource()`。1.19.4 起，服务端用 `ClientboundDamageEventPacket` 把伤害类型同步给客户端（客户端拿它播放受伤动画）。实施前要在 1.21.11 源码里核实：这个字段在客户端确实有值、什么时候清空（§12 待核实 1）。核实不通过，就只加三个 `flags`，伤害类型改由反思从前后状态推断。

`when` 里能用 `lastDamage`（"刚被摔伤"也是一种局面），但它主要服务于证据。

### 2.3 近处实体感知：不补【P3-D3】

**已定（2026-10-26）：不新增实体状态来源。实体已经记录在记忆 NBT 里**（`entities_union.nbt`，`core.nbt.query` 的 `entities`：类型、坐标、生命值、`living.onFire` 等）。慢树可以在树里查。

由此带来的边界，实施和验收时要记住：快树的 `when` 只读轮询缓存，读不了 NBT 查询；而且记忆只在 `vision/snapshot` 采集时才更新。所以**快树仍然认不出"附近有僵尸"**，僵尸场景保持下面"只验一半"的安排。以后如果要让快树对实体做出反射，再回到这一节。

以下是初稿原文，保留作背景：

集成方案的验收写了"`/summon` 僵尸"。现在的四个状态来源里，看得到实体的只有 `f3` 的准星目标，而且只有正对着时才有。快树认不出"附近有僵尸"，反思写不出能用的 arm。

要补就得新加一个状态来源（比如 `entities`：附近的活体实体，带视线遮挡过滤）。这涉及观察边界（墙后的实体客户端也知道，人看不到）、轮询代价、字段薄化，是一份独立的设计。按"先写设计文档 → 审阅 → 再实施"的流程，它不该夹在 P3 里。

**倾向**：P3 验收只用**环境危险**（水、岩浆、火、摔落、冻伤）。僵尸场景 P3 只验一半：受伤能记下来，`lastDamage.type` 是 `mob_attack`；反思时大模型应当看出"没有能认出它的条件"，并用 `fast_skip` 说明缺什么（§6.1）。实体感知另写设计。

### 2.4 没有任务时的死亡【P3-D4】

P2 的 `checkDeath` 只在任务存在期间工作。P3 之后 `player` 一直轮询，没任务时的死亡也要处理：

- 记 `death` 快树事件（高信息量，§3.1）
- 自动重生，流程复用 `respawn()`：等到没死且生命值回满，超时只记 `player/respawn-failed`，不影响别的东西
- 有任务时仍走 P2 §8.3 的流程，另外**同时**记一条快树事件。死亡既是慢树的 `died` 请求，也是快树的原料，两边互不替代

## 3. 快树事件流

### 3.1 事件与信息量

落盘位置不变：`runtime/fast/events.jsonl`，跨任务累积，**全量写**（T9 约束 2：压缩只在喂给大模型时做）。每条事件有一个快树范围内的递增 id（`e<N>`），反思时按它引用。

| 事件 `kind` | 判据 | 信息量 | 进反思批次 |
|---|---|---|---|
| `unhandled-harm` | 命中 `otherwise` 期间掉血或死亡 | **高** | 是 |
| `arm-failed` | 命中真实 arm，情节以 `FAILURE` 结束 | **高** | 是 |
| `arm-harmed` | 命中真实 arm，情节以 `SUCCESS` 结束，但情节中掉血或死亡 | 中 | 是 |
| `arm-ok` | 命中真实 arm，`SUCCESS`，没掉血 | 低 | 否，只计入 arm 统计（§3.4） |
| `death` | 死亡（有没有任务都记）。若死在上面某个事件进行中，就并进那条（`died: true`），不单独成条 | 高 | 是 |

"掉血"的判据：相邻两次轮询之间 `vitals.health` 下降。回血不算。吸收护盾（金苹果的黄心）下降不算受伤，P3 不看它。

**`otherwise` 每 tick 都命中，空闲 tick 不记**（T9 约束 5）。现有的 `fast/episode-start` / `fast/episode-end` 这类过程记录保留，它们是事件的原材料。上表的事件在过程结束时写一条汇总，带 `kind`、`level`、`id`。

### 3.2 合并：一场危险只算一个事件【P3-D5】

P2 场景 1 的教训：agent 泡在水里，溺水反射 6 分钟触发了 58 次。如果一次情节就是一条事件，一批反思装满了同一件事。

- **`unhandled-harm` 按"事故"记**：第一次掉血开一个事故，之后每次掉血都并进来；连续 `fastIncidentQuietMs`（倾向 **5000 ms**）没有再掉血，或者进了真实 arm 的情节，或者死亡，事故就结束，写一条事件。事件里有：起止时间、掉血总量与次数、各次 `lastDamage.type` 的计数、是否死亡、最低生命值和最低氧气
- **同一个 arm 的相邻情节合并**：上一次情节结束后 `fastEpisodeMergeMs`（倾向 **10000 ms**）内又进了同一个 arm，就并进同一条事件，记 `episodes: n`。级别取各次中最高的，比如 58 次溺水上浮里只要有一次还在掉血，就是 `arm-harmed`
- **两次情节之间的掉血也算进这一组**（实现时补的）：在合并窗口内、命中 `otherwise` 的间隙里掉血，说明反射没把危险解决掉。若把它记成单独的 `unhandled-harm`，溺水反射的每个间隙都会开一个事故，又回到 58 条事件的局面
- 合并只发生在事件记录这一层。底下的 `fast/episode-*` 过程记录照常一条不少地落盘

### 3.3 每条事件带什么

| 字段 | 说明 |
|---|---|
| `id`、`kind`、`level`、`startedAt`、`endedAt` | |
| `fastVersion`、`arm`（名字，`otherwise` 时为 null）、`status`、`episodes` | |
| `harm` | `{ total, hits, types: { 'minecraft:drown': 3 }, minHealth, minAir, died, deathMessage }` |
| `before` / `after` | 状态快照名（§3.5），不内联 |
| `armError` | `arm-failed` 时，失败叶子的错误原文 |
| `taskId`、`taskNode` | 当时有没有任务，任务树在跑哪个叶子。只给反思一点背景："人在执行'走去 x'时掉进了岩浆"；不带慢树的其他上下文 |

### 3.4 arm 统计

执行器在内存里给每个 arm 记 `{ hits, ok, harmed, failed, lastHitAt }`，按快树版本分开记，**从事件流重放得出**。重启后从 `events.jsonl` 读回来，不另存一份。反思时 `fast_inspect` 的 `arms` 能看（§6.2），`/bt fast status` 也显示。

arm 统计是"这条反射有没有用"的唯一依据：一条从来没命中过的 arm、一条命中了总在 `FAILURE` 的 arm，大模型据此决定改不改、删不删。**统计只是证据，删不删由大模型决定**（不做自动淘汰，T9 的淘汰机制待定）。

### 3.5 状态快照

沿用 P2 的思路，事件里只写快照名，内容按需取：

- `before`：事故开始前或情节开始时的**缓存**状态（来不及现场读；通常只有 `player` 和 `when` 用到的来源）
- `after`：事件结束时**现场读全**（`player` / `inventory` / `f3` / `container`），和 P2 的 `episode-end` 一样。`f3` 里有脚下方块和坐标，判断"站在什么上面受的伤"靠它
- 快照存进 `runtime/fast/snapshots/<eventId>.json`。和任务的快照缓冲不同，它要跨重启留着，因为反思可能在下次启动后才发生
- 保留最近 `fastSnapshotKeep`（倾向 **200**）个事件的快照，更早的删掉。事件行本身永久保留

## 4. 批量、触发、限流

### 4.1 触发【P3-D6】

待反思的事件 = 高、中信息量，且还没进过批次的事件。满足任一条件就打一批：

| 触发 | 倾向 |
|---|---|
| 待反思事件数 ≥ `fastBatchSize` | **3**。快树样本天然稀疏（T9），批太大要等很久；太小（1）又起不到合并相似事件的作用 |
| 任务结束（`done` / `failed`）或进入空闲，且待反思事件 ≥ 1 | 是（集成方案 §7.4.3 原文） |
| `death` 事件 | **立即**，不等凑批。死亡是最贵的样本，下一次可能就在几分钟后 |
| 人手动 `/bt fast reflect` | 是（测试用，§9） |

**快树正处在情节中（命中真实 arm 且未结束）不打批**，等它结束。这样这次情节本身也能进批。

### 4.2 限流与排队

- 同时在飞的快树反思不超过 `fastReflectMaxParallel`（初值 **1**）。超出的批次排队，按"最早的高信息量事件"先后出队
- **在飞期间新来的事件不进当前批次**，留给下一批。新事件是在旧版本快树下发生的，可能正是当前反思要修的问题；等补丁落盘后，下一批里看到的仍是旧版本事件。所以批次目录里每条事件都标着 `fastVersion`，大模型能看出"这是旧版本下的事"
- 一批最多 `fastBatchMaxEvents`（倾向 **10**）条，按信息量从高到低排，超出的留给下一批（集成方案 §7.4.3 的"从低端截断"）

### 4.3 批次结束

反思会话以下面三种方式之一结束这一批：

- `fast_submit_patch` 被接受：补丁落盘、新版本生效（§8）
- `fast_skip`：说明这批为什么不改（比如"缺少认出僵尸的感知"、"这是一次偶发的摔伤"）
- 不合法尝试用完（`maxInvalidAttempts`，与 P1 同一个值），或回合出错重试用完：批次记为 `abandoned`

三种结局都写进事件流（`fast/batch-end`），批次里的事件标记为"已反思"，**不会再进下一批**。理由写在 `fast/batch-end` 里，`/bt fast log` 能看。

## 5. 快树反思会话

### 5.1 会话的生命周期【P3-D7】

集成方案 §7.4.4 已定：快树反思**不进任务会话**，用 `ctx.agents.create()` 开专用会话。剩下的问题是开几个、开多久。

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 每批开一个新会话，批次结束就关** | 上下文干净；以后放开并行时天然隔离；上一批的推理不会带偏下一批 | 每批重新付系统提示词的钱（快树会话的系统提示词不大） |
| B. 一个常驻的快树会话，批次排队进来 | 能"记得"上一批想过什么 | 上下文越来越长、要压缩；放开并行就得改回 A |

**倾向 A**。快树的状态全在树和版本链里，上一批的结论已经落成了补丁和 `fast/batch-end` 里的理由，`fast_inspect versions` 都能看到，不需要靠会话上下文记住。

**要先验证**：`ctx.agents.create()` 开的会话在 DSH web 界面里能不能看到、能不能在里面插话（§12 待核实 2）。看不到也能工作，但你在验收时只能从 `/bt fast log` 和会话日志文件看大模型怎么想的。

**实现（2026-10-26）**："批次结束就关"落成"批次结束后不再往这个会话发东西"，**不调用 `dispose()`**。DSH 的 `dispose()` 会把会话从存储里移除，会话日志就看不到了。留着的会话是空闲的，只占一点内存。

### 5.2 消息正文：目录

| `what` | 参数 | 返回 |
|---|---|---|

## 7. 补丁

### 7.1 格式【P3-D8】

arm 用**名字**寻址。名字就是 `then` 根节点的 `name`，在一棵快树里必须唯一，并且**跨版本稳定**（行为树设计 §8.3）。快树的节点 id 每次编译都会重新分配，不能用来寻址。

```json
{
  "batchId": "b7",
  "base": 4,
  "reason": "e41 三次摔伤都发生在从高处走下时……",
  "ops": [
    { "op": "add", "before": "灭火", "arm": { "when": { ... }, "then": { "seq": "落地前蹲下", "do": [ ... ] } } },
    { "op": "replace", "name": "灭火", "arm": { ... } },
    { "op": "remove", "name": "离开岩浆" },
    { "op": "move", "name": "溺水上浮", "after": "灭火" }
  ],
  "code": [ { "name": "fast.fall-risk", "signature": { ... }, "body": "..." } ]
}
```

- `add`：给 `before` / `after` 之一（arm 名字），都不给就加在末尾（`otherwise` 之前）。**插入位置就是优先级**：`Match` 第一个成立的 `when` 赢
- `replace`：整条 arm 换掉，`when` 和 `then` 一起。名字可以改，改了以后旧名字就不存在了
- `remove`、`move`
- `otherwise` 不能改。它永远是"什么都不做"，快树进化只增减真实 arm
- 一个补丁可以有多条 op，按顺序应用；任何一条不合法，整个补丁拒绝
- 这对应集成方案原文的 `add-arm` / `modify-arm` / `remove-arm`。`modify` 改成 `replace`，因为局部修改 `when` 或 `then` 里的某个节点没有稳定 id 可以寻址；另外加了 `move`

### 7.2 条件代码【P3-D9】

快树的 `when` 多数要新写条件代码（`code/...`）。P1 里任务树的代码草稿落在任务目录里，任务结束就没了；快树是常驻的，它用的代码也得常驻。

**倾向**：补丁里的 `code` 在补丁被接受时**写进胶囊库**，名字强制加 `fast.` 前缀，按内容哈希存成 `fast.xxx@hash`。新版本快树里的引用钉到这个哈希上（`pinRefs`）。

- 好处：回滚到旧版本时，旧版本引用的旧代码还在（胶囊库按哈希只增不删），回滚不会因为代码变了而失效
- 补丁被拒时代码**不入库**。`fast_inspect eval` 求值时代码只在内存里

### 7.3 校验

在已有的 `kind: 'fast'` 校验之上，P3 加：

| 规则 | 为什么 |
|---|---|
| `base` 必须是当前最新版本，不是就拒绝，结果里附上最新版和差异（§8.2） | T9 约束 3：写操作串行化 |
| `batchId` 必须是当前在飞、属于这个会话的批次 | 和 P2 的"请求过期即拒"同一思路 |
| arm 名字唯一、非空；`replace` / `remove` / `move` 的目标存在 | 寻址 |
| 真实 arm 数 ≤ `fastMaxArms`（倾向 **30**，T 画像里快树规模估计 10–30） | 快树每 tick 都要算 |
| 每个 arm 的 `then` 节点数 ≤ `maxExpansionNodes`（15） | 与慢树展开同一上限 |
| `when` 引用的条件代码 `read` 只能是状态来源（`player` / `inventory` / `f3` / `container`）。读到的来源进轮询集合，所以 `when` 只读缓存 | 快树不能现场读（`local_cached`） |
| `then` 里**必须能结束**：不能有不带 `until` 的 `Repeat`，`Steps` 里的 `wait` 总和不超过 `fastMaxEpisodeMs`（倾向 **30000 ms**）。另外执行器给每个情节加一个总超时，超时按 `FAILURE` 结束 | 情节不结束，慢树就永远被挂着 |
| 条件代码在沙箱里试跑一次（用当前缓存状态），超过 `conditionTimeoutMs` 拒绝 | 快树每 tick 都要算它 |

### 7.4 不做回归测试

已定（集成方案 §11 第 9 条）：补丁通过校验就落盘，不先跑回归。改坏了由后续反思纠正，必要时人手动回滚。

## 8. 版本链、生效与回滚

### 8.1 文件

```
src/bt/trees/fast/
  v5.json        执行格式的完整快树（现在已经这样存）
  v5.meta.json   { version, base, by: 'reflection' | 'rollback' | 'manual', batchId, events: [...], ops, reason, createdAt }
```

`latestFastTree` 不变，仍然取 N 最大的一版。

### 8.2 版本冲突

`base` 不是最新版时拒绝。工具结果里附上：最新版号、`base` 到最新版之间每一版的 `reason`，以及两版快树的差异，让大模型在新版上重做。P3 的并行度是 1，这种情况只会在下面这个时机出现：反思进行中，人用 `/bt fast rollback` 回滚或手动放了一版。

### 8.3 生效时机

- 补丁接受后马上写文件，在下一个 tick 边界换上新树
- **快树正在情节里（`preempting` 或 `running`）时不换**，等情节结束再换。现在的 `loadFastTree` 遇到情节会强行结束它（`endEpisode(null, 'replaced')`），P3 改成延后
- 换上后刷新轮询集合；记一条 `fast/loaded`（带版本号、来源批次）
- 慢树不受影响：换快树不打断任务，在飞的慢树请求也不过期

### 8.4 回滚【P3-D10】

**倾向**：`/bt fast rollback <N>` 把第 N 版的内容**另存为新的一版**（`by: 'rollback'`，`base` 记回滚前的版本），而不是把"当前版本"指针挪回去。

- 版本链只增不减，"最新的就是生效的"这条不变量保持不变，装载逻辑不用改
- 回滚本身也留在历史里，下一次反思用 `fast_inspect versions` 能看到"v6 是人从 v4 回滚的，v5 被撤销了"，不会把刚撤销的改动再做一遍
- 回滚时如果有在飞的反思，它基于的版本就过期了，提交会被拒（§8.2），重做

### 11.2 游戏内验收

**准备**：
1. mod 已改（`player` 新字段、`LivingEntityAccessor`），要重新 `./gradlew runClient`
2. `start-dsh.bat stevex` 启动，**新开会话**。`/bt fast status` 应显示 `快树 v0，版本链最新 v0`
3. 先在普通问答里让大模型 `mod_query player`，确认能看到 `flags.onFire` / `inLava` / `lastDamage`
4. 日志：事件在 `steveX/runtime/fast/events.jsonl`（`fast/event`、`fast/batch-start` / `fast/batch-end`），快照在 `runtime/fast/snapshots/`，版本在 `src/bt/trees/fast/`

**游戏内验收场景**（从空快树起步，`src/bt/trees/fast/` 为空）：

1. **溺水 → 新 arm**：站进深水里不动，到掉血为止 → `unhandled-harm`（`minecraft:drown`）。凑批或 `/bt fast reflect` → 反思交出补丁 → 生成 v1。再次站进水里 → 新 arm 在掉血前接管（`arm-ok` 或 `arm-harmed`）
2. **岩浆 / 着火**：脚下放岩浆，或 `/setblock ~ ~ ~ fire`，验证 `onFire` / `inLava` 字段能被写进 `when`。死在岩浆里 → `death` 事件立即触发反思
3. **坏 arm 被纠正**：手动 `/bt fast load` 一条故意写错的 arm（比如溺水时按潜行），反复触发 → `arm-harmed` → 反思用 `replace` 或 `remove` 改掉它
4. **回滚**：`/bt fast rollback 1`，`/bt fast log` 里出现 `by: rollback` 的新版本；之后的反思能在 `fast_inspect versions` 里看到它
5. **和慢树的配合**：执行任务时掉进水里 → 新 arm 抢占 → P2 的 `recover` 请求照常发出；反思和慢树请求同时进行时互不阻塞
6. **僵尸（只验一半，§2.3）**：`/summon zombie`，被打 → `unhandled-harm`（`mob_attack`）→ 反思大概率 `fast_skip` 并说明缺少感知。这一项不判对错，只看它是否写出了合理理由

**结果（2026-10-26，场景 1 前半，会话 `session-aaccf156-…`）**：
- 事件流：站在水底 23 秒淹死 → 一条 `unhandled-harm`（高）：24 次 `minecraft:drown`、`died: true`、死亡信息"Player778淹死了"；24 次掉血并成一条（事故合并生效）。掉血总量 39.7 大于 20，是因为期间饱和度在回血，属实
- 没有任务时死亡 → 同一秒自动重生
- 死亡立即打批 b1 → `ctx.agents.create` 开会话（`stevex` 预设）→ 大模型 8 步：`fast_inspect` 看 event / trace / 前后快照 / live，查 `command_docs` / `data_shapes`，**提交前用 `eval` 在 before@e1（true）、live#1 与 after@e1（false）上验证了条件**，一次通过 → v1「水下缺氧上浮」（`fast.low-air-underwater`：在水里且 air ≤ 40；先两次 `camera/turn dy:-90` 抬头，再按跳 + 前进 2.5 秒），条件代码入库并钉住 hash
- **发现执行器 bug，已修**：编译器把快树的 seq 缺省成 `reactive`（系统提示词写的是缺省 `memory`）。reactive seq 每 tick 从第一个孩子重跑，已完成的「抬头」会被重置重做、「上浮」每次刚开始就被中止——v1 这条 arm 一旦触发就会一直转视角，直到 30 s 超时按 FAILURE 结束。修法：快树 seq / sel 缺省改为 `memory`（反应式在 Match 一层）；快树里显式写的 reactive seq / sel 也要求最后一个孩子之前是纯节点（同 P2-D16）。v1 已按原样另存为 v2（只改 mode，`by: manual`）。新增回归测试，旧代码下失败

**结果（2026-10-26 第二轮）**：
- **场景 1 通过**：v3 下三次站进深水，「水下缺氧上浮」在 air 降到 36 / 32 / 29 时接管，每次约 2.8 s、`SUCCESS`，**没有掉血** → 三条 `arm-ok`（低，只计统计）
- **意外收获——骷髅（原场景 6）**：沙滩上被骷髅连射死 12 次（e2–e13，`minecraft:arrow`、`attacker: minecraft:skeleton`）。b2 的反思看出"低血 + 正在挨远程火力"，写了 `fast.low-health-under-fire`（血量 ≤ 70% 且 2 秒内被箭 / 敌对生物打中）与「低血被射击横向疾跑规避」→ v2。`lastDamage.attacker` 让快树**不靠实体感知也认得出"在被骷髅打"**，P3-D3 说的"只能验一半"不成立
- v2 是在旧进程里生成的（编译器还是旧的缺省 reactive），它的新 arm 一触发就跑满 30 s 超时（e14 `arm-failed`）。重启后 v2 过不了新校验 → 退回空快树。b5 的反思**自己读出了原因**（"reactive seq 前面是 steps，会从头重跑"），把两条 arm 的根都改成 memory → v3。b3 正确地 `fast_skip`：e3 是 v1 下的事件，v2 已经处理
- **又修了两处**：
  1. 版本文件被覆盖：人手放的 v2（只改 mode 的 v1）被旧进程的反思用同一个版本号盖掉了——旧进程内存里的最新版还是 v1。现在每次写之前重新扫目录，版本文件用 `wx` 只增不改，抢先写过的同号版本 → 拒绝并附差异
  2. 死亡连发时一事件一批：每次死亡都立即打批，并行已满就排成 b3、b4…，每批只有一条同样的事件、各开一个会话。现在并行已满时不打批，触发保留到有空位：在飞期间攒下的事件一起进下一批
- **未覆盖**：v3 的「低血被射击横向疾跑规避」改好之后还没被触发过；e14 还在待反思里，下一批会带上
