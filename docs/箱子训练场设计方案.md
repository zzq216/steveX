# 箱子训练场设计方案（存取物品专项）

> 状态：**C-S1–C-S3 已实施**（2026-11-14），单元测试通过，待游戏内验收（§6）。审阅结论：C1–C13 全部按建议方案（C6 选 A，`dest=partial` 留接口暂不开放；C8 多拿判 `overshoot`，算失败）。实施说明见 §7。
>
> 补充（2026-11-14）：§8 增加漏斗、发射器两种容器（C14–C20）。审阅结论：全部按建议；C-S4、C-S5 已实施，单元测试通过，待游戏内按 §8.4 验收（实施说明见 §8.5）。
>
> 对应《训练课程设计大纲》阶段 B 的 B2（箱子存取，漏斗另议，见大纲 D5）。整体沿用《工作台训练场设计方案》（下称"3×3 方案"）的架构：插件主控；mod 以服务器身份布置场地；每轮开一个新会话；记录写 jsonl。下面只写和 3×3 方案不同的部分。
>
> 目标：新建一块场地，正前方放一个箱子（小箱子或大箱子）。训练 agent 在箱子和物品栏之间搬运**指定数量**的指定物品。重点练两项：大纲 A3 的定量拆分，以及不同容器的格号对照。

## 1. 用户原始流程

1. agent 传送到对应的训练场地中。正前方放一个箱子，agent 的视角对着箱子，直接右键就可以打开
2. 清空 agent 身上的所有物品
3. 开始计时，并随机发布下面两种任务之一：
   1. **取**：往箱子里放物品，占箱子容量的随机 0–1/2。在 DSH 发布任务，要求 agent 从箱子里取指定数量的某种物品放进物品栏。指定数量也在"能填满箱子 0–1/2 的物品数量"里随机。指定数量比箱子里实有的多时，把箱子里的这种物品全部取出即可
   2. **放**：往 agent 身上放物品，占物品栏容量的随机 0–1/2。在 DSH 发布任务，要求 agent 把物品栏里指定数量的某种物品放进箱子。数量规则同上，不够时全部放进去即可
4. 检测到物品栏或箱子里出现指定的目标物品时，停止计时并记录
5. 设计控制变量：可以控制发布哪种任务，以及指定数量和实有数量的大小关系

本方案保留第 1–3 步和控制变量。以下几处做了调整：
- 第 1 步的提示语（C7）
- 第 3 步"0–1/2"的含义（C3、C5）
- 箱子里的内容：只放目标物品不够（C4）
- 第 4 步的判定和计时（C8、C9）

| S4 | 箱子上方的方块是导体方块（`isRedstoneConductor`），或者上面坐着猫时，箱子打不开（`ChestBlock.java:322-343`） | 场地要保证箱子上方是空气 |

| S7 | 关闭界面时，光标上的物品放回物品栏，物品栏满了就掉在地上（`AbstractContainerMenu.removed` / `dropOrPlaceInInventory`，`:586-604`） | 判定要处理光标上的物品（C8）；掉在地上的物品要算进"总数守恒" |
| S8 | `PICKUP_ALL`（双击收拢）会扫描整个界面，包括箱子格和背包格。`ChestMenu` 没有覆盖 `canTakeItemForPickAll` | 收拢会把两边的同类物品都吸进光标，是可以利用、也可能踩坑的机制，由 agent 自己摸索 |
| S9 | 收纳袋 `BundleItem` 覆盖了 `overrideStackedOnOther` / `overrideOtherStackedOnMe`，点击它或拿它点别的格子，效果和普通物品完全不同 | 物品池排除收纳袋（C3） |

| S12 | 现有的判定靠 `crafted` 统计（`trainer.js` 的 `judge`）。和箱子存取无关 | 箱子题要另写一个判定器（C8、C11） |

## 3. 总体设计

```
/bt train chest [kind=..] [rel=..] [chest=..] [stack=..] [fill=..] [types=..] [runs=..] [seed=..] [item=..]
        │
插件 训练器 ──► 出题器（storage）：按种子生成 {kind, chest, 目标物品 T, 干扰物品, 两边的布局, n, k}
        │
        ├─► mod arena/prepare：搭场地 / 放箱子（小或大）/ 清空并布置箱子 / 清空并布置物品栏 / 对准箱子 / aimOk 自检
        │          并登记本轮目标 {item: T, from, to, want}，tick 里检测首次到达的时刻
        ├─► 新会话里发任务（模板 chest_take.md / chest_put.md）
        ├─► 轮询 arena/status，直到任务结束或超时
        └─► arena/finish → 判定器（storage）：最终两边的计数 → outcome → 写 runtime/training/chest.jsonl
```

和 3×3 的区别：
- 出题器和判定器换成"存取"题型的（C11）
- mod 的 `prepare` / `status` / `finish` 多了箱子的布置和读取
- 计时由 mod 在 tick 里检测"到达目标状态"（C9）

## 4. 决策点

### C1　场地

| 方案 | 做法 |
|------|------|
| **A** | 新增场地 `chest`，origin `(10000, 120, 10060)`，和 craft3x3 相隔 30 格。每轮由 `prepare` 按本轮抽到的大小放小箱子或大箱子 |
| B | 小箱子、大箱子各开一块场地 |

**建议：A。** 一块场地就能在同一批训练里混着抽两种箱子，记录也在同一个文件。`/arena chest` 传送到场外平台，`/bt train chest` 开始训练。

### C2　箱子的位置、朝向和自检

- **小箱子**：放在 3×3 方案里工作台的位置 `(ox, oy+1, oz+2)`。`FACING=north`（正面朝向玩家），`TYPE=SINGLE`。
- **大箱子**：
  - `(ox, oy+1, oz+2)` 设为 `LEFT`，`(ox+1, oy+1, oz+2)` 设为 `RIGHT`，两块都 `FACING=north`（S5）；
  - 准星对着玩家正前方那一半（`LEFT`），俯角算法和工作台一样；
  - 两块的上方都必须是空气（S4）。场内本来就是空的，搭建时显式清掉这两格的上方。
- **换箱子大小**：本轮和上一轮大小不同时，`build` 要把多出来的那半改回空气（或补上）。被挖掉的同样补回。
- **自检**：`prepare` 结束前，除了射线检测 `aimOk`，还要通过合并容器读一次容量，写进 `chestSlots`（27 或 54），并核对和本轮抽到的大小一致。不一致说明大箱子没有连上，这一轮记为 `aborted` 并停止整组（同 3×3 的 `aimOk=false`）。
- **等客户端更新视线目标**：发任务前等 100 ms，同 3×3。

**建议**：采用以上做法。

### C3　物品池

- **来源**：`data/item-props.json`（S10），堆叠上限也从它取。
- **排除**：
  - 收纳袋（S9）；
  - 配置项 `exclude`，默认只含 `minecraft:bundle`。

  其他特殊物品（潜影盒、带耐久的工具）按普通物品对待：它们在箱子里存取时没有特殊行为。
- **按堆叠上限分档**：控制变量 `stack=64|16|1|mix`。`mix` 先等概率抽一档，再在档内抽物品，免得 875 种 64 叠的物品把 16 叠、1 叠的挤掉。
- **干扰物品**：与目标物品 T 不同，堆叠档不受 `stack` 限制，从整个池里抽（C4）。

**建议**：采用以上规则。`item=` 固定目标物品，此时 `stack` 不起作用。

### C4　箱子里放什么：目标物品要拆成碎叠，并加入干扰物品

如果来源方只有目标物品一种，"取 k ≥ n 个"就只是把东西全部 Shift 点出来，练不到"挑出目标"和"定量拆分"。所以：

- **种类**：控制变量 `types=1-4`（默认 `1-4` 随机）。`types=1` 时只有目标物品；`types=t` 时另有 t−1 种干扰物品。
- **格数分配**：来源方的占用格数 s 定好后（C5），目标物品至少占 1 格，每种干扰物品至少占 1 格，剩下的格随机分给各种物品。
- **每格数量**：在 `[1, 该物品的堆叠上限]` 里均匀随机。这样目标物品自然会碎成几叠不满的。
  - 补充（2026-11-14）：控制变量 `fill=random|full|mix`，默认 `random` 即上面的规则；`full` 时来源方每格（目标和干扰物品）都取满堆叠上限，用来练整组搬运；`mix` 每轮在两者间等概率选。随机数量下「多格都满一组」几乎抽不到（一格满 64 的概率 1/64），所以单独开这个选项。
- **位置**：在来源方的全部格子里随机挑（取：箱子的 27 或 54 格；放：物品栏 0–35 格，快捷栏也算）。

**建议**：采用以上规则。

### C5　"0–1/2"的含义，以及数量关系 `rel`

**来源方的存量**：
- 占用格数 s 在 `[types, ⌊容量/2⌋]` 里随机。容量指来源方的格数：取时是箱子的 27 或 54 格，放时是物品栏的 36 格。
- 用户流程写的下限是 0。但 s=0 时没有题，所以下限取 `types`（每种物品至少 1 格）。

**目标物品实有 n 个，要求 k 个**：k 不单独随机，而是由控制变量 `rel` 生成：

| `rel` | k 的取值 | 练的是什么 |
|------|---------|-----------|
| `lt` | `[1, n−1]` 均匀随机 | 定量拆分：从若干叠里凑出恰好 k 个（大纲 A3） |
| `eq` | `n` | 全部搬走。指令里不说"全部"，要 agent 自己读出实有数量 |
| `gt` | `[n+1, Kmax]` 均匀随机，`Kmax = ⌊容量/2⌋ × T 的堆叠上限`，也就是用户说的"能填满 1/2 的数量" | 读出不够、改为全部搬走 |
| `mix`（默认） | 三种等概率 | |

- `lt` 要求 n ≥ 2。抽到 n=1 时（例如堆叠上限 1、只占 1 格），就给目标物品再加 1 格。还不够（s 已经到上限）就重抽这一轮，种子仍然可以复现。
- 本轮应当搬走的数量记为 `want = min(k, n)`。

**建议**：采用上表。

### C6　目标方的初始内容（需要你定）

目标方指东西要搬去的那一边：取时是物品栏，放时是箱子。用户流程里，取时清空了物品栏，放时没说箱子里有没有东西。

| 方案 | 做法 | 能练到什么 |
|------|------|-----------|
| **A**（默认） | 目标方一律为空 | 和用户流程一致，判定最简单 |
| B | 控制变量 `dest=empty\|partial`。`partial` 时，目标方预先放 1–⌊容量/4⌋ 格东西，其中可以有目标物品的不满堆和干扰物品 | 合并进已有的同类不满堆（Shift 点击会先叠进去，S3）；目标方原有的目标物品不能算进 k |

**建议：先按 A 实施，同时把 `dest` 变量留好接口，`partial` 等 A 跑稳了再开。**

- 开 `partial` 时，出题器要保证目标方装得下：目标方空着的格数 ≥ 来源方的总格数。
- 装不下这种情况，以后可以单独做成一类难题。

按 C5 的上限，A 一定装得下：
- 取：箱子最多一半，即 27 格，物品栏有 36 格；
- 放：物品栏最多一半，即 18 格，箱子至少 27 格。

### C7　任务文案

用户流程第 1 步里的"直接点击右键就可以打开"是在教做法，按 3×3 方案 W6 的原则去掉。"不够就全部搬走"和"其他物品不要动"是题目要求，不是方法，要写进指令；不写的话，`gt` 题和"多拿干扰物品"就没有标准答案。

| 模板 | 文案 |
|------|------|
| `chest_take.md` | `你正前方有一个箱子，视角已经对准它。请从箱子里取出 {{k}} 个 {{target}} 放进你的物品栏；箱子里的 {{target}} 不足 {{k}} 个时，把它们全部取出。其他物品不要动。` |
| `chest_put.md` | `你正前方有一个箱子，视角已经对准它。请把你物品栏里的 {{k}} 个 {{target}} 放进箱子；物品栏里的 {{target}} 不足 {{k}} 个时，把它们全部放进去。其他物品不要动。` |

- 文案不说箱子的大小、不说实有多少，这些都由 agent 自己读。
- 如果你认为"视角已经对准它"也算提示，可以删掉。

**建议**：采用上表。

### C8　判定（需要你定"多拿算不算失败"）

不采用用户流程第 4 步的"出现目标物品"：取的第一叠一进物品栏，这个条件就成立了，而且它分不出"恰好 k 个"和"多拿了"。

改为在**任务结束时**按两边的计数判定。计数按物品 id 合计，不看格子位置，agent 整理过格子不算错。

记号：
- 来源方的 T 初始为 n，目标方的 T 初始为 d₀（C6 方案 A 时 d₀=0）；
- 结束时来源方、目标方、光标上 T 的数量分别为 src、dst、cur；
- 掉在场内地上的 T 记为 drop（S7）。

| outcome | 条件 |
|---------|------|
| `success` | 任务以 done 结束，并且：① `dst − d₀ = want`、`src = n − want`；② 每种干扰物品在两边的数量都和初始一样；③ 光标为空，地上没有掉落物 |
| `overshoot` | `dst − d₀ > want`，T 搬多了 |
| `disturbed` | T 的数量对，但动了干扰物品（②不满足） |
| `lost` | 物品总数比初始少，或者有掉落物，或者箱子被挖掉（物品会掉出来） |
| `false_success` | 任务以 done 结束，但以上都不满足（T 搬少了、光标上还拿着等） |
| `failed` / `timeout` / `aborted` | 同 3×3 |

- 判定顺序：`aborted` → `lost` → `overshoot` → `disturbed` → `success` / `false_success` / `failed` / `timeout`。
- 光标上还拿着东西时，`arena/finish` 先**计数**，再清空光标。不能先让它落回物品栏再数，否则"拿在手上没放下"会被当成已经放进去。

**需要你定**：多拿（`overshoot`）算不算失败？
- **建议算**。和合成训练的"不多做"一致，也符合大纲 §1 第 2 条"做多了、做少了、动了不该动的格子都算失败"。
- 如果不算，就把它并进 `success`，记录里仍然留着 `overshoot` 字段。

### C9　计时

用户流程第 4 步说"检测到目标状态时停止计时"。这对应一个**时刻**，不需要打断 agent：

- **`reachedMs`**：mod 在服务器 tick 里检测，第一次满足 C8 `success` 条件 ①②③ 的时刻，只记第一次。和 `craftedAtMs` 一样在 tick 里做，精度是 1 tick，而不是轮询的 1 秒。条件需要的目标信息由 `prepare` 登记：`{item, from, to, want, baseline}`。
- **`openedMs`**：第一次打开箱子界面（`containerMenu instanceof ChestMenu`）的时刻。
- **`taskMs`**：任务结束的时刻，同 3×3。

到达目标状态后不打断 agent：要让它自己核对完成情况、自己交差（同 3×3）。三个时刻把用时拆成三段：开箱前、搬运、搬完到交差。

**建议**：采用以上做法。

### C10　箱子被挖掉

同 3×3 方案 W8 的方案 A：
- 每轮 `prepare` 都重新放箱子；轮次进行中被挖掉不补放；
- `status` / `finish` 返回 `stationIntact`（大箱子要两半都在才算完好）。

箱子被挖掉时里面的东西会掉出来，按 C8 判为 `lost`。下一轮 `prepare` 会清除场内的掉落物（S11）。

**建议**：采用。

### C11　训练器按题型拆分

`trainer.js` 现在把"合成题"的出题、发放、判定写在一起。大纲 §4 要求每个题型一个出题器和一个判定器。本方案借这个机会拆开：

- 场地配置加一个 `type` 字段：`craft`（现有的 craft2x2 / craft3x3，缺省值）或 `storage`（本方案）。
- 每个题型一个模块，都提供这几样：
  - `parseArgs`：解析 `/bt train` 的选项
  - `sample`：出题
  - `prepareParams`：要传给 mod 的参数
  - `instruction`：生成指令
  - `judge`：判定
  - `recordFields`：记录要写的字段
- 训练器只管轮次、会话、超时、记录这套公共流程。

不在这次重写合成题型。只把现有代码原样搬进 `craft` 模块，保证 craft2x2 / craft3x3 的行为和随机数序列不变，旧种子仍能复现。

**建议**：采用。以后阶段 A 的其他题型（A2、A3 等）也按这个接口加。

### 8.2 决策点

**C14　选项形式**
- `chest=` 增加两个值 `hopper`、`dispenser`，再加一个 `all`（四种容器等概率）。
- `mix` 仍然只在小箱子和大箱子之间抽，这样旧种子出的题不变，已有记录可以对比。
- 选项名仍叫 `chest`，记录字段 `chest`、mod 返回的 `chestSlots` 也不改名。这些名字现在泛指"场内容器"，在文档里注明。
- 另一种做法是新增 `container=` 选项、废弃 `chest=`。改动面更大，旧记录也要兼容。

**建议**：用前一种，`chest=small|large|hopper|dispenser|mix|all`。

**C15　漏斗锁定**

| 方案 | 做法 | 评价 |
|---|---|---|
| A | 漏斗正下方的地板换成红石块。按 S17，漏斗的 `ENABLED` 一直是 false，既不推送也不吸收 | 原版"锁住的漏斗"就是这样做的，稳定；红石块是场景里看得见的事实 |
| B | 漏斗上方放一个整格方块。按 S16，上方是整格方块时不吸收掉落物 | 也能用。但上方多出一个方块，挡视线、改变场景，而且漏斗仍然是"启用"状态 |
| C | 不处理，靠判定兜底 | 有 S16 说的漏洞：扔掉多拿的物品会被吸回，判成 `success` |

- A 的实施要点：
  - 搭建时，地板这一格也从工作站的方块表里取（缺省还是石头）。
  - 同一列先放地板、再放漏斗，漏斗放下时就已经收到信号。
  - 换成别的容器时，地板先恢复成石头，再放新容器，所以发射器不会被这块红石触发。
  - 红石块算进 `stationIntact` 的检查（S22）：被挖掉就判 `lost`，和 C10 一致。
- 大纲 D5 问的是"物品放进漏斗后被传走"这种自动搬运。本方案不练它，留给以后另开的题型。

**建议**：A。

**C16　发射器朝向，以及不加投掷器**
- 发射器用默认朝向 `NORTH`，出口对着玩家；场内没有信号，不会动作（S18）。
- 投掷器和发射器是同一种界面（S14），不另加。

**建议**：如上。

**C17　出题时的容量规则**

只在新容器上才会触发；原来的小箱子、大箱子不会碰到这些上限，同种子出题不变，实施后用旧代码对比确认。

- **取物题**（来源是容器）：
  - 种类数的上限改成 `一半 − 目标最少格数 + 1`。目标最少格数平时是 1；`rel=lt` 且目标不可堆叠时是 2。
  - 例如漏斗的"一半"是 2 格：普通情况最多 2 种；`lt` 且目标不可堆叠时只能有 1 种。
  - 这条规则修的是 S21 的越界：原来遇到这种组合会给出 3 格。
- **放进题**（来源是物品栏，目标是容器）：
  - 目标物品在物品栏里最多占 D 格，D 是容器格数（漏斗 5、发射器 9）。这样 n ≤ D × 堆叠上限，`eq` / `gt` 要求全部放入时一定装得下；`lt` 时 k < n，也装得下。
  - 干扰物品不用搬，不受这个限制。
  - 总格数的上限也随之变成 `min(一半, 种类数 − 1 + D)`。
  - 分配剩余格子时，如果抽中的是已经满 D 格的目标，就改分给干扰物品。只有在这个上限真正起作用时才多用随机数。
- `gt` 时 k 的上限仍是 `一半 × 堆叠上限`。

**建议**：如上。

**C18　任务文案**
- `chest_take.md` 和 `chest_put.md` 里的"箱子"改成变量 `{{container}}`，按本轮容器填：小箱子、大箱子都填"箱子"，漏斗填"漏斗"，发射器填"发射器"。
- 这只是如实描述场景，不提示格号和界面差异。

**建议**：如上。

**C19　记录与报告**
- 记录的 `chest` 字段直接记本轮容器（`small` / `large` / `hopper` / `dispenser`）。
- 报告 `--by chest` 的分组名增加"漏斗""发射器"。
- 不新增列。

**建议**：如上。

**C20　观察什么（不改胶囊、不加提示）**
- 前几轮漏斗、发射器题，预计会在规划或执行时碰到现有胶囊的报错，然后重新规划。
- 要看的是复盘时的做法：是把容器格数改成从界面推出来，还是另存一份专用的胶囊。
- 这些都由 agent 自己决定。训练报告按 `--by chest` 对比各容器的成功率和用时。

**建议**：照此执行。建议先用 `chest=hopper`、`chest=dispenser` 分别跑几轮，再用 `chest=all` 混着跑。

### 8.4 验收（实施后）

1. `chest=small/large` 用旧种子出题，结果和改动前完全一样。
2. 用 `chest=hopper` 跑几轮：
   - `aimOk=true`、`chestSlots=5`；
   - `container/get` 的 `type` 是 `hopper`；
   - 漏斗下面是红石块，漏斗方块状态 `enabled=false`；
   - 往漏斗上方扔一个物品，它不会被吸进漏斗，判 `lost`。
3. 用 `chest=dispenser` 跑几轮：`aimOk=true`、`chestSlots=9`、`type` 是 `generic_3x3`，发射器不会动作。
4. 用 `chest=all` 让四种容器轮流出现：
   - 场地里不残留红石块，也不残留半个箱子；
   - 发射器从来没有被触发。
5. 放进题用 `rel=gt`，漏斗、发射器各跑一组：要求全部放入时，容器一定装得下。
6. 取物题在漏斗上用 `rel=lt stack=1`：每道题都只有 1 种物品，目标占 2 格。
