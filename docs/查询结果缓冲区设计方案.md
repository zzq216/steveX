> 目标：树里查询的完整结果放进缓冲区，不进黑板，黑板里只放一个句柄。树可以：
> - 在缓冲区上再查询；
> - 把句柄交给代码，处理整份数据；
> - 代码算出的大结果（比如一条几千个点的路线）也放回缓冲区。

## 1. 问题

1. **黑板一个值最多 16 KB**（F2）。地形一条约 100 字节，一个值只装得下约 160 条。`core.nbt.query` 的上限是 512 条，在树里其实用不满：超过 16 KB 就写黑板失败，节点 FAILURE。
2. **查询参数只能写字面量**（F5）。树里不能"按我现在的位置查周围"。真实任务里位置不固定，长距离寻路只能一段一段地按当前位置查（《算法层与执行层设计方案》§7.1）。
3. **代码算出的大结果也放不进黑板**：沙箱输出最多 64 KB，再写黑板还受 16 KB 限制（F4）。一条几千个点的路线放不下。

## 3. 总体设计

```
树里的查询（core.nbt.query / core.json.query，into）
   │
   ▼
缓冲区（宿主内存，挂在任务上）── 句柄 "buf:…" ──► 黑板
   │                                               │
   ├─ core.buffer.query：再筛、计数 ◄───────────────┤
   └─ Compute：handle 输入 → 沙箱拿到整份数据；handle 输出 → 结果放回缓冲区
```

- **缓冲区**：宿主内存里的一份份结果，每份挂在一个任务上，任务结束时释放。
- **句柄**：一个短字符串，指向一份缓冲区。它能整体序列化、很小，所以放进黑板以后，F3 里那些复制、指纹都不受影响。
- **只在树里**：缓冲区由树里的节点建，也只由树里的节点用。大模型在产出树的回合本来就拿不到数据（F1），它看到的只是句柄和摘要（Q7）。

## 4. 决策点

### Q1　为什么不直接调大黑板的上限

最简单的做法是把 `maxValueBytes` 从 16 KB 调到几 MB。不这样做的原因（F3）：

- 黑板会被整份复制进每一个展开、修复、复盘请求，以及任务摘要。调到几 MB，这些请求每个都带着几 MB 的地形；
- 每次进入调用胶囊的节点都要对参数算指纹，参数里有几 MB 的数组，每次都要重新算一遍；
- 《nbt查询api设计方案》§5.4 已经为这个理由选过方案 A（F10）。

句柄让这些机制都不用面对大数据，查询和代码的能力却一点不少。

**建议：采用。不调大黑板上限，用缓冲区。**

### Q2　缓冲区和句柄

- **放在插件进程的内存里**，不落盘，不新增任何文件读写。
- **挂在任务上**：任务的主树、子树、展开出来的节点都能用同一份；别的任务用不了。快树这一稿不接（Q10）。
- **句柄的形状**：`buf:<任务内序号>`，比如 `buf:3`。
- **新增值类型 `handle`**：签名里可以声明 `{ type: 'handle' }`。黑板里它就是一个字符串。
- **每份缓冲区带的元数据**：
  - 从哪来：数据源（`nbt:terrain`、`json:recipes`、`buffer:buf:2`、`code:<条目名>`），以及查询参数或产生它的节点 id；
  - 条数、字节数、字段（投影的列名；代码产出的记为"代码给出的"）；
  - 版本戳：数据源的版本，代码产出的取它所有输入句柄的版本；
  - 建立的时刻、建它的节点 id。

**建议：采用。**

### Q3　树里怎么建、怎么查

1. **`code/core.nbt.query`、`code/core.json.query` 加 `into`**（字面量 `true`）：
   - 全部命中进缓冲区，不受 `limit` 截断，输出 `handle`、`matchedCount`、`sourceVersion`，不输出 `result`；
   - 输出的形状由字面量 `into` 决定，装载时就能确定，不破坏 §3.1"静态可判"的初衷；
   - 不给 `into` 时和现在完全一样。
2. **新的宿主条目 `code/core.buffer.query`**：
   - 输入 `from`（`$键名`，类型 `handle`）、`filters`、`fields`、`limit`、`into`；
   - 输出同上：不给 `into` 是 `result`（受 512 条和黑板 16 KB 的限制），给了是新的 `handle`；
   - `fields` 只能取这份缓冲区已有的列，用了没有的列就是这个节点 FAILURE。
3. **`filters` 里的条件值可以引用黑板**（`$键名`），例如：

   ```json
   { "filters": { "pos.0": { "min": "$x0", "max": "$x1" }, "pos.2": { "min": "$z0", "max": "$z1" } } }
   ```

   这就是"按我现在的位置查周围"。只放开条件**值**：
   - `path`、`fields`、`limit`、`into` 仍然只能写字面量，数据源和输出的形状照样在装载时确定；
   - `filters` 的**键**（查哪个字段）也只能写字面量，所以查询的语义仍然能静态审阅，变的只是区间的数值；
   - 运行时解析出来的值按原有规则校验（区间必须是数字……），不合格就是这个节点 FAILURE，原因写明是哪个键。

**建议：采用。** 第 3 条是对《nbt查询api设计方案》§3.1 的修订（Q9）。

### Q4　沙箱里怎么用句柄

**输入**：代码条目的签名可以声明 `handle` 类型的输入，例如：

```json
"inputs": { "terrain": { "type": "handle", "required": true } }
```

- Compute 调用时照常写 `"params": { "terrain": "$terrain" }`；
- 宿主在进沙箱前把句柄换成那份数据（记录数组），按 JSON 交进去，代码里拿到的 `params.terrain` 就是数组。沙箱"进出都经过 JSON"的规矩不变（F4）；
- 同一份缓冲区第一次进沙箱时把 JSON 文本生成好、存着，后面再用不重复序列化；
- 参数指纹（F3）对句柄只算句柄字符串，不算它指向的数据。

**输出**：签名里声明为 `handle` 的输出，代码照常返回数组或对象。宿主把它存成一份新的缓冲区，黑板只写句柄。这一项不受沙箱 64 KB 输出上限的限制，改由缓冲区的上限管（Q6）。比如寻路代码返回一条几千个点的路线，用的就是这一条。

**超时**：几十万条数据的解析就要上百毫秒，1000 ms 的缺省超时不够用。有 `handle` 输入或输出的调用，超时改为缺省 5000 ms（配置项 `sandbox.handleTimeoutMs`），解析和序列化的时间都算在里面。

**建议：采用。**

### Q5　缓冲区旧了怎么办

缓冲区存的是建立时那一版的结果。之后 agent 走动、看见新东西，记忆文件会更新（F8）。

- 每份缓冲区记着数据源的版本戳（Q2）。
- `core.buffer.query` 的输出、`bt_view` / `bt_inspect` 的摘要里带 `stale`：数据源现在的版本和它的不一样就是 `true`。只做一次 stat，开销很小。
- **不自动刷新**：旧了还用不用、什么时候重查，由树决定。分段寻路"走完一段、重看、重算"（《算法层与执行层设计方案》§7.1）本来就是这个节奏。
- 代码产出的缓冲区：任何一个输入句柄 `stale`，它就 `stale`。

**建议：采用。**

### Q6　上限

| 项目 | 缺省 | 超出时 |
|---|---|---|
| 单份缓冲区的条数 | 200000 | 建立失败，节点 FAILURE，原因写明"命中 N 条，超过上限"，可以加筛选条件缩小 |
| 单份缓冲区的大小（JSON 字节） | 32 MB | 同上 |
| 每个任务的缓冲区总大小 | 128 MB | 按最久没用过的先删，被删的句柄再用时报"缓冲区已经释放"，并写明是被上限挤掉的 |
| 每个任务的缓冲区个数 | 64 | 同上 |

都是配置项（`buffers.*`）。200000 条约是 4 × 4 区块的场地里露在外面的地形的二三十倍，够查一块几百格见方的已探索区域。

不给 `into` 的查询仍然是现在的上限（512 条、256 KB，写黑板 16 KB）。

**建议：采用。**

### Q7　在哪里能看到

大模型在产出树的回合拿不到数据（F1），这里也只给句柄和摘要，和 I13"黑板只给形状不给值"一致：

- **`bt_view`** 新增一段"缓冲区"，每份一行：句柄、来源、条数、大小、字段、是否 `stale`、建它的节点。
- **`bt_inspect blackboard`**：值是句柄的键，旁边附上这份缓冲区的摘要，不展开内容。
- **展开、修复、复盘请求**：黑板里的句柄照常出现（它只是个短字符串），附上摘要。
- **事件日志、任务历史**：只记句柄和摘要，不记内容。

**建议：采用。**

### Q8　生命周期

- **建立**：树里的节点（Q3、Q4）。
- **释放**：任务 `done` / `failed` 时全部释放（F9）。被上限挤掉的单份提前释放（Q6）。复盘在任务结束以后，这时只剩摘要（Q7）。
- **插件重启**：缓冲区在内存里，重启就没了。重启后恢复的任务，黑板里的句柄再用时报"缓冲区已经释放（插件重启过）"，由树重查。这一稿不落盘（Q10）。
- **胶囊**：存进胶囊库的代码条目可以声明 `handle` 输入输出。胶囊里只存签名和代码，不存任何缓冲区。

**建议：采用。**

### Q9　和已定规则的关系

要修订《nbt查询api设计方案》的地方：

| 那份方案的条目 | 原来 | 改为 |
|---|---|---|
| §3.1 四个参数只能写字面量 | `path`、`filters`、`fields`、`limit` 全部字面量 | `filters` 的**条件值**可以引用黑板；`filters` 的键、`path`、`fields`、`limit` 以及新增的 `into` 仍然只能写字面量（Q3） |
| §5.4 v1 不暴露句柄 | 句柄只在宿主内部 | 句柄可以进黑板，类型 `handle`（Q2） |
| §10 审阅点 1（动态参数是 v2） | 暂缓 | 部分落地：只放开条件值 |

不变的：
- I13：查询工具仍然只在普通问答回合可用，三个工具都不改；
- 数据源白名单（五个 NBT 源、白名单 JSON）、路径语法、读一致性（`SOURCE_UNSTABLE`）；
- 黑板"值可整体序列化、有大小上限"这条系统级不变量。句柄恰恰是为了守住它。

实施时把这几处改动同步写回那份方案，并在 `command_docs`、`data_shapes` 里讲清楚 `into`、`core.buffer.query`、`handle`。只讲接口的边界，不教怎么用来寻路。

**建议：采用。**

### Q10　暂不做的部分

- **紧凑的地形格式**（比如按列给出地表高度）：先看整条记录的数组在沙箱里够不够快。不够，再考虑在 `core.buffer.query` 里加输出形式。
- **快树使用缓冲区**：快树的反应要快、要短，用不着大数据。
- **跨任务共享、落盘**（Q8）：长期任务真的需要时再做。
- **查询工具的分页**：查询工具只在普通问答回合可用（F1），和训练、任务无关，这一稿不动。

1. 树里的查询：
   - `core.nbt.query` 加 `into: true` 以后，黑板里只有句柄、`matchedCount`、`sourceVersion`，没有 `result`；`matchedCount` 等于命中总数，不受 `limit` 截断；
   - 不给 `into` 时和改动前一样；
   - `core.buffer.query` 能在缓冲区上筛、投影，也能 `into` 出一份新的；`fields` 用了缓冲区里没有的列，节点 FAILURE。
2. 沙箱：
   - 一份 5 万条的地形缓冲区交给一个 Compute，代码能拿到整个数组，算完的结果写黑板；
   - Compute 返回一条几千个点的路线（`handle` 输出），黑板里只有句柄，`core.buffer.query` 能读到这些点。
3. 动态条件：`filters` 里用 `$x0` 这类引用，按黑板里的值筛；值不是数字时节点 FAILURE，原因写明是哪个键。
4. 别的任务用这个句柄报错。
5. 旧了：建好缓冲区以后走动、snapshot，`bt_view` 里这份显示 `stale`。
6. 上限：超过单份条数上限报错，写明命中多少条；超过任务总量时最久没用的被挤掉，再用它报"被上限挤掉"。
7. 任务结束后句柄失效；重启插件后，恢复的任务里旧句柄报"插件重启过"。
8. 展开、修复、复盘请求和事件日志、任务历史里只有句柄和摘要，没有记录内容；请求的大小和改动前同一量级。
9. 普通问答回合的 `nbt_query`、`json_query` 和改动前完全一样；产出树的回合仍然调不到它们。
