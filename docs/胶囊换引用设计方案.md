# 胶囊换引用设计方案

> 状态：**P-S1–P-S4 已实施**（2026-11-15），单元测试通过，待游戏内按 §6 第 3 条观察。审阅结论：R1–R7 全部采纳建议。实施说明见 §7。
>
> 目标：复盘时改进了一个被子树引用的胶囊（存了同名新版），能用一次很便宜的调用，让引用它的子树也改用新版。不需要 agent 重写整棵子树。

## 1. 问题

胶囊按内容哈希存。子树保存时，里面引用的胶囊会钉到当时的版本（`code/x@hash`）。之后 `code/x` 再存新版，已经存下的子树仍然用旧版（`prompts/skills/reflect.md`："已经存下的树钉着旧版，不受影响"）。

要让子树改用新版，现在唯一的办法是用 `capsule_save` 把整棵子树重交一遍：完整的 `signature` + `body`、`replaces`、`versionNote`，还要过写死值检查。子树很大时，这比改代码本身贵得多。

切石机训练（任务 10–13）里，这直接造成了复盘的空转：

| 复盘 | 现象 |
|------|------|
| 任务 12（c11） | 单步 274 s、输出 4.8 万 token，在思考里写出了 `plan-fill-batches` 改进后的完整代码，最后没存。理由是"实改胶囊中的 plan-fill-batches 需要同时重存钉着旧哈希的树胶囊，本次不划算" |
| 任务 13（c12） | 一开始就列出树钉着的 10 个代码哈希，然后说"要改补料算法，就得同时改代码和树，改动更大"，最后也没改 |
| 任务 6、10、11、12 | 同一个补料问题先后被记了 4 次 open，每次复盘都重新取证、重新设计 |

## 2. 已核实的事实

| # | 事实 | 对方案的影响 |
|---|------|------------|
| F1 | 存进库的树，里面的引用一律带哈希（`library.js`、`build.js` 的 `pinRefs`）；装载时不会自动换成最新版，取不到就报错（算法层 §8.4） | 换引用必须产生子树的新版本，不能改成装载时取最新版。那样会破坏"同一个引用永远是同一份内容" |
| F2 | 本地库里最新版的子树共 39 棵，其中 17 棵引用了别的子树 | 换引用会连锁：子树 T1 改用新版代码，T1 本身就有了新版，引用 T1 旧版的 T2 也要跟着换 |
| F3 | 现在就有 7 棵子树的最新版钉着某个依赖的非最新版（如 `trees/chest.take-exact` 钉着 `code/chest.plan-take-exact` 的旧版；4 棵钉着 `trees/craft.once-in-inventory-2x2@18cffa3d`） | 有的可能是故意留着旧版（版本说明里可以写"旧版在某种情况下更好"）。所以不能一律换成最新版，要换哪些由 agent 指定 |
| F4 | `capsule_save` 替换同名条目时，`versionNote` 必填（改了什么、哪一版在什么情况下更好），之后用到相关版本的任务要核对 | 只换引用的新版本没有自己的优劣判断，判断都在被换的那个胶囊的版本说明里，不应该再让 agent 写一遍 |
| F5 | 写死值检查拿条目里的字面量和这次任务观察到的值比对（`literals.js`） | 只换引用时 body 的其余部分没变，这些字面量在当初保存时已经检查过了 |
| F6 | 换了版本的胶囊，输入输出（`signature`）可能变了 | 换完必须照常过树的校验（`validateTree`）；不过就报错，交给 agent 手工重存 |
| F7 | 使用统计按哈希累计；`capsule_search` 那一行显示的是同名所有版本的合计，`capsule_get` 另外显示"这一版"的统计 | 子树换引用后，新版"这一版"的统计从 0 开始，搜索结果那一行不受影响 |
| F8 | 复盘回合能调用哪些工具由 guard 按请求类型准入 | 新工具要加进复盘回合的准入名单 |

## 3. 总体设计

新增一个复盘工具 `capsule_repin`：把库里某棵子树最新版中，指定名字的引用换成那些名字现在的最新版，存成这棵子树的新版本。其余内容（`signature`、`preconditions`、`description`、其他引用）原样保留。

```
capsule_repin { requestId, tree: "trees/<name>", refs: ["code/<name>", "trees/<name>", …] }
→ 已存：trees/<name>@<新 hash>（换了：code/x @aaaa → @bbbb）
  还钉着 trees/<name> 旧版 @<旧 hash> 的树：trees/p@…、trees/q@…
```

配套两处只是给信息：

- `capsule_save` 存同名新版（`replaces`）成功时，结果里列出"最新版还钉着它旧版的子树"；
- 复盘 skill 里"已经存下的树钉着旧版，不受影响"后面补一句：要让它们改用新版，用 `capsule_repin`。

这是补能力、说清楚工具边界，没有教 agent 该不该换。

## 4. 决策点

### R1　做成新工具，还是 `capsule_save` 的参数

| 方案 | 做法 | 说明 |
|------|------|------|
| **A** | 新工具 `capsule_repin { requestId, tree, refs }`，一次换一棵树 | 参数少、语义单一；连锁时一棵一棵换，每次几秒 |
| B | `capsule_save` 加参数 `repin: [树…]`，存新版代码的同时把这些树也换掉 | 少一次调用；但 `capsule_save` 的参数已经很多，同一次调用里一部分成功、一部分失败时不好说清 |
| C | 存新版时自动换掉所有引用旧版的子树 | 和 F3 冲突：故意留着旧版的树会被悄悄换掉 |

**建议：A。**

### R2　换哪些引用

| 方案 | 做法 |
|------|------|
| **A** | `refs` 必填：列出要换的名字（`code/x`、`trees/y`，不带哈希），每个都换成它现在的最新版。树里没有这个名字，或者已经是最新版，就报错 |
| B | `refs` 可省略，省略时把所有不是最新版的引用都换掉 |

B 会把 F3 里故意留着的旧版一起换掉。**建议：A。**

### R3　版本说明

| 方案 | 做法 |
|------|------|
| **A** | 自动生成，不让 agent 写：版本记录里写 `parent`、`by`（任务 id），加一个 `repin` 字段：`[{ ref: "code/x", from: "aaaa", to: "bbbb" }]`。`change` 自动写成"只换了引用：code/x @aaaa → @bbbb"；不写 `claims`，`none` 写"只换了引用，两版的差别见 code/x@bbbb 的版本说明"。`capsule_get` 的版本链显示成"换引用：…" |
| B | 和 `capsule_save` 一样要求 agent 写 `versionNote` |

用到新版子树的任务，执行时也会执行新版代码，所以代码那边的判断照常会被核对（F4）。**建议：A。**

### R4　校验

- 编译和树校验照常做（F6）：换了版本的胶囊输入输出变了，就返回校验错误，提示用 `capsule_save` 手工重存。
- 不做写死值检查（F5）。
- 不检查 `read` 是否缺失：这项检查只在带 `from`、从任务树存子树时才有。
- 锁定的条目（手工做的基础条目）不能被替换，所以也不能换引用，直接报错。

**建议：采用。**

### R5　连锁

| 方案 | 做法 |
|------|------|
| **A** | 不自动连锁。结果里列出"最新版还钉着这棵树旧版的子树"（不含已下架的），要不要接着换由 agent 决定 |
| B | 加 `cascade: true`，把引用它旧版的子树一层层全部换掉 |

B 同样会碰到 F3 的问题，而且一次调用改多少棵树不可控。**建议：A。**

### R6　能在哪些回合用

| 方案 | 说明 |
|------|------|
| **A** | 只在复盘回合用，和 `capsule_save` 一样 |
| B | 复盘和整理（`/bt curate`）回合都能用 |

复盘回合手上有这次任务的证据，新版代码通常也是在这里存的。整理回合没有任务证据，也不存新版本。**建议：A。** 以后整理时如果确实需要，再放开。

### R7　"引用它旧版的子树"怎么找

- 扫描 manifest 里每个名字的最新版子树（已下架的不算），看它的 body 里有没有引用某个名字的非最新版本。
- 库目录里那些旧版本文件不扫：它们已经不是最新版，规划时不会被选中。
- 快树（`src/bt/trees/fast/`）不在范围内：快树补丁有自己的保存流程。

**建议：采用。**

   - `capsule_repin { tree: "trees/t", refs: ["code/x"] }` 产生 `trees/t` 的新版本：除了这一个引用，body 完全相同，`description` 保留，版本记录带 `repin`；

2. 换上去的版本改了输入名时，返回校验错误、什么都不写。
3. 在游戏里跑一次切石机训练。如果复盘时 agent 改进了 `plan-fill-batches`，看它是否用 `capsule_repin` 换掉 `trees/stonecutter.cut-multi-fill-exact` 的引用，以及下一轮规划用到的是不是新版。

## 7. 实施说明（2026-11-15）

**胶囊库（P-S1）**：`src/capsules/library.js`、`src/capsules/save.js`

- `capsuleRefs(body)` 收集子树正文里所有的 `ref`
- `staleDependents(key)`：扫描 manifest 里每个名字最新版的子树（跳过已下架的和 key 自己），找出钉着 key 某个非最新版的，返回 `[{ ref, pins }]`
- `repinTree({ library, registry }, tree, names)`：
  1. 取 `tree` 的最新版（写了哈希就必须是最新版；锁定的拒绝）；
  2. 对 `names` 里的每个名字，把正文里该名字的所有引用换成最新版；
  3. 名字带了哈希、是草稿、是这棵树自己、树里没引用它，或者已经是最新版，都逐条报错；
  4. 换完照常跑 `validateTree`，不过就返回错误、什么都不写；
  5. 用原来的 `description`、`signature`、`preconditions` 写成新版本。返回 `changes: [{ ref, from: [旧哈希…], to }]` 和 `parent`

**版本记录（P-S2）**：`src/capsules/versions.js`、`src/tools/knowledge.js`

- `record` 多一个可选的 `repin` 字段。`capsule_get` 的版本链里，这种版本多一项 `repin`，显示成"code/x @旧 → @新"
- 自动生成的说明：`change` = "只换了引用：…"，`none` = "只换了引用，两版的差别见被换胶囊的版本说明（…）"，不写 `claims`
- 如果换出来的内容和库里已有的某一版完全相同，就不覆盖那一版原有的记录

**工具（P-S3）**：`src/tools/reflect.js`、`src/llm/bridge.js`、`prompts/skills/review.md`

- `capsule_repin { requestId, tree, refs }`：加入复盘回合的准入名单（`REFLECT_TOOLS`、`REFLECT_ONLY_TOOLS`），整理回合和规划回合都不能用
  - 成功时记录版本说明，记事件 `capsule/repinned`，并把新版本加进本次复盘的已存清单（`bt_reflect_done` 的 `saved`）
  - 结果里的 `dependents` 列出最新版还钉着这棵树旧版的子树
- `capsule_save` 存同名新版成功时，结果里多一个 `pinnedOld`，渲染成"最新版还钉着它旧版的子树：…"
- 复盘 skill 第 10 行补了一句"要让库里某棵树改用新版，用 `capsule_repin`（只换引用，存成那棵树的新版本）"
- guard 不用改：它按请求类型的工具名单准入

**测试（P-S4）**：`test/reflect.test.js` 新增一条，覆盖：

- 存新版代码后列出钉着旧版的子树；
- 各种拒绝：`refs` 为空、带哈希、名字不存在、树不存在、不是子树、树里没引用、不是最新版、别的会话调用、已经是最新版、锁定条目；
- 换一层：正文除了这个引用完全相同，`description` 和 `signature` 保留，版本记录正确，往上一层的子树只列出不换；
- 按指定换上一层；
- 新版改了输入名时校验不过、manifest 不变；
- 工具渲染、事件、已存清单、准入、skill 文案
