## 0. 一句话

路由 = **填槽 → 订阅 → 通用编排**。
本阶段交付的是这套"插座"和"空插头"——**不交付插头里的电路**（提示词正文与处理器实现）。

---

## 1. 为什么换掉"三分类 + 硬编码编排"

旧设计把输入压成一个枚举（`normal / fact / task`），编排器里写死顺序、组合、失败隔离、话术。后果：

| 要新增的东西 | 旧设计要改的地方 |
|---|---|
| 快树指导 | 枚举加值、路由分支、排序规则、组合、失败隔离、话术、日志字段 |
| 事实 + 任务同时 | 专门写组合分支 |
| 以后加"技能库修改 / 联网搜索 / 定时提醒" | 每加一个都要改一遍编排器 |
| 追问 | 当成"空意图"的特例 |

组合数随路由类型数呈 N×M 增长。槽位式设计把这个 N×M **消灭在结构里**：槽位正交，组合由订阅自动产生。

- 内容层改动不触碰编排器；编排器改动不影响内容文件。

## 3. 槽位模型（框架固定）

**槽位**是输入的一个正交维度；每个槽位有封闭词表，`none` 显式表示"没有"，`unknown` 表示"判不出来"。

### 3.1 v1 槽位表（接口）

| 槽位 | 取值 | 消费者 |
|---|---|---|
| `domain` | `minecraft` / `general` / `unknown` | 所有 MC 处理器的准入 |
| `knowledge` | `none` / `fact` / `unknown` | `fact` 处理器 |
| `action` | `none` / `execute` / `unknown` | `task` 处理器 |
| `artifact` | `none` / `fast_tree` / `unknown` | `unsupported` 桩；将来的快树处理器 |

> 槽位的**自然语言定义与判定细则**属于内容层，留空（§16 占位清单 #1）。

规则（框架）：

- **正交**：槽位独立判定；多个非 `none` = 多意图，天然支持；
- **只填路由级槽位**：目标、数量、坐标等参数**不是**路由槽位（v1），由任务流内部提取；
- **`unknown` 是合法值**，触发追问（§8）；词表可以加值，不影响编排器。

### 3.2 Slot 对象与 `payload`

每个槽位的运行时结构固定为：

```json
{ "value": "…", "payload": null }
```

> **2026-10-28 删除 `confidence`**：模型自报的置信度不是真实概率，拿它和阈值比较等于和编出来的数比较；它表达的"拿不准"与 `unknown` 重复，还会出现 `execute` 配 0.5 这类自相矛盾的组合，并多出一类校验失败。"不确定"现在只用 `unknown` 表达。模型多给了 `confidence` 字段时校验忽略它，不报错。

| 槽位 | `payload` 承载什么 | 示例 |
|---|---|---|
| `domain` | `null`（通常不需要内容） | — |
| `knowledge` | 查询/要记住的内容摘要（短文本或小对象） | `"钻石的生成高度"` / `{ "fact": "坐标 100,64,100" }` |
| `action` | 要做的事的摘要（短文本） | `"挖 8 个铁矿"`；**不是**完整参数集或计划 |
| `artifact` | 要修改的产物与意图摘要 | `{ "target": "fast_tree", "intent": "优先挖铁" }` |

约束：

- `payload` 可为 `null`；**键必须存在**（与 `value` 一样）。
- `payload` 只供处理器 `run` 使用：**`match` 与排序只读 `value`**，不得依赖 `payload`（保证路由可判定、可测试）。
- `payload` 是**短摘要**，不替代下游的参数提取与任务分解；具体 schema 属内容层，留空（§16 #12）。
- `payload` **默认不写日志**（只记 `value` 与 payload 的存在性/长度），避免扩散用户原文与敏感内容。

## 4. 处理器与订阅（接口固定，内容留空）

### 4.1 声明字段（框架契约）

```text
handler = {
  id:        string
  match:     (slots) => boolean      // 订阅哪些槽位
  provides:  string[]                // 提供的产物，供软依赖排序
  requires:  string[]                // 软依赖：提供者被选中时排前，没选中也照跑
  onFailure: "continue" | "stop"
  priority:  number                  // 无依赖关系时的排序
  run:       (slots, context) => ResponsePart   // 内容层实现，本阶段为空；可读 payload
}
```

`match` 只读 `value`；每个槽位的 `payload` 只在 `run` 里使用。

### 4.2 v1 处理器（id 固定，`run` 留空）

| id | 订阅（示例声明，取值待统筹） | 本阶段行为 |
|---|---|---|
| `fact` | `domain=minecraft` 且 `knowledge=fact` | 空实现，返回占位 |
| `task` | `domain=minecraft` 且 `action=execute` | 空实现，返回占位 |
| `unsupported` | `artifact != none` | 固定占位文案："该能力暂不支持" |
| `clarify` | 决定性槽位 `unknown` | 返回占位追问文本 |
| `default` | 没有其它处理器命中时由编排器兜底 | 空实现，返回占位 |

> `requires` / `onFailure` / `priority` 的**实际取值**留空（§16 #7）；上表只是让框架可测的示例声明。

### 4.3 新增一条路由 = 做什么

| 新能力 | 需要改的东西 |
|---|---|
| 快树指导（将来） | 注册 `fast-tree` 处理器（替换桩）；槽位值已存在 |
| 技能库修改 | `artifact` 加值 + 注册处理器 |
| 联网搜索 | `knowledge` 加值 + 注册处理器 |
| 定时提醒 | 新增槽位 `schedule` + 注册处理器 |

**编排器、日志结构、追问协议、响应拼接全部不改。**

## 5. 通用编排器（机制固定，内容留空）

编排器只有四步，与具体路由类型无关：

1. **选择**：运行所有 `match(slots) === true` 的处理器；
2. **独占**：`clarify` 命中则只运行它，其余跳过；
3. **排序**：按 `requires`/`provides` 软依赖拓扑排序，同层按 `priority`；
4. **执行与合并**：依次运行，按 `onFailure` 决定继续/中止；各 `ResponsePart` 按顺序拼接。

由此自然得到（**无需特判**）：多槽位组合、事实先于任务、失败隔离、无命中走默认、追问独占。

### 5.1 桩路由器（仅开发/测试）

框架阶段需要在不接 LLM 的情况下跑通编排：

- **桩路由器**实现与真实路由器相同的接口，输入可由测试脚本指定（返回一份固定的槽位 JSON）；
- 真实路由器的提示词正文留空（§6），框架不依赖其内容；
- 框架测试全部用桩路由器驱动（§15）。

### 5.2 接口边界

```text
Router:      MessageContext -> SlotJSON
Orchestrator: SlotJSON + MessageContext -> Response
Handler:      (SlotJSON, MessageContext) -> ResponsePart
```

路由器可替换（LLM / 桩 / 将来规则引擎），编排器不感知实现。

## 6. 提示词模板（骨架）

路由提示词 = 固定顺序的块，**块标题与顺序现在定，正文留空**：

| 块 | 作用 | 本阶段 |
|---|---|---|
| `[SYSTEM]` | 通用行为约束 | 复用现有系统提示词 |
| `[SLOT_DEFS]` | 4 个槽位的定义、判定问题与 `payload` 提取规则 | **正文留空**（内容文件） |
| `[RULES]` | 正交、unknown、不对称成本原则 | **正文留空**（内容文件） |
| `[FEW_SHOT]` | 每槽位独立示例（不做组合枚举） | **正文留空**（内容文件） |
| `[OUTPUT]` | JSON schema 与校验规则 | **固定**（§7） |
| `[CONTEXT]` | 最近 N 轮对话 + 待定追问 | 运行时注入（N 占位 6） |
| `[USER]` | 用户指令 | 运行时注入 |

- 内容文件缺失或为空时：路由器可加载桩内容并明确报错，**不得静默用空提示词上线**。
- few-shot 的**覆盖要求**现在定：纯事实、纯任务、事实+任务、寒暄+事实、`unknown`、`artifact=fast_tree`；具体示例留空。

## 7. 输出契约（固定）

```json
{
  "slots": {
    "domain":    { "value": "minecraft", "payload": null },
    "knowledge": { "value": "fact",      "payload": "钻石的生成高度" },
    "action":    { "value": "execute",   "payload": "去挖钻石" },
    "artifact":  { "value": "none",      "payload": null }
  },
  "reason": "一句话判据",
  "clarification": null
}
```

约束：

- 四个槽位**必须全部给出**（含 `none` / `unknown`），且每个槽位都带 `payload` 键（可为 `null`，只供 `run` 使用）；
- 决定性槽位有 `unknown` ⇒ 只运行 `clarify`；`clarification` 是追问时用的那句话，**不单独触发追问**（2026-10-28）；
- **禁止**：回答问题、调用工具、输出计划、附带解释。

校验规则（框架）：JSON 可解析、四槽位齐全、值在词表内、`unknown` 按 §8 处理；不合法 → 重试一次 → 仍不合法走追问。

## 8. 追问（机制固定，话术留空）

- **触发**：任一**决定性槽位**为 `unknown`（2026-10-28 起只看这一处；置信度阈值与"clarification 非空"两条触发已删除）。
  - "决定性" = 不同取值会导致不同的处理器集合。
- **行为**：`clarify` 独占执行；保存槽位草稿（含 `payload`）与待定状态；下一条消息带着它重新填槽。
- **规范**：优先二选一；不重复同一句；**上限 2 次**，仍判不出 → 强制二选一。
- **话术留空**（§16 #4）；追问轮不执行任何处理器，也不走正常回答。

---

## 9. 多意图与执行（机制固定）

- 多意图不是特例：`knowledge=fact` + `action=execute` 天然命中两个处理器；
- 顺序由软依赖决定，不由"类别对"硬编码；
- 失败隔离由各处理器的 `onFailure` 声明；
- 用户可见回复 = `ResponsePart` 按执行顺序拼接；
- `artifact=fast_tree` + `action=execute`：`unsupported` 说明 + 任务照跑——按槽位**部分支持**，不因一个槽位不支持而整体拒绝。

## 10. 日志（schema 固定，sink 留空）

每次路由写一行到完整日志：

| 字段 | 说明 |
|---|---|
| `messageId` / 时间 | 关联用户消息 |
| `slots` | 四个槽位的值；`payload` 默认不落日志（只记存在性与长度） |
| `handlers` | 命中的处理器 id 与执行顺序 |
| `clarification` | 追问文本（如有） |
| `outcomes` | 各处理器成功/失败 |
| `userCorrected` | 用户随后是否改口 |

新增处理器自动出现在日志（按 id），无需新增字段。落地 sink 与展示留空（§16 #9）。

## 11. 失败模式（框架层）

| 情形 | 处理 |
|---|---|
| 路由输出非法 JSON / 缺槽位 | 重试一次；仍失败 → 追问，不默认执行任务 |
| 路由超时 / 模型不可用 | 降级为追问或明确报错，不猜测 |
| 决定性槽位 `unknown` | `clarify` 独占追问 |
| 追问超过 2 次 | 强制二选一 |
| 处理器失败 | 按 `onFailure`：`continue` 不阻塞其它处理器，`stop` 中止后续 |
| `artifact` 命中但无真实处理器 | `unsupported` 桩返回占位文案，不做任何写操作 |
| 提示词内容文件缺失/为空 | 框架报错并拒绝上线；测试用桩内容 |
| 误路由被用户纠正 | 记录 `userCorrected`；按新槽位重新分派 |

**不对称成本原则**（写进内容层规则块）：任务误判为正常回答 = 目标丢失；正常问题误判为任务 = 白跑昂贵的慢树生成。对 `action=execute` 保守，对 `knowledge=fact` 宽松。

## 12. 与既有设计的接口

- **单一真相**：`skills` 的前提条件应与**处理器的 `match` 谓词**同源；路由提示词只是把谓词翻译成自然语言。当前导图已出现漂移（快树分支删了、skill 前提还在），本方案以处理器表为准。
- **事实库 / 记忆世界**：`fact` 处理器的去向，沿用记忆系统设计。
- **慢树生成 / 任务执行**：`task` 处理器只负责启动，内部沿用 [算法层与执行层设计方案.md](算法层与执行层设计方案.md) 与 [行为树节点设计方案.md](行为树节点设计方案.md)。
- **完整日志**：§10 是它的一个新段。
- **提示词注入**：路由提示词独立于系统提示词；填槽完成后只注入命中处理器需要的 skills。

## 14. 实施顺序

### 阶段 A：框架（本阶段）

1. 槽位 schema + JSON 输出契约；
2. 提示词模板骨架（七块，正文留空的文件占位）；
3. 处理器注册接口 + 通用编排器（选择 / 独占 / 软依赖排序 / 失败策略 / 响应拼接）；
4. 桩路由器 + 五个处理器桩（空实现 / 占位文案）；
5. 追问状态机骨架 + 日志 schema 骨架；
6. **框架测试**：用脚本化槽位 JSON 驱动，断言选择、顺序、拼接、追问、失败策略、未支持能力；
7. 内容文件加载器（缺失/为空要报错，不允许静默上线）。

### 阶段 B：内容（后续，全局统筹后）

8. 槽位定义正文、规则块、few-shot、追问话术；
9. `fact` / `task` 的 `run` 实现与 skill 提示词；
10. 真实阈值与处理器声明取值；
11. 评测集与调参；
12. 快树处理器（替换 `unsupported` 桩）。

## 15. 框架验收标准

框架阶段完成时，必须满足（不依赖任何提示词正文与真实处理器）：

1. 给定一份脚本化槽位 JSON，编排器的**选择、顺序、拼接**与声明一致且可断言；
2. 增删处理器**不需要修改编排器**；
3. `unknown` → 只运行 `clarify`，不执行其它处理器；
4. `artifact=fast_tree` → 只返回占位文案，**不发生任何写操作**；
5. 处理器失败按 `onFailure` 表现（继续/中止）；
6. 内容文件缺失或为空时，框架**拒绝上线**（测试环境用桩内容）；
7. 日志字段完整（§10），新增处理器自动出现在日志里；
8. 路由实现可替换（桩 / LLM），编排器与测试不感知差异；
9. `payload` 原样传给 `run`、不参与 `match`/排序、默认不进日志；
10. 领域核心脱离 DSH 可单测（DSH 适配层只做注册与注入）；
11. 插件可配置切换：`router-provider` 切 `mode=stub`；`router-handlers` 禁用某 handler → 对应槽位降级为 `unsupported`，核心照跑；
12. turn end（成功/失败/中止任一）都会执行 turn scope 的 disposer：LIFO、单个失败不阻塞其余、重复清理幂等；
13. 常驻注册与回合级注册分开：插件卸载撤销常驻注册，turn end 撤销回合级注册。

## 17. 插件化实现（DSH / Cordis）

> DSH 是 **all-plugin 的 Cordis harness**：模型适配、工具注册、会话日志、agent loop 本身都是插件；**事件是扩展点**，新行为挂在已文档化的扩展点上，不改 loop。本方案的路由系统按同样方式拆成插件，领域逻辑与 DSH 适配层分离。

### 17.1 两条硬约束

1. **插件只通过服务与事件通信**：不 import 其它插件的内部模块；服务定义（interface）是唯一契约。
2. **DSH 更新频繁**：每个插件声明 `engines.dsh`（或 peer）版本范围；不兼容安装由插件管理器拒绝（v0.2.1-alpha.3 起 `engines.dsh` 优先于 peer）。领域逻辑不得依赖 DSH 内部实现。

### 17.2 两层结构（降低更新冲击的关键）

| 层 | 内容 | 依赖 DSH？ |
|---|---|---|
| `router-domain`（纯逻辑层） | 槽位校验、编排器（选择/独占/软依赖排序/失败策略/拼接）、handler 注册表、追问状态机 | **否**（可独立单测） |
| `router-core`（薄 Cordis 插件） | 把 domain 挂到 `ctx.router`、监听 `agent/pre-step`、调用 `agent.inject` / `ctx.systemPrompt` / `ctx.tools` | 是（唯一适配层） |

> `router-domain` 可以只是 `router-core` 包内的一个子目录（仍保持零 DSH 依赖），**不必单独发包**——分层是代码边界，不是包边界。

DSH 升级时通常只需要改 `router-core` 的适配代码；槽位、编排、handler 与提示词内容不受影响。

### 17.3 插件拆分

| 插件（包） | Cordis 角色 | 提供 / 注册 | 依赖 | 阶段 |
|---|---|---|---|---|
| `router-core` | 服务提供者 + 扩展点消费者 | 服务 `ctx.router`；`agent/pre-step` 监听；`router-domain` 的宿主 | `router-domain` | A |
| `router-provider` | Router provider（**一个插件，两种模式**） | `mode: "llm" \| "stub"`（validated Config）；llm 模式读提示词块并调用 `ctx.llm` 填槽，stub 模式返回脚本化槽位 | `ctx.llm`（仅 llm 模式）、`ctx.router` | A（stub）/ B（llm 内容） |
| `router-handlers` | Handler 集合（**一个插件，五个 handler**） | 一次性注册 `fact` / `task` / `default` / `unsupported` / `clarify`；`enabledHandlers` 由 Config 控制 | `ctx.router`、事实/慢树能力服务（内容阶段） | A（桩）/ B（真实 run） |
| `router-prompts` | 资源包 | 提示词块、few-shot（或作为各插件 config 指向的文件） | — | A（空文件占位） |

说明：handler 的 `run` **不等于**执行整个流程。fact/task 的流程本体仍在各自能力插件/服务里；路由 handler 只做**准入与编排**（把正确的提示词、工具与上下文放进本轮）。

### 17.4 如何挂进 DSH 的回合

路由发生在 **`agent/pre-step`**（waterfall；监听器可以改写或拒绝本轮输入）：

1. `router-core` 调 `router-provider`（`mode=llm` 或 `stub`）得到 `SlotJSON`；
2. `router-domain` 选择并排序 handler；
3. 命中 `clarify` → 通过 `agent.inject()` 注入追问所需的上下文；本轮**不加载任何 skill**；
4. 其余情况 → 选中的 handler 通过 `ctx.systemPrompt` 的分段与 `ctx.tools` **只准入自己需要的提示词与工具**；
   - `fact` handler 的结果可作为模型可见上下文经 `agent.inject()` 进入同一步；
   - `task` handler 准入慢树生成的 skill 提示词与工具，由模型 step 执行。
5. 显式旁路命令（如直接改快树）用 `ctx.commands`，不经过自然语言路由（本阶段不做）。

> **触发频率**：`agent/pre-step` 是**每个 step** 都会触发的（包括工具结果驱动的后续 step）。`router-core` 只在 claim 到**新用户消息**时填槽；同一 turn 的后续 step 复用该 turn 的槽位决策（按 turn id 缓存）。turn scope 也在首次填槽时创建。

这样，"事实先于任务"仍由编排器的软依赖完成，而不是写死在 DSH 的 turn 流程里。

### 17.5 插件间契约

- **Service Definition**（`router-domain` 导出类型，`router-core` 提供）：
  - `registerHandler(handler) → disposer`
  - `decide(slots) → { handlers, order }`
  - `turnScope(turnId) → { onDispose(fn) }`（回合结束统一清空，§17.5.2）
  - 待定追问状态（按 session 持有）
- **Provider 接口**：`fillSlots(context) → SlotJSON`；`router-llm` 与 `router-stub` 实现同一接口，可互换。
- **Handler 接口**：`match / provides / requires / onFailure / priority / run`（§4.1）。
- 所有注册使用 Cordis 的 effect/disposer，插件卸载即回滚；不持有跨插件全局单例。
- **配置外置**：阈值、启用的 handler、提示词文件路径都是各插件的 validated `Config`（`cordis.yml` 可改），代码里不写死可变参数（DSH 规则：无可变硬编码）。

#### 17.5.1 注册与清理（Disposer）

**需要 disposer 的：所有"注册进服务"的东西。**

| 注册物 | API（示意） | 生命周期 |
|---|---|---|
| 提示词分段 / 动态上下文 | `ctx.systemPrompt.section(...)` / `ctx.systemPrompt.context(...)` | 返回"exact Cordis effect disposer"；插件卸载即撤销 |
| 工具 | `ctx.tools.register(...)` | 返回注销 disposer |
| 事件监听（含 `agent/pre-step`） | `ctx.on(...)` | 返回 disposer；随插件生命周期 |
| 服务 / provider | 插件 `apply` 内注册 | 由 Cordis 作用域管理，卸载回滚 |

规则：

- 所有注册放在 `apply` 内，使用 `ctx.effect(() => { …; return dispose })` 或保留 API 返回的 disposer；**不写模块级单例、不跨插件共享可变状态**。
- 这是 Cordis 的"可逆副作用"约定：插件卸载/热重载后不能留下上一份提示词或工具。

**不需要 disposer 的：单次注入。**

- `agent.inject(message)` 是一次性的：只落在"下一次被接纳的请求"，返回 `void`，用完即消耗，不需要也不能手动清理。
- 因此 `agent/pre-step` 里优先用**单次注入**传递本轮内容（事实结果、追问上下文）；**不要为了"本轮"去注册持久的分段/工具**。
- 如果确实需要在 pre-step 里做**作用域注册**（例如给本轮临时加一个工具限制或提示词分段），**不要自己记着释放**——交给"回合作用域"（§17.5.2），由编排器统一清空。

一句话：**注册要 disposer，注入不用；临时注册交给回合作用域，回合结束统一清空。**

#### 17.5.2 回合作用域（Turn Scope）与统一清理（2026-10-18 定）

比"每个 handler 自己记着在回合结束时 dispose"更可靠的做法：**handler 产生的 disposer 统一上报给编排器，`router-core` 在 turn 结束无条件执行。**

- **接口**：`run(slots, context)` 的 `context.turn` 提供 `onDispose(fn)`；handler 需要时注册，拿到即忘。
- **创建**：`router-core` 在本轮第一次处理新用户消息的 `agent/pre-step` 创建 turn scope（按 turn id 持有），把 `context.turn` 交给 handler。
- **清理时机**：`agent/turn-stopping`（turn 结束前的 live 钩子，成功/失败/中止都会经过）无条件执行；`turn/end`（持久事件）可作为幂等兜底。框架实现采用前者（`src/index.js`）。
- **清理规则**：
  - **LIFO**（后注册先释放），与资源获取顺序相反；
  - 每个 disposer 单独 `try/catch`，一个失败不影响其余；
  - disposer **幂等**保护；执行后清空列表，重复清理无副作用；
  - 清理动作写日志（turn id、数量、失败项），但不阻塞 turn 结束。
- **与插件生命周期 disposer 的分工**：

| 作用域 | 放什么 | 谁来释放 |
|---|---|---|
| **turn scope**（§17.5.2） | 只在本轮有效的产物：临时提示词分段、工具限制、事实注入的临时状态 | `router-core` 在 turn end 无条件清空 |
| **Cordis effect / 插件 disposer**（§17.5.1） | 插件卸载才撤销的常驻注册：服务、常驻提示词分段、工具 | Cordis 在插件卸载/热重载时回滚 |

两者**不混用**：常驻注册不得塞进 turn scope；turn 产物也不得依赖插件卸载来清。

> 为什么更好：清理点只有一个，且在**成功 / 失败 / 中止**三条路径上都会执行；handler 不需要知道 turn 生命周期的细节，也不容易漏 dispose。代价是 turn scope 只表达"回合级"资源——需要 step 级资源的 handler 要自己管（或未来扩展 step scope）。

### 17.6 更新韧性（为什么不容易被 DSH 更新打断）

- **薄适配层**：只有 `router-core` 接触 DSH 扩展点；更新时改这一层。
- **Provider 可替换**：`router-provider` 的 `mode` 从 `llm` 切到 `stub`（同一插件、同一接口），编排照跑；DSH 升级导致 LLM 适配不可用时仍可降级。
- **Handler 可禁用**：`router-handlers` 的 Config 里移除某个 handler → 对应槽位降级为 `unsupported`，核心仍工作。
- **显式失败而非静默**：插件激活时探测所需服务/事件；缺失则明确报错或降级，不静默走错路由。
- **版本边界**：每个包声明 `engines.dsh`；不兼容的安装被 plugin manager 拒绝，不会带病启动。
- **内容与代码分离**：提示词/示例是资源或 config，调内容、换模型不改代码。

### 17.7 打包与放置

- **不要修改 npm 安装的 DSH 包**：安装或升级会覆盖 `node_modules`。插件作为仓库内的独立本地包维护，通过 `dsh plugin --profile <profile> add <package>` 或 bundle 的 `cordis.patch.yml` 装载。
- 包清单最小集：`package.json` 的 `dsh.bundle.patch`、`engines.dsh`、host/client exports；host 入口即 `export function apply(ctx, config)`。
- 拆包粒度：框架阶段可先合并成一个包（`router-core` 内含 stub 与五个 handler 桩），内容阶段再拆细；**拆分不影响编排器与接口**。

### 17.8 框架阶段的插件交付

- **A 阶段**：`router-domain`（作为 `router-core` 包内子目录）+ `router-core` 插件 + `router-provider`（`mode=stub`）+ `router-handlers`（五个 handler 桩）+ 空提示词资源；单元测试直接驱动 `router-domain`（零 DSH），另加一条 profile 冒烟（stub provider）。
- **B 阶段**：`router-provider` 的 llm 模式内容 + `router-handlers` 中 fact/task 的真实 `run` 与提示词；按 §16 清单填充。
- 验收沿用 §15，并补：领域核心可脱离 DSH 单测、插件可配置切换/禁用、`engines.dsh` 声明齐全。
