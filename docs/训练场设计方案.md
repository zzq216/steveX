# 训练场设计方案（2×2 合成专项）

> 状态：**S1–S3 已实施**（2026-10-31），游戏内验收通过（§7 第 1–4 条）。S4（游戏内按钮）实施后撤回，原因见 §8.5。实施说明见 §8。T1–T11 采纳建议方案，T12 撤回。T13（每轮一个新会话）已实施（S5），待游戏内验收（§7 第 8–9 条）。T8 第 6 步（重置配方书）保留。§6 的细节已核实。T14（多份材料、指定产物个数，2026-11-02 补充）已实施（S6，§8.7），待游戏内验收（§7 第 10–13 条）。
>
> 目标：在 agent 所在的单人测试世界里建一块可重复使用的训练场地。一条命令就能跑一轮或多轮"给材料 → 发任务 → 判定 → 记录"，用来做高层动作（先从物品栏 2×2 合成开始）的专项训练，并留下可以比较的训练曲线。

## 1. 用户原始流程

1. agent 传送进训练场地（只需一层地板）
2. 清空 agent 身上所有物品
3. 从能用 2×2 合成的物品里随机挑一个，把 1 份合成材料随机放进物品栏
4. 开始计时，并在 DSH 发布任务，例如 `/bt task 现在你的物品栏中有某个物品的1份合成材料，请合成该物品`
5. 检测到物品栏里有目标物品时停止计时并记录

入口：用新命令传送到场地外，场地外放一个按钮，按下开始训练；也可以直接用命令开始。训练结束后自动传送回场地外。

本方案保留这个流程，补上第 2 节列出的缺口。

## 2. 已核实的事实与缺口

| # | 事实 | 对方案的影响 |
|---|------|------------|
| F1 | `/tp` 是原版命令 | 同名注册会覆盖或冲突，需要另起名字（T1） |
| F2 | 插件和 mod 之间是请求/响应式 WebSocket（`src/mod/client.js`），mod 没有主动推事件的通道 | 游戏内按钮无法直接在 DSH 开回合：主控只能放在插件，按钮靠插件轮询（T2、T12） |
| F3 | `raw_commands.js` 会把 `methods.js` 里的**所有**方法自动登记成 agent 可用的原始命令（`SKIPPED` 除外） | 新增的场地 API 必须显式对 agent 隐藏，否则 agent 能自己给自己发材料、判自己成功（T3） |
| F4 | agent 能调用 `chat/send`，以 `/` 开头就作为命令执行 | 世界开了作弊时 agent 可以 `/give` 出目标物品，"物品栏有目标物品"会误判为成功（T4） |
| F5 | stevex mod 有 `main` 入口（`SteveX implements ModInitializer`），单人游戏时内置服务器和 mod 在同一个 JVM 里 | mod 可以注册服务器命令、监听服务器 tick，并以服务器身份执行操作，**不需要给玩家开作弊**（T3） |
| F6 | `recipes.json` 共 1026 条配方（有序 706、无序 320）。能放进 2×2 的有 427 条：有序配方图案不超过 2 行 2 列，或无序配方材料不超过 4 个。其中 82 条的某个材料可以是多种物品之一（例如任意木板） | 抽样需要规则：去重、多选材料怎么落到具体物品（T7） |
| F7 | 任务结束信号是执行器的 `task` 事件（`state: done/failed`），之后可能还接复盘回合和整理回合；`bridge.busyReason()` 能告诉我们现在能不能发新任务 | 多轮训练时，下一轮要等 `busyReason()` 为空再开（T11） |
| F8 | DSH 提供每个回合的精确 token 用量：`@deepseek-ai/dsh-token-meter` 的 `deriveTurnTokenUsage(events)` 从 `turn/start` 到 `turn/end` 的会话事件中汇总出 `{ uncachedInputTokens, outputTokens, totalTokens, cacheReadTokens?, reasoningTokens? }`；无法确证时返回 `undefined` | 记录里加上本任务各回合的 token 合计（T10） |
| F10 | 1.21.11 里 `crafted` 统计只在从合成结果槽取出物品时增加（`ResultSlot.checkTakeAchievements` → `ItemStack.onCraftedBy` → `awardStat(Stats.ITEM_CRAFTED…)`）；服务器侧用 `ServerPlayer.getStats().getValue(Stats.ITEM_CRAFTED.get(item))` 读取 | T4 的判定依据成立；`/give` 和捡起掉落物都不会让它增加 |
| F11 | 配方书重置用 `ServerPlayer.resetRecipes(Collection<RecipeHolder<?>>)` | T8 第 6 步直接调用它，不需要执行命令 |
| F9 | `runtime/` 已经在 `.gitignore` 里 | 训练记录放 `runtime/training/`，天然不提交，符合"训练产物只存本地"的约定 |

## 3. 总体设计

```
DSH 会话                              stevex mod（单人内置服务器）
──────────────────────                ─────────────────────────────
/bt train craft2x2 [选项]
  │ 等 busyReason() 为空
  │ 抽样配方 → 生成材料清单
  ├─ arena/prepare ───────────────▶  传送进场；清空物品栏、光标物品，关闭界面；
  │                                   清掉场内掉落物；回满血量和饥饿；固定白天；
  │                                   重置配方书；发放材料（随机槽位）；
  │                                   记下 crafted 统计基线；进入"本轮进行中"
  ├─ bridge.startPlanning(任务描述)   ← 计时起点 t0
  │      … agent 规划、执行行为树 …   服务器 tick：crafted 统计增加
  │                                   → 记 craftedAt（只记第一次）
  ├─ 轮询 arena/status（1 秒一次）
  │ 任务 done/failed，或超时（插件中止任务）
  ├─ arena/finish ────────────────▶  读最终物品栏与统计；传送回场地外；
  │                                   结束"本轮进行中"
  └─ 判定结果 → 追加一行 runtime/training/craft2x2.jsonl → 下一轮
```

要点：
- **插件是主控**：发任务、等任务结束、判定、记录都在插件里完成；mod 只负责场地操作和以服务器身份读取数据。
- **场地操作走服务器身份**：玩家不需要作弊权限，agent 的 `/give` 会直接失败（T3、T4）。
- **成功判定不只看物品栏**（T4）。
- **合成成功不中断 agent**：只记时间，等任务自然结束再传送出场（T6）。

## 4. 决策点

### T1　命令命名

| 命令 | 位置 | 作用 |
|------|------|------|
| `/arena <场地>` | MC 游戏内（mod 注册的服务器命令） | 把执行者传送到该场地外的平台。本轮进行中时拒绝执行 |
| `/bt train <场地> [item=<物品>] [runs=<次数>] [seed=<种子>]` | DSH 会话 | 开始训练，可以连续跑多轮 |
| `/bt train stop` | DSH 会话 | 中止当前轮并停止后续轮次（本轮记为 `aborted`） |
| `/bt train status` | DSH 会话 | 当前轮次、目标、已用时间、累计成绩 |

**建议**：采用上表。游戏内命令只负责传送到场外，开始训练统一走 DSH。原因是 `/arena` 对 agent 也可见（它能 `chat/send`），只开放这种无害操作最安全。

### T2　主控放在插件

插件是唯一能在 DSH 发任务（`bridge.startPlanning`）的地方（F2）。

**建议**：主控逻辑全部放在插件，新增 `src/training/`。mod 侧只提供场地原语。

### T3　场地操作通道

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A | 插件借 agent 自己的 `chat/send` 执行 `/tp`、`/clear`、`/give` | 不改 mod | 世界必须开作弊，agent 也能用这些命令作弊；命令会留在聊天记录里，agent 看得到；还依赖聊天界面状态 |
| **B** | stevex mod 新增 `arena/*` 方法，在内置服务器上以服务器身份执行 | 可以关闭作弊；能精确读取统计、记录合成时刻；对 agent 不可见 | 要改 Java，重新构建 mod |

**建议：B**。新增方法（只供插件使用）：

| 方法 | 作用 |
|------|------|
| `arena/build` | 幂等地搭建场地：场内 9×9 一层地板，场外平台和告示牌（T9） |
| `arena/prepare` | 参数 `{ arena, items: [{id, count}], seed }`，执行 §3 中 prepare 的全部步骤，返回发放结果和统计基线 |
| `arena/status` | 返回 `{ active, craftedAt, craftedDelta, inventoryHasTarget, insideArena }` |
| `arena/finish` | 返回最终物品栏摘要和统计差值，并传送出场 |

对 agent 隐藏的方式有三层：
- 在 `raw_commands.js` 里，把 `arena/` 前缀并入 `SKIPPED`；
- 词汇表和提示词里不出现这些方法；
- 加一条测试，断言 agent 的注册表里没有 `arena/*`。

前提：只支持单人游戏（`getSingleplayerServer()` 不为空）。多人服务器上调用会返回明确的错误。

### T4　成功判定与防作弊

判定只看事实，不靠 agent 自己报告：

| 结果 | 条件 |
|------|------|
| `success` | 任务 `done`，且本轮 `minecraft.crafted:<目标>` 统计增加至少 1 |
| `crafted_but_failed` | 统计增加了，但任务以 `failed` 结束（做出来了，但 agent 自认为失败） |
| `false_success` | 任务 `done`，但统计没有增加（虚报成功） |
| `failed` | 任务 `failed`，统计没有增加 |
| `timeout` | 达到时间上限，插件中止任务（统计是否增加另外记录） |
| `aborted` | 人工 `/bt train stop`，或场地操作出错 |

- 用 `crafted` 统计而不是"物品栏里有没有"，原因是只有真正从合成结果槽取出物品才会计数，`/give`、捡起掉落物都不算。物品栏状态仍然记录下来，作为参考。
- 测试世界要**关闭作弊**（T3 方案 B 的前提），agent 的 `/give` 会自然失败。
- **不限制** `chat/send`：按"只补能力与证据"的原则，agent 能用的能力保持不变，作弊空间由环境封住，而不是靠规则禁止。如果 agent 在本轮用过 `chat/send`，在记录里标出来。

**建议**：采用上表。

### T5　任务描述是否说出目标物品

| 模式 | 示例 | 考察的能力 |
|------|------|-----------|
| **named**（建议默认） | `你的物品栏里有合成 木棍（minecraft:stick）所需的 1 份材料，请合成 1 个 木棍。` | 合成操作本身，最接近真实使用 |
| hidden | `你的物品栏里有某个物品的 1 份合成材料，请把它合成出来。` | 先根据材料反推配方，再合成 |

- 模板放在 `prompts/training/craft2x2_named.md` 和 `craft2x2_hidden.md`，用配置项 `training.craft2x2.mode` 切换。
- 两种模板都**不提示**做法（不提"打开物品栏""用 2×2 合成格"），这符合"不教写法"的原则。
- hidden 模式下，判定统计改看"本轮这份材料能合成的所有结果"中任意一个是否增加。同一组材料可能对应多个配方，最后记录实际做出了什么。

**建议**：默认 named，hidden 作为可选模式。

### T6　合成成功后的时机与超时

- 检测到合成后只记录 `craftedAt`，**不中断** agent。等任务 `done/failed` 后再调用 `arena/finish` 传送出场。这样能避免执行中的行为树和视觉记忆被瞬移打乱，也能观察到 agent 合成后是否正确结束任务。
- 时间上限 `training.timeoutSec` 默认 **600 秒**（规划回合较慢），从 t0 起算。到时插件中止任务，等执行器真正停下后再 finish。
- **修订（2026-11-07）**：`timeoutSec` 改为**不算等本任务 LLM 回合**（规划 / 展开 / 修补请求开着的时间）的用时上限；另设含 LLM 回合的总上限 `wallTimeoutSec`（默认 2400 秒），防回合卡住。两者都可按场地覆盖。原因：第一次设计新做法的规划回合要想十几分钟（session-53bff863 规划 880 秒，600 秒时被判超时）。超时时除了中止任务 / 关掉请求，还取消会话里还在跑的回合；关掉的请求再被提交时，拒绝消息带上关闭原因。训练记录新增 `llmWaitMs`。
- **修订（2026-11-07，session-a1a0dc6c）**：每批开始前先查 `arena/status`。mod 说还有进行中的一轮、而这一批还没开始，就是上一个 DSH 进程留下的（DSH 在一轮中途被关掉，没人调 `arena/finish`，之后的 `arena/prepare` 全被拒）：按它的场地调 `arena/finish`（传送出场），在控制台提示"清理了上次没结束的一轮"，再开始。一个 DSH 进程只有一个训练器，不会清掉别人的轮次。
- 任务结束后的复盘和整理回合不计入本轮用时（见 T11）。

**建议**：采用以上规则，超时默认 600 秒，可配置。

### T7　抽样规则

- **候选集合**：有序配方的图案不超过 2 行 2 列；无序配方的材料不超过 4 个。共 427 条（F6）。按配方名去重，同一产物可能有多条配方（例如 `black_dye` 与 `black_dye_from_wither_rose`），抽到哪条就发哪条的材料。
- **多选材料**：一个材料符号能匹配多种物品时，从中随机选一种。同一符号的所有格子用同一种物品，这样材料清单更简洁，也一定能合成。
- **数量**：按 1 份配方计算，每个格子 1 个，相同物品合并后发放。
- **随机槽位**：在 36 个主物品栏槽位里随机放置，相同物品随机拆成若干堆（如 3 个可能是 3 / 2+1 / 1+1+1），各堆放到不同槽位，同样由种子决定。
- **可复现**：每轮记录 `seed`。`seed=` 参数可以固定一组轮次的序列。
- **固定目标**：`item=stick` 固定目标物品（专项训练用）。不传则每轮随机。
- **排除名单**：配置项 `training.craft2x2.exclude`，默认为空。实际训练中发现需要排除的配方（比如染色这类重新上色的配方）再加进去。

**建议**：采用以上规则。

### T8　每轮重置的状态

由 `arena/prepare` 一次性完成，保证各轮相互独立：

1. 关闭当前打开的界面，清空光标上的物品。关界面会让 2×2 合成格里的物品退回物品栏，所以必须先关界面再清空。
2. 清空物品栏，包括副手和盔甲槽。
3. 清除场内掉落物和经验球。
4. 回满生命和饥饿，清除状态效果，切换为生存模式。
5. 固定白天、晴天；场地范围内不刷怪（场地在高空，并在地板上方做禁止刷怪处理）。
6. 重置配方书：收回所有已解锁的配方。配方书本身仍是 agent 可用的能力。
7. 发放材料，并记录 `crafted` 统计基线。

**定案**：采用以上全部 7 步（含第 6 步）。

### T9　场地坐标与形态

- 位置：主世界 `(10000, 120, 10000)` 附近，远离出生点，避免和日常测试区域混在一起。可配置。
- 场内：9×9 石头地板，四周用屏障方块围 3 格高，防止走出场地或掉下去。agent 出生在中心点，朝向固定。
- 场外：场地 `-x` 方向相邻的 5×5 平台，放一块告示牌（写场地名和用法）。
- 由 `arena/build` 幂等搭建：已存在的方块不重复放置，可以随时重建。

**建议**：采用以上设置。

### T10　训练记录

每轮在 `runtime/training/<场地>.jsonl` 追加一行，只存本地，不提交：

```json
{
  "arena": "craft2x2", "run": 3, "batch": "b20261031-1", "seed": 81723,
  "recipe": "stick", "target": "minecraft:stick", "mode": "named",
  "items": [{ "id": "minecraft:oak_planks", "count": 2 }],
  "sessionId": "session-…", "taskId": "t42", "outcome": "success",
  "t0": "2026-10-31T10:00:00.000Z",
  "craftedMs": 41250, "taskMs": 48900,
  "craftedDelta": 1, "inventoryHasTarget": true,
  "planAttempts": 1, "treeVersions": 2, "nodeCalls": 17,
  "turns": 3, "tokens": { "input": 41200, "output": 3900, "total": 45100, "cacheRead": 30000 },
  "capsules": ["crafting.inventory_craft"], "usedChatSend": false,
  "error": null
}
```

- `craftedMs` 由 mod 在合成那一刻记录服务器时间后换算，精度高于 1 秒的轮询间隔。
- 规划次数、树版本数、节点调用次数和用到的胶囊，可以从 bridge 和胶囊统计 `stats.json` 中按 `taskId` 取得。
- `turns` 和 `tokens` 统计本任务的规划、修补、展开回合（也就是 t0 到任务结束之间绑定到本任务请求的回合），不包括之后的复盘和整理回合。每个回合用 `deriveTurnTokenUsage` 计算后相加（F8）。只要有一个回合返回 `undefined`，`tokens` 就记为 `null`，`turns` 照常计数，不做估算。
- 另有脚本 `npm run training-report`，按目标物品汇总成功率、中位用时和虚报率，也可以只看最近 N 轮。

**建议**：采用以上字段。

### T11　多轮训练与复盘、整理的衔接

- 每一轮都是一个普通任务，复盘和整理都照常按现有配置触发，训练器不做特殊处理。
- 开下一轮前等待 `bridge.busyReason()` 为空，也就是复盘或整理回合结束之后。等待时间不计入任何一轮。
- 和整理频率的配合：专项训练时可以把 `curate.everyTasks` 设为例如 10，训练器只是普通的任务来源，不需要额外的配置。

**建议**：采用以上衔接方式。

### T12　游戏内按钮（第二阶段，已撤回）

- mod 在服务器侧监听场外按钮被按下，记一条待处理事件。
- 插件在没有训练、会话空闲时，每 2 秒调用一次 `arena/poll`。拿到事件后，在**最近一次执行过 `/bt train` 或 `/bt task` 的会话**里开始训练。复用 `deliverIdle` 等待会话空闲。
- 限制：如果插件从未在任何会话里用过训练命令，按钮无效，并在游戏内告示牌或动作栏提示"请先在 DSH 会话里执行一次 /bt train"。DSH 空白会话的限制见 README。
- 按钮由人在同一个客户端里按下；agent 自己也能看到并按下按钮。训练进行中（含等待复盘、整理的间隙）所有按钮事件一律忽略，不分是谁按的。

**定案**：放到第二阶段，第一阶段只做命令入口。第二阶段实施后撤回，见 §8.5。

### T13　每轮一个新会话（S5，2026-10-31 补充）

**问题**：S1–S3 里一组训练的每一轮都在执行 `/bt train` 的那个会话里跑（`batch.sessionId`）。每轮的规划、展开、修补回合和任务结束后的复盘回合都堆在同一份上下文里：第 3 轮的 agent 看得到前两轮的完整过程，各轮不再是独立样本。

跨轮次该保留的东西不受影响：胶囊库、事实库、快树都在会话之外，是 agent 在训练中积累的经验，不算污染。

**做法**：每轮用 `ctx.agents.create` 新建一个会话，复用快树反思会话已有的建会话代码（`openSession`，预设 `stevex`）。新会话一建好就由规划请求开第一个回合，DSH Web 能正常显示，不会碰到空白会话的限制。

| # | 问题 | 定案 |
|---|---|---|
| N1 | 第 1 轮也新建会话吗 | 是。每轮都新建；执行 `/bt train` 的会话只当控制台 |
| N2 | 控制台会话里显示什么 | 每轮开始、结束各插一条通知（`inject`，不开新回合，不污染控制台的上下文），例如"第 2/3 轮：会话 session-xxx，目标 minecraft:stick"、"第 2/3 轮结果 success，41 秒" |
| N3 | 用完的会话怎么处理 | 保留不关，在 DSH Web 里能翻看每轮的思考过程；记录多一个 `sessionId` 字段。跑 20 轮就多出 20 个会话 |
| N4 | 新会话用什么模型 | 控制台会话当前用的模型（在控制台换模型，训练跟着换）；取不到时用 DSH 的默认模型 |
| N5 | 复盘与整理 | 复盘留在那一轮自己的会话里，只看本轮。自动整理照旧发到最近结束的任务所在的会话，也就是最后一轮的会话。**2026-11-07 修订**：自动复盘另开会话（不带规划回合的上下文），整理随之发到复盘会话；训练器等本轮会话与复盘会话都空闲（见任务历史方案 §7.5） |
| N6 | 建会话失败 | 本轮记 `aborted`，停止整组（同 `arena/prepare` 失败） |

- DSH 的会话没有标题字段：会话列表里分不出哪个是第几轮，靠控制台里的通知或记录里的 `sessionId` 对应。
- 控制台会话被关掉：已经开始的一轮照常跑完，之后的轮次停止（没有地方发通知，也取不到要跟随的模型）。
- 本轮会话在训练中被关掉：同现有处理，任务立即失败，本轮按 `failed` 记录（N6 只管建会话失败）。

**定案**：采用以上做法（N1–N6 全部按建议）。

### T14　多份材料、指定产物个数（S6，2026-11-02 补充）

**问题**：每轮只发 1 份材料、合成 1 次，2×2 已经练熟了（胶囊库收敛到一个入口）。真实任务大多带数量（"做 8 根木棍"），而且有一个单次题碰不到的难点：材料多于所需时要**在做够时停下**。在产物格上按 Shift 会一直合成到材料用完，所以最省事的取法反而会做多。

**做法**：在现有训练场上加两个参数，不新建场地，mod 也不用改。craft2x2 和 craft3x3（《工作台训练场设计方案》）共用。

| 参数 | 含义 |
|---|---|
| `n` | 发几份材料：每种材料的数量 × n，再走 T7 的随机拆堆 |
| `m` | 要合成几次。文案里**写产物个数** `want = m × 配方单次产量`（`recipes.json` 的 `count`），agent 要自己查产量换算成次数，例如木棍一次 4 根，"合成 8 个木棍"就是 2 次 |

```
/bt train craft2x2 runs=10               # 都不写：n 在 1–64 里随机，m 随之随机（见"缺省"）
/bt train craft2x2 n=4 m=2 runs=10       # 固定：4 份材料，要 2 次的产物
/bt train craft2x2 n=2-5 runs=10          # n 每轮在 2–5 里随机；m 省略时在 1…n−1 里随机
/bt train craft3x3 item=stick n=3 m=1     # 和 item= / seed= 组合
/bt train craft2x2 n=1 m=1 runs=10        # 单次模式：和 T14 之前完全一样
```

- **取值**：`n`、`m` 都可以写固定值 `k` 或范围 `a-b`，由本轮的种子抽取，取值范围都是 1–64。必须 `m ≤ n`：固定值违反时直接报错；`n` 是范围、`m` 固定时，只在 `n ≥ m` 的值里抽。`m` 省略时：`n = 1` 则 `m = 1`，`n ≥ 2` 则 `m` 在 `1…n−1` 里抽。`m = n`（`n ≥ 2` 时）只在显式指定时出现，作为"全部做光"的对照组
- **放得下才发**：本轮的 n 还要满足"材料和产物都能放进主物品栏"，见下面的"抽样补充"。1–64 只是输入范围，放不放得下按每轮抽到的配方和材料实际计算
- **缺省**：都不写等于 `n=1-64`、`m` 省略，也就是每轮在默认范围里随机抽。场地配置里可以改默认值 `training.arenas.<场地>.portions` / `crafts`（格式同命令行），命令行优先
- **单次模式**：显式写 `n=1 m=1` 时，跟 T14 之前完全一样：用原模板（"合成 1 次"）、跳过抽 n、m 的随机数、判定退化为 T4，所以旧 seed 仍能复现、能和旧记录直接比较。注意：缺省改成随机之后，**不带 n、m 的命令行为变了**，要复现旧轮次必须写 `n=1 m=1`
- **模式**：只支持 `mode: named`。hidden 模式不说目标是什么，也就没法要求个数，所以 hidden 场地的缺省是单次模式；显式写了不是 1 的 `n`、`m` 时直接报错

**判定依据**：沿用 T4 的 `crafted` 统计。1.21.11 里从产物格取出时，`ResultSlot.checkTakeAchievements` 用实际取出的个数调用 `onCraftedBy(player, removeCount)` → `awardStat(ITEM_CRAFTED, removeCount)`；Shift 连续合成时每做一次都会计一次。所以 mod 现在返回的 `craftedDelta[target]` 就是本轮做出的产物个数，记为 `made`。

**判定表**（做多了判失败）：

| 结果 | 条件 |
|---|---|
| `aborted` / `timeout` | 同 T4，优先于下面各项 |
| `overshoot` | `made > want`，不管任务怎么结束（做多了，判失败） |
| `success` | 任务 `done`，且 `made == want` |
| `false_success` | 任务 `done`，但 `made < want`（含 0；没做够却报成功） |
| `crafted_but_failed` | 任务 `failed`，但 `made == want` |
| `failed` | 任务 `failed`，且 `made < want` |

`n = m = 1` 时 `want` 就是单次产量，Shift 也只能做 1 次，`overshoot` 不会出现，判定表退化为 T4。

**任务文案**：新增模板 `craft2x2_multi.md`、`craft3x3_multi.md`（3×3 版前面加工作台那一句，同《工作台训练场设计方案》W6）。单次模式用原模板，其余都用新模板，包括随机抽到 `n = m = 1` 的轮次（同一组训练的文案保持一致）：

> 你的物品栏里有合成 {{portions}} 次 {{target}} 所需的材料。请用这些材料合成 {{want}} 个 {{target}}，不要多做。

（2026-11-02 修订：原文是"所需的 {{portions}} 份材料"。第一次测试里 agent 把"24 份"读成了 24 个物品，为了把数凑上去翻源码查配方；改成"合成 24 次所需的材料"，和后半句"合成 5 个"不会混淆。）

"不要多做"是在说明验收标准：做多了判失败，任务就得把这个要求写出来，否则不公平。它不说该怎么做（不提 Shift、不提逐个取），所以不违背"不教写法"。

**抽样补充**（T7）：
- **放得下的条件**：主物品栏只有 36 格，要同时装下三样东西，按各自的堆叠上限算最少格数：
  1. **材料**：一份材料里物品 i 有 c_i 个、堆叠上限 s_i，占 Σ ⌈c_i × n ÷ s_i⌉ 格
  2. **产物**：按 **n 份全部做光**预留，占 ⌈产量 × n ÷ s_产物⌉ 格，而不是只留 `want` 的位置。原因：只留 `want` 的位置时，物品栏会在做够时恰好满，Shift 连续合成会因为没地方放而停在正好的数量上，"做多了"就测不出来了；按全部做光预留，物品栏永远不会替 agent 停手
  3. **合成剩余物**：有些材料合成后留下东西（牛奶桶 → 桶、蜂蜜瓶 → 玻璃瓶，源码里的 `craftRemainder`），n 份全部做完会留下 Σ ⌈r_j × n ÷ s_j⌉ 格的剩余物
  
  三项加起来 ≤ 36 才放得下。这是保守算法：实际合成时材料会从物品栏移进合成格、空出格子，三项不会同时占满。例如蛋糕一份是 3 牛奶桶（s = 1）+ 2 糖 + 1 鸡蛋（s = 16）+ 3 小麦：牛奶桶占 3n 格，蛋糕本身（s = 1）占 n 格，做完剩 3n 个桶（s = 16），再加其余材料，n = 7 时共 33 格、n = 8 时 37 格，所以 n_max = 7；一般材料和产物 s = 64，n = 64 也只占十来格
- **放不下就按可用范围重抽**：先在用户给的范围里抽 n；放不下时，算出这份材料能放下的最大值 n_max（上式 ≤ 36 的最大 n），在 `[下限, min(上限, n_max)]` 里重抽一次（`m` 省略时随后在 `1…n−1` 里重抽）。重抽也由本轮的种子决定，可以复现
  - 可用范围是空的（`n_max` 小于用户范围的下限，或小于固定的 `m`）：没指定 `item=` 时重新抽配方，最多 20 次，仍不行本轮记 `aborted` 并停止整组；指定了 `item=` 时同样先换这个产物的其他配方或材料选项，都不行就报错
  - 用 `n=k` 固定时不重抽：放不下直接报错，并给出这份材料的 n_max
- **堆叠上限与剩余物从哪来**：插件里没有这两项数据，`recipes.json` 也没有。新增提取脚本 `scripts/extract-item-props.js`，从 1.21.11 的反编译源码 `Items.java` 读出每个物品的堆叠上限和合成剩余物，写到 `data/item-props.json`（`{ "minecraft:milk_bucket": { "maxStack": 1, "remainder": "minecraft:bucket" }, … }`，和 `recipes.json` 放在一起；2026-11-02 起两者都提交进 git，见 §8.7）
  - 堆叠上限的写法有三种：没写就是 64；`stacksTo(k)` 是 k；`durability(…)`（工具、武器、盔甲、弓等有耐久的物品）会把上限设为 1，有的是 `Item.Properties` 的辅助方法（`sword(…)`、`humanoidArmor(…)` 等）在内部调用它
  - 剩余物：`craftRemainder(X)`
  - 覆盖范围：`recipes.json` 里出现过的所有材料、产物，以及它们的剩余物。遇到认不出的写法就报错停下、列出物品，不按 64 猜
- **数据有误时的后果**：mod 发放时用的是游戏里真实的堆叠上限（`getDefaultMaxStackSize`）。数据比真实值小，只是少发几份，不出错；比真实值大，可能真的放不下，`arena/prepare` 报"空槽不够"，本轮记 `aborted` 并停止整组，错误信息里提示重新生成 `item-props.json`。产物或剩余物的数据偏大不会让 prepare 出错，但可能让物品栏在做光之前就满，削弱"做多了"的检测。验收时用 `inventory` 读出的 `maxStack` 对照一遍
- **拆堆**（2026-11-02 修订：先定堆数，再在堆数内随机拆，取代原来的"按个拆碎再合并"）：
  - 单次模式不变，仍按 T7 的规则拆（每两个之间一半概率断开），旧 seed 照样复现
  - 多份模式：
    1. 堆数范围：下限 K_min = Σ ⌈c_i × n ÷ s_i⌉（每种材料都按堆叠上限放满）；上限 K_max = min(36 − 产物预留 − 剩余物预留, Σ c_i × n)（每堆至少 1 个）。n ≤ n_max 保证 K_min ≤ K_max
    2. 按种子在 [K_min, K_max] 里均匀抽总堆数 K
    3. 把 K 分给各材料：每种先给它的最少堆数 ⌈c_i × n ÷ s_i⌉，多出来的堆逐个随机分给还能再拆的材料（一种材料最多拆成每个 1 堆）
    4. 每种材料拆成分到的 k_i 堆：先每堆 1 个，余下的逐个随机放进没满（< s_i）的堆。拆出来的堆偏均匀（64 块木板分 4 堆多是 16 上下），考察的重点是"做够就停"，不是整理碎堆
  - 每堆都不超过堆叠上限，多份模式下 mod 的兜底拆堆不会触发，记录里的槽位就是实际发放的槽位
  - 原来的做法（按个拆碎再合并到放得下）实测堆数中位数 2×2 是 24、3×3 是 32，n 大时物品栏几乎总被铺满，见 §8.7
- **随机数顺序**：先抽配方和材料，再抽 n、m（含重抽），最后拆堆和槽位。单次模式跳过抽 n、m 这一步，序列和 T14 之前一致

**配方信息的边界**（2026-11-02 补充，起因同上）：第一次多份测试（会话 session-295692be）里，提示词已经写了"不需要翻源码查配方"，agent 仍在规划回合连续 6 次查源码。原因有两个：一是上面那处措辞让它对不上数；二是它想在规划时弄清目标要不要先做中间产物（打蜡铜活板门可以从铜锭做起），而规划回合既不能查配方表、也读不到背包，源码是它唯一能看到配方内容的地方。处理（都不拦截，只补证据和说明边界）：
- **请求模板**（`prompts/requests/plan.md`、`expand.md`）：明确"工作台 / 背包合成配方（shaped / shapeless）都在 `json.recipes` 里；配方的内容（形状、材料、产量、要不要先做中间产物）不在本回合弄清楚，在树里读、由条件代码 / Compute 按读到的内容决定；`mc_source_*` 用来确认游戏机制，不用来查合成配方；熔炼、切石、锻造等 `json.recipes` 里没有的配方照常可以查源码"
- **源码工具附说明**：`mc_source_search` 的结果里有、或 `mc_source_read` 读的是 `net/minecraft/data/recipes/` 下的文件时，结果前面附一句"这是配方生成器；工作台合成配方已在 `json.recipes` 里、在树里读；这里的熔炼、切石、锻造等 `json.recipes` 没有"
- **不封这个目录**：`data/recipes/` 除了工作台合成，还有切石（约 245 处）、熔炼与烹饪（约 88 处）、锻造（约 21 处）、transmute 合成、特殊配方的登记和配方书解锁条件，而 `extract-recipes.js` 只提取了 shaped / shapeless 两类，这些对 agent 来说只能从源码查。等以后把这些也提取进 `json.recipes`，"配方只从 `json.recipes` 来"才完全成立，那时再考虑在工具层拦截
- 以上都是软约束，再观察一两轮，看规划回合还翻不翻源码

**计时**：mod 只记第一次合成的时刻（`craftedMs`）。另加 `reachedMs`：插件轮询 `arena/status` 时，`made` 第一次达到 `want` 的那一次轮询的时刻（精度是 `pollMs`，默认 1 秒）。`n = m = 1` 时它和 `craftedMs` 是同一件事。

**记录新增字段**（T10）：`portions`（n）、`crafts`（m）、`yield`（单次产量）、`wanted`（want）、`made`、`overshoot`（`max(0, made − want)`）、`reachedMs`。单次模式的轮次也写上这些字段（值为 1、1、产量、产量……），另记 `single: true`，方便和多份轮次放在一起比较。

**报告**（S3）：多一列"超量"（`overshoot` 的轮数）；`--by` 增加 `portions`，按 `n/m` 组合汇总（例如 `4/2`）。成功率就是"恰好做够"的比例。

**超时**：多次合成更费时间，暂不另设。需要时用场地的 `timeoutSec` 调整。

### 8.8 修正：复盘中途 /bt train stop 停不下来（2026-11-07）

- **现象**：一轮任务做完、进入复盘时输入 `/bt train stop`，控制台一直显示"正在停止：中止第 1 轮"，训练不结束
- **原因**：任务已经结束，停止只设了标记；训练器在等这一轮的复盘结束（`busyReason` = 复盘请求没结束），而复盘回合没有人打断，等待循环里也不检查停止标记
- **修正**：停止时，训练器在等待循环里调用 `Bridge.abandonReviews` 放弃所有在飞的复盘 / 整理请求（复盘按 abandoned 关闭，任务历史照样写一条没有评估的记录），再经 `cancelTurn` 取消这些请求所在会话的当前回合（DSH `agent.cancel({ kind: 'hook' })`）。先关请求再取消回合，回合被取消走 `agent/error` 时请求已经关了，不会重发。回合不响应取消时，从按下停止起最多再等 30 秒
- **记录**：做完的那一轮保留真实的判定结果（如 `success`），不改成 `aborted`；控制台提示改为"第 N 轮已经做完，中断它的复盘 / 整理"
- **测试**：`training.test.js` 1 条（复盘中停止、回合不响应取消时 30 秒放弃）、`reflect.test.js` 1 条（`abandonReviews`）
