# 熔炉训练场设计方案

> 状态：**第二版已实施**（2026-11-20），单元测试通过，待游戏内按 §6 验收。第一版（2026-11-19，K1–K13 全部采纳建议）已经实施并跑过 2 轮训练。审阅后改了任务目标：
> - 只练"把指定数量的原料、燃料放进对应的格子，然后关掉炉子界面"（关界面这条是 2026-11-20 补的，见 §8 C9）；
> - 不再要求等炉子烧完、把产物拿回来，也不再加速炉子。
>
> 改动的理由、逐项内容（C1–C8）见 §8。正文已经按第二版改写；§7 是第一版的实施说明，其中第二版要改的地方都已标出。
>
> 本方案沿用《工作台训练场设计方案》（下称"3×3 方案"）、《箱子训练场设计方案》（下称"箱子方案"）和《切石机训练场设计方案》（下称"切石机方案"）的整体架构：
> - 插件主控，mod 以服务器身份操作场地；
> - 每轮一个新会话，记录写进 jsonl；
> - "恰好达到"的时刻由 mod 在 tick 里检测。
>
> 下面只写和它们不同的部分。
>
> 目标：另建一块场地，场内正前方放一台熔炉、高炉或烟熏炉（每轮随机）。训练 agent 往炉子的原料格、燃料格里各放恰好指定的数量，然后关掉炉子界面。炉子按原版速度工作，不要求等它烧完。

## 1. 用户原始流程

1. agent 传送到对应的训练场地中。正前方放一台熔炉、高炉或烟熏炉（随机），agent 的视角对着它，直接点右键就能打开
2. 清空 agent 身上的所有物品
3. 开始计时，并发布任务：
   - 按这台炉子，找出能烧的物品和能当燃料的物品，各随机选一种
   - 给 agent 2 格原料，总数在 64–128 之间随机；2 格燃料，总数也在 64–128 之间随机
   - 要求 agent 把 n 个原料放进原料格、m 个燃料放进燃料格（n、m 都是 1–64 的随机数），并把烧出的产物放回自己的物品栏
4. 检测到炉子里恰好有指定的原料和燃料时，加速 tick，让物品很快烧完，然后恢复 tick。检测到物品栏里有目标数量的产物（不多不少）时，停止计时并记录

第二版保留第 1–3 步的放料部分，去掉"把产物放回物品栏"和第 4 步的加速与产物检测（§8）：

- 放料对不对，看物品栏少了多少（K4）；
- 到达条件是"放对了并关掉界面"，不看产物（K5）；
- 炉子按原版速度工作，不加速（K6）。

另外，物品池要先过滤，燃料要按燃烧时长分组抽（K2、K3）。

## 3. 总体设计

流程和切石机方案相同：

1. 插件出题；
2. `arena/prepare` 放好炉子、发材料、对准视角、登记目标；
3. 发布任务，轮询 `arena/status`；
4. 任务结束后调用 `arena/finish`，判定并写记录。

插件侧新增一种训练题型 `cook`（和 `craft`、`storage`、`stonecut` 并列），在新文件 `src/training/cook.js` 里实现，接口和 `stonecut.js` 相同。训练器、记录、报告、每轮新会话都直接复用。

mod 侧有三处改动：

1. 增加三种工作站 `furnace` / `blast_furnace` / `smoker`；
2. 炉子工作站的 `status` 返回物品栏、光标、炉子三格、地上的计数；
3. 增加一种"炉子"写法的到达检测。

## 4. 决策点

### K1　场地、工作站和视角

- 新增场地 `furnace`，origin 设在 `(10000, 120, 10120)`，和切石机场地间隔 30 格。场地的搭建、清场、屏障墙、告示牌逻辑原样复用。
- 每轮的工作站由插件在 `prepare` 时指定（`station=random` 时三选一，等概率）。`prepare` 本来就带 `station` 参数，所以每轮可以不同。
- 炉子放在 `(ox, oy+1, oz+2)`，`FACING` 朝北，正面对着玩家。炉子是整格方块，现有的俯角公式和 `aimOk` 自检不用改。
- `/arena furnace` 传送到场外平台，`/bt train furnace` 开始训练。

**建议：采用。**

### K2　物品池

原料池：这台炉子能烧的原料，去掉下面几类：

1. 堆叠上限不是 64 的（F7：工具、盔甲、马铠等）；
2. 本身是燃料的（F7：原木、木头）；
3. `exclude` 里的。

过滤后，熔炉剩 69 条配方、80 种原料，高炉剩 22 种，烟熏炉剩 9 种。

燃料池：去掉堆叠上限不是 64 的和熔岩桶（F5、F7），剩 214 种，分 10 档。

组合约束：

- **燃料不能和产物相同**（F8）。抽到这种组合时，在同一档里换一种燃料；这一档只有它一种时，换一档。不要求 agent 拿产物，但它拿了也不算错（K5），所以这条仍然要留着。
- 原料和燃料不会相同（第 2 类已经排除）。

**建议：采用。**

### K3　抽样

**原料**：按产物分组，先抽组，再在组内抽原料。16 种带釉陶瓦合成一组（类似切石机方案里铜合并成一个家族）。分组后熔炉 42 组，高炉 10 组，烟熏炉 9 组。

这样做的原因是：按原料平均抽的话，11 种树叶（都烧成落叶堆）和 16 种带釉陶瓦会占熔炉池的三分之一以上。

**燃料**：先在 10 档燃烧时长里等概率抽一档，再在档内抽一种。

| 方案 | 做法 | 效果 |
|------|------|------|
| A | 燃料按物品平均抽 | "300"档（原木、木板、木制品）约占 59%，煤、烈焰棒几乎抽不到 |
| **B** | **先按燃烧时长抽档，再在档内抽一种** | 各档机会相同，燃料的种类更分散 |

**数量**：

- 原料总数 R 在 `raw` 范围（默认 64–128）里抽，分进 `rawSlots` 格（默认 2）。每格至少 1 个、最多 64 个，在这个限制下随机分配。
- 燃料总数 F 同理（`fuel`、`fuelSlots`）。
- n 在 `n` 范围（默认 1–64）里抽，m 在 `m` 范围（默认 1–64）里抽，都不超过发下去的总数。
- 4 个格子的位置在 36 格里随机。

**随机数抽取顺序**（同一种子出同一道题）：工作站（`random` 时）→ 原料组 → 原料 → 燃料档 → 燃料（冲突时按 K2 重抽）→ 原料格数 → R → 原料分格 → 燃料格数 → F → 燃料分格 → n → m → 格位打乱。

`input=<id>` 固定原料、`fuelItem=<id>` 固定燃料，这时跳过对应的分组抽样。固定的组合违反 K2 时，直接报错。

**建议：B。**

### K4　放料怎么判：看物品栏少了多少

F4 说明"炉子里恰好有 n 个原料、m 个燃料"这个状态不会出现，所以改为按以下几处计数：

- 物品栏（不含光标）；
- 光标；
- 炉子的三格；
- 场内地上。

原料只能去这几个地方：物品栏、光标、原料格、地上，或者已经烧掉。燃料只能在物品栏、光标、燃料格、原料格、地上，或者已经烧掉。所以：

- **放进炉子的原料** = R − 物品栏 − 光标 − 地上（原料格里剩的加上已经烧掉的）；
- **烧掉的原料** = 上式 − 原料格里的原料；
- **烧掉的燃料** = F − 物品栏 − 光标 − 地上 − 燃料格 − 原料格里的燃料。

"放对了"就是：物品栏里原料恰好剩 R − n、燃料恰好剩 F − m，光标为空，原料格里只有原料。放完以后，这个状态就一直保持（炉子再怎么烧，物品栏都不变），所以检测时刻是确定的。

| 方案 | 做法 | 问题 |
|------|------|------|
| 用户原案 | 看炉子里两格的数量 | 状态不会出现（F4） |
| **A** | **看物品栏少了多少** | 无 |
| B | 冻结炉子：放对之前不让它点火 | 要改原版行为（mixin），agent 会看到一台"放了燃料也不着"的炉子，和它读到的源码不符 |

**建议：A。**

### K5　到达条件：放对了并关掉界面，不看产物

只练"把指定数量的东西放进对应的格子，然后关掉炉子界面"：

- 放好以后必须关掉炉子界面才算完成（§8 C9）；
- 不要求等炉子烧完，也不要求把产物拿回物品栏；
- agent 拿了产物也不算错（按原版速度，放料期间产物格里可能已经出了几个）。

真实游戏里，放好料以后会关掉界面先去做别的事，过一阵再回来取。"放好、关掉就算完成"更接近这种用法，也不会让 agent 学成"一直守着炉子等"。

**建议：采用。**

### K6　加速：不加速

炉子按原版速度工作。第一版的"只加速这一台炉子"（mod 每 tick 对它多调用几次 `serverTick`）整个去掉：

- 插件不再传 `speed`，命令行和场地配置不再有这个选项；
- mod 删掉加速代码和 `speed` 参数，不留不用的能力；
- 文案删掉"比平常快 50 倍"那句。

去掉的理由：真实世界里没有这么快的炉子；而第二版不看产物（K5），也就不需要等炉子烧完。

**建议：采用。**

### K7　判定

任务结束时，按 K4 的几处计数判定。设：

- **产物总数** = 物品栏 + 光标 + 产物格 + 地上 + 原料格、燃料格里的产物；
- **额外物品** = 开局时没有、也不是这次产物的物品。

| 顺序 | 结果 | 条件 |
|------|------|------|
| 1 | `aborted` | 手动停止 |
| 2 | `lost` | 炉子被挖掉；场内地上有物品；或者产物总数 ≠ 烧掉的原料数（F1：每烧一个产出一个）且没有额外物品，比如东西被扔出场外 |
| 3 | `overshoot` | 烧掉的原料 > n，或者烧掉的燃料 > m。烧掉的东西拿不回来，没法挽回 |
| 4 | `misplaced` | 原料格里有原料以外的东西；燃料格里有燃料以外的东西（比如把能当燃料的产物放了进去）；或者出现了额外物品（比如铁锭在 2×2 里合成成铁粒、石头被二次烧成平滑石头，F9） |
| 5 | `timeout` | 超时 |
| 6 | `success` / `false_success` / `failed` | 任务以完成结束时，如果到达条件（K8）成立就是 `success`，否则是 `false_success`（包括放对了但没关界面）；其余情况是 `failed` |

- 放进去还没烧掉的多余原料、燃料，可以再拿回来，所以只在最后看物品栏是否恰好剩 R − n 和 F − m。
- 产物拿没拿、拿了多少不判；炉子里还剩多少原料、燃料也不判。
- 中文名：`overshoot` 沿用"放多"，`misplaced` 是"放错"。

**建议：采用。**

### K8　"恰好达到"的检测（mod）

沿用箱子方案 C9：mod 在服务器 tick 里检测，记下第一次达到的时刻 `reachedAtMs`，不打断 agent。

`Expect` 增加一种炉子写法：`expect: { cook: { raw, rawLeft, fuel, fuelLeft, product } }`。同时满足下面几条就算到达：

1. 容器界面已关闭（服务器端的当前菜单回到玩家自己的背包菜单；客户端按 E 打开的背包服务器看不到，算已关闭）；光标为空（界面关闭时光标上的东西会退回物品栏）；
2. 物品栏里 `raw` 恰好是 `rawLeft`（R − n）个，`fuel` 恰好是 `fuelLeft`（F − m）个；物品栏里没有这三种以外的物品（产物可以有，也可以没有）；
3. 原料格要么是空的，要么只有 `raw`；燃料格要么是空的，要么只有 `fuel`。

产物格、炉子是否还在烧，都不看。

**`status`**：炉子工作站返回下面几项。只读计数，不改动状态，`finish` 的顺序不用改。

- `held`、`carried`、`dropped`；
- `furnace: { input, fuel, output, lit }`，前三项是各格的 `{id: count}`，`lit` 是方块状态；
- `containerOpen`：玩家是否还开着容器界面。`finish` 先读状态再关界面，所以记下的是 agent 自己留下的样子。

**`prepare` 返回服务器端的真实数值**，供插件和数据文件核对，不一致就终止本轮并报"数据过期，请重跑提取脚本"：

- `burnTicks`：用这台炉子的规则算（F3）；
- `cookTicks`：按配方查；
- `product`：配方的产物；
- `maxStack`：原料和燃料的堆叠上限。

这些数值不参与判定，但 agent 能从 `json.cooking`、`json.items` 查到同样的数据，核对一下能保证数据没过期。

**燃料和堆叠上限**：扩展 `extract-item-props.js`。

| 方案 | 做法 | 说明 |
|------|------|------|
| **A** | **从源码提取**：解析 `FuelValues.vanillaBurnTimes` 里每一行的 `.add(…, 表达式)` 和 `.remove(…)`，标签按 jar 里的标签文件展开，`Blocks.X` 按 `Blocks.java` 查注册名；表达式按 Java 整数运算求值（基准值 200）。认不出的写法报错退出，不猜 | 和现有提取脚本"规则只在源码里、认不出就报错"的做法一致；`prepare` 时还会和服务器真实数值核对（K8），提取错了能当场发现 |

### K11　任务文案

和切石机方案 Q7 一样，文案只说现状和要求，不提右键、Shift 点击、怎么拆分物品堆，也不说物品栏里各有多少。

- `{{stationName}}` 是 熔炉 / 高炉 / 烟熏炉，`{{station}}` 是方块 id；

### K12　超时、炉子被挖、胶囊库

- **超时**：只有两种物品要放，和箱子场地一样，`timeoutSec` 为 **600 秒**。
- **每轮重置炉子**（F11）：`prepare` 先清空炉子的三格，再把那一格换成空气，然后放一台新的。这样上一轮剩下的东西、点燃状态、烧制进度、存着的经验都会清掉。拆除时弹出的经验球，由 `prepare` 现有的第 3 步清理掉。
  - 本方案不清 agent 自己身上的经验，它对任务没有影响。
- **炉子被挖**：同 3×3 方案 W8 的 A。轮次中被挖掉不补放，记录 `stationIntact=false`，判为 `lost`。
- **胶囊库**：原样带进训练。箱子训练里学到的"精确搬运 k 个"子树，可能会被拿来往原料格、燃料格里放恰好 n、m 个，这正是想观察的迁移。训练前先备份 `src/capsules/`。

**建议：全部采用。**

### K13　暂不做的部分

以下内容等基本训练稳定后再考虑，现在不做：

- **"烧出 k 个"任务**：只给目标产量，燃料放多少由 agent 自己按燃料时长算，再回来取产物。这更接近生存中的真实需求，可以作为另一种任务模式；做的时候也按原版速度，靠"放好料先去做别的事"来避免干等。
- 一轮里烧多种原料、物品栏里放干扰物品
- 营火、漏斗自动化
