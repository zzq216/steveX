# 胶囊库整理范围设计方案

> 状态：**R-S1–R-S4 已实施**（2026-11-21），单元测试通过，待 DSH 内按 §7 验收。审阅结论：决策点全部按建议执行。实施时和方案不同或补充的地方见 §8。
>
> 本方案修改《胶囊库整理设计方案》（下称"整理方案"）§5.3 的证据部分（决策点 C3、C5）。触发方式、整理回合能用的工具（C1、C2、C4）都不变。
>
> 目标：`/bt curate` 缺省只整理**上次整理之后用过或新存的条目**，加上和它们**有引用关系、同一领域**的条目；其他条目这一次不看。全库整理保留为 `/bt curate all`。

## 1. 起因

2026-11-21 的一次 `/bt curate`（会话 74652f92，请求 k1）：

| 项目 | 数值 |
|------|------|
| 用时 | 123 秒，17 次模型调用 |
| 工具调用 | 72 次：`capsule_get` 约 65 次，返回 15 万字符；`capsule_search` 4 次，返回 2.2 万字符 |
| 上下文 | 从 1.8 万涨到 12.3 万 token |
| token | 共 126 万，其中缓存读取 113 万（约 90%）、未命中输入 9.3 万、输出 1.9 万 |
| 结果 | 改了 4 条说明，没有下架 |

过程：
1. 库里 198 条，超过 `listLimit`（150），请求只给了目录；
2. agent 用 `capsule_search(includeRetired: true, limit: 100)` 翻了两页，把全部名字列出来。其中 106 条是已下架的；
3. 再按文件夹逐批 `capsule_get`：craft、inv、container、stonecutter、enchant、furnace、beacon、anvil、smithing 都看了一遍，返回的内容全部留在上下文里；
4. 和最近任务无关的条目读回约 11 万字符，大约占全部读取量的 70%。

原因有两个：
- 请求里只说"之后结束了 8 个任务"，没有"哪些条目被用过、被改过"；整理回合又不能用 `task_search` / `task_get`。agent 没有办法确定范围，只能全库看。它在结尾写的"最近 8 个任务（6 轮锻造训练 + 3 轮批量锻造）"是猜的。
- 目录把已下架的条目也算了进去（198 条里有 106 条），活跃的只有 92 条。

## 2. 已核实的事实

| # | 事实 | 对方案的影响 |
|---|------|------------|
| F1 | **用过的条目**：`stats.json` 的 `refs` 按完整引用记，每项有 `lastUsed`（执行器节点退出事件的时刻，`stats.js` 314 行）。子树里面的节点也有 `ref`，所以子树内部用到的条目也会记下。快树里的使用不计入（整理方案 D6） | "上次整理之后用过"可以直接用 `lastUsed` 判断，按名字取各版本的最大值（`byName` 汇总时 `lastUsed` 取最大，327 行） |
| F2 | **整理的时刻**：`stats.json` 的 `curate.lastAt` 在**发出**整理请求时就更新（`curateStarted`，`bridge.js` 746 行），整理被取消也照样更新；每次整理结束（`done` / `abandoned`）在 `<capsulesDir>/curate.jsonl` 写一行，带 `at` 和 `outcome`（`closeCurate`，835–844 行） | 基准时刻要取"上次**完成**的整理"，从 `curate.jsonl` 读，不能用 `curate.lastAt`（R1） |
| F3 | **新存的条目**：manifest 只记每个名字的最新哈希、说明、下架标记，**没有保存时间**。版本文件的修改时间不可靠：`library.describe` 改说明时会重写当前版本文件（`library.js` 318–329 行），改名迁移脚本也会重写文件。`versions.json` 只记替换出来的新版本（有 `at`、`by`），第一次存的名字没有记录 | 要给 manifest 加一个保存时间（R2） |
| F4 | **引用关系**：子树正文里任何对象上的 `ref` 字符串都是对另一个条目的引用（`capsuleRefs`，`library.js` 377–386 行）。代码条目不引用别的条目（整理方案和"技能只在树层组合"的决定） | 相关条目只需要沿子树找一层：核心子树引用了谁，谁（活跃子树）引用了核心条目（R3） |
| F5 | **领域**：新名字都写成"领域.做什么"（命名规则，`capsules/save.js`）。2026-11-21 的改名迁移之后，库里活跃条目都符合这条规则 | "同一领域"直接取名字的第一段（R3） |
| F6 | **复盘能改的说明**：复盘回合只能改这次任务用到的、或本次复盘存下的条目的说明（`reflectRefs`，`bridge.js`） | 复盘改过的条目一定在"用过"或"新存"里，不需要另记"说明改过"（R2） |
| F7 | **2026-11-15 的决定**：用户否决了"在整理请求里附上次整理以来的**任务摘要**"，理由是预先挑好、汇总好的证据会限制 agent 自己决定看什么 | 本方案列出的是**条目**（和现在的全库清单同一种证据，只是范围缩小），不列任务；范围外的条目 agent 照样能查、能改（R7、§3 最后一段） |
| F8 | **原决策 C3 的备选**"只列上次整理以来用过的"当时没被采用，理由是"看不到长期没人用的条目" | 长期没人用的条目留给全库整理（`/bt curate all`）看（R5） |

**按这次的库实际算一遍**（基准取上一次完成的整理 2026-11-21 10:53:31，活跃条目 90 条）：

| 范围 | 条数 |
|------|------|
| 核心：之后用过的 12 条 + 之后改过文件的 9 条，去重后 | 14 |
| 有引用关系的相关条目（一层） | 18 |
| 同一领域的其余条目（anvil、enchant、smithing、craft；不含已算进上一行的） | 23 |
| 合计 | 55；其余 35 条活跃条目不在范围里 |

> 核心的 14 条里，`trees/craft.2x2-once` 和 `trees/craft.table-exact-amount` 是因为上一次整理改了说明、文件被重写才算进来的（F3）。正式实现用 manifest 的保存时间以后，这类条目不会再被误算。

## 3. 总体设计

`/bt curate`（以及自动整理）发出的请求里，"胶囊库"一节换成"本次整理范围"：

```text
本次整理范围：上次整理完成于 2026-11-21T10:53:31Z（k1），之后结束了 8 个任务。
核心条目 14 条：之后在任务里用过的、之后新存的（含新版本）。
相关条目 18 条：和核心条目有引用关系的子树和代码。
同领域的其余条目 23 条：只列名字。
库里还有 35 条活跃条目不在范围里；已下架的 106 条不列。

## 核心条目
- trees/smithing.make-batch@…（子树）用过 … 次 / … 个任务（… 成 … 败）｜同名旧版本 2｜之后：用过、新存｜说明……
- code/smithing.plan-batch@…（Compute）……
……

## 相关条目
- code/inv.count-items@…（Compute）……｜被 trees/smithing.make-batch 引用｜说明……
……

## 同领域的其余条目（只列名字，要看用 capsule_get）
- anvil：code/anvil.inputs-ready、code/anvil.plan-combine-into-inputs、……
- craft：code/craft.plan-2x2-chain-with-intermediates、……
```

- 核心条目、相关条目每条一行，写法和现在的全库清单一样（统计摘要、同名旧版本数、版本判断、已知问题、说明），另加一项"之后：用过 / 新存"或"被谁引用 / 引用了谁"；
- 同领域的其余条目只列名字，按领域分组，用来查重复；
- 范围是**重点，不是边界**：`capsule_search`、`capsule_get` 不加限制，agent 认为需要时可以看、可以改范围外的条目。skill 里说清楚这一点。

## 4. 决策点

### R1　基准时刻：上次完成的整理

- 从 `curate.jsonl` 里找最后一行 `outcome: 'done'` 的 `at`。被取消的、会话丢失的整理不算（F2）；
- 全库整理（`/bt curate all`）完成后也算一次完成的整理，之后的缺省整理从它开始算；
- 从没完成过整理（没有 `curate.jsonl` 或里面没有 `done`）时，自动按全库整理发，请求里写明原因。

`stats.json` 的 `curate.sinceLast` / `lastAt` 照旧在发请求时更新，只给自动触发计数用（整理方案 C1），不再当基准。

**建议：采用。**

### R2　核心条目：之后用过的、之后新存的

活跃条目（不含已下架、内置、`task/` 草稿）里，满足任一条：

1. **用过**：同名各版本的 `lastUsed` 最大值晚于基准（F1）；
2. **新存**：manifest 里这个名字的 `savedAt` 晚于基准。

`savedAt` 是新加的字段（F3）：
- `library.save` 写 manifest 时记下当前时刻。同内容已存在、manifest 没变时不更新；
- `library.describe`、`retire` 不改它；
- 改名迁移脚本（`capsule-rename.js`）给新名字记迁移的时刻：改过名的条目下一次整理会被看到，这正是需要的；
- 旧条目没有这个字段：按"不是新存"处理，不回补。它们要么在用（会因为第 1 条进入范围），要么留给全库整理。

不另记"说明改过"：复盘只能改用过的或本次存下的条目（F6），已经在这两类里；整理自己改的说明发生在基准之前。

**建议：采用。**

### R3　相关条目：引用关系一层，同领域只列名字

| 方案 | 做法 | 这次的条数 |
|------|------|-----------|
| A | 只看核心条目 | 14 |
| **B** | **核心 + 引用关系一层（完整行）+ 同领域的其余条目（只列名字）** | **14 + 18 行，另 23 个名字** |
| C | 核心 + 引用关系 + 同领域，全部完整行 | 55 行 |

- **引用关系**（F4）：核心子树正文里引用的条目；正文里引用了核心条目的活跃子树。只走一层，不继续往外扩；
- **同领域**（F5）：名字第一段相同的其余活跃条目。只列名字的原因：craft 这类领域条目多，完整行会把范围撑回全库的一半以上；查重复时先看名字就够判断要不要 `capsule_get`；
- A 看不到"新存的子树和库里已有的哪条重复"，这是整理最该发现的问题。

**建议：B。**

### R4　已下架的条目不列

缺省整理和全库整理都不列已下架的条目，只写一句总数，并说明要看的话用 `capsule_search` 加 `includeRetired`。

全库整理改为**只按活跃条目数**和 `listLimit` 比较：现在活跃条目 90 条，低于 150，全库整理会直接给出完整清单（约 2.5 万字符），不必再逐条 `capsule_get`。

**建议：采用。**

### R5　两种模式和命令

| 命令 | 范围 |
|------|------|
| `/bt curate` | 缺省：R2、R3 的范围 |
| `/bt curate all` | 全库（活跃条目），和现在一样，只是去掉已下架的（R4） |

- 自动整理（`curate.everyTasks > 0`）用缺省范围；
- 长期没人用的条目、迁移脚本留下的旧说明这类问题，只有全库整理能看到（F8）。这次 4 处修改里，有 2 处 craft 说明里的旧名字就属于这一类。建议跑过迁移脚本后、或者隔一段时间，手动跑一次 `/bt curate all`；
- 不做"每隔 K 次自动全库整理"：全库整理成本高，什么时候需要由人决定。

**建议：采用。**

### R6　范围是空的：不发请求

上次整理完成后既没有用过的条目，也没有新存的条目时，不发请求，直接回复：

```
上次整理（<时刻>）之后没有任务用过、也没有新存的胶囊，不需要整理。要整理全库用 /bt curate all
```

自动整理遇到空范围时不发，计数照旧清零。

**建议：采用。**

### R7　范围外：能看、能改，不拦

- 工具不加限制，守卫不变（整理方案 C4）；
- skill 加一段："请求里列的是这次的整理范围，先看它们。为了判断重复或取代关系，可以查看范围外的条目；发现范围外的条目确实有问题，也可以改，在 `bt_curate_done` 的理由里写明为什么看了范围外的条目"；
- 请求不列任务、不列任务摘要（F7）。

**建议：采用。**

### R8　记录

`curate.jsonl` 每行多三个字段：
- `mode`：`scoped` / `all`；
- `since`：基准时刻（全库整理为 null）；
- `scope`：`{ core, related, domain, outside, retired }` 各几条。

`/bt status` 显示整理中的请求时也带上模式。

**建议：采用。**

## 5. 命令

| 命令 | 含义 |
|------|------|
| `/bt curate` | 整理上次整理之后用过、新存的条目和相关条目；范围是空的就不发 |
| `/bt curate all` | 整理全库（活跃条目） |

其余用法不变：有任务或请求没结束时不发、不排队。

## 7. 验收

1. 单元测试覆盖 R1–R8。
2. 本地库：
   - 现有 90 条活跃条目都没有 `savedAt`，第一次缺省整理只按"用过"算核心；
   - 存一个新版本后再整理，它出现在核心条目里，标"新存"；
   - 改说明后 `savedAt` 不变。
3. 在 DSH 里：
   - 跑几轮训练后 `/bt curate`，请求里只有范围内的条目，用时、token 和这次（123 秒、126 万）对比。粗估在 30–40 万 token、1 分钟左右，以实测为准；
   - 紧接着再敲一次 `/bt curate`，得到"不需要整理"的回复；
   - `/bt curate all` 给出完整的活跃条目清单，不含已下架的。
