### 2.2 system prompt 的结构

# skill：慢树大纲

把一条指令写成一棵**马上可以开始执行**的树。

## 步骤

1. **看有什么可用**：`capsule_search` 看有没有做过的同类子树或代码；`command_docs` 查原始命令的名字与参数。要写处理数据的条件代码 / Compute，先用 `data_shapes` 查数据长什么样：`state.*`（玩家状态、背包、F3、容器界面）、`json.recipes`（配方）、`nbt.*`（记忆世界）的字段结构与词表（枚举型字段的全部取值，如 `container.type` 的工作台是 `"crafting"`）。字段含义用 `command_docs` 查对应的读取命令（`inventory`、`container/get`……）。**不要猜字段名**——猜错了，条件代码要么永远不成立，要么像"找不到字段就返回 true"那样形同虚设。你看不到当前状态的值——它们由树去读（见下面"先读后展开"）。
2. **拆任务**：把指令拆成几个子任务（按先后顺序）。
3. **只沿第一条路径拆到底**：只拆**第一个**子任务，得到它的几个子子任务；再只拆其中**第一个**……直到第一个可以直接写成具体节点（`steps` / `act` / `compute` / `cond` / `forEach`）为止。
4. **其余全部留成 `expand`**：同一层的后续兄弟、上面各层的后续子任务，都写成 `{ "expand": 目标 }`。目标写清楚"要达成什么"，不写"怎么做"——展开时你能看到那时的状态，会比现在想得更准。
5. **一次提交**：用 `bt_submit_tree` 交回，`requestId` 用请求里的那个。被拒绝就按错误原文修正后重交。

形状：

    seq 任务
    ├─ seq 子任务1
    │   ├─ 子子任务1          ← 具体节点
    │   ├─ expand 子子任务2
    │   └─ expand 子子任务3
    ├─ expand 子任务2
    └─ expand 子任务3

## 先读后展开

你写大纲时不知道现状（背包里有什么、配方是什么、附近有什么）。不要猜，**把"读"写成第一条路径上的具体节点**，把依赖读取结果的部分留成 `expand`：

    seq 做木镐
    ├─ compute code/core.json.query → recipe.pickaxe   ← 具体节点：查配方
    ├─ expand 按 $recipe.pickaxe 准备材料              ← 展开时黑板里已有 recipe.pickaxe
    └─ expand 合成木镐

- 读状态：条件代码 / Compute 的 `read`（`player` / `inventory` / `f3` / `container`）；查记忆：`code/core.nbt.query`；查配方等数据：`code/core.json.query`
- 读到的结论写进黑板（带前缀的键名），后面用 `$键` 引用，**不要把值抄成字面量**
- 需要按情况分支（有工作台 / 没有），就写成 `sel` + `cond`，让树在执行时判断

## 注意

- 具体节点要有验收：关键的 `steps` / `act` 写 `expect`，让失败有证据。
- 需要算东西（点击计划、坐标、计数）就写 Compute 代码，放在提交的 `code` 字段里。
- 指令不清楚、或者当前做不到（缺前置条件又无从获取）：用 `ask_user_question` 问人，或 `bt_abort_task` 放弃并说明原因。

### 4.6 树的设计要点

1. **大纲只拆第一条路径**：v1 只把“查配方 + 读背包”写成具体节点，其他全部 `expand`。这样第一次提交 7 个节点就够，且后续展开时模型能看到真实黑板形状。
2. **所有数据由树自己读**：配方来自 `code/core.json.query`，背包/界面来自 `read: ["inventory"/"container"]`；代码里没有写死 `oak_planks`、格子号、坐标。
3. **数量由配方推导**：`planksNeeded = pattern 非空格数 × count`；木板种类取 `key` 的并集（12 种，允许混用不同木材）。
4. **点击计划分成两类**：
   - 无序单品（原木→木板）：整堆进一格 + shift 点产物 N 次 + 剩余放回（`plan-planks`）；
   - shaped 配方（工作台）：左键拿整堆 → 右键每格放 1 → 多余放回 → shift 点产物（`plan-table`）。
5. **每段都有复核**：木板复核、成品复核、收尾复核；复核统一走“重新 read → 写黑板 → cond 判断”，不假设点击一定成功。
6. **成品判定同时看数量与合成格**：`have >= need && (type == "none" || gridLeft == 0)`，避免“本来就有工作台”被误判成刚合成好。
7. **收尾先关界面再读**：开着合成界面时，产物/合成格在菜单里而不是纯背包，容易看错。

## 6. 关键观察与问题复盘

### 6.1 第一次 `bt_submit_tree` 被拒：`writes` 只能映射 outputs

- 错误：`writes["craft.plan"] must be one of the outputs (...) or a path into one`。
- 模型原本想用 `writes: {"craft.plan": "."}` 把整个结果对象写进一个键；规则不允许 `"."` 映射整个结果。
- 修正：把 8 个输出逐个映射到 `craft.*` 键；第二次提交被接受。
- 启示：`writes` 的语义是“黑板键 → 结果里的路径”，不是“黑板键 → 整个结果”。如果要一个对象，需要在 outputs 里声明一个 object 字段，再用 `键.字段` 映射。

这是本次最值得记录的问题。

树的编译/执行语义（`dsh-plugins/agent/src/bt/nodes.js`、`build.js`）：

- `Condition` 节点的命令 `sources = node.read ?? []`；执行时 `sources.length === 0 ? judge({}) : game.read(sources)`（`nodes.js` 的 `Condition.onTick`）。因此 **`read: []` 的条件代码拿到的是空快照 `{}`，没有 `container`/`inventory` 字段**。
- `task/menu-open` 的代码是 `var c = state.container || {}; var t = c.type || 'none'; return t === p.expected;`。在空状态下：
  - `expected: "inventory"` → `'none' === 'inventory'` → **恒 false**；
  - `expected: "none"` → `'none' === 'none'` → **恒 true**。
- `Steps` / `Action` 的 `expect` 条件不受影响：`WorldLeaf.observed` 会把 `ctx.observe.sources`（默认 `inventory/container/f3`）一起读进来，所以 `expect` 能看到真实界面状态。

在 v6 树里，5 个 `menu-open` 节点全部是 `read: []`（编译后），后果：

| 节点 | 期望 | 实际结果 | 影响 |
|---|---|---|---|
| `n1.1.3.1.1.2.2.e`（expect） | inventory | 通过 | 正常（expect 拿到观测状态） |
| `n1.2.1.1.1`（cond） | inventory | **FAILURE**（应为 SUCCESS，若界面已开） | sel 走第二支，按了一次 E；观测 diff 为 null，说明这次按键没有造成界面变化 |
| `n1.2.1.1.2.e`（expect） | inventory | 通过 | 正常 |
| `n1.3.1.1.1`（cond） | none | **SUCCESS**（空状态恒真） | 跳过 `container/close`，关闭分支未执行 |
| `n1.3.1.3.1`（cond flag-true） | true | 通过 | 正常（参数是黑板布尔，不需要 state） |

因此：

- 模型在复盘中说的“误判 FAILURE、白按了一次 E”与空状态机制一致：cond 在没有 `read` 时不可能读到真实界面，返回值只由 `expected` 决定；观测 diff 为 null 说明那次按键至少没有造成可见的界面变化（是否“白按”取决于当时界面是否已开，树本身无法证明）。
- “界面已关”这个结论**没有被这棵树证明**：`n1.3.1.1.2`（容器关闭 Steps）从未执行，cond 只是空状态恒真。任务结束时界面是否真的关闭，需要看执行器/游戏侧是否有其他关闭逻辑；本树没有做这件事。
- 已保存的 `code/ui.menu-open` 在前置条件里明确要求“节点带 `read: ["container"]`”，`trees/craft.in-player-grid` 里的两个 cond 也都带了 `read: ["container"]`，说明模型已经把这条教训固化进胶囊。

### 6.3 其它值得注意的点

1. **异步交错**：模型每次提交后回合立即结束，树在后台跑；`expand` 请求可以在模型还在生成上一步收尾文字时入队（r2 就是如此）。排时间线时要区分“模型回合时间”和“任务执行时间”。
2. **树是逐步长出来的**：v1 只有 7 个节点，最终 42 个结构节点（+3 个 expect）；每轮只展开一个 `expand`，符合慢树设计。
3. **`data_shapes` 只给形状**：模型看不到 `craft.planksTotal` 等值，只能通过树里的 `read`/`compute` 把结论写进黑板；这保证了树的可复用性。
4. **思考 token 远大于文字 token**：turn 3 step 1（16.6K 输出）和 turn 5 step 1（10.3K 输出）几乎全是推理；文字输出只有 498 / 430 token。
5. **缓存命中率高**：23 步累计 1.23M cache-read，未缓存输入只有 43K；system prompt + 历史是主要复用对象。
6. **没有使用修复请求**：全程没有 `recover` / `escalate` / `failed` / `died`，也没有 `bt_submit_patch`。唯一的失败是 `sel` 的分支试探，不足以触发修复。
7. **工具结果都很小**：除 `command_docs`（13.4 KB）和 `data_shapes`（1.8 KB）外，其余工具结果都在 1 KB 上下；提交类结果主要是“已接受：… 新节点：…”的短回执。
