# 胶囊版本说明设计方案

> 状态：**已实施**（2026-11-07），V1–V11 全部按建议，单元测试通过，待游戏内验收（§6 最后一条）。实施说明见 §7。
>
> 目标：复盘存同名新版本时，记下新旧两版**区别在哪、各自在什么情况下更好**，并把这条判断当作**待验证的假设**，由以后用到这些版本的任务顺带核对。旧版本不再因为"被替换"而消失，而是成为有适用条件的备选。不引入 A/B 对比、回归集这类依赖大量任务的机制——真实世界里任务稀疏，同一局面不会重现。

## 1. 用户原始想法

1. 复盘存新版本时，给新版本和旧版本各加一段简短描述：说明它们的区别，以及在什么情况下比对方更优
2. 真实 MC 世界里任务稀疏，复杂的更新方式（A/B、回归集）效果不佳，要用轻量的办法

讨论中补充的三点（见对话分析）：说明本身是单样本推断，要带证据来源与状态；要标出从没执行过的版本；规划时要能看到旧版本和这些说明。

## 2. 已核实的事实与缺口

| # | 事实 | 对方案的影响 |
|---|------|------------|
| V-F1 | 胶囊按内容哈希存，`capsule_save` 带 `replaces`（旧版哈希）就是有意替换；manifest 只记最新版的哈希和 description（`library.js:225`），**不记上一版是谁** | 版本链要从现在开始自己记（父版本 = `replaces`）；已有的旧版本没有父子关系 |
| V-F2 | `use` / `compute` 不带哈希时取 manifest 里的最新版（`library.js:151`）；带哈希就钉住那一版，旧版文件一直在 | 选用旧版**已经可行**（写 `@旧哈希`），缺的只是"知道有它、知道什么时候该用它" |
| V-F3 | `capsule_search` 只列最新版；usage 是**同名各版本加总**。`capsule_get` 给这个版本与同名全部版本的统计，`latest` 字段只在取到旧版时出现 | 规划时看不出"这一版跑过没有"、看不到旧版的存在与适用情况（V5、V6） |
| V-F4 | 统计按完整引用（`名字@哈希`）记在 `stats.json`，没被用过的版本没有记录 | "从没执行过"可以直接判定：这个哈希在 stats 里没有任务记录（V6） |
| V-F5 | 实例：`trees/craft.batch-one-shot` 已有 6 个版本，只有 2 个有执行记录；`code/craft.plan-batch-exact@e43d68cc`（fcb9be89 复盘存的"对半递减"版）一次都没跑过就成了默认版本，随后又被 `plan-batch-any-cells` 取代 | 没跑过的版本成为默认、版本之间区别不可见，都是真实发生的情况 |
| V-F6 | description 在哈希之外（`capsule_describe` 改它不换版本）。近几轮 agent 把实测数据不断写进 description，`batch-one-shot` 的说明已有约 600 字，混着"做什么"和"各次实测成本" | 版本间的差异和实测要有自己的位置，description 回到"做什么、什么前提下用"（V9） |
| V-F7 | 任务历史已有一套"待验证 → 核对"机制：`task_assess` 的 issues / review，状态 open / resolved / wrong / blocked；问题挂到胶囊上（`notes.json`，在条目之外、不改哈希） | 版本判断的核对直接仿照它，存在条目之外（V1、V4） |
| V-F8 | 胶囊库、`stats.json`、`notes.json` 都只留本地、不进 git | 新文件同样只留本地 |

## 3. 总体设计

```
复盘：capsule_save（replaces = 旧哈希）
   └─ 必填 versionNote：
        change  —— 相对旧版改了什么（一两句）
        claims  —— 1–3 条判断：{ better: new | old, when: 可观察的条件, basis: measured | inferred, evidence? }
                    或 none：旧版在任何情况下都不会更好的理由（纯修 bug）
   → 写进 versions.json：名字 → 各版本 { parent, at, by, change, claims[status=open] }

规划 / 展开 / 修补
   ├─ capsule_search：每条多 versions（版本数）、untested（最新版从没执行过）、
   │                  以及"旧版在什么情况下更好"的短句（旧版有 claims 时）
   └─ capsule_get：版本链（每版：哈希、父版本、改了什么、判断与状态、这一版的使用统计、已知问题数）
        agent 自己决定用最新版、钉某个旧版，或写 sel [新版, 旧版] 兜底 —— 系统不替它选

以后的任务用到了某个版本（最新或旧版都算）
   └─ 复盘请求列出"涉及这些版本的待核对判断"
        task_assess.claims：逐条 { ref, claim, status: confirmed | refuted | open, evidence }
        → 更新 versions.json 里那条判断的状态与核对记录
```

要点：
- **记差异，不做对照实验**：每次替换只多写两三句话，不额外跑任务
- **判断是假设**：默认 open，只有以后真用到相关版本的任务能把它改成 confirmed / refuted；证据随稀疏的任务慢慢累积
- **证据摆出来，选择交给 agent**：系统只显示版本数、是否执行过、判断与状态，不自动切换默认版本，不提示"应该用哪一版"——符合"只补能力与证据，不教写法"

## 4. 决策点

### V1　说明存在哪里

| 方案 | 说明 |
|---|---|
| **建议：条目之外的 `src/capsules/versions.json`** | `{ "<folder>/<name>": { "<hash>": { parent, at, by, change, claims: [...] } } }`。和 `stats.json`、`notes.json` 一样在条目之外，不影响哈希。存新版时还要给**旧版**补"什么情况下旧版更好"，旧版文件是按哈希存的，放在外面不用改它 |
| 备选：写进条目文件（像 description 那样不进哈希） | 要同时改新旧两个版本文件；版本链分散在多个文件里，查起来要全部读一遍 |

`by` 记写下这条说明的任务 id；`at` 记时间。

### V2　存新版本时写什么

`capsule_save` 带 `replaces` 时新增**必填**参数 `versionNote`：

```json
{
  "change": "开背包改成先读一次，没开才按 E，按完等 250 ms 再轮询",
  "claims": [
    { "better": "new", "when": "开局背包界面是关着的", "basis": "measured", "evidence": "task-20261107050121-1：旧版按了两次 E，16 次调用" },
    { "better": "old", "when": "开局背包已经打开、且要立刻摆料", "basis": "inferred" }
  ]
}
```

或者纯修错时：`{ "change": "…", "none": "旧版在开局界面关着时会多按一次 E，没有更好的情况" }`。

| 子项 | 建议 | 备选 |
|---|---|---|
| 是否必填 | **必填**（只在带 `replaces` 时）。不写会被拒绝，按"存不进去就改了重交、不计次数"的现有规则处理 | 选填：多数时候会被省略，说明就形同虚设 |
| claims 条数 | **1–3 条**；或写 `none` 说明为什么旧版没有更好的情况。二者必选其一 | 不限条数：容易写成长篇 |
| `better` | `new` / `old` 两值。"新版更好的情况"和"旧版更好的情况"都写在新版的这条记录里，读的时候按版本拆开显示 | 新旧各存一段自由文本：没法逐条核对 |
| `basis` | `measured`（这次或以往任务的指标看到的，`evidence` 必填，写任务 id 与数字）/ `inferred`（推测，包括没跑过的代码的预期效果） | 不分：读的人分不出哪些是实测 |

### V3　判断里的"情况"怎么写

在 `capsule_save` 的参数说明里写明：`when` 写**执行前或执行时能观察到的条件**（材料分成几堆、产量是否大于 1、界面开着还是关着、2×2 还是 3×3……），比较成本以 **mod 调用次数**为准；执行时间受服务端与网络影响，不能单独作为"更好"的依据。

| 方案 | 说明 |
|---|---|
| **建议：只写进参数说明** | 告知判断要能被以后的任务核对、哪个指标稳定；不做内容检查 |
| 备选：校验里拒绝只提执行时间的 `when` | 关键词检查容易误伤，也属于替它写 |

### V4　判断怎么被核对

| 子项 | 建议 | 备选 |
|---|---|---|
| 谁来核对 | **用到了相关版本的任务**在复盘时核对：本任务执行时进过的版本（成本画像里的胶囊引用，含子树里的）只要出现在某条判断的"新版"或"旧版"一侧，那条 open 判断就列进复盘请求 | 只核对"规划时看过 capsule_get 的"：会漏掉直接 `use` 的情况 |
| 复盘请求里怎么呈现 | 新增一段"涉及这次所用版本的待核对判断"：每条写胶囊、版本对（新 ← 旧）、判断原文、basis、编号。没有就写"（没有）" | 并进"以往任务里待验证的问题"：两种东西混在一起，编号容易错 |
| 怎么提交 | `task_assess` 新增可选 `claims` 数组：`{ ref: "<名字>@<新版哈希>", claim: <编号>, status: confirmed / refuted / open, evidence }`，规则与 review 一致（对不上时列出可核对的项；evidence 必填） | 新工具：多一个要记住的工具 |
| 状态 | `open`（默认）→ `confirmed` / `refuted`；保留核对记录（谁、何时、依据）。可以被多次核对，以最后一次为准，记录全留 | 只允许核对一次：单样本问题又回来了 |
| 只用到一侧时 | 这次只用了新版，也能核对"新版更好"那条（比如这次条件满足，新版表现如判断所说），也能把"旧版更好"那条标为 open 不动 | 必须两侧都用过才能核对：真实世界里几乎不会发生 |

### V5　规划时看得到什么：`capsule_search`

每条结果在现有字段之外新增（只在有内容时出现）：

| 字段 | 内容 |
|---|---|
| `versions` | 同名版本数（≥2 时才出现） |
| `untested` | `true` = 列出的这一版（最新版）在 stats 里没有任何执行记录 |
| `olderBetterWhen` | 最多 2 条：旧版更好的情况 + 那一版的哈希 + 判断状态，如 `"@6021d51a：开局背包已经打开（inferred，open）"`；refuted 的不列 |

| 方案 | 说明 |
|---|---|
| **建议：如上，只给短句** | 规划时一眼看到"有旧版、它在什么情况下可能更好、最新版跑没跑过"；细节去 `capsule_get` |
| 备选：只给版本数 | agent 不会为了一个数字去翻每个条目 |

### V6　规划时看得到什么：`capsule_get`

新增 `versionChain`：从这一版往上，沿 `parent` 最多列 5 版；每版一项：

```
{ ref, parent, at, change, claims: [{ better, when, basis, status, reviews? }], usage: { tasks, successes, failures } | "未执行", knownIssues: 条数 }
```

- `parent` 未知（本方案实施前存的版本）时写 `null`，`change` 写"（没有记录）"
- 取的是旧版时照旧带 `latest`，`versionChain` 从最新版往下列，让 agent 看到自己钉的那一版处在链上哪里
- 同名但不在这条链上的版本（以前没记父子关系的）放在 `otherVersions`：只列哈希与使用统计

### V7　默认版本规则

| 方案 | 说明 |
|---|---|
| **建议：不变，仍取最新版** | 只把 `untested` 标出来。用不用、要不要 `sel [新版, 旧版]` 兜底由 agent 决定 |
| 备选 A：新版跑成功一次前，默认仍是旧版 | 任务稀疏时新版可能长期轮不到；而且"成功一次"本身就是单样本 |
| 备选 B：新版失败时执行器自动回退旧版 | 要改执行器；失败原因不一定是版本问题，自动回退会掩盖真正的错误 |

### V8　已有的旧版本

| 方案 | 说明 |
|---|---|
| **建议：不补写** | 实施前存的版本 `parent` 为空、`change` 为"（没有记录）"；从下一次 `replaces` 开始积累。`capsule_describe` 不扩展到版本说明 |
| 备选：给整理回合加补写工具 | 补写的人看不到当时的证据，写出来的多是推测 |

### V9　description 与版本说明分工

在 `capsule_save` 的参数说明与 `review.md` 里写明：description 写"做什么、什么前提下用"；**相对旧版的改动与各次实测放进 versionNote**。

| 方案 | 说明 |
|---|---|
| **建议：只写分工，不限长度** | 告知各自放什么 |
| 备选：description 超过 200 字警告 | 需要时再加 |

### V10　整理回合（/bt curate）的配套

整理回合现在看到的清单每行有"旧版本 N 个"、使用统计、已知问题数；能做的是下架（按名字）和改说明。版本说明出现后：

| 子项 | 建议 | 备选 |
|---|---|---|
| 清单每行 | 在"旧版本 N 个"旁加：最新版是否从没执行过（`未执行`）、版本判断的状态计数（如"判断 open 2 / 成立 1 / 不成立 1"）。只是证据，整理时据此决定要不要下架、改说明 | 不加：整理时要逐条 `capsule_get` 才看得到 |
| `capsule_get` | 与规划时相同，带 `versionChain`（V6），整理回合自动得到 | — |
| `curate.md` | 补两句：`capsule_get` 能看到版本链与判断；description 写"做什么、什么前提下用"，相对旧版的改动与实测在版本说明里（V9）——整理时可以把说明里堆积的实测数据删掉，版本说明里已有记录 | 不改 skill：整理模型可能又把实测写回 description |
| 整理回合能否改版本说明 / 判断 | **不能**。判断只由用到相关版本的任务核对（V4），补写没有证据（V8） | 给整理回合加改判断的工具 |
| 下架 | 不变：仍按名字下架，版本说明保留；撤销下架、同名存新版清下架标记的规则照旧。跨名字的取代（如 `plan-batch-exact` → `plan-batch-any-cells`）仍用 `supersededBy` + `reason` 记录，不进版本说明 | 下架单个版本：等于第二套"默认版本"规则，与 V7 冲突 |

### V11　离线胶囊 GC（`scripts/capsule-gc.js`）的配套

现在的 GC 规则：没有任何已保存的树引用、最近 30 天没用过的版本，移进 `archive/`。这正好会把"旧版在某些情况下更好"的备选版本收走——它们一般没有树引用，也可能很久没被用到（V-F2：选用旧版靠的就是它们还在）。

| 子项 | 建议 | 备选 |
|---|---|---|
| 保留规则 | 新增：某个版本作为"旧版更好"一侧、且那条判断状态不是 `refuted`，这个版本保留（理由写"版本判断：在 … 时更好（open / confirmed）"）。判断被核对为不成立后，它回到普通规则 | 不改 GC：备选版本几个月后被归档，版本说明里的"旧版更好"指向一个取不到的哈希 |
| 版本链里有版本被归档 | `capsule_get` 的 `versionChain` 照列，那一项标"已归档"、不给统计；`capsule_search` 的 `olderBetterWhen` 不列已归档的版本 | 归档时连版本说明一起删：丢掉改动历史 |
| `versions.json` 本身 | 不归档、不裁剪（每条只有几句话） | 跟着条目一起归档 |

## 6. 验收清单（实施后）

- 带 `replaces` 存新版本：没有 versionNote、claims 与 none 都没写或都写、`measured` 缺 evidence → 拒绝并给出逐条错误；正确时 `versions.json` 记下 parent、change、claims（status=open）
- 不带 `replaces`（新名字）存条目：不要求 versionNote
- `capsule_search`：最新版没执行过 → `untested: true`；有旧版且旧版有"旧版更好"的判断 → `olderBetterWhen` 出现，refuted 的不出现
- `capsule_get`：列出版本链；实施前的版本 parent 为 null；取旧版时 `latest` 与 `versionChain` 同时出现
- 用到某个版本的任务做成后，复盘请求列出涉及它的 open 判断；`task_assess.claims` 写错编号时报错列出可核对项；核对后 `versions.json` 里状态更新、保留核对记录
- 整理请求的清单：最新版没执行过的条目带 `未执行`；有版本判断的条目带状态计数
- GC 演练：作为"旧版更好"一侧、判断未被否定的版本出现在保留列表里并写明理由；判断被否定后同一版本进入归档列表
- 在游戏内：一轮训练里 agent 替换某个胶囊时写下 versionNote；下一轮规划时 `capsule_search` 能看到 `versions` / `untested`；用到它的复盘核对了判断

## 7. 实施说明（2026-11-07）

- `src/capsules/versions.js`（新）：`CapsuleVersions`——`check`（versionNote 校验）、`record`、`chain`、`claimsInvolving`、`protectedVersions`、`claimCounts`、`review`；文件 `<capsulesDir>/versions.json`（在 `src/capsules/` 下，已被 .gitignore 排除）
