# 多世界记忆隔离设计方案（v2.55）

> 状态：**代码已完成，待游戏内验收**（2026-10-27）。D1–D11 按 §8 推荐项定案；两个 mod `compileJava` 通过，Node 测试全过；§10 游戏内验证尚未执行。实施细节与偏差见 §13。
>
> 范围：采集端（`stevex-template-1.21.11`）、记忆端（`stevex-test-template-1.21.11`）、agent 读取端（`src/nbt/`、`dsh-plugins/agent`）三处的记忆文件定位与切换。
> 不改各文件的内部格式（维度分桶、区分片都保持原样）。

## 1. 背景与缺口

记忆文件都写在 `<gameDir>/stevex/vision/`，按维度分桶（v2.32），但**不区分存档或服务器**：

| 位置 | 现状 |
|------|------|
| 采集端各 store | 目录写死 `DIR_NAME = "stevex/vision"`，构造时 `gameDirectory.resolve(DIR_NAME)`（如 `TerrainUnionStore.java:65,101`、`ContainerMemoryStore.java:80,120`） |
| 采集端生命周期 | store 是 `VisionCollector` 的 `static final` 字段（`VisionCollector.java:45-69`）、`ContainerMemoryStore` 是单例（`:98`），**整个游戏进程只 `load()` 一次**，进出世界不重载、不清空 |
| 记忆端 | `MemoryConfig` 按固定候选路径自动探测 `stevex/vision/...`（`MemoryConfig.java:212,243,269`）；只有一个记忆世界 `worldName = "MemoryWorld"` |
| agent 端 | `visionRoot` 固定为 `vendor/stevex-template-1.21.11/run/stevex/vision`（`config.js:18`），启动时建一次查询 API（`runtime.js:97`） |

后果（先在存档 A 探索，再进存档 B）：

1. A 的主世界地形、容器、实体、群系记忆全部并进 B 的 `minecraft:overworld` 桶，agent 会"记得"B 里不存在的箱子和方块。
2. 两个世界同坐标的累积记录互相覆盖（区文件 `r.<X>.<Z>.nbt` 同名）。
3. 同一个游戏进程里换存档也一样，因为内存里的 store 不重载。
4. 记忆世界里已经铺好的 A 的方块不会消失，B 的内容叠在上面。

## 2. 关键事实（已核实）

- **单人存档可以拿到存档目录**：`mc.getSingleplayerServer().getWorldPath(LevelResource.ROOT)`（`MinecraftServer.java:1969`），存档目录可写，能在里面放标记文件。存档显示名 `getWorldData().getLevelName()`（`Minecraft.java:1521`）可重复，不能当键。
- **多人只能拿到地址**：`mc.getCurrentServer()` → `ServerData.ip`（`ServerData.java:26`），另有 `isLan()` / `isRealm()`。服务器目录不可写。
- **哈希种子拿不到**：客户端只有 `BiomeManager.biomeZoomSeed`，是 `private final`（`BiomeManager.java:16`），要读得加 accessor Mixin。
- **换维度不会触发重新连接**：维度切换走 respawn 包，Fabric `ClientPlayConnectionEvents.JOIN` 只在登录时触发一次；`DISCONNECT` 在退出世界或断线时触发。所以按 JOIN 切换世界，不会和 v2.32 的维度分桶冲突。
- **采集写入都在渲染线程**，JOIN 回调也在客户端主线程，两者不会并发。唯一的后台线程是 `UnionSaveScheduler`（异步落盘 union 区文件，另有 shutdown hook 兜底，`UnionSaveScheduler.java:68`）。切换前必须让它把旧世界的待写快照写完。
- **`memory_cells.bin` / `memory_sprites.bin` 由记忆端写**，路径跟随 `terrain.nbt` 所在目录（`MemoryConfig.java:317,341`），采集端 `MemoryCellsReader` / `SpriteTableCache` 再从同一目录读。只要两端对"当前世界目录"取得一致，这两个文件自然跟着走。
- **记忆世界完全由文件派生**：`resetOnLaunch=true` 时删档重建（`MemoryWorldManager.java:155`），重建后靠全量文件复原，不丢信息。
- **胶囊（`src/capsules/`）和事实库（`facts/`）是 MC 通用知识**，与具体世界无关，不在本方案范围内。

## 3. 总体设计

在 `stevex/vision/` 下加一层世界目录，根目录放一个指针文件，三端都通过指针定位当前世界：

```
<gameDir>/stevex/vision/
  current.json                 指针：当前（或最近）世界
  worlds/
    sp-New_World-1a2b3c4d/     单人存档
      world.json               本世界元数据
      terrain.nbt  entities.nbt  entities_union.nbt
      terrain_union/  block_entities/  containers/  biomes/
      memory_cells.bin  memory_sprites.bin
    mp-play.example.com_25565/ 多人服务器
      ...
    _legacy/                   v2.55 之前的旧数据（D7）
```

```
采集端  JOIN → 算 worldKey → 旧世界落盘并关闭 → 打开新世界的 store 组 → 写 current.json
        DISCONNECT → 落盘，current.json 置 inWorld:false（保留 worldKey）
记忆端  每次轮询先看 current.json（mtime 门控）→ worldKey 变了 → 换源目录 + 重建记忆世界
agent   每次加载数据源先读 current.json → 定位世界目录 → 查询结果带 world 字段
```

### 3.1 `current.json`

```json
{
  "worldKey": "sp-New_World-1a2b3c4d",
  "dir": "worlds/sp-New_World-1a2b3c4d",
  "kind": "singleplayer",
  "label": "New World",
  "inWorld": true,
  "since": 1761500000000
}
```

- 写法：先写临时文件再 rename（原子替换），读端不会读到半个文件。
- `dir` 是相对 `stevex/vision/` 的路径；读端校验它必须落在 `worlds/` 下（不接受 `..` 或绝对路径）。
- 文件不存在：读端回退到旧行为（直接读 `stevex/vision/` 根目录），方便升级过渡。

### 3.2 `world.json`（每个世界目录一份）

```json
{ "worldKey": "...", "kind": "singleplayer|multiplayer|lan|realm", "label": "...",
  "firstSeen": 1761500000000, "lastSeen": 1761600000000 }
```

只用于人和工具辨认目录，读写都不依赖它。

## 4. worldKey 怎么算

### 4.1 单人存档（D2）

在存档目录写标记文件 `<save>/stevex/world_id.json`：`{ "id": "<uuid>", "folder": "<存档文件夹名>" }`。

- 没有标记 → 生成新 uuid 并写入。
- 有标记但 `folder` 和当前文件夹名不一致 → 视为复制出来的存档，重新生成 uuid（复制品不继承原存档的记忆）。
- 目录名 `sp-<文件夹名净化>-<uuid 前 8 位>`。净化规则：只留 `[A-Za-z0-9._-]`，其余换成 `_`，最多 32 字符。

这样处理了三种情况：删档后用同名新建（新 uuid）、复制存档（folder 不符 → 新 uuid）、在游戏里改显示名（文件夹不变 → 同一 key）。

### 4.2 多人（D3）

`mp-<host>_<port>`：host 转小写，省略端口时补 `25565`，净化规则同上。LAN 用 `lan-` 前缀，Realms 用 `realm-` 前缀。

已知限制，写进文档但本期不处理：

- 同一地址的服务器重置了地图，会沿用旧记忆。
- 一个地址背后挂多个子服（BungeeCord / Velocity），会共用一份记忆。
- LAN 每次开放端口随机，同一个 LAN 世界会得到不同 key。

## 5. 采集端设计

### 5.1 按世界整组重建 store（D6）

新增 `VisionWorldContext`，持有一个世界的全部 store 实例：terrain / entity / blockEntity / biome / terrainUnion / entityUnion / container，以及该世界自己的 `UnionSaveScheduler`。各 store 的构造参数从"写死 `gameDirectory + DIR_NAME`"改成"传入世界目录 `Path`"。构造时已有的 `load()` / `migrateLegacyIfPresent()` 照旧执行。

- `VisionCollector` 的 `static final` store 字段改为 `VisionWorldContext.current()` 取用。
- `ContainerMemoryStore.get()` 改为委托 `current().containers()`。
- `MemoryCellsReader` / `SpriteTableCache` 的读路径改为 `current().dir()`。
- 没有活动上下文（标题界面）时，采集 API 返回明确错误 `NO_WORLD`，不写任何文件。

各 store 不用逐个加"清空并重载"的代码，换世界就是丢掉整组旧实例、建一组新实例。

### 5.2 切换流程（D4）

在 `SteveXClient` 里注册 `ClientPlayConnectionEvents.JOIN` / `DISCONNECT`：

**JOIN**
1. 算出 worldKey（§4）。
2. 如果和当前上下文相同（例如断线重连），什么都不做。
3. 否则：旧上下文 `close()`，也就是让调度器同步执行一次 `fire()` 把待写快照全写完、容器提交、停止调度线程。
4. 建新上下文（`createDirectories` + 各 store `load()`），写 `world.json`。
5. 最后原子写 `current.json`。

**DISCONNECT**：旧上下文 `close()`，`current.json` 改 `inWorld:false`，保留 `worldKey`（D5）。

shutdown hook 改为关闭当前上下文。

### 5.3 快照响应

`vision/snapshot` 响应和 `status` 增加 `worldKey` 字段，agent 能直接看到自己在哪个世界。

## 6. 记忆端设计（D8）

- `MemoryConfig` 的自动探测改为：先读 `<候选根>/stevex/vision/current.json` 得到世界目录，再在世界目录里找各源；`current.json` 不存在时回退现有候选路径。显式配置的路径仍然优先，并且不随世界切换。
- `MemoryWorldManager` 每次轮询先对 `current.json` 做 mtime 门控。`worldKey` 变化时：
  1. 停止各复原通道；
  2. 退出并删除记忆世界存档，复用 `resetOnLaunch` 的删档路径；
  3. 按新目录重新解析所有源路径，重建并进入记忆世界，全量复原。
- `inWorld:false` 时记忆世界保持不动，不重建。
- `memory_cells.bin` / `memory_sprites.bin` 随 terrain 目录写进世界目录。切换瞬间如果还有一次写入落在旧目录，只影响旧世界，不会串到新世界。

## 7. agent 端设计（D9、D10）

- `src/nbt/loader.js`：`visionRoot` 含义改为 `stevex/vision` 根目录。每次 `load` / `version` 先读 `current.json`（按 mtime 缓存），解析出世界目录。缓存键从 `sourcePath` 改为 `世界目录 + sourcePath`，世界变了旧缓存自然失效。
- 查询结果的 meta 增加 `world: { key, label, inWorld }`。
- `current.json` 校验：`dir` 必须解析到 `visionRoot/worlds/` 下，否则报 `SOURCE_CORRUPT`。这沿用 agent 只按白名单读文件的约束。
- `config.js` 的 `visionRoot` 值不变（仍然指向根目录），用户不需要改配置。
- 运行中的行为树任务遇到世界切换（D10）：本期不自动处理，只把 `worldKey` 暴露在 status / snapshot / 查询 meta 里。

## 8. 决策点

| # | 问题 | 选项 | 推荐 |
|---|------|------|------|
| D1 | 存储布局 | A. 世界子目录 + `current.json` 指针；B. 固定活动目录，换世界时整目录换入换出；C. 像维度那样在文件内再加一层世界桶 | **A**。B 要在两个进程都可能在读的时候搬目录，崩溃一半会丢数据；C 文件越来越大，旧世界数据每次都要读 |
| D2 | 单人 worldKey | A. 存档内 uuid 标记 + 文件夹名校验；B. 存档文件夹名；C. 存档显示名 | **A**。B 分不清"删档重建同名"；C 可重复 |
| D3 | 多人 worldKey | A. 规范化地址；B. 地址 + 哈希种子（需 accessor Mixin） | **A**，限制写进文档。B 也只解决"地图重置"一种情况 |
| D4 | 切换时机 | A. JOIN 时按 key 切换、DISCONNECT 时落盘；B. 首次采集时懒切换 | **A**。B 会让 status 在采集前报错世界 |
| D5 | 不在世界时 `current.json` | A. 保留最近 worldKey，标 `inWorld:false`；B. 清空 | **A**。离线时仍能查上次世界的记忆，记忆端也不会误重建 |
| D6 | 采集端实现方式 | A. 按世界整组重建 store（`VisionWorldContext`）；B. 每个 store 加 `rebind(dir)` | **A**。复用现有构造和加载逻辑，不用逐个写清空代码 |
| D7 | 现有旧数据 | A. 首次升级移入 `worlds/_legacy/`，不自动使用；B. 归给第一个进入的世界；C. 删除 | **A**。不知道旧数据属于哪个存档；想继续用可以手动把 `_legacy` 改名成对应 key |
| D8 | 记忆端换世界 | A. 同一个记忆世界删档重建；B. 每个 worldKey 一个记忆存档 | **A**。记忆世界是派生数据，重建不丢信息；B 会堆积存档 |
| D9 | agent 读取 | A. 每次加载读指针（mtime 缓存），结果带 `world`；B. 启动时读一次 | **A**。agent 运行期间用户可能换存档 |
| D10 | 运行中任务遇到换世界 | A. 本期不处理，只暴露 worldKey；B. 自动以 `by:'executor'` 中止当前任务 | **A**。先观察实际出现频率，再决定要不要让执行器介入 |
| D11 | 旧世界目录清理 | A. 不自动清理；B. 超过 N 天未进入自动删 | **A**。记忆是 agent 的长期资产，删除交给用户 |

## 9. 正确性要点

- **不串世界**：三端都只通过 `current.json` 找目录。采集端写 `current.json` 发生在新上下文加载完成之后，旧上下文在此之前已同步落盘，所以不会有"旧世界数据写进新目录"的窗口。
- **不丢数据**：切换走同步 `fire()`，和现有 shutdown hook 用的是同一条落盘路径。
- **同世界重连不抖动**：JOIN 时 key 相同直接跳过，记忆端看到 `worldKey` 不变也不重建。
- **维度分桶不受影响**：世界目录内部仍是 v2.32 的 `worlds[<dimId>]` 结构，换维度不触发 JOIN。
- **向后兼容**：`current.json` 不存在时，记忆端和 agent 都回退到根目录读取。

## 10. 验证步骤

1. 单人存档 A 探索，退出，检查 `worlds/sp-A-*/` 有数据、`current.json` 为 `inWorld:false`。
2. 进入存档 B：`current.json` 指向 B；B 目录从空开始；agent 查询 B 附近箱子查不到 A 的记录；记忆世界重建，只出现 B 的内容。
3. 回到 A：A 的记忆完整恢复，记忆世界重建为 A 的内容。
4. 删除 A 后新建同名存档：得到新 key，不继承旧记忆。
5. 复制 A 的存档文件夹后进入：得到新 key。
6. 同一存档内主世界 → 下界 → 主世界：`worldKey` 不变，记忆世界不重建，维度桶行为与 v2.32 一致。
7. 切换瞬间强杀进程：旧世界 union 区文件完整，重启后旧世界数据可读。
8. 升级首次启动：旧数据出现在 `worlds/_legacy/`，根目录不再有散落的 `.nbt`。
9. agent 端单测：`current.json` 指向 `worlds/` 外（`..`、绝对路径）时报 `SOURCE_CORRUPT`；世界切换后缓存失效。

## 13. 实施说明

### 13.1 采集端

- 新增 `vision/WorldKey.java`（§4）、`vision/CurrentWorldFile.java`（`current.json` / `world.json` 原子写 + D7 旧数据迁移）、`vision/VisionWorldContext.java`（D6）。
- 各 store 构造改为接收世界目录：`VisionTerrainStore(dir)`、`VisionEntityStore(dir)`、`VisionBlockEntityStore(dir)`、`VisionBiomeStore(dir)`、`TerrainUnionStore(scheduler, dir)`、`EntityUnionStore(scheduler, dir)`、`ContainerMemoryStore(dir)`、`SpriteTableCache(dir)`、`MemoryCellsReader(dir)`；写死的 `DIR_NAME` 全部去掉。
- `VisionCollector.getXxxStore()`、`ContainerMemoryStore.get()`、`SpriteTableCache.get()` 改为转发到 `VisionWorldContext.require()`，不在世界里抛 `IllegalStateException("not in a world")`。调用方（`ObjectResolver.resolve`、容器提交、`vision/entity`）原本就在 try 内，转成错误返回。`ContainerMemoryTracker` 不再缓存 store 实例。
- `SpriteTableCache` 也按世界一份：记忆端把 sprite 表写进 cells 同目录，换世界后旧实例读的是旧目录的表。
- `UnionSaveScheduler.close()`：拒收新请求 → 取消未到点的排定（`setExecuteExistingDelayedTasksAfterShutdownPolicy(false)`）→ 等正在跑的写完（最多 10 秒）→ 调用线程上补写一次 → 注销 shutdown hook。每个世界一个调度器，hook 不会越积越多。
- `vision/snapshot`：在 WS 线程上取一次当前上下文读 cells，派发到渲染线程后核对上下文没换，换了返回 `world changed during snapshot`，不把旧世界的这一帧写进新世界。
- `SteveXClient` 注册 `ClientPlayConnectionEvents.JOIN` / `DISCONNECT`，两个回调都经 `client.execute` 落到主线程。识别不了世界（既非单人也没有服务器信息）时关掉当前上下文、本次会话不采集。

### 13.2 记忆端

- `MemoryConfig.currentWorld()`：在三个候选根目录（与旧版自动探测同一组）里找 `current.json`，mtime 门控；`dir` 必须规范化后落在 `worlds/` 下。各 `resolveXxx` 在有指针时只在世界目录里找，没有指针回退旧探测链；显式配置的路径仍最优先。
- 记忆世界是由哪个源 worldKey 建出来的，记在 `config/stevex-test/memory_source.json`（建档时写）。
- `MemoryWorldManager.watchSourceWorld`（每 20 tick）：记忆世界开着、采集端 `inWorld:true`、worldKey 与记录不同 → 标记重建并 `disconnectFromWorld`；开档状态机回到主菜单后 `bootstrap` 删档重建。`bootstrap` 在启动时也做同样的比对（记录缺失 = v2.55 之前建的档，也重建）。
- 删档失败（集成服务器还没完全退出 / 存档被占用）时不打开旧档，交给状态机重试（最多 3 次）。否则会把旧世界的内容当成新世界的记忆。
- `SpriteAlphaTable.flushIfDirty`：目标路径变了也重写（新世界目录里还没有这张表，采集端会对几何段 fail-closed）。
