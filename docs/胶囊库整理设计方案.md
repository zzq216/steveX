# 胶囊库整理设计方案

> **依据**：[算法层与执行层设计方案.md](算法层与执行层设计方案.md) §8.6 GC、§8.7 淘汰与【审阅点 9】；[目标Agent画像.md](目标Agent画像.md) §T9 待定项（淘汰 / 置信度 / 探索配额）；[P4实施细则.md](P4实施细则.md)（复盘与 `capsule_save`）。
> **目标**：训练越久，胶囊库越大。给库补上三件事——**记录每个胶囊用得怎么样**（证据）、**清掉没人引用的旧版本**（GC）、**隔一段时间开一个整理回合，让模型看全库、把过时的条目下架或改好说明**（整理能力）。
> **原则**（[agent-learns-not-taught]）：只补能力与证据，不写"成功率低于 X% 就删""两个说明相似就合并"这类规则；要不要下架、怎么合并由整理回合里的模型看证据决定。
> **不动**：胶囊的哈希与引用格式、`code/` `trees/` 两个文件夹、`capsule_search` 的排序方式、快树版本库。
> **状态**：2026-10-29 D1–D12 按推荐通过；同日加 C1–C6（整理回合独立于复盘，取代 D11），C1 的 `curate.everyTasks` 默认 0。**同日代码完成、离线测试通过，待 DSH 内验收**（实现说明见 §10）。

## 1. 现状与缺口

| 部分 | 现状 | 缺口 |
|---|---|---|
| 写入 | `capsule_save` 做写前校验后落盘，manifest 指向最新版；同名同内容（同哈希）不重复写 | 不去重：名字不同、作用相近的条目并存 |
| 旧版本 | 改一个字符就是新哈希，老文件原样留下 | 没有 GC（§8.6 只有规则） |
| 检索 | `capsule_search` 按关键词命中数排序，结果只有引用、种类、说明与输入 / 输出名 | 看不出一个条目**用过没有、靠不靠谱** |
| 使用记录 | **没有**。节点事件（`events.jsonl` 的 `event: "node"`）只记节点 id，不记它调用的胶囊引用 | 想统计得先把 ref 记进事件 |
| 下架 | 没有。条目一旦进库就永远出现在搜索结果里 | 没有"已过时 / 被某某取代"的标记 |
| 淘汰 / 合并 | 【审阅点 9】待定 | — |

已核实的几个事实（决定了实现方式）：

1. 节点进出事件由 `executor.js` 的 `onNode` 写出：`{ event: 'node', phase, id, type, name, status, error }`，**只有任务树有，快树没有**。`error` 只在 `FAILURE` 时带 `node.lastError`。
2. 条件节点**判为假**与**求值报错**都返回 `FAILURE`，区别在于报错时 `lastError` 有值——所以"真 / 假 / 报错"三种结果可以分开。Compute 的 `FAILURE` 一律带错误信息。
3. 子树内部节点的 id 形如 `n1.3.1.1/c.1.2`（调用点 id + `/` + 胶囊体内 id），胶囊体里的引用要回到子树胶囊的 body 去查。
4. 已保存的树分布在三处：库里的 `trees/`、每个任务的 `runtime/tasks/<taskId>/trees/v<N>.json`、快树版本库 `src/bt/trees/fast/`。§8.6 写的"扫描 `src/bt/trees/`"只覆盖了第三处，需要更新。
5. 库目录 `src/capsules/` 与 `runtime/` 都被 `.gitignore` 忽略，是只在本机的训练产物；`runtime/` 还可能被人手动清理。
6. 复盘把草稿转正时会记 `capsule/saved` 事件，带 `from: "task/<名字>"`，可以把草稿和转正后的条目对上。

## 2. 总览

```
任务结束（task/done | task/failed）
  → 统计：读本任务 events.jsonl 里带 ref 的节点退出事件 → 累加进 src/capsules/stats.json      (§3)
  → 复盘（不变）：capsule_save / bt_reflect_done；capsule_search 的结果里能看到统计
  → capsule_search / capsule_get 的结果附带统计（只展示，不参与排序）                           (§4)
  → 整理计数 +1；curate.everyTasks > 0 且攒够、且空闲 → 自动发整理请求（默认 0 = 不自动）

/bt curate（人手动）或自动触发 → 整理回合                                                       (§5)
  → 证据：全库清单（按名字排序）或目录
  → 整理模型：capsule_retire / capsule_describe / bt_curate_done

离线（人手动跑）：npm run capsule-gc —— 先归档再删除没人引用的旧版本                             (§6)
```

分三个阶段，可以分开验收：**S1 统计与展示** → **S2 GC** → **S3 整理回合与下架**。S1 越早上线越好：数据晚收一天就少一天。

## 3. S1：使用统计

### 3.1 事件里记下 ref（D1）

`onNode` 的退出事件加一个字段 `ref`：节点调用胶囊时（Compute、条件、SubTree）写它**钉过哈希**的完整引用，其余节点不写。

```json
{"event":"node","phase":"exit","id":"n1.2.1.2.1","type":"Condition","name":"木板已够","status":"FAILURE","ref":"task/planks-enough@848cddf9"}
```

只在退出事件上加：结果在退出时才知道，进入事件不需要。子树内部节点的事件照样带它自己的 ref，不必再回子树 body 里查。

### 3.2 记哪些数

按**完整引用**（带哈希）记，展示时再按名字汇总（D3）。每条：

| 字段 | 含义 |
|---|---|
| `calls` | 退出次数（一个节点在 `retry` / `repeat` / `forEach` / reactive 复查里会退出多次，每次都算） |
| `ok` / `fail` / `error` | Compute 与 SubTree：`ok` = SUCCESS，`error` = FAILURE（都带错误信息），`fail` 恒为 0；条件：`ok` = 真，`fail` = 假，`error` = 报错 |
| `tasks` | 用过它的任务数 |
| `tasksDone` / `tasksFailed` | 这些任务里最终成功 / 失败的个数 |
| `firstUsed` / `lastUsed` | 首次 / 最近一次使用的时间 |
| `errors` | 最近 3 条错误信息样本：`{ taskId, nodeId, message }`，message 截到 200 字 |
| `draft` | 转正前作为草稿时的同一组数字（D5），没有就不写 |

**不记**"这个胶囊该为任务失败负多少责任"之类的归因分数：那是一种判断，交给看证据的模型（原则）。`tasksFailed` 只是并列事实——用过它的任务里有几个失败了。

条件的"假"不是坏事（守卫本来就会判假），所以 `fail` 与 `error` 分开，展示时也分开写。

### 3.3 何时统计、存在哪（D2、D4）

- **何时**：任务结束（`task/done` / `task/failed` 写盘之后、发复盘请求之前）读本任务的 `events.jsonl`，汇总后累加进统计文件。复盘请求因此能看到包括本任务在内的数字。
- **幂等**：统计文件记一个已处理任务 id 的集合，同一个任务不会被加两次（手动 `/bt reflect` 重复复盘、进程重启都不影响）。
- **存在哪**：`src/capsules/stats.json`，跟库放在一起（同样被 git 忽略）。**不写进条目文件**：条目的哈希覆盖 signature + preconditions + body，统计放进条目会让哈希每次都变。
- **重建**：附一个 `npm run capsule-stats -- --rebuild`，从 `runtime/tasks/*/events.jsonl` 全量重算。`runtime/` 被清理过就只能重算到剩下的部分——所以 `stats.json` 本身才是长期记录，重建只是兜底。
- **旧日志**：本次改动之前的事件没有 `ref`，**不回补**（D4）。

```json
{
  "version": 1,
  "tasks": ["task-20261027155431-1"],
  "refs": {
    "code/ui.menu-open@646b7f7e": { "calls": 4, "ok": 2, "fail": 2, "error": 0, "tasks": 1, "tasksDone": 1, "tasksFailed": 0, "firstUsed": "…", "lastUsed": "…", "errors": [] }
  }
}
```

### 3.4 草稿转正时的数字（D5）

草稿 `task/<名字>@h1` 在复盘里被存成 `code/<新名字>@h2`，两者哈希不同。若不处理，新条目进库时永远显示"尚无记录"，而让模型决定保存它的，恰恰就是它在这次任务里的表现。

做法：处理 `capsule/saved` 事件（带 `from`）时，把该草稿在本任务里的数字拷到新 ref 的 `draft` 字段下。和库里条目自己的数字分开，展示时写成"转正前（草稿）：……"。注意统计在复盘**之前**跑，那时还没有 `capsule/saved`；所以统计在复盘结束（`reflect/done`）时再跑一小段，只处理本任务的 `capsule/saved`。

### 3.5 快树（D6）

快树没有节点事件，条件每 tick 都求值，"调用次数"没有意义。第一版**不统计快树**里的使用；`fast.*` 条件代码的统计里只会有它们在任务树里被用到的部分。展示时对 `fast.` 开头的条目加一句"快树里的使用不计入"，避免模型把"尚无记录"读成"没用"。

## 4. S1：在哪里展示（D7）

| 位置 | 展示什么 |
|---|---|
| `capsule_search` 的每一行 | 一个短摘要，如 `用过 12 次 / 5 个任务（4 成 1 败），报错 1 次`；条件写成 `判真 7 / 判假 4 / 报错 0`；没有数据写 `尚无记录` |
| `capsule_get` | 完整统计 + 错误样本 + 草稿时期的数字 |
| 系统提示词 | **不放**（与 2026-10-28 删掉 catalog 的理由一致） |

**排序不变**，仍按关键词命中数。按使用次数或成功率排序会造成冷启动陷阱（[目标Agent画像.md](目标Agent画像.md) §T9）：新条目永远排在后面 → 永远没被选 → 永远没数据。展示数字但不替模型排，由它自己权衡。

措辞上统一用"尚无记录"，不用"0 次"——没被用过不等于没用。

`prompts/skills/review.md` 第 8 行（"结果里每个条目只有引用、种类、description 与输入 / 输出名"）相应改成提到统计摘要。

## 5. S3：整理回合与下架

> 2026-10-29 改（C1–C6）：下架不放进复盘，改成单独的**整理回合**。原 §5.2「复盘请求里多一节证据」（D11）取消。

### 5.1 为什么单独一个回合

| | 放进复盘 | 整理回合 |
|---|---|---|
| 看到什么 | 只有本任务碰过的胶囊 | 全库，同类条目可以横向比较 |
| 证据量 | 每次只多一个任务，容易因一次偶然失败就下架 | 隔很多任务，统计更厚 |
| 开销 | 每个任务都付 | N 个任务付一次 |
| 职责 | 复盘既管存又管删 | 复盘只管"存不存"，整理只管"库乱不乱" |

复盘回合因此**不变**：不加证据小节，也不能用 `capsule_retire`（C6）。复盘中用 `capsule_search` 照样能看到 S1 的统计，判断"是不是和已有条目重复"够用了。

### 5.2 触发（C1、C2）

- **手动**：`/bt curate`，和 `/bt task` 一样用 followup 在当前会话开一个回合，消息来源 `{ kind: 'stevex-bt', requestId, reason: 'curate' }`（路由照旧跳过 `stevex-*`）。
- **自动**：配置 `curate.everyTasks`，**默认 0 = 只能手动**。设为 N > 0 时，每结束 N 个任务（含失败的，计数在任务结束时 +1）自动发一次，发往最后一个任务所在的会话；回合开头先说明"已累计 N 个任务，开始整理胶囊库"，人可以随时取消。
- **只在空闲时发**：攒够数时如果有任务在跑、或有复盘没结束，就等它们都结束再发；已经有一个整理请求没结束时不重复发。手动 `/bt curate` 遇到这些情况直接返回说明，**不排队**（2026-10-29 确认）：人等手头的事做完再敲即可。
- **计数**：存在 `stats.json` 的 `curate: { sinceLast, lastAt, lastRequestId }`；整理请求发出时清零。被人取消的整理不自动重发。

### 5.3 证据（C3、C5）

整理请求给一份**全库清单**，每个条目一行，**按名字排序**，不按好坏排、不预先挑"可疑条目"：

```text
## 胶囊库（9 条，其中已下架 0）
- code/craft.count-wood-materials@cda0628b（Compute）用过 5 次 / 3 个任务（3 成 0 败）｜同名旧版本 0｜统计背包里的木板……
- code/fast.low-health@…（条件）尚无记录（快树里的使用不计入）｜……
- code/ui.menu-open@646b7f7e（条件）判真 7 / 判假 4 / 报错 0，5 个任务（4 成 1 败）｜同名旧版本 1｜条件：当前打开的……
- trees/craft.in-player-grid@08a42c19（子树）……
```

- 统计摘要与 `capsule_search` 的写法相同（§4），已下架的条目标"已下架：<理由>，取代者 <ref>"。
- 再附一行：上次整理的时间、之后结束了几个任务。
- **条目超过 `curate.listLimit`（默认 150）时不给全量清单**，改给目录：各名字前缀（`craft.` `ui.` `fast.`……）下有几条、其中几条已下架、几条尚无记录。细节由模型用 `capsule_search` / `capsule_get` 自己查。

### 5.4 工具（C4）

整理回合可用：查询类工具（`capsule_search` `capsule_get` `data_shapes` `command_docs`……）+ 下面三个。后三个**只在整理回合可用**（`CURATE_ONLY_TOOLS`，guard 照旧拦其他回合）。不给 `capsule_save`：不经任务验证的新代码不进库；合并 = 复盘时存下更通用的新条目，下一次整理时下架老条目并写上取代者。

**`capsule_retire`**：

```json
{ "ref": "code/craft.plan-stack-craft", "reason": "被 craft.plan-planks-clicks 取代：后者处理了余料放回", "supersededBy": "code/craft.plan-planks-clicks" }
```

- **`reason` 必填**（非空字符串，截到 500 字）：缺了就返回错误、不下架。理由会记进 manifest 与 `curate.jsonl`，以后回看时能判断当初为什么下架、是不是误判；`undo` 也要写 `reason`（为什么撤销）。人用脚本时 `--reason` 同样必填。
- **按名字下架**（`文件夹/名字`，可省哈希，D8）：manifest 里该名字加 `retired: { at, reason, supersededBy?, requestId }`。条目文件不动、哈希不变。
- **下架后**：`capsule_search` 默认不返回它（`includeRetired: true` 才返回，并标"已下架"）；`capsule_get` 照常可取，显示下架原因与取代者；**已经带哈希的引用照常能装载**——历史树必须能重放（§8.4）。新提交的树里引用已下架的名字：校验器给一条**警告**（不是错误），写明取代者（D9）。
- **撤销**：`undo: true`。复盘里再 `capsule_save` 一个同名的新版本时也自动清掉下架标记。
- **`locked` 条目不能下架**（内置的 `core.*` 和人锁定的条目），返回错误（D10）。
- 人也可以用脚本：`npm run capsule-retire -- <ref> --reason …`。

**`capsule_describe`**：改一个条目的说明。

```json
{ "ref": "code/ui.menu-open", "description": "条件：当前界面类型是否等于 params.screen（inventory / crafting / none）……" }
```

- 说明不在哈希里（§8.4），改说明**不产生新版本**：更新 manifest，并把当前版本文件里的 `description` 一起改掉。
- 内置条目不能改；人锁定的条目可以改（`locked` 只防删除，§8.2）。
- 库大了以后，"搜不到合适的条目"多半是说明写得不好，而这只有横向比较时才看得出来。

**`bt_curate_done`**：`{ requestId, reason }` 结束整理，什么都不改也要调用并写明理由。没调用就结束回合时，照复盘的做法补一次提醒。

### 5.5 记录

每次整理在 `src/capsules/curate.jsonl` 追加一行：`{ requestId, at, trigger: 'manual'|'auto', sinceLast, retired: [...], undone: [...], described: [...], reason }`。下架与改说明的旧值也记进去，便于人回看与撤销。

### 5.6 不做的事（D12 之外）

- 不做相似度算法找合并候选：清单按名字排序，同类条目自然挨在一起；模型也可以用 `capsule_search` 搜同类词。
- 不做探索配额：排序不看统计，没有冷启动陷阱需要补救；以后要按统计排序时再一起设计。
- 不自动删除任何条目：下架只是不出现在搜索里；真正移走只有 S2 的 GC，而 GC 会保留当前版本（含已下架的）。
- 整理回合不跑 GC：GC 保持离线、由人执行。

## 6. S2：GC（离线脚本，D12）

`npm run capsule-gc`（在 `dsh-plugins/agent` 里），**默认只演练**（打印将回收的条目），加 `--apply` 才动手。

**保留集**（任一满足即保留）：

1. manifest 里每个名字的当前版本（含已下架的）
2. `locked` 条目
3. 被以下任一棵树引用过的版本（扫描所有 `ref` 字段，带哈希的才算）：
   - 库里 `trees/` 的全部条目（含旧版本）
   - `runtime/tasks/*/trees/v*.json`
   - `src/bt/trees/fast/` 下的快树版本
4. 保留集里的子树胶囊**再引用的**版本（传递闭包）
5. `stats.json` 里 `lastUsed` 在最近 N 天内的（`--keep-days`，默认 30，D12）：防止 `runtime/` 被清理后，最近还在用的版本被当成无人引用）

**不在保留集的**：移到 `src/capsules/archive/<日期>/<文件夹>/<名字>@<哈希>.json`，并在 `archive/index.jsonl` 记一行（原路径、归档原因、当时的统计）。**不真删**——进化史本身是资产（§8.6）。`stats.json` 里对应的条目跟着移进归档索引。

装载一个已归档的引用时，`library.get` 的报错要写明"已归档在 archive/…，GC 时无人引用"，而不是笼统的"找不到"。

§8.6 的"扫描 `src/bt/trees/`"同步改成上面三处。

## 7. 决策点

| # | 问题 | 推荐 | 备选 |
|---|---|---|---|
| D1 | 怎么知道节点调用了哪个胶囊 | 节点**退出事件**加 `ref` 字段（执行器一行改动） | 不改事件，统计时按节点 id 去对应版本的树文件里查 ref（要跟踪 `expansion/applied` / `patch/applied` 的版本切换，子树内部还要再查一层，容易错） |
| D2 | 何时统计 | 任务结束时增量累加，复盘结束时再处理 `capsule/saved` | 只做离线批量重算（复盘时看不到本任务的数字） |
| D3 | 统计的粒度 | 按完整引用（带哈希）记，展示时按名字汇总 | 只按名字记（新版本会继承旧版本的好坏，看不出改版是变好还是变坏） |
| D4 | 旧日志要不要回补 | 不回补，从改动上线起记 | 写一个按树文件反查 ref 的回补脚本（就是 D1 的备选，只为几十个旧任务不值得） |
| D5 | 草稿转正后的数字 | 拷到新条目的 `draft` 字段，单独展示 | 不拷，新条目从"尚无记录"开始 |
| D6 | 快树里的使用 | 第一版不统计，展示时注明 | 统计快树情节里"触发了哪个分支"（要先给快树补事件，另立方案） |

### 10.2 与方案的出入

1. **统计由事件流驱动，不是任务结束时读 `events.jsonl`**（§3.3）。执行器的 `event` 本来就带着每条记录，边跑边累计到本任务、`task/done | failed` 时一次并账，不受内存里事件条数上限的影响，也不依赖 `runtimeDir`。重建脚本把文件里的行按同样顺序喂给同一个 `observe`，结果一致（有测试）。
2. **草稿数字在 `capsule/saved` 事件到达时就拷**（§3.4 说在复盘结束时处理）：`capsule/saved` 在复盘中途写进同一个事件流，到时直接处理更简单，效果相同。草稿数字只在内存里留最近 5 个任务；进程重启后再手动复盘转正的条目拿不到草稿数字（重建时能补上）。
3. **下架警告由 bridge 给，不是校验器**（D9）：校验器只有"错误"一种结果。bridge 在大纲 / 展开 / 补丁被接受后扫描新节点的 `ref`，把警告放进提交结果，`renderSubmission` 附在后面。
4. **子树 / Compute 的失败都记 `error`**（§3.2 原样实现），展示时写"成功 x / 失败 y"；只有条件分"判假"与"报错"。
5. **整理回合出错直接按 abandoned 关闭**：DSH 里人取消回合也走出错路径，分不出来，按 §5.2"被取消的整理不自动重发"一并处理。
6. **自动整理用 `deliverIdle`**：触发点可能在复盘回合中途（`bt_reflect_done` 里关闭复盘 → 检查计数），那时回合还在 running，直接 followup 会丢；等会话 idle 再发（同 2026-10-27 的出错重试修复）。
7. `capsule_retire` 的 `reason` 由 DSH 的参数 schema 先挡一遍（缺了就是参数错误），bridge 再查空白字符串。

### 10.3 DSH 内验收清单

1. 跑一个用到库里胶囊的任务 → `npm run capsule-stats` 能看到数字，和 `events.jsonl` 里带 `ref` 的退出事件对得上
2. `/bt curate` → 回合里出现全库清单；有任务在跑时 `/bt curate` 直接返回说明
3. 让模型下架一个条目（带 `supersededBy`）、改一条说明 → `bt_curate_done`；`src/capsules/curate.jsonl` 有一行
4. 下一个任务：`capsule_search` 不再返回下架的条目、能搜到新说明；大纲若引用了下架的名字，提交结果里有警告、任务照跑
5. 把 `curate.everyTasks` 设成 1，跑一个任务 → 复盘结束后自动来一个整理回合，开头写明"自动发起"
6. `npm run capsule-gc`（演练）输出合理；需要时 `-- --apply`
