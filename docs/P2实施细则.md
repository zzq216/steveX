## 0. 一句话与范围

**P1 让大模型能"往前写"树；P2 让它在树被打断、走不通、或者人死了之后，能"回头改"树。**

| 在 P2 里 | 不在 P2 里 |
|---|---|
| 四类请求交给大模型：`recover` / `escalate` / `failed` / `died` | 快树事件流与快树进化（P3） |
| `bt_submit_patch`（补丁）、`bt_inspect`（按需查看证据） | 任务结束的反思与 `capsule_save`（P4） |
| 请求过期（I4）的完整规则 | `fact_*` / `mc_source_*`（P5） |
| 让树能自己发现记忆过期：reactive 序列的复查间隔、记忆查询读最新数据（§6） | 路由 LLM 填槽（路由阶段 B） |
| 死亡检测、自动重生（含一处 mod 改动） | §7.5 ② 的"换目标重试" |
| | ~~依赖集与 `invalidated` 请求~~（2026-10-25 删除，§6.1） |

**验收**（集成方案 §10，随 §6 修订）：任务中被打断后能续上；任务用到的记忆过期（方块被人挖掉）时，树里写了复查的能在复查时发现，没写的在节点失败后经 `failed` 请求重规划。本文 §11 把它细化成可执行的场景。

## 2. 请求总表

| 请求 | 触发 | 目录的标题行（§4.2） | skill | 期望的提交 |
|---|---|---|---|---|
| `recover` | 快树命中真实 arm、情节以 `SUCCESS` 结束，且情节开始时任务树有叶子在跑 | 被中断的叶子、快树 arm 名 | 慢树恢复 | `bt_submit_patch`（空补丁 = 原树继续）/ `bt_abort_task` |
| `escalate` | 同上，但情节以 `FAILURE` 结束（快树认出了局面但处理不了） | 同上 + arm 的错误原文 | 慢树恢复 | 同上 |
| `failed` | 根 `FAILURE`，且原地重试一次后仍失败 | 失败节点、错误原文（含失败前的状态差异） | 慢树反思 | 同上 |
| `died` | 死亡（§8） | 死亡信息、死亡时运行的节点 | 慢树恢复 | 同上 |

**四类请求共用一套回答方式**：补丁或放弃。P1 的 `answerRequest({ action: 'continue' })` 改为"空补丁"，不再单独存在。

**四类请求也共用一套证据方式**（§4）：消息里推一份目录，内容由大模型用 `bt_inspect` 自己取。

**准入的工具**：`command_docs` · `data_shapes` · `capsule_*` · `bt_view` · `bt_inspect`（§4.4）· `bt_submit_patch` · `bt_abort_task`。记忆世界的值仍然不给（§4.5）。

## 3. 补丁：`bt_submit_patch`

### 3.1 格式

```json
{
  "requestId": "r12",
  "ops": [
    { "op": "replace",       "id": "n1.3",   "node": { …编写格式… } },
    { "op": "insert-after",  "id": "n1.2",   "node": { … } },
    { "op": "insert-before", "id": "n1.4",   "node": { … } },
    { "op": "remove",        "id": "n1.5" }
  ],
  "code": { …可选，任务内代码草稿，同 P1… }
}
```

- `ops: []` = **原树继续**：被中断的叶子已经归零，从它重新开始
- 每个 `node` 是编写格式的子树，经编译器分配 `id`；大模型只点名 `id`，从不写 `id`（行为树设计 §8.4）
- `code` 与 P1 相同：先写进任务草稿区，再编译校验

**【P2-D1】操作集多一个 `insert-before`**。行为树设计 §8.4 只列了 `replace` / `insert-after` / `remove` 三种，但只有 `insert-after` 就没法在一个序列的**开头**插入节点。各类请求都会遇到"在当前步骤前补一步"，当前步骤又常是序列第一个孩子：`recover` 抢占时关掉了工作台，放料前要先重新打开；`failed` 缺材料（或者记忆里的原木已经没了），合成之前要先补材料、走过去之前要先重新找；`died` 东西掉了，继续之前要先捡回来或重新收集。这些前置步骤是任务自己的需要，快树是通用反射，不知道慢树下一步需要什么，所以不能交给快树做。不用 `insert-before` 的绕法是 `replace` 当前步骤为 `seq[新步骤, 原步骤]`，但大模型要把原步骤整段抄一遍，原步骤的 id 也变了；如果改成插到外层序列，当序列是根、是选择器的分支或循环体时，语义也会变。倾向：加上。

### 3.2 规则：补丁不能改已经过去的事

任务树是 `memory` 模式：已完成的孩子不会再跑。补丁如果改的是已完成的部分，改了也不生效——这种"看起来接受了、实际什么都没发生"的补丁最难排查。所以：

| 操作 | 目标在哪里 | 结果 |
|---|---|---|
| `replace` / `remove` | 已完成（父序列游标的左侧） | **拒绝**，错误里说明"n1.2 已经执行完，改它不会重跑；要补做，在当前位置 `insert-before`" |
| `replace` / `remove` | 当前位置（被中断的叶子，或它的祖先） | 接受；被替换的部分从头开始，祖先游标保留 |
| `replace` / `remove` | 还没执行到 | 接受 |
| `insert-*` | 插入点在已完成的两个孩子之间 | **拒绝**，理由同上 |
| `insert-before` 当前孩子 / `insert-after` 最后一个已完成的孩子 | 正好在游标处 | 接受；**新节点下一个执行**，原来的当前孩子顺延 |

**【P2-D2】** 倾向按上表执行。替代方案是"改已完成的部分时自动把游标拨回去"，但那等于让大模型隐式地决定重跑哪些步骤，不如让它显式写 `insert-before`。

### 3.3 新节点的 `id`

**【P2-D3】** 补丁产生的子树根用 `<锚点 id>.p<新版本号>` 为前缀：在 v5 里 `insert-after n1.2` 得到 `n1.2.p5`（它的孩子 `n1.2.p5.1`……）；`replace n1.3` 得到 `n1.3.p5`。

- 理由：P1 的展开沿用 `<被替换节点>.1`，展开只会发生一次，不冲突；补丁可以对同一个位置反复打，必须带版本号才不会撞 `id`，事件日志里也能一眼看出"这个节点是第几版补丁加的"
- 同一个补丁里对同一锚点有多个插入时，按顺序编号 `n1.2.p5`、`n1.2.p5b`……（实现时定，不影响语义）

### 3.4 校验与生效

1. 逐条编译 `node`；**整份补丁的新节点合计**不超过 `maxExpansionNodes`（15），超了提示把一部分改成 `expand`
2. 把补丁应用到执行格式树的副本上，整树过校验器（黑板读引用的来源、胶囊引用、快树规则、§6.2 的 reactive 规则……与展开相同）
3. 不合法 → 错误原文作为工具结果返回，计一次不合法尝试，同一请求 3 次 → 任务失败（与展开一致）
4. 合法 → 换上新树（版本号 +1，写树版本链），**对失败路径上的节点做 `reopenFailure`**（`failed` 请求时根是 `FAILURE`，不重开就一直停在失败状态），任务回到 `running`

## 4. 证据：推目录，按需取（2026-10-25 改）

### 4.1 原则

原稿给每类请求定了一份固定证据清单（`recover` 三份状态加一个前置求值，`failed` 失败节点加失败路径……）。那张清单是我们在替大模型猜它需要什么。改为：**请求消息只推一份目录，具体内容由大模型用 `bt_inspect` 自己选、自己取。**

不是完全不推，原因有两条：

1. 大模型只能去要它知道存在的东西。完全不推，它连有哪些快照、出事的是哪个节点都不知道
2. 出事的节点和错误原文几乎每次都要看，推过去能省一次往返

除此之外都按需取。看到某类问题时该查什么，这本身就是 agent 要在训练中学会的东西（与 §6.1 同一方向）；P4 反思时还可以从会话记录里统计它实际查了哪些证据，作为以后调整目录的依据。

### 4.2 推送：目录

```
failed：节点 n1.3.2「放料」失败
错误：expect 不成立：…（失败前已发生：…）
路径：n1「做木镐」→ n1.3「合成」→ n1.3.2「放料」
可查看（bt_inspect）：
  快照  before@n1.3.2, after@n1.3.2, before@n1.3.1, after@n1.3.1, …（共 14 份）
  事件  148 条
  黑板  6 个键：plan, table, logs, …
  记忆来源  terrain：n1.2 读于 v41，现在 v47
```

| 项 | 内容 |
|---|---|
| 标题行 | 按请求类型，见 §2 表 |
| 错误 | `failed`：失败节点的错误原文（`WorldLeaf` 已经把"失败前已发生：…"拼进了错误里）；`escalate`：快树 arm 的错误原文；`died`：`deathMessage` |
| 路径 | 根到出事节点（失败 / 被中断 / 死亡时运行）的 `id` 链，每层附名字 |
| 快照 | §4.3 缓冲里现有快照的**名字**，新的在前；不含内容 |
| 事件 | 本任务事件日志的条数 |
| 黑板 | 键名；不含值 |
| 记忆来源 | **【P2-D17】** 本任务里执行过的查询节点各自读到的数据源版本，与发请求时的当前版本比较，只列出已换代的。只比版本戳（`stat`），不比内容、不归因、不触发任何请求。作用是让大模型在反思时能想到"可能是记忆过期了"；它是证据，不是指令 |

### 4.3 执行器要留下什么：快照缓冲

现在 `WorldLeaf.observed` 的前后快照用完就丢，事件日志里只留差异。要让快照能按需取，每个任务维护一个**快照缓冲**：

| 快照名 | 何时存 | 内容 |
|---|---|---|
| `before@<id>` / `after@<id>` | 每个 `Steps` / `Action` 执行前 / 后（失败时 `observed` 本来就会补读一次"后"） | `observed` 读到的来源 |
| `interrupt` | 抢占时 | 快树缓存里有的部分（抢占要快，来不及现场读），通常只有 `player` |
| `episode-end` | 快树情节结束、发 `recover` / `escalate` 之前 | **现场读全** `inventory` / `container` / `f3` / `player` |
| `death` / `respawn` | §8.3 | 死前缓存 / 重生后现场读全 |
| `live#n` | `bt_inspect` 的 `live` 每调用一次 | 那一刻现场读到的来源，存下来以便之后拿它做差异 |

- 同一个叶子在循环里多次执行时，名字带次数：`before@n1.3.2#2`
- 叶子快照只保留**最近 `snapshotKeep`（20）个叶子**的，环形淘汰；特殊时刻的快照保留到任务结束。任务结束整个缓冲丢弃，不落盘（差异已经在事件日志里）
- `Condition` / `Compute` 不存快照（它们不改世界）
- 一份快照是 mod 几个来源的读取结果，几 KB，20 个叶子的量可以忽略

### 4.4 `bt_inspect`

一个工具，按 `what` 选查看方式。原计划的 `bt_history` 并进来，不再单独做。只能看**当前请求所属的任务**。

| `what` | 参数 | 返回 |
|---|---|---|
| `events` | `node?`（`id` 前缀）、`type?`、`last?`（默认 30） | 本任务事件日志的过滤结果，`observe` 事件里的差异照给 |
| `snapshot` | `name`、`sources?`、`against?`（另一份快照名） | 这份快照（可只取部分来源）；带 `against` 时返回两份之间的差异（`diffState`） |
| `node` | `id` | 节点定义（编写格式）、状态、`lastError`、执行次数、`origin`（补丁来源） |
| `eval` | `id`、`at?`（快照名，缺省 = 现场读） | 用当前（或某份快照里的）状态和当前黑板对一个 `Condition` 节点求值，返回真 / 假与出错原因。取代原稿里写死的"左兄弟前置求值" |
| `blackboard` | `keys` | 这些键的值 |
| `live` | `sources`（`player` / `inventory` / `container` / `f3` 的子集） | 现在读一次；同时存成 `live#n` 快照 |
| `versions` | — | 每个执行过的查询节点：数据源、读到的版本、当前版本（目录里只列换代的，这里列全） |

- 每次结果不超过 `inspectMaxBytes`（8000 字节），超了截断并提示缩小范围（只取部分来源、加过滤、用 `against` 只看差异）
- `bt_view` 不变，继续负责看整棵树；`bt_inspect` 负责看"发生了什么"
- `live` 读世界期间如果又发生了快树情节或死亡，请求照 §5 过期，与读不读无关

### 4.5 边界

**【P2-D18】** 大模型自己选看什么，但能选的范围有边界：

1. **记忆世界（NBT / JSON）的值仍然不给**：修复回合里没有 `mod_query` / `nbt_query` / `json_query`，只有 `data_shapes` 看形状。修复时如果能直接查到"另一个箱子在 (12,64,-3)"，补丁就会写死坐标，agent 永远学不会在树里写查询——这正是 §6.1"记忆过期要靠 agent 自己学"的前提
2. 能看到的值都来自**自己的状态和树自己的执行过程**：快照、黑板、事件、`live`。黑板里可能有树自己从记忆里查出来的值（比如 `$chest` 的坐标），这是"树当时用了什么"，判断时需要；按 §4.6 处理
3. 白名单与密钥目录的限制不变：`bt_inspect` 只碰执行器内存与本任务的事件日志，不碰任何文件路径参数
4. **准入**：四类修复请求的回合，以及普通问答回合（用户问"刚才为什么失败"）；`plan` / `expand` 回合不给（I13：它们看不到世界状态）

### 4.6 证据里的具体值与 I13

I13 不给大模型看实例值，是为了不让它把值抄进树。但修复**必须**能看具体值——"背包第 5 格：木板×3 → 空"正是判断 M 做到哪的依据，去掉就判断不了。

**【P2-D4】** 倾向：

1. **`bt_inspect` 照常给值**（判断必需）
2. **补丁产生的节点打来源标记** `origin: { request: "r12", type: "recover" }`，存进树版本链。P4 提取可复用子树时据此识别"这是为某一次情况临时打的补丁"，不当作通用结构直接提取
3. 「慢树恢复」skill 里明确：看到的值用来**判断**，补丁里仍然靠读取节点和 `$键` 取数据，不写死格子号

替代方案是证据也只给形状，代价是大模型基本无法判断"做到哪了"，恢复会退化成"总是从头重跑"。

## 5. 请求过期（I4）

现有机制：在飞请求期间又发生新事件 → 标 `stale` → 提交时被拒、附新证据、不计入不合法次数。P2 把"哪些事件让哪类请求过期"定死：

| 在飞的请求 \ 新事件 | 快树情节 | 死亡 |
|---|---|---|
| `expand` | **不过期**（【P2-D13】） | 过期 |
| `recover` / `escalate` / `failed` | **不过期**（【P2-D19】，2026-10-25 改） | 过期 |
| `died` | **不过期**（同上） | 过期 |

**【P2-D13】为什么展开请求不因快树情节过期**：任务挂起等展开时没有叶子在跑，情节不会打断任何东西；而按 I13，展开回合里大模型本来就看不到世界状态，情节改变的东西它也没看过——它交回的子树不会因此变得不对。P1 现在的代码会把它标过期，P2 改掉，省一次无谓的拒绝。

**【P2-D19】为什么修复请求也不因快树情节过期（2026-10-25，场景 1 首测后改）**：原规则让挂起期间的每次情节都使在飞的修复请求过期。首测（`task-20261025114148-2`）里 agent 一直泡在水里，溺水反射只会原地上浮，6 分钟里触发 58 次，恢复请求 r6 被标过期 51 次，大模型交的 4 次补丁全部被拒，任务卡死。理由与 D13 相同：挂起时没有叶子在跑，情节打断不了什么；而且证据改成了按需取（§4），大模型要最新状态随时用 `bt_inspect` 的 `live`。代价是补丁可能基于稍旧的状态写成——补丁生效后局面若仍危险，快树会再打断、发新的 `recover`，自然纠正。挂起期间的情节只记 `request/not-stale`，不存 `episode-end` 快照（持续危险里会无限累积）。反射本身处理不了危险是快树能力问题，属于 P3。

现在只有**死亡**会让请求过期。被拒时工具结果附**合并后的新目录**（§4.2；多个新事件按发生顺序列出标题行，新事件产生的快照进快照列表）。被拒后请求恢复成"未过期"，大模型在同一回合里基于新证据重交。

## 6. 记忆过期：交给树自己处理

### 6.1 为什么删掉依赖集（2026-10-25 定）

原方案（行为树设计 B9 / §7.6、集成方案 §5.3）：查询节点读到的记忆条目记成依赖集，执行器轮询，条目变了就挂起任务、发 `invalidated` 请求。删掉的理由：

1. **提前量很小**：记忆世界来自客户端，变化要等 agent 加载到那片区块、看到之后才会进记忆。走到桥边才发现桥没了，这时寻路节点也差不多同时失败——依赖集比"节点失败"早不了多少
2. **实现很重**：身份字段注入、依赖生命周期、变化判据、自身动作归因（要在 mod 里加动作账本）、覆盖时长、账本断档……绝大部分复杂度都在处理"依赖跨过了消耗它的动作"，而这正是隐式依赖的固有问题
3. **目标是让 agent 自己学会**：记忆会过期是 Minecraft 世界的常态。与其由执行器替它盯着，不如让它在训练中因为过期吃过亏（节点失败 → `failed` → 反思），然后学会在树里写"用之前先复查"、"边做边复查"，再经 P4 把带复查的子树存下来复用。**提示词不教这两种写法**

执行器只需要让这两种写法**写得出来、跑得通**。现在都不行：reactive 序列在任务树里会自我中止（§6.2），查询快照按任务钉住、复查永远读到旧数据（§6.3）。这两处就是 §6 的全部改动。

"边做边复查"不需要新的 watch 节点：reactive 序列里排在前面的 `Condition` / `Compute` 就是守卫，下面加上复查间隔即可。

### 6.2 reactive 序列：复查间隔

**【P2-D14】** 编写格式加 `every`（毫秒），执行格式同名：

```json
{ "seq": "去开箱子", "mode": "reactive", "every": 2000, "do": [
    { "compute": "code/core.nbt.query", "params": { … }, "writes": { "rows": "chest" } },
    { "cond": "blackboard/compare", "params": { … "$chest" … } },
    { "act": "…走过去…" }
] }
```

**语义**（设当前活跃孩子是第 k 个，它前面的 0…k-1 号称为守卫）：

| 情况 | 行为 |
|---|---|
| 没有活跃孩子（首次进入，或上一轮已结束） | 从 0 号起依次跑，停在第一个未通过（`FAILURE` 或 `RUNNING`）的孩子上，与现在相同 |
| 有活跃孩子，距上次复查不到 `every` | **只 tick 第 k 个**，守卫不重跑 |
| 有活跃孩子，到了复查时间 | 开始一轮复查：依次重跑守卫。守卫返回 `RUNNING`（现场读状态 / 查询还没回来）→ **不算翻转**，本 tick 照常 tick 第 k 个，下个 tick 接着等这个守卫 |
| 复查中守卫 `SUCCESS` | 继续复查下一个守卫；全部通过 → 本轮复查结束，计时归零 |
| 复查中守卫 `FAILURE` | 中止第 k 个，序列返回 `FAILURE`（与现在的 reactive 语义相同） |

- 这同时修掉了 §1 表里的问题：现在守卫的 `RUNNING` 会被当成"停在了别的孩子上"而中止第 k 个
- **默认值**：任务树里写了 `mode: 'reactive'` 而没写 `every` → 用配置 `reactiveEveryMs`（1000）。快树不变：缺省仍是每 tick（快树的条件读缓存，同步、便宜）
- **下限**：任务树里 `every` < 200 → 校验错误（复查要现场读，太频繁会和动作抢 mod 的读取）

**【P2-D16】任务树里 reactive 的校验规则**：

1. 只允许在 `Sequence` 上用。任务树里的 reactive `Selector`（高优先级分支一通过就切过去）的分支本身就带动作，复查时会真的去执行动作，和正在跑的分支同时动，语义说不清。它留在快树里
2. **除最后一个孩子外都必须无副作用**：`Condition`、`Compute`，或者只由它们组成的控制节点 / 装饰器。复查会重跑守卫，守卫里有 `Action` / `Steps` 就会重复做事
3. 违反时的错误提示照 P1 `hintFor` 的格式，说明原因与改法

### 6.3 记忆查询读最新数据

**【P2-D15】** 查询快照由"按任务钉住"改为"每次执行读最新版本"：

1. 缓存键从 `(taskId, path)` 改为 `(path, 版本戳)`。查询节点每次执行先取一次版本戳（只 `stat`，装载器已有 `versionOf`），没变 → 直接用已解析的结果（不重复解析，开销与现在相当）；变了 → 解析新版本，旧版本没人用时淘汰
2. **一致性的范围缩到一次查询执行**：一次查询内部只看同一个版本；同一任务里先后两次查询可能看到不同版本——这正是复查要的
3. `releaseTask` 退化为缓存清理
4. 查询节点把读到的版本写进事件日志，供 §4.2 的 P2-D17 比较、也供回放时知道当时看到的是哪一版

- 原来按任务钉住的理由是"同一棵保存的树跑出同样结果"（nbt 查询设计 §5.1 / 行为树设计 §8.4）。但记忆世界本来就在变，钉住换来的只是"复查必然看不到变化"；回放需要的可复现性由日志里的版本记录提供
- JSON（配方等）同样处理，规则统一；这些文件基本不变，实际没有区别
- 拍板后同步修改 [nbt查询api设计方案.md](nbt查询api设计方案.md) §5.1 与 [json查询api设计方案.md](json查询api设计方案.md) 的快照语义

### 6.4 删除之后，过期怎样暴露

| 树怎么写的 | 记忆过期时发生什么 |
|---|---|
| 没有复查 | 用到旧数据的节点失败（走不到、`expect` 不成立……）→ 原地重试一次 → `failed`，目录里有 P2-D17 的版本换代行 → 大模型反思、打补丁 |
| 用之前复查（`memory` 序列里在动作前重新查询 + 条件） | 复查条件 `FAILURE` → 同上走 `failed`，但失败点就是复查条件，原因一目了然 |
| 边做边复查（§6.2 reactive + `every`） | 下一次复查发现 → 中止动作 → 序列 `FAILURE`；外层有 `sel` 备选就在树内消化，没有就走 `failed` |

三条路都走现有的 `failed`，不新增请求类型。

## 7. 根失败（`failed`）

流程不变：根 `FAILURE` → 原地重试失败叶子一次 → 仍失败 → `failed` 请求。P2 的改动：

1. DSH 里不再由本地应答器直接放弃，交给大模型，skill 用「慢树反思」（集成方案 §4.6）
2. 补丁生效时对失败路径 `reopenFailure`（§3.4）
3. **【P2-D11】`bt_history` 并入 `bt_inspect`**（2026-10-25 改）：失败的原因常常在更早的节点上（比如三步之前的点击其实没生效），只看失败节点不够。集成方案 §5.1.2 给 `failed` 准入的 `bt_history`，P2 由 `bt_inspect` 的 `events`（过滤事件日志）与 `snapshot`（更早叶子的前后快照）覆盖（§4.4）。树版本链的"取某一版、两版之差"留到 P4

## 8. 死亡与重生（I12）

### 8.1 现状的缺口

- **检测**：`player` 有 `vitals.health`，生命值为 0 可以作为判据；但 mod 没有暴露"是否在死亡界面"，也没有死亡信息
- **重生**：mod **没有**重生的方法。行为树设计里写的"`respawn` 原语"随语义原语撤销（B10）已不存在；死亡界面不是容器界面，现有 API 都点不到它的按钮

### 8.2 需要改 mod

**【P2-D10】** 倾向：在采集端 mod 加一个方法、两个字段。

| 改动 | 内容 |
|---|---|
| `player` 加字段 | `dead`（`player.isDeadOrDying()`）、`deathMessage`（当前界面是 `DeathScreen` 时的死亡信息文本，否则为 `null`） |
| 新方法 `player/respawn` | 调 `LocalPlayer.respawn()`，与死亡界面的"重生"按钮完全相同 |

按此前定下的判定准则（新增界面操作 API 时，看该状态在客户端有没有服务端回读通道；有才能走语义通道），重生**有回读通道**——`LocalPlayer.respawn()` 发 `ServerboundClientCommandPacket(PERFORM_RESPAWN)`（`1.21.11_src/net/minecraft/client/player/LocalPlayer.java:323-326`），服务端回 respawn 包后，客户端在 `ClientPacketListener.handleRespawn` 里关掉死亡界面（`ClientPacketListener.java:1337-1339`）。死亡界面的按钮本身也只是调这个方法（`DeathScreen.java:49-52`）。所以走语义通道与真人点按钮在状态上等价，不需要 GUI 控件 API（该方案仍搁置）。

- P2 的 Java 改动只有这一处（原 §6.4.1 的自身动作账本随依赖集删除），构建后要重新部署采集端
- 极限模式（`hardcore`）下按钮是"旁观"而不是重生，`player/respawn` 返回错误，任务失败

### 8.3 执行器的处理顺序

1. **检测**：任务存在期间，`player` 始终在轮询集合里（每 200 ms 一次，便宜）；`dead` 为真（或 mod 未升级时 `health` ≤ 0）→ 死亡
2. 记下**死前状态**：最近一次缓存的背包与坐标（死后背包已掉落，读不到了），存成 `death` 快照（§4.3）
3. 任务树走默认中止流程（松键、关容器）
4. 自动调 `player/respawn`，轮询到 `dead` 为假、生命值回满（超时 10 s → 任务失败）
5. 现场读一次重生后的状态，存成 `respawn` 快照
6. 发 `died` 请求，目录（§4.2）的错误行是 `deathMessage`、路径是死亡时运行的节点；死前 / 重生后的状态由大模型按需取（`snapshot death against respawn` 即掉了什么）
7. 在飞请求期间死亡 → 标过期（§5），附新目录

死亡同时是快树事件流的高信息量事件（集成方案 §7.4.2），那部分在 P3。

### 11.1 实现中发现、已一并修掉的缺口

**树自己中止的叶子没有人松键。** 快树抢占、暂停、放弃都走默认中止流程（松键、关容器），但树**内部**中止叶子时（§6.2 的复查守卫不成立、`Timeout` 到时）没有：被作废的 `Steps` 后面的"松开"不会再执行，键一直按着。P1 里根失败最终会走 `finishTask('failed')` 松键，问题被掩盖了；P2 起 `failed` 请求要等大模型回答，期间 agent 会一直往前走。修法：任务树一个 tick 里有叶子被中止 → 执行器**只松键**（`releaseKeys`，不关容器）；发 `failed` 请求前同样只松键——不关容器，因为"原地再来"可能还要在这个界面里继续。

**游戏内验收**（集成方案 §10，随 §6 修订）：

> **进度（2026-10-25）**：场景 1 通过（`task-20261025120206-1`）；场景 4 的"请求等待期间死亡"通过（`task-20261025120908-2`，死亡信息读取与自动重生在真实客户端生效）。场景 2、3 与"执行中死亡 → `died` 请求"暂时碰不到，步骤与期望移到 [P2待测场景.md](P2待测场景.md)，以后补测。场景 1 首测暴露的两个问题已修：`bt_inspect events` 的 INVALID_TOOL_OUTPUT（事件里的 `undefined` 字段）与恢复请求被反复过期（P2-D19）

1. **打断后能续上**：让 agent 做木镐，在它往工作台放料的中途，用命令在脚下放水（触发溺水反射），或者手动按 E 关掉界面。期望：快树情节结束 → `recover` 请求 → 大模型交补丁（比如 `insert-before` 重新打开工作台）→ 任务做完
2. **记忆过期走 `failed`**：让 agent 用 `core.nbt.query` 查到附近的箱子并去取东西；它走过去的途中，人把箱子挖掉。期望：取东西的节点失败 → `failed` 请求，目录里有该数据源的版本换代行 → 大模型重规划（换一个箱子或放弃）
3. **reactive 复查能跑通**（手写树，不经大模型）：`seq reactive every=1000 [查询箱子 → 条件"箱子还在" → 走过去]`，途中挖掉箱子。期望：1 秒左右内中止移动，序列返回 `FAILURE`；不挖时一路走到，途中移动不被守卫的现场读取打断
4. **死亡**：任务中用 `/kill` 杀掉 agent。期望：自动重生 → `died` 请求 → 大模型重规划或放弃
