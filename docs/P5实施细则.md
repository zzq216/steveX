## 2. 入口：事实确认回合

### 2.1 两个入口，同一个实现【P5-D1】

| 入口 | 什么时候用 |
|---|---|
| `/bt fact <陈述>` | 现在就能用：`followup` 叫醒会话，在一个新回合里确认（同 P1 的 `/bt task`） |
| 路由 `fact` handler | 槽位判出"知识 = 事实"时，在人发起的这个回合里确认。路由阶段 B 之前 provider 是 stub，只有 stub 槽位给出 `fact` 时才会走到 |

两个入口都调插件的 `factInTurn` / `startFactCheck`，回合里做的事完全一样。**倾向：两个都做**——`/bt fact` 用来验收，handler 真实化后阶段 B 接上就自动生效，和 P1 处理 `task` handler 的方式一致。

### 2.2 `factInTurn` 的形状

```text
ctx.stevexBt.factInTurn({ agent, turn, statement })
  → { ok: true, text }     text = 要放进本 step 的正文（陈述 + 「事实确认」skill）
  → { ok: false, error }
```

- 绑定本回合的工具名单（§8 表的"事实确认"行），回合结束解除——和规划回合一样由 guard 执行
- `task` handler 同一回合也被选中时（人的话里既有事实又有任务），`fact` 先跑（路由已有的软依赖），两段正文都放进本 step，工具名单取并集

### 2.3 事实确认回合不是请求【P5-D2】

**倾向：不登记成执行器请求，没有"必须提交"的约束。** 确认的结论可以是"源码不支持这个说法，不写入"，没有一个必交的提交工具可以等。回合结束时只受 §7 的提醒约束：查了源码却没写事实 → 提醒一次。

| | 不是请求（倾向） | 当成请求，必须以 `fact_write` 或 `fact_reject` 结束 |
|---|---|---|
| 说法是错的 | 回复人"源码里不是这样"即可 | 要多一个 `fact_reject` 工具 |
| 回合中途人插话聊别的 | 自然 | 会被提醒拉回来 |
| 有没有结论可查 | 只在会话日志里 | 事件里有一条 `fact/rejected` |

## 3. 事实条目

### 3.1 格式【P5-D3】

一条事实一个 JSON 文件：`steveX/facts/<name>.json`。下面的陈述与行号只是示意格式，没有核对过源码。

```json
{
  "name": "damage.lava-sets-fire",
  "statement": "实体在岩浆里时每 tick 尝试点燃自己 15 秒，并受到 4 点岩浆伤害（火焰抗性免疫）",
  "refs": [
    { "file": "net/minecraft/world/entity/Entity.java", "lines": [1621, 1640], "sha": "3f2a9c1e" }
  ],
  "tags": ["damage", "fire", "lava"],
  "rev": 1,
  "createdAt": "2026-10-26T…Z",
  "source": { "kind": "fact-check", "sessionId": "session-…", "taskId": null, "requestId": null }
}
```

| 字段 | 说明 |
|---|---|
| `name` | 库内名字，小写、点分（同胶囊的命名规则），由大模型起。**按名字寻址**：查、改、引用都用它 |
| `statement` | 一句话的事实，≤ 500 字。写"是什么"，不写"该怎么做" |
| `refs` | 源码引用，1–5 条，每条一个文件 + 行号范围（§4） |
| `refs[].sha` | 写入时被引那几行的内容哈希（8 位），由工具算，不由大模型给。基准换版本后能查出哪些引用失效了（§4.3） |
| `tags` | 可选，给 `fact_search` 用 |
| `rev` | 修订号，从 1 起（§3.3） |
| `source` | 写入时所在的回合：事实确认 / 规划 / 展开 / 修复 / 复盘 / 快树反思，带会话、任务、请求 id。由工具填 |

为什么按名字、不按内容哈希（胶囊是按哈希）：胶囊被树钉住版本，改了不能影响已存的树；事实没有被谁钉住，修订后大家就该看到新版。

### 3.2 存储

- `steveX/facts/<name>.json`：当前版
- `steveX/facts/history/<name>@<rev>.json`：被修订掉的旧版，原样留着（追溯"当时为什么这么认为"）
- 不建 manifest：`fact_search` 每次扫目录（§5）。条目上千之前扫目录够快；压缩机制做的时候再一起加索引

### 3.3 修订：同名要 `replaces`【P5-D4】

照胶囊的 P4-D8：

- 名字不存在：直接写，`rev: 1`
- 名字已存在：**必须写 `replaces: <当前 rev>`**，否则拒绝，错误里附上已有条目的陈述与引用，让大模型决定是"修订它"还是"另起一个名字"
- `replaces` 不是当前 rev：拒绝（期间别人改过）
- 修订 = 旧版挪进 `history/`，新版 `rev + 1`

**不做删除工具**：错的事实用修订改对；真要删由人手动删文件（进 git，有记录）。

### 3.4 没有"状态"字段

不加 `verified` / `confidence` 之类：能写进库的就是带着有效源码引用的（§4），这就是它唯一的"可信"来源。引用失效了由 §4.3 的检查标出，不是一个手填的状态。

### 3.5 压缩机制：P5 不做【P5-D5】

mc_agent.md 写了"事实库：设计压缩机制"，集成方案 §9 说"格式与压缩机制另写文档"。**倾向：P5 不做**——现在一条都没有，压缩要解决的问题（条目太多、彼此重复、`fact_search` 结果太长）要等数据长出来才看得清。§5 的结果上限先兜住"结果太长"。

## 4. `fact_write` 的校验

### 4.1 参数

```text
fact_write({
  name, statement,
  refs: [{ file, lines: [start, end] }],
  tags?,
  replaces?          // 名字已存在时必填：当前 rev
})
```

### 4.2 校验规则【P5-D6】

| # | 规则 | 理由 |
|---|---|---|
| 1 | `file` 是基准里的相对路径（`/` 分隔），过 §6.3 的路径检查 | 和 `mc_source_read` 同一个边界 |
| 2 | 文件存在、是 `.java`；`1 ≤ start ≤ end ≤ 文件行数` | 集成方案 §9 的硬约束 |
| 3 | 单条引用 ≤ 80 行 | 一引就是整个文件等于没引 |
| 4 | 1–5 条引用 | 一条事实要靠十几处源码才说得清，说明它该拆成几条 |
| 5 | `statement` 非空、≤ 500 字；`name` 合规 | |
| 6 | 同名 → `replaces`（§3.3） | |

**不查"引用的行和陈述有没有关系"**：那是语义判断，机器做不了；"与源码一一对应"的保证就到"引用真实存在、范围不大"为止。陈述对不对，靠的是大模型确实读过那几行（§7 的提醒、§9 的 skill）。

### 4.3 引用失效的检查

`refs[].sha` 是写入时那几行的内容哈希（去掉行尾空白后算）。基准换版本（MC 升级、重新反编译）后：

- `/bt facts check`：逐条重算哈希，列出对不上的引用（文件没了 / 行数不够 / 内容变了）
- 不自动处理：失效的事实由人或大模型重新确认后修订

P5 里基准不会变，这条主要是给以后换版本留的口子；成本只是写入时多算一个哈希。

### 4.4 相近的已有事实

写入成功后，工具结果附上**按陈述的词找到的、最相近的至多 3 条已有事实**（同 §5 的匹配方式）。不拦截、不判断矛盾，只让大模型看到"库里已经有这些"——重复了可以改成修订，矛盾了可以回头确认。

## 5. `fact_search`【P5-D7】

```text
fact_search({ query?, tags?, limit? })
```

- `query`：按空白拆成几个词，`name` / `statement` / `tags` 里含任一词就返回，含的词越多越靠前（同 P4 的 `capsule_search`）；不给 = 全部
- `tags`：只要带这些标签的
- 返回每条的 `name`、`statement`、`refs`（文件 + 行号，**不带源码正文**，要看就 `mc_source_read`）、`rev`；`limit` 缺省 20、上限 50
- 引用已失效的（§4.3，哈希对不上）在结果里标出来

**倾向：P5 只做多词匹配**。中文陈述没有分词，"岩浆着火"搜不到"在岩浆里会着火"——这是已知短板，大模型可以拆词多搜几次；条目多了以后和压缩机制一起换检索方式。

## 6. `mc_source_search` / `mc_source_read`

### 6.1 ripgrep 从哪来

- 插件用 `createRequire` 按包名解析 `@vscode/ripgrep` 拿到 `rgPath`，**不靠 PATH**（这台机器上没装 `rg`）
- 现在它是 DSH 的间接依赖。**倾向：在插件的 `package.json` 里显式声明 `@vscode/ripgrep`**（同版本 1.18.0），免得 DSH 哪天换掉 `dsh-tool-fs-search` 就断了（§12 #1）
- 解析不到 → `mc_source_search` 返回错误"ripgrep not found"，其余工具照常

### 6.2 参数与输出【P5-D8】

```text
mc_source_search({ pattern, fixed?, path?, glob?, context?, limit? })
```

| 参数 | 说明 |
|---|---|
| `pattern` | 正则（ripgrep 语法）；`fixed: true` 按字面量搜 |
| `path` | 只搜这个子目录（基准内相对路径，如 `net/minecraft/world/entity`），过 §6.3 检查 |
| `glob` | 文件名过滤（如 `*Entity*.java`），只许文件名模式：不许 `/`、`..`、`!` 开头 |
| `context` | 每处命中前后各带几行，0–3，缺省 0 |
| `limit` | 最多几处命中，缺省 50、上限 200；超了提示缩小范围 |

输出：`相对路径:行号: 内容`，路径一律相对基准、`/` 分隔——**正好是 `fact_write` 的 `refs[].file` 要的形状**。

```text
mc_source_read({ file, start?, end? })
```

- 读一段，带行号；一次 ≤ 300 行（缺省从 `start` 读 200 行），超了截断并提示
- 输出头一行写明文件总行数，方便定位

调用 ripgrep 的方式：`spawn(rgPath, args, { cwd: 基准目录 })`，参数数组直接传（不经 shell）；固定带 `--no-config`（不读用户的 `.ripgreprc`）、`--no-follow`、`--type java`、`--line-number`、`--no-heading`、`--color never`、`--max-columns 300`（混淆过的超长行截掉）。超时 10 s。

### 6.3 读取边界【P5-D9】

你定过"agent 只能读白名单目录"（`configs/environments/` 里有 API key）。`mc_source_*` 的白名单只有一个目录：源码基准。

| 检查 | 拒绝什么 |
|---|---|
| 不是字符串、空串、含 NUL | |
| 绝对路径、盘符（`C:`）、UNC（`\\`）、以 `/` 或 `\` 开头 | 跳出基准的直接写法 |
| 规范化后任何一段是 `..` | `net/../../configs/…` |
| `path.resolve(基准, file)` 的结果不在 `realpath(基准)` 之下 | 兜底 |
| `fs.realpath` 之后不在基准之下 | 符号链接 / 目录联接（现在没有，防以后） |
| `mc_source_read` / `fact_write`：不是 `.java` 文件 | `META-INF/MANIFEST.MF` 之类 |

- `mc_source_search` 永远以基准为 `cwd`、搜索根是基准或其中经过检查的子目录；`glob` 只能是文件名模式（§6.2），不能用来把搜索范围引到外面
- 基准目录在插件配置里（`facts.sourceRoot`，缺省 `steveX/1.21.11_src`），**不由大模型给**
- 单元测试覆盖上表每一种拒绝，含 `../configs/environments/…`

## 7. 查了源码就要补事实库【P5-D10】

集成方案 §4.4 已定：本回合调用过 `mc_source_search` / `mc_source_read`，却没有调用 `fact_write` → `steer` 提醒"本回合查阅了 MC 源码，请按「完善事实库」skill 总结用到的事实并写入"，正文附该 skill。**不计入**不合法次数；每回合最多一次；大模型说明理由（例如只是确认了一个方法名）后可以结束回合。

实现要定的细节：

- **记录**：guard 放行 `mc_source_*` / `fact_write` 时按 `sessionId#turn` 记一笔。guard 拿不到回合号（§12 #2），回合号取 `agent/pre-step` 里记下的该会话当前回合
- **和请求提醒的先后**：回合结束时先问请求（任务桥 / 快树桥）。**请求还没交 → 只发请求的提醒**，事实提醒等下一次回合要结束时再说；请求交了（或没有请求）→ 再看事实提醒。倾向这样排，免得一次 `steer` 塞两件事、大模型只顾其一
- **范围**：所有回合——规划、展开、修复、复盘、快树反思会话、事实确认、普通问答。普通问答回合里人问"岩浆伤害多少"，大模型查了源码，同样该写进库

## 9. 提示词

| 文件 | 内容 |
|---|---|
| `prompts/requests/fact_check.md` | 事实确认回合的正文：人说的陈述 + 「事实确认」skill |
| `prompts/requests/fact_reminder.md` | §7 的提醒，附「完善事实库」skill |
| `prompts/skills/fact_check.md` | 「事实确认」 |
| `prompts/skills/fact_record.md` | 「完善事实库」 |

「事实确认」只讲**机制和规则**（`agent-learns-not-taught`）：

- 事实库是什么：带源码引用的 MC 事实，`fact_search` 查；源码基准是什么、`mc_source_*` 怎么用
- 先查事实库，库里有且引用有效就不必再查源码
- 结论有三种：源码支持（写入）、源码不支持（回复人源码里实际是怎样，可以把实际情况写成事实）、查不清（说明查到哪一步）
- `fact_write` 的规则：引用的硬约束（§4.2）、同名 `replaces`、相近事实的提示

「完善事实库」讲"写什么"的**格式**要求：一条事实一件事；陈述写"是什么"；引用指向能直接看出这件事的那几行。**不写**：哪些事实值得记、粒度多大、名字怎么起。

## 11. 实施顺序与验收

**顺序**：

1. **P5a 源码**：路径检查、`mc_source_search` / `mc_source_read`、ripgrep 解析（含显式依赖）
2. **P5b 事实库**：`facts/` 的读写与修订、`fact_write` 校验、`fact_search`、`/bt facts`
3. **P5c 回合**：`factInTurn` / `/bt fact`、路由 `fact` handler 真实化、工具准入、§7 的提醒、提示词
4. **P5d 收尾**：文档（集成方案 §5.1.2 表、§9、§10 行；`已实现内容.md`；插件 README）

每步带单元测试（假的 mod + 假的会话）；§6.3 的每种拒绝都有用例。

### 11.1 实现中定下的细节

- **代码位置**：`src/facts/source.js`（`SourceTree`：路径检查、读取、ripgrep）、`src/facts/store.js`（`FactStore`）、`src/tools/facts.js`（四个工具）、`src/llm/fact_turns.js`（`FactTurns`：事实确认回合与提醒）；路由 `fact` handler 调 `ctx.stevexBt.factInTurn`
- **ripgrep 用 `--json` 输出**（不用 §6.2 写的 `--line-number --no-heading`）：路径、行号、命中 / 上下文由结构给出，不用解析冒号；超长行由插件截到 300 字符
- **总是给 ripgrep 搜索路径**（不给 `path` 时传 `.`），stdin 设为 ignore：不给路径时 rg 发现 stdin 不是终端会去搜 stdin，一直等到超时（实测踩到）
- **截断**：命中数到 `limit` 就结束 rg 进程；截断时去掉最后一处命中之后、属于下一处命中的前置上下文。rg 多线程，命中的先后不固定
- **相近事实用"英文词 + 中文二字组"的重合比例**（≥ 30%，至多 3 条），不用 `fact_search` 的按空白拆词：中文陈述没有空白，拆词几乎永远落空（单元测试发现）。`fact_search` 本身仍按 D7 做多词匹配
- **事实确认回合的消息来源是 `{ kind: 'stevex-fact', reason: 'fact-check' }`**：路由只处理 `user` 来源的消息，不会再路由一遍；提醒的 steer 也是 `stevex-fact` 来源但 `reason: 'fact-reminder'`，不触发绑定
- **工具准入的实现**：`bridge.js` 新增 `FACT_TOOLS`（四个），并进 `KNOWLEDGE_TOOLS`——所有请求、快树会话（`FAST_TOOLS` 由它组成）、事实确认回合都带上；普通会话名单本来就是全部工具
- **事实确认回合里被 guard 拒绝时的理由**写"while confirming an MC fact"，不再说"answering an executor request"
- **`mc_source_search` 的 `path` 也可以是单个 `.java` 文件**（DSH 内验收后加，2026-10-27）：大模型把 `path` 指向 `Entity.java` 被拒为 "not a directory"，改用 `glob` 才绕过去；越界检查不变，非 `.java` 文件仍拒绝
- **`fact_write` 的 `source.kind`**：`fact-check` / 请求类型（`plan` / `expand` / `failed` / `reflect` …）/ `fast-reflect` / `chat`

### 11.2 DSH 内验收（不需要进游戏）



| # | 场景 | 通过的标准 |
|---|---|---|
| 1 | `/bt fact 玩家在岩浆里会着火` | 大模型先 `fact_search`（空）→ `mc_source_search` / `mc_source_read` → `fact_write`；`steveX/facts/` 出现一个文件，引用的文件与行号在基准里真实存在、确实讲这件事 |

## 13. 决策点汇总

| # | 位置 | 问题 | 倾向 |
|---|---|---|---|
| **P5-D1** | §2.1 | 入口 | **已定**：`/bt fact <陈述>` 与路由 `fact` handler 都做，共用 `factInTurn` |
| **P5-D2** | §2.3 | 事实确认回合是不是请求 | **已定**：不是：没有必交的提交工具，结论可以是"不写入"；只受 §7 的提醒约束 |
| **P5-D3** | §3.1 | 条目格式 | **已定**：一条一个 JSON，按名字寻址；`statement` + 1–5 条 `refs`（含工具算的内容哈希）+ `tags` + `rev` + `source` |
| **P5-D4** | §3.3 | 修订 | **已定**：同名必须 `replaces: <rev>`；旧版挪进 `history/`；不做删除工具 |
| **P5-D5** | §3.5 | 压缩机制 | **已定**：P5 不做，等条目多了再定 |
| **P5-D6** | §4.2 | 引用校验 | **已定**：基准内 `.java`、行号有效、单条 ≤ 80 行、1–5 条；不做语义判断；写入后附至多 3 条相近事实 |
| **P5-D7** | §5 | `fact_search` | **已定**：多词任一命中、按命中数排序；只返回引用不返回源码；失效引用标出 |
| **P5-D8** | §6.2 | `mc_source_*` 的参数 | **已定**：search：正则 / 字面量、子目录、文件名 glob、0–3 行上下文、≤ 200 处；read：≤ 300 行、带行号 |
| **P5-D9** | §6.3 | 读取边界 | **已定**：只读源码基准；拒绝绝对路径、`..`、跳出基准的链接、非 `.java`；基准目录由配置给，不由大模型给 |
| **P5-D10** | §7 | 查了源码没写事实 | **已定**：所有回合都提醒一次、不计次数；请求还没交时先只提醒请求 |
| **P5-D11** | §8 | 工具准入 | **已定**：`fact_*` / `mc_source_*` 进所有回合（含快树会话的 `fact_write`），改正集成方案 §5.1.2 的表 |
