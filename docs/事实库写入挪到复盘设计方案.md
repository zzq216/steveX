# 事实库写入挪到复盘设计方案

> 状态：**F-S1–F-S4 已实施**（2026-11-23），单元测试通过，待训练中观察效果（§4、§6）。审阅结论：E1–E7 全部按建议执行（E2 选 A；E5 的 a、c 照改，b、d、e 不变）。实施说明见 §7。
>
> 已经确定的方向（2026-11-23 用户确认）：
> - "完善事实库"的提醒不再在规划 / 展开 / 修复回合末尾发，挪到复盘时做；
> - 相应调整复盘的触发条件，保证查过源码的任务都会复盘。

## 1. 起因

2026-11-23 的 3 轮村民交易训练（`task-20261123081955-1`、`-082536-2`、`-083532-3`）里：

1. **写进事实库的内容没经过执行验证，而且写错了。**
   - 第 1 轮规划回合读了交易界面的源码，回合末尾收到"完善事实库"提醒，当场写下 6 条事实。
   - 其中 `merchant.result-quick-move-trades-once` 写的是"Shift 点结算格一次只成交一次"。实际上 `AbstractContainerMenu.doClick` 会循环调用 `quickMoveStack`，付款够几次就成交几次。
   - 那一轮付款只够换 1 次，执行结果"看起来对得上"，错误就留下了，直到第 2 轮复盘才被改正。
2. **提醒拖长了任务会话。**
   - 提醒在树已经提交、开始执行之后才发，又追加几步：第 1 轮 29 秒，第 3 轮 38 秒。
   - 第 1 轮的修复请求还因为规划回合没收尾，多等了 9 秒（"让路"只在提醒发出前生效）。
3. **复盘时手上有执行证据，规划时没有。**
   - 复盘能用 `bt_inspect` 看快照、事件、黑板，能对照源码读到的机制和这次实际发生的事。
   - 第 2 轮的复盘就是这样，用快照里的"付款格 38→2、uses 0→9"纠正了那条错事实。

## 3. 决策点

### E1　规划 / 展开 / 修复回合：不提醒，改成记账

这三类回合（请求类型 `plan`、`expand`、`recover`、`escalate`、`failed`、`died`）调用 `mc_source_search` / `mc_source_read` 时，不再在回合末尾提醒，改为记到这个任务名下：

```
{ tool: 'mc_source_read', file, start, end, requestId, at }
{ tool: 'mc_source_search', pattern, path?, hits, requestId, at }
```

- 记在 bridge 上，按 `taskId` 存。规划回合时任务还没开始，执行器的事件日志写不进去，所以不放在事件日志里。
- 只记位置，不记源码内容和 agent 的结论：复盘时要看原文，自己用 `mc_source_read` 读。
- 普通问答、`/bt fact` 事实确认、快树复盘回合**不变**，仍按 S1 提醒。

**建议：采用。**

### E2　这三类回合还能不能写事实

| 方案 | 做法 | 问题 |
|------|------|------|
| A | 拿掉 `fact_write`，只留 `fact_search` / `fact_get` / `mc_source_*` | 规划时确实看懂了也写不进去，要等复盘 |
| B | 保留 `fact_write`，只是不提醒 | 没经过执行验证的事实照样能写进去（第 1 轮那条错事实也可能是 agent 自己主动写的） |

方案 A 的代价不大：复盘一定会发生（E5），规划时读到的东西复盘时还能写。事实库是所有任务共用的，进库的东西最好都经过一次执行对照。

guard 会拒绝在这三类回合调用 `fact_write`，返回原因"事实在复盘时写（那时能对照这次执行的结果）"。

**建议：A。**

### E3　复盘怎么知道规划时读过哪些源码

复盘另开会话（S5），看不到规划回合的对话。

- **目录加一行**："源码：本任务的规划 / 展开 / 修复回合查过 N 处（`bt_inspect` what: `sources`）"。没有查过就不列这一行。
- **`bt_inspect` 加 `what: 'sources'`**：列出 E1 的记账（文件 + 行号范围 / 搜索模式 + 命中数 + 哪个请求），按时间排。只在复盘回合可用；修复回合没有这个必要，它就在规划的同一个会话里。

这和目录里其他项的用法一样：只列"有什么可看"，看不看、看多少由 agent 决定。不把记账内容预先塞进复盘消息。

**建议：采用。**

### E4　复盘回合末尾的提醒

复盘回合要结束时（`bt_reflect_done` 之后），满足下面全部条件就 steer 一次「完善事实库」：

1. 这个任务的回合查过源码（E1 的记账不为空），**或者**复盘回合自己查过源码；
2. 复盘回合没有成功写过事实。

每个复盘回合至多一次；agent 说明理由（例如"查到的内容不构成事实"）就可以结束，和现在一样。

`fact_reminder.md` 的 `{{when}}` 按来源换成：

- "本任务的规划 / 展开 / 修复回合（目录里的「源码」）"；
- "本回合"；
- 或者两者都有。

正文其余部分不变，`fact_record.md` skill 不变。

**建议：采用。**

### E5　复盘的触发条件

| # | 情况 | 现在 | 改成 |
|---|------|------|------|
| a | done，`onDone = 'changed'`，`doneChanges` 为空（例行重复） | 不复盘 | `doneChanges` 加一条"本任务的回合查过 MC 源码"：查过就复盘 |
| b | failed，人放弃（`by: user`，包括 `/bt train stop`）或会话没了（`by: session`） | 不复盘 | **不变**：人停下的任务不自动复盘（P4-D1），这次查的源码就不会写成事实；需要时可以手动 `/bt reflect` |
| c | `reflect.enabled = false` | 都不复盘 | 退回现在的做法：在规划 / 展开 / 修复回合末尾提醒，`fact_write` 也照旧给这三类回合（E2 不生效）。否则关掉复盘就再也没有地方写事实 |
| d | `reflect.onFailed = false`，任务失败 | 不复盘 | **不变**，这次查的源码不会写成事实。这个开关是人特意关的，缺省为真 |
| e | 训练器多换 / 换错中止（`by: arena`）、超时（`by: timeout`）、agent 放弃（`by: agent`） | 复盘 | 不变 |

a 是必须改的：训练进入稳定期后大量轮次会走"例行重复不复盘"。如果某一轮又去查了源码（例如碰到新职业的新交易），不改的话这次读到的东西就丢了。

**建议：a、c 照改，b、d、e 不变。**

### E6　记录

- 任务历史和训练记录各加两个数：
  - `sourceReads`：任务回合查源码的次数（E1 的记账条数）；
  - `factWrites`：复盘时成功写的事实条数（新写和修订都算）。
- 报告不加列，需要时从记录里看。用来观察 E1–E5 的效果：规划会话的尾巴有没有消失、事实有没有照常写进库。

**建议：采用。**

### E7　提示词和文档

- `bridge.js` 中 `FACT_TOOLS` 的注释改为：`fact_write` 只给复盘、问答、事实确认、快树复盘回合（E2）。
- 复盘 skill（`review.md`）第 37 行已经写了"确认了用 `fact_write` 写成事实"，**不改**。
- 规划 / 展开 / 修复的 skill 本来就没提 `fact_write`，不用改。
- README、`已实现内容.md` 同步。

## 4. 预期效果

| 指标 | 现在（3 轮村民交易） | 预期 |
|------|------|------|
| 规划会话交树后的尾巴 | 提交后的总结 5–10 s，加补写事实 29–38 s | 只剩提交后的总结 |
| 修复请求被规划回合挡住 | 第 1 轮 9 s | 只剩提交后的总结（"提交后结束回合"另议，本方案不含） |
| 事实写入 | 规划时凭读源码写，第 1 轮写错 1 条 | 复盘时对照执行结果写 |
| 复盘耗时 | — | 查过源码的任务会多几步写事实。复盘在另一个会话里，和下一轮之间本来就要等它结束 |

## 6. 验收

1. 规划回合读源码后交树：回合末尾没有"完善事实库"提醒；调用 `fact_write` 被拒，并返回原因。
2. 这个任务的复盘请求目录里有"源码：查过 N 处"，`bt_inspect what: sources` 能列出位置。
3. 复盘没写事实就 `bt_reflect_done`：收到一次提醒；写了就没有提醒。
4. done、例行重复、但规划时查过源码的任务会复盘；没查过的照旧跳过（`reflect/skipped`）。
5. `reflect.enabled = false` 时恢复原来的行为。
6. 普通问答回合、`/bt fact` 回合的提醒和写事实不受影响。
7. 训练记录有 `sourceReads`、`factWrites`。

## 7. 实施说明（2026-11-23）

- **`FactTurns`**（`src/llm/fact_turns.js`）新增 `reviewTasks`、`onTaskSource`、`taskSources`、`onWrite` 四个选项。
  - `note(sessionId, kind, detail)`：查源码时按回合来源判断；是规划 / 展开 / 修复回合，就把 `detail` 记到任务名下，并给这个回合打上"任务回合"标记。
  - 打标记的原因：同一回合里交了树以后，请求绑定已经释放，回合末尾再按来源判断会被当成普通问答，又发出提醒。
- **复盘回合的提醒**（`reviewReminder`）：
  - 文案按查源码的来源换：任务回合、本回合，或两者都有；
  - 复盘回合自己查了源码，同样走"让路"推迟。
- **记账内容**（`src/tools/facts.js`）：
  - `mc_source_read` 记文件和实际读到的行号范围；
  - `mc_source_search` 记搜索模式、`path` / `glob`、命中数和文件数；
  - 查失败的也记，带 `error: true`。
- **Bridge**：
  - 新增 `factsAtReview`、`requestTools(type)`（复盘关掉时给产出树的回合补上 `fact_write`）、`noteSource`、`sourcesOf`、`noteFactWrite`、`factCounts`；
  - `REQUEST_TOOLS` 里规划 / 展开 / 修复的名单不再含 `fact_write`；
  - 记账在复盘结束（同一任务没有别的复盘开着）或任务不复盘时释放；
  - 训练记录的 `sourceReads`、`factWrites` 从请求上的计数累加，不受释放影响。
- **guard**：这三类回合调用 `fact_write` 时，拒绝理由是"在复盘时写，那里能对照这次执行的结果，查过的源码位置在那里列出来"，不用"树要自己读数据"那句。
- **`bt_inspect what: sources`**：
  - 由 `Bridge.inspect` 在复盘回合接住；
  - 别的回合返回"只在复盘回合可看"；
  - 执行器那一层（`evidence.inspect`）走到 `sources` 时返回同样的错误。
- **任务历史**：`metrics` 加 `sourceReads`、`factWrites`。
- **测试**：
  - `facts.test.js`：复盘模式下的 `FactTurns`；
  - `reflect.test.js`：名单、记账、目录、`bt_inspect sources`、例行重复也复盘、记账释放、复盘关掉照旧；
  - `plugin.test.js`：规划回合查了源码交树后不再提醒，`fact_write` 被拒并给出原因，记账带请求 id；
  - 插件 320 条、根目录 320 条通过。
- **同时修了 `container/get` 的 `inputB`**（村民交易训练中发现的）：没有第二种付款物时输出 `null`，不再是 `{ id: minecraft:air, count: 0 }`，和接口说明一致。
