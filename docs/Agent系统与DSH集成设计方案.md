# Agent 系统与 DSH 集成设计方案（草案，待审阅）

> 定义 steveX 的 agent 系统如何搭在 DeepSeek Harness（DSH）上：进程与插件划分、行为树执行器与大模型之间怎么通信、给大模型哪些工具、提示词和 skill 怎么进入请求、两套日志怎么互相定位、任务的生命周期，以及分阶段实施的顺序。
> 本文档只定义**集成层**。节点语义见 [行为树节点设计方案.md](行为树节点设计方案.md)；胶囊库与 Compute 见 [算法层与执行层设计方案.md](算法层与执行层设计方案.md)；路由见 [路由系统设计方案.md](路由系统设计方案.md)；NBT 查询见 [nbt查询api设计方案.md](nbt查询api设计方案.md)；总体蓝图见 [mc_agent.md](../../mc_agent.md)。

## 0. 一句话

**DSH 管"想"，执行器管"做"。** 大模型只在 DSH 的 agent 回合里出现，产出的是**树**（大纲、展开、补丁、胶囊），不直接按键；行为树执行器是 DSH 宿主进程里的一个**常驻服务**，按 tick 跑快树和慢树、直连 mod。两者之间只有两条通道：执行器用 `agent.followup()` **叫醒**大模型，大模型用 `bt_submit_*` 工具**交回**树。

## 2. 进程与插件

### 2.1 进程布局

```
┌──────────────────────────── DSH 宿主进程（npm run dsh -- web）────────────────────────────┐
│                                                                                            │
│   DSH 内核：agent loop · 会话日志 · 工具流水线 · LLM 适配 · Web UI                          │
│                                                                                            │
│   @stevex/dsh-router ── agent/pre-step ──► 填槽 → 选 handler → 注入 skill / 工具准入        │
│                                                                                            │
│   @stevex/dsh-agent                                                                        │
│     ├─ game   ctx.stevexGame   mod 连接 · 命令注册表 · 状态缓存                              │
│     ├─ bt     ctx.stevexBt     执行器（tick 循环）· 编译器 · 校验器 · 黑板 · 任务生命周期      │
│     └─ memory ctx.stevexMemory NBT 查询 · 依赖集 · 事实库 · MC 源码检索 · 胶囊库             │
│                                                                                            │
└───────────────┬───────────────────────────────────────────────┬────────────────────────────┘
                │ ws://127.0.0.1:25550（JSON-RPC）                │ 读文件
                ▼                                               ▼
     采集端 mod（真实世界客户端）  ───── 写 ────►  run/stevex/vision/*.nbt（记忆）
```

**为什么执行器在 DSH 进程里，而不是 steveX 自己的 `npm start` 进程**：

- 执行器要调 `agent.followup()` 叫醒大模型，`Agent` 对象只存在于 DSH 进程里。放在另一个进程就要自己做一层 IPC，再给 DSH 写一个"远程叫醒"插件——多一个进程、多一套协议，没有收益。
- DSH 已经有 Web UI、会话持久化、工具流水线，steveX 的 Express 面板（8090）不必再承担 agent 的人机界面。

**steveX 现有代码的去向**：

| 现有 | 去向 |
|---|---|
| [src/mod/client.js](../src/mod/client.js)（`ModWSClient`）、[methods.js](../src/mod/methods.js) | `game` 子模块**直接复用**（ESM 包 import CJS 模块） |
| [src/nbt/](../src/nbt/)（NBT 查询 API） | `memory` 子模块**直接复用** |
| [src/agent/](../src/agent/)（3 秒轮询）、[src/llm/deepseek_client.js](../src/llm/deepseek_client.js) | **不再用于 agent 路径**。大模型调用全部走 DSH |
| [src/web/](../src/web/)（8090 面板）、[control_panel.html](../control_panel.html) | 保留为**调试工具**。mod 允许多个 WS 连接（已核对 `AgentWebSocketServer.onOpen` 无连接数限制），但面板发按键会和执行器打架——**只在任务暂停时使用** |

### 2.2 插件包

| 包 | 位置 | 内容 | 状态 |
|---|---|---|---|
| `@stevex/dsh-router` | [dsh-plugins/router/](../dsh-plugins/router/) | 槽位路由（已有框架）。本方案把 `task` / `fact` handler 从桩换成真实实现（§6.1） | 阶段 A 已实现 |

**为什么第一版合成一个包（I8）**：三个子模块之间调用密集（执行器要查记忆、记忆要知道当前在飞的请求），拆成三个 Cordis 插件就要先定三套服务接口并处理加载顺序，而接口现在还在变。照 [路由](路由系统设计方案.md) §17.7 的先例：**分层是代码边界，不是包边界**，接口稳定后再拆。

### 2.3 包内分层

## 3. 两个循环

### 3.1 大模型循环（DSH agent 回合）

就是 DSH 原生的 turn / step：领取消息 → 组装提示词与工具 → 请求模型 → 执行工具 → 下一步或结束。steveX 不改它，只通过扩展点（`agent/pre-step`、`agent/turn-stopping`、工具）参与。

**大模型在一个回合里做的事**：读状态、查记忆、查事实与源码、看当前树，最后**提交一棵树**（或补丁、或胶囊）。提交就是回合的产出。

### 3.2 执行循环（`bt` 子模块的 tick 循环）

```
每个 tick：
  1. game 刷新快树要用的状态缓存（轮询集合由快树推出，§3.3）
  2. tick 快树（Match）                         ← 永远在跑，任务挂起时也跑
  3. 按 [行为树] §7.2 的四种情况决定：抢占 / 恢复 / 升级 / 什么都不做
  4. 检查依赖集失效标记（[行为树] §7.6）
  5. 任务树处于 running → tick 任务树
     任务树返回 NEEDS_EXPANSION / 需要恢复 / 依赖失效 / 根失败 → 挂起任务树，向大模型发请求（§4）
  6. 写任务事件日志（§8.2）
```

**两个循环之间没有同步等待**：执行器发出请求后立刻回到 tick（任务树挂起，快树照跑）；大模型的提交在工具执行时被执行器接收，下一个 tick 生效。

### 3.3 tick 来源与状态缓存

- **tick 频率暂不决定**，训练时再调整。第一版由执行器自己的定时器驱动，间隔是 `Config` 项 `tickMs`。
- **mod 目前只有请求—响应**，没有主动推送（已核对 `AgentWebSocketServer`）。
- 已核对的来源：`player` 只含生命 / 饥饿 / 氧气 / 状态标志 / 药水效果 / 属性，**不含坐标**（`PlayerApi.java`）；坐标、朝向、准星目标在 `f3`；背包在 `inventory`。"是否开着容器"不在这三者里，来源待 P0 确认。

**两棵树读状态的方式不同（2026-10-23 定）**：

| | 快树 | 慢树（任务树） |
|---|---|---|
| 什么时候读 | **每个 tick**都要判断全部 `when` | 只在执行到读取点（Condition、`Repeat` 的 `until`）的那一刻 |
| 怎么读 | **轮询缓存**：`game` 后台定时拉，`when` 读缓存（`local_cached`，[行为树](行为树节点设计方案.md) §9.1） | **按需读取**：到读取点时现场问一次 mod |
| 为什么 | tick 内来不及现场问 | 读取时机确定，不必一直拉；而且读到的一定是新的——不会出现"刚合成完、缓存里还是旧背包"的误判 |

**轮询什么由快树决定**：注册表给每个 Condition 标明它读哪个来源（氧气 → `player`，准星目标 → `f3`）。执行器从当前快树全部 `when` 用到的来源推出轮询集合，不需要人配置。**第一版快树是空的（§7.4）→ 完全不轮询**；手写一条"溺水上浮"测试时只拉 `player`。轮询间隔是 `Config` 项，训练时再调。

**按需读取不能卡住 tick**：执行到读取点时先发出请求，任务树本 tick 返回 `RUNNING`（读取点本身的结果还没出来）；期间快树照常 tick；数据回来后的下一个 tick 再用新数据求值该 Condition。

- 将来 mod 加推送时只改 `game` 的数据来源，Condition 与执行器不变。

~~**【审阅点 1】** 第一版各状态来源的轮询频率。~~ **已由上表解决（2026-10-23）**：轮询集合由快树推出，慢树按需读取。

## 4. 执行器 ↔ 大模型的通信

### 4.1 叫醒：`followup` + 自定义来源（I3）

执行器需要大模型时，调用该任务所属会话的 `agent.followup(message)`：

- DSH 语义：`followup` 排入一个**新回合**并唤醒 agent（[runtime-types.d.ts](../node_modules/@deepseek-ai/dsh-agent/lib/types/runtime-types.d.ts) `followup()`）。agent 正在跑别的回合（比如人正在聊天）时，它在收件箱里排队，不打断当前回合。
- **消息来源用自定义 kind**：DSH 的 `MessageSourceMap` 是可合并扩展的（[message.d.ts](../node_modules/@deepseek-ai/dsh-llm/lib/types/message.d.ts)），我们声明 `{ kind: 'stevex-bt', taskId, requestId, reason }`。
- **路由插件只对 `kind === 'user'` 的消息填槽**。执行器发来的请求已经知道自己是什么（展开 / 恢复 / 反思……），不需要路由猜；对应的 skill 由执行器自己放进消息（§6.2）。这是对 [dsh-plugins/router/src/index.js](../dsh-plugins/router/src/index.js) 的一处改动：`agent/pre-step` 里先看来源。
- 消息带 `form: 'notice'` 和一行 `summary`（如"展开节点 n1.3：下到 y=16 附近的矿层"），DSH Web UI 里折叠显示，展开可看全文。

**为什么不用 `steer` / `inject`**：`steer` 会插进正在进行的回合，人正在问别的事时会被打断；`inject` 不唤醒 agent，空闲时请求会一直挂着。执行器的请求是**独立的一件事**，就该是独立的回合。

### 4.2 展开请求（`NEEDS_EXPANSION`）

```
执行器                                          大模型（新回合）
  │ 任务树到达 PendingExpansion n1.3
  │ 挂起任务树，建 request r7
  │── followup ───────────────────────────────►│ 消息：goal + 树概览（带 id）+ 黑板形状
  │                                            │       + skill「慢树展开」（不附当前状态，I13）
  │                                            │ 调 command_docs / capsule_* / bt_view …
  │◄── bt_submit_expansion(r7, subtree) ───────│
  │ 编译 + 校验
  │   不通过 → 工具结果返回错误原文 ──────────►│ 修正，再次提交（同一回合内）
  │   通过   → 挂上子树（id 前缀 n1.3）
  │            工具结果：ok + 新子树的 id 列表 ─►│ 回合结束
  │ 下一个 tick 恢复任务树
```

- **校验错误作为工具结果返回**，大模型在**同一回合**里修正——不需要执行器再发一次 `followup`。
- **3 次上限**（[行为树](行为树节点设计方案.md) §4.3）由执行器按 request 计数：同一个 `requestId` 第 3 次不合法 → 任务失败（§7）。

### 4.3 恢复请求（快树情节结束）

快树命中真实 arm 并返回 `SUCCESS` → 执行器发恢复请求。消息附 [行为树](行为树节点设计方案.md) §6.5.2 的三样证据：被中断的最小任务（`Steps` 的命令或原语及参数）、前置 Condition 的求值结果、中断前后的世界差异。skill：「慢树恢复」。

大模型用 `bt_submit_patch` 交回补丁（`replace` / `insert-after` / `remove`，[行为树](行为树节点设计方案.md) §8.4），或交一个**空补丁**表示"原树继续"，或调用 `bt_abort_task` 放弃任务。

### 4.4 必须以提交结束回合（I5）

执行器发出的每个请求都在等一个提交。大模型如果只说了话、没调提交工具就要结束回合：

- `bt` 监听 `agent/turn-stopping`，发现本回合对应的 request 仍未被回答 → 调 `agent.steer()` 发一条提醒（"请用 bt_submit_* 提交，或 bt_abort_task 放弃"）。DSH 在回合边界会重读收件箱，有新的 steer 就再跑一步（[runtime-types.d.ts](../node_modules/@deepseek-ai/dsh-agent/lib/types/runtime-types.d.ts) `agent/turn-stopping` 注释）。
- 这次提醒**算一次不合法尝试**，计入 3 次上限。
- 人发起的回合（`kind: 'user'`）不受这条约束——人可能只是在聊天。**例外（P1 实现时定）**：路由 `task` handler 在人发起的回合里登记了规划请求，这个回合就绑定了该请求，同样受提醒约束——它已经被判定为"要做事"，不是闲聊。

**回合出错**（第二次首测后补）：回合以错误结束（如模型返回了坏的工具参数 JSON，`MALFORMED_RESPONSE`）时不经过 `agent/turn-stopping`，请求会一直挂着、挡住后面的任务。`agent/error` 监听接住：绑定了请求的回合出错 → 算一次不合法尝试，用 `followup` 开一个新回合重试（消息附错误原文，来源带同一个 `requestId`，新回合重新绑定）；次数用完 → 规划作废 / 任务失败。

**查了源码就要补事实库（2026-10-24 定）**：同一个 `agent/turn-stopping` 监听还检查一件事——本回合调用过 `mc_source_search` / `mc_source_read`，却没有调用 `fact_write` → `steer` 提醒"本回合查阅了 MC 源码，请按「完善事实库」skill 总结用到的事实并写入"，提醒正文附该 skill。对**所有**回合生效（任务、展开、恢复、事实问答），因为"事实库里没有、只好查源码"在哪类回合里都可能发生。这条提醒**不计入** 3 次上限；每回合最多提醒一次，大模型若判断查到的内容不构成事实（例如只是确认了一个方法名），可以说明理由后结束回合。

### 4.5 一个任务至多一个在飞请求（I4）

请求在飞时（大模型还没提交），执行器可能又遇到新事件：又被快树打断了一次、依赖集又失效了。

规则：

1. **不发第二个请求。** 新事件记进任务事件日志，并标记当前请求**过期**。
2. 大模型提交时，执行器检查请求是否过期。过期 → **拒绝这次提交**，工具结果返回"世界已变化"+ 新事件的证据，大模型在同一回合里基于新证据重做。**拒绝不计入 3 次上限**——不是大模型写错了。
3. 不调用 `agent.cancel()` 打断在飞的回合：取消会丢掉大模型已经查到的东西，而且取消后的回合边界处理比"拒绝提交"复杂得多。

这条同时回答了 [行为树](行为树节点设计方案.md) §6.5.2 的待定项"恢复请求在飞行中时又被抢占：丢弃旧请求还是排队"——**都不是，是让旧请求过期、由提交时的检查兜住**。

### 4.6 其余请求类型

| 触发 | 请求 reason | 附带证据 | skill | 期望的提交 |
|---|---|---|---|---|
| 新任务（人下指令） | —（由路由 `task` handler 在人发起的回合里处理，不经 `followup`） | 指令 + 当前状态 | 「慢树大纲」 | `bt_submit_tree` |
| `PendingExpansion` | `expand` | §4.2 | 「慢树展开」 | `bt_submit_expansion` |
| 快树情节结束 | `recover` | §4.3 | 「慢树恢复」 | `bt_submit_patch` / `bt_abort_task` |
| ~~依赖集失效~~ | ~~`invalidated`~~ | ~~哪些依赖变了、变成什么~~ | ~~「慢树恢复」~~ | 2026-10-25 删除（§5.3） |
| 快树命中 arm 但返回 `FAILURE` | `escalate` | 命中的 arm、当前状态 | 「慢树恢复」 | 同上 |
| **死亡**（2026-10-24 新增） | `died` | 死亡前后的背包与坐标、死因（若有）、当时运行的节点 | 「慢树恢复」 | 同上 |
| 任务树根 `FAILURE`（§7.5 ① 之后） | `failed` | 失败节点、mod 错误原文、当前状态 | 「慢树反思」 | `bt_submit_patch` / `bt_abort_task` |
| 任务结束（成功或失败） | `reflect` | 任务事件日志摘要、树的版本链 | 「慢树反思」 | `capsule_save`（可多次）后 `bt_reflect_done` |

**死亡的处理顺序**：执行器检测到死亡（生命值为 0 或出现死亡界面）→ 任务树走默认中止流程 → 执行器**自动**调用 `respawn` 原语（[行为树](行为树节点设计方案.md) §9.4）→ 重生完成后发 `died` 请求。重生由执行器做而不交给大模型：它是唯一的正确动作，不需要规划。死亡同时作为高信息量事件进快树事件流（§7.4.2）。

快树的反思与进化**不在本表里**：它不走任务会话、也不经路由，由执行器在独立的反思会话里触发，见 §7.4（2026-10-23 更正：原写"第一版不做"是错的——**不做的只是"人用自然语言指导快树"的路由**，快树进化本身是 agent 的一部分）。

#### 5.1.0 任务内代码草稿（2026-10-24 新增）

大模型在**规划时**（新任务、`expand`、恢复）就可以写新的 Compute 代码，不必等到反思：

- 三个提交工具（`bt_submit_tree` / `bt_submit_expansion` / `bt_submit_patch`）带一个可选的 `code` 字段：`{ 名字: { signature, body } }`，格式与胶囊库的代码条目相同（[算法层](算法层与执行层设计方案.md) §8.2），只是不进库
- 草稿存在 `steveX/runtime/tasks/<taskId>/code/`，树里用 `task/<名字>` 引用（前缀 `task/` 与 `code/` / `trees/` 并列）。**只在本任务内可引用**，任务结束即不可再用
- 校验与运行完全照库条目：静态校验 `signature`，在同一个沙箱里跑，同样的预算（[算法层](算法层与执行层设计方案.md) §3.3 / §3.4）
- 草稿可以在后续提交里**覆盖**（同名重写），树版本链记录每一版
- **转正**：任务结束的反思里，大模型用 `capsule_save` 把好用的草稿存进胶囊库，此后变成 `code/<名字>@hash`。这就是"没审查过的代码只活在当前任务里"——审查方案将来落在转正这一步

#### 5.1.1 `mod_query`：直接用 mod API（2026-10-23 改）

原设计的 `mc_state` 是一个自定义的"玩家状态"聚合工具，**已删除**——读状态直接用 fabric mod 已有的 API，没有理由再包一层：

- **一个工具、透传方法**：参数是 `{ method, params }`，与 steveX 现有的 `/api/mod/:method` 透传同构。方法的说明与参数 schema **从 [methods.js](../src/mod/methods.js) 生成**，mod 加了方法这里自动跟上，不维护第二份文档
- **只放行只读方法**（白名单按 `methods.js` 的 `category` 与方法名定）：

  | 放行 | 方法 |
  |---|---|
  | `query` 类 | `player` / `inventory` / `f3` / `sound` / `profiler` |
  | 其他只读 | `status` / `tablist` / `settings/get` / `container/get` / `sign/get` / `book/get` / `vision/entity` |

- **不放行**：所有 `key/*` / `camera/*` / `container/slot` 等有作用的方法（I2：对世界的作用只能经过树）；以及 **`vision/snapshot`**——它虽然是感知，但会写记忆文件，属于采集循环的职责，不该由大模型在回合里随手触发
- 读到的是**实时值**，和 Condition 读玩家自身状态是同一个来源（[行为树](行为树节点设计方案.md) §4.1）。方块与实体照旧走 `nbt_query` 查记忆

执行器自己的状态缓存（§3.3）也是轮询这几个 mod 方法，和 `mod_query` 共用 `game` 里的同一个连接。

| 请求 | 共用的读 / 查工具 | 专有工具 |
|---|---|---|
| 新任务（`task` handler） | `command_docs` · `data_shapes` · `capsule_*` · `fact_search` · **`mc_source_*`** | `bt_submit_tree` · **`fact_write`** |
| `expand` | 同上 + `bt_view` | `bt_submit_expansion` · **`fact_write`** |
| `recover` / `invalidated` / `escalate` / **`died`** | 同上 + `bt_view` | `bt_submit_patch` · `bt_abort_task` · **`fact_write`** |
| **`failed`（慢树反思，任务中）** | 同上 + `bt_view` · **`bt_history`** | `bt_submit_patch` · `bt_abort_task` · **`fact_write`** |
| **`reflect`（慢树反思，任务结束）** | 同上 + `bt_view` · **`bt_history`** · `mc_source_*` | **`capsule_save`** · `fact_write` · `bt_reflect_done` |

| **普通问答 / 事实问答**（路由 `default` / `fact`，不产出树） | `mod_query` · `nbt_query` · `json_query` · `command_docs` · `capsule_*` · `fact_search` · `mc_source_*` | `fact_write`（`fact`） |

上表产出树的各行都**不含** `mod_query` / `nbt_query` / `json_query`（2026-10-24，I13，见 §5.1.3）。

**规划时也能查源码、写事实（I10，2026-10-24）**：目标流程要求"获取已知信息"时就能查 MC 源码，查了源码说明事实库里缺这条信息，要当场调用「完善事实库」skill 补进去。因此所有规划类请求都准入 `mc_source_*` 与 `fact_write`（上表加粗处）。触发规则见 §4.4。

**规划时可以写新代码（I11）**：上表的提交工具（`bt_submit_tree` / `bt_submit_expansion` / `bt_submit_patch`）都可以附带代码草稿，见 §5.1.0。

**慢树反思与快树反思是对称的**：都有"看事件"（`bt_history` / `fast_events`）、"看树"（`bt_view` / `fast_view`）、"提交"、"结束"四件套。区别只在提交的东西——慢树反思把任务里好用的子树和代码**存进胶囊库**（`capsule_save`，对应 [mc_agent.md](../../mc_agent.md)"提取合适的慢树模块和 ts 代码，保存以复用"），快树反思**改快树本身**（`fast_submit_patch`）。原因是慢树每个任务重新生成、用完即弃，值得留下的只有可复用的部分；快树全局唯一、长期演进，反思的产物就是它的下一版。

#### 5.1.3 产出树的回合不给数据（I13，2026-10-24）

**树要用到的数据，必须由树自己读取。** 理由：

- **可复用**：大模型规划时看到"原木在 36 号格"，就会写出 `container/slot {slot: 36}`。这棵树只对那一次成立，提取成胶囊后换个背包布局就失效；训练要产出的可复用高层动作因此无从谈起。查询与读取写在树里（`compute core.json.query` → `compute` 算点击计划 → `forEach` 点击），物品名、格子号就都是参数或 `$键`，子树天然可参数化
- **判断进树**：看不到现状，大模型只能把"有工作台吗"写成 `sel` + `cond`，而不是自己看一眼再决定。带判断的子树才能换场景复用
- **新鲜**：树里的读取发生在执行到那一步时，不会用规划时就已过期的数据
- **可反思**：查询作为节点留在事件日志与树版本链里；直接调工具的查询只在会话日志里，提取胶囊时拿不到

做法：

1. **工具准入**：规划、展开、恢复、反思（含快树反思）的回合不准入 `mod_query` / `nbt_query` / `json_query`（§5.1.2）。普通问答回合照常准入——用户问"我血量多少"不写树，不存在复用问题
2. **请求里不附当前状态**；**黑板只给形状**（类型、结构、列表长度，不给值）。`bt_view` 同样只给形状
3. **skill 写明"先读后展开"**：缺信息就把读取写成第一条路径上的具体节点，读到的结论写进黑板，依赖结论的部分留成 `expand`；黑板值一律 `$键` 引用。代价是多一次展开往返，可以接受
4. **结构与词表要给（第三次首测后补，2026-10-24）**：只禁不给会逼模型猜——日志里它已经把配方查询写进了树，却仍去调 `json_query`，因为同一次提交里还要写处理配方记录的代码，得知道 `pattern` / `key` 的格式；写界面判断时又因为不知道工作台界面的 `container.type` 是什么，只好用正则 `/craft/` 猜。所以模型能看到的信息分三类：

   | 类别 | 例子 | 给不给 | 理由 |
   |---|---|---|---|
   | **结构** | `pattern: list of string`、`key: map<字符, list of string>` | 给 | 写代码必需，与某一次实例无关 |
   | **词表**（枚举型字段的取值范围） | `container.type ∈ {none, inventory, crafting, furnace…}`、`recipe.type ∈ {shaped, shapeless}` | **给** | 可复用的树本来就要拿这些常量比较（`type === 'crafting'`），它们是接口的一部分 |
   | **实例值** | 原木在 36 号格、背包里有 5 块、某个坐标、木镐配方的具体图案 | 不给 | 抄进树里就无法复用 |

   落在 `data_shapes`：状态来源的词表是**静态表**（`game/vocab.js`，按 mod 与 MC 源码列出并注明出处——一次快照只看得到当前那一个值，统计不出范围）；白名单 JSON 是静态参考数据，词表从全量记录**统计**（不超过 16 种取值的字符串字段列全部取值，多的只给种数）；记忆世界是世界状态，从中统计出的"取值"（附近有哪些实体）是实例值，**只给结构**。配套：规划 / 展开请求正文开头写明本回合不能调用的三个工具；守卫的拒绝理由给出树里的等价写法并指向 `data_shapes`
5. **仍有具体值的地方**：P2 的恢复 / 失败请求要附中断前后的状态差异、mod 错误原文；快树反思的 `fast_events` 要附情节前后的状态。这些是判断"出了什么问题"必需的证据，不能去掉。所以"不写死"最终的关口在**保存胶囊时**（P4 `capsule_save`）：提取子树时检查本该是参数的值是否被写成了常量（例如与当时黑板或证据里的值相同的字面量），具体规则在 P4 定

**没有任何按键 / 点击工具。** 大模型对世界的一切作用都要经过树：这是行为树设计的前提（可中止、可恢复、可回放），也让"模型做了什么"只有一条记录路径。

**【审阅点 3，已定 2026-10-23】** 调试时偶尔需要让大模型"直接按一下"：**第一版不给**；真需要时由人用 steveX 面板（8090）操作。

### 5.2 工具的实现约定

### 5.4 DSH 内置工具的处理

steveX 的 agent 不是编程助手，DSH 默认装载的大量工具对它是噪声，甚至是风险（`bash` / `pwsh` / `write` / `edit` 能改本机文件）。`@stevex/dsh-profile` 用 `ctx.tools.restrict` 只放行：

| 保留 | 理由 |
|---|---|
| steveX 的全部工具（§5.1） | — |
| `ask_user_question` | 任务指令不清时追问人 |
| `todo_write` | 可选：大模型在长回合里自己记步骤 |

其余（shell、文件读写、web、subagent、workflow、`skill`……）第一版全部关闭。

**实现（2026-10-24，DSH 内首测后修订）**：首测发现只靠 `restrict` 不够——会话默认用 DSH 的 `standard` 预设，它在 agent 层装上编程工具；`restrict` 挡住了大部分，但 `subagent`（预设里 `delegation` 组件在隔离作用域里延迟注册）不受限制，模型真的派了一个能读写工作区的子 agent。现在是三层：

| 层 | 做什么 | 管什么 |
|---|---|---|
| 预设 `stevex`（profile 包定义，设为默认） | 只装人设、`ask_user_question`、`todo_write`、上下文压缩；人设换成 steveX（原预设开头是 "You are a coding agent"） | 从源头不装 |
| `planner.exclusiveTools` | 每个会话 `restrict` 到 steveX 工具 + `extraTools`，**整个会话不变** | 模型看得见什么 |
| 工具守卫（`ctx.tools.guard`） | 不在名单里的调用一律拒绝；绑定了请求的回合按该请求的名单（I13） | 模型调得动什么——兜住漏过可见性限制的工具；**§5.1.2 的按请求准入也由它执行** |

**按请求准入不用 `restrict`（第二次首测后改）**：DSH 在 `agent/pre-step` 之前就组装好了本步的工具清单，pre-step 里设的 `restrict` 要到下一步才生效（日志：每个请求回合第 1 步仍是全集，第 2 步才移除，回合结束又加回）；而且工具清单每个请求回合变两次，会断 KV 缓存前缀（§6.3）。所以工具清单整个会话保持不变，请求回合里不该用的工具由守卫拒绝，拒绝理由里写明此刻允许哪些。代价是模型偶尔多一次被拒的调用。

预设只对新建会话生效（会话保存创建时的预设）。

**用户命令要声明 `input`**：DSH Web 输入框里，没有 `input` 的命令只在单独输入（`/bt`）时执行，带参数（`/bt task …`）会被当作普通消息发给模型。`/bt` 已声明 `input.hint`。

**【审阅点 5，已定 2026-10-23】** `mc_source_search` / `mc_source_read` **自己写**：包一层 ripgrep，路径限定在源码基准目录（§9）。不复用 DSH 的 `grep` / `read`——它们与会话 `cwd` 和沙箱策略绑定，限定范围要动 profile 的沙箱配置，比写一个薄工具麻烦。

## 6. 提示词与 skill

### 6.1 路由 handler 的真实实现

[路由](路由系统设计方案.md) 阶段 B 的内容，本方案只定它和 agent 的接口：

| handler | 在人发起的回合里做什么 |
|---|---|
| `task` | 登记新任务与 request（§5.3）；注入「慢树大纲」skill；准入提交类工具。回合内大模型调 `bt_submit_tree`，执行器开始跑 |
| `fact` | 注入「事实确认」skill；准入 `fact_search` / `mc_source_*` / `fact_write` |
| `default` | 正常回答；只准入读状态 / 查知识类工具 |
| `clarify` / `unsupported` | 不变 |

**新任务与正在跑的任务冲突**（任务串行，D12）：`task` handler 发现已有任务在跑时，第一版**不自动替换**，而是回复人"当前任务是 X，要放弃它吗？"。人确认后由 `bt_abort_task` 放弃旧任务。

### 6.2 skill 的放法（I6）

| skill | 何时进请求 | 由谁放 |
|---|---|---|
| 慢树大纲 | 新任务 | 路由 `task` handler（`agent.inject` / 回合作用域的提示词分段，[路由](路由系统设计方案.md) §17.5） |
| 慢树展开 | `expand` 请求 | 执行器，写在 `followup` 消息正文里 |
| 慢树恢复 | `recover` / `invalidated` / `escalate` | 执行器，同上 |
| 慢树反思 | `failed` / `reflect` | 执行器，同上 |
| 事实确认 | 路由判出事实 | 路由 `fact` handler |

**「慢树大纲」与「慢树展开」的写法约定（2026-10-24 定，内容层必须写进 skill 正文）**：一轮只沿**第一条路径**拆到底，其余全部留成 `expand`。例：任务拆成子任务 1–4 → 只拆子任务 1，得到子子任务 1–4 → 拆不动了 → **只把子子任务 1 写成具体节点**，子子任务 2–4 与子任务 2–4 全部是 `expand`：

```
Sequence 任务
├─ Sequence 子任务1
│   ├─ 子子任务1          ← 具体节点
│   ├─ expand 子子任务2
│   ├─ expand 子子任务3
│   └─ expand 子子任务4
├─ expand 子任务2
├─ expand 子任务3
└─ expand 子任务4
```

整条路径在**一个回合**里想完、一次提交，提交后立即可以执行。展开请求用同样的写法：交回的子树里可以再带 `expand`，于是这套做法逐层递归。单次提交的节点数上限（[行为树](行为树节点设计方案.md) §8.5，初值 15）按这个形状估计够用，训练时观察。

**不用 DSH 的 `skill` 工具让大模型自己挑。** 每个场景该用哪个 skill 是确定的（路由判出来的，或执行器知道自己发的是什么请求），交给大模型挑只会多一次出错机会。skill 正文放在 `prompts/skills/*.md`，与代码分离，改内容不改代码。

### 6.3 常驻系统提示词

用 `ctx.systemPrompt.section`（[dsh-system-prompt/lib/types/index.d.ts](../node_modules/@deepseek-ai/dsh-system-prompt/lib/types/index.d.ts)）注册，按顺序：

1. **身份与边界**：你在真实客户端里，只知道自己见过的世界；对世界的一切作用都要写成树
2. **树的编写格式速查**（[行为树](行为树节点设计方案.md) §8.5 的映射表 + 一个完整例子）
3. **语义原语清单**（名字 + 一句话；详细参数用 `command_docs` 查）
4. **胶囊库 manifest 摘要**（按任务类型分片，[算法层](算法层与执行层设计方案.md) §8.7）

**动态内容不进系统提示词**：当前状态、当前树、黑板都通过工具读或写进请求消息。系统提示词只放很少变化的东西，保护 DSH 的 KV 缓存前缀（[DSH 功能总结](deepseek-harness功能总结.md) §3.4"缓存前缀是性能红线"）。

## 7. 任务生命周期

### 7.1 状态机

```
            人下指令（task handler）
   idle ──────────────────────────► planning ──bt_submit_tree──► running
    ▲                                                              │  ▲
    │                                     NEEDS_EXPANSION / 恢复 / │  │ 提交通过
    │                                     依赖失效 / 根失败         ▼  │
    │                                                          suspended
    │                                                              │
    │        ┌──────────── 根 SUCCESS ─────────────────────────────┤
    │        │             3 次不合法 / bt_abort_task / 无法恢复 ──┤
    │        ▼                                                     ▼
    └──── reflecting ◄──────────────────── done ／ failed ◄────────┘
     bt_reflect_done
```

**2026-10-26（P4-D3）**：`reflecting` 不是执行器状态，是 bridge 里一个在飞的 `reflect` 请求；执行器的任务停在 `done` / `failed`，不挡新任务（[P4实施细则.md](P4实施细则.md) §2.3）。

| 状态 | 快树 | 任务树 | 大模型 |
|---|---|---|---|
| `idle` | **跑** | 无（「0」，D12） | 只在人说话时工作 |
| `planning` | 跑 | 无 | 写大纲 |
| `running` | 跑 | tick | 空闲 |
| `suspended` | 跑 | 挂起（不 tick，游标保留） | 有一个在飞请求 |
| `done` / `failed` | 跑 | 冻结，存档 | — |
| `reflecting` | 跑 | 冻结 | 反思，可能存胶囊 |

**快树在所有状态下都跑**——它是安全兜底，与有没有任务无关。

### 7.2 任务与会话的绑定

- 一个任务**属于发起它的 DSH 会话**；执行器的 `followup` 只发给这个会话的 agent（`ctx.agents.get(sessionId)`）。
- 一个会话里可以先后跑多个任务（一棵慢树 = 一个任务，不是一次对话，D12）。
- **第一版只支持一个身体**（一个 mod 连接）、同时一个任务。

**【审阅点 6，已定 2026-10-23】** 会话被关掉（DSH Web UI 里关了这个会话）而任务还在跑：执行器找不到 agent → **任务立即进入 `failed`**，走默认中止流程并记日志；**不尝试 `resume` 会话**。此时没有会话可发反思请求，任务不进 `reflecting`。

### 7.3 人的控制

用 `ctx.commands` 注册用户命令（不需要模型回合即可执行）：

| 命令 | 作用 |
|---|---|
| `/bt status` | 当前任务状态、树概览、在飞请求 |
| `/bt pause` / `/bt resume` | 暂停 / 继续任务树（快树照跑）。暂停期间可以用 8090 面板手动操作 |
| `/bt abort` | 放弃当前任务（走默认中止流程，不进反思） |
| `/bt run <file>` | 跑一棵手写的树文件，不经大模型（阶段 P0 的主要入口，§10） |

### 7.4 快树与快树进化（I9，2026-10-23 更正）

**快树进化是 agent 的一部分**，对应 [mc_agent.md](../../mc_agent.md) 的"获取快树执行过程的完整信息 → 合并相似突发事件 → 反思并优化快树（限制并行数量）"。第一版不做的只是**路由层的"快树指导意见"**——即人用自然语言直接改快树（[路由](路由系统设计方案.md) 已定排除）。快树进化由**执行器触发**，不经路由。

#### 7.4.1 装载

执行器装载 `src/bt/trees/fast/` 版本链的最新版；没有文件时用**只有 `otherwise` 的空 `Match`**。可以手写一两条反射（溺水、着火）作为初始版本。

#### 7.4.2 事件：什么会被记下来

执行器把快树相关的事件写进**快树事件流**（`steveX/runtime/fast/events.jsonl`，跨任务累积，与任务无关）：

| 事件 | 信息量 | 说明 |
|---|---|---|
| 命中真实 arm + `FAILURE` | **高** | 认出了局面但处理不了 |
| **命中 `otherwise` 期间受伤 / 死亡** | **高** | 快树**没认出**局面——这是"新增 arm"的唯一来源。判据：生命值下降或死亡，且下降发生时快树命中的是 `otherwise` |
| 命中真实 arm + `SUCCESS`，但情节中仍受伤 / 死亡 | 中 | 处理了，但处理得不好 |
| 命中真实 arm + `SUCCESS`，毫发无伤 | 低 | 只计入该 arm 的命中统计，不进反思批次 |

每条事件带情节前后的玩家状态（生命、饥饿、氧气、坐标、手持）、命中的 arm 与快树版本号、当时的慢树任务 id（若有）。**每 tick 的空闲状态不记**（T9 约束 5）。

#### 7.4.3 触发：批量、合并、限流

按 [目标Agent画像.md](目标Agent画像.md) T9 的已定约束：

- **批量**：事件只记录不立即反思。攒够 `Config.fastBatchSize` 条高 / 中信息量事件，或任务结束、或进入 `idle` 时，打成一批
- **合并相似事件**：由**批次窗口隐式完成**——同一批里的事件一起交给大模型，由它判断哪些是同一种局面。不写相似度算法
- **限制并行**：同时在飞的快树反思会话不超过 `Config.fastReflectMaxParallel`（初值 **1**）；超出的批次排队
- **排序**：批次内按信息量从高到低排列（上表），超出提示词预算时从低端截断

#### 7.4.4 在哪里跑：独立的快树反思会话

快树反思**不发给任务会话**，而是用 `ctx.agents.create()` 开一个**专用会话**：

- 任务会话一次只允许一个在飞请求（I4）。快树反思要是排在里面，会挡住慢树的展开与恢复——这正是 mc_agent.md 原写法"快树暂停 → 反思"的那个问题，换了个地方重现
- 快树反思不需要慢树的上下文；放在任务会话里只会污染慢树的上下文、挤占 KV 缓存
- 会话里只准入 `fast_*` 工具与接口知识工具（`command_docs` / `fact_search` / `mc_source_*`；2026-10-24 去掉 `mod_query`，I13），skill 为「快树反思」+「快树生成」，由执行器写在消息正文里（同 §6.2）

#### 7.4.5 落盘：门槛与版本

大模型用 `fast_submit_patch` 提交。执行器的处理：

1. **校验**（在 [行为树](行为树节点设计方案.md) 校验器之上，快树专有的规则）：
   - `when` 只能用 `cost: local_cached` 的命令（原语白名单，T9 约束 4）
   - arm 的 `then` 里**不得出现 `PendingExpansion`**——快树运行时没有大模型（[行为树](行为树节点设计方案.md) §7.1）
   - 不读写黑板；根必须是 `Match` 且 `otherwise` 存在
2. **版本冲突**：补丁写明基于哪个版本。基于的不是最新版 → 拒绝，工具结果附上最新版与两版差异，让它在新版上重做（与 I4 的"过期即拒"同一思路；同时满足 T9 约束 3"对同一棵树的写操作串行化"）
3. **门槛：没有人审，校验通过即自动落盘**（2026-10-24 改）。`add-arm` / `modify-arm` / `remove-arm` 一视同仁，各生成一个新版本。

   > 原设计（T9）是"`add-arm` 自动、`modify-arm` / `remove-arm` 进待审队列"。改为全自动的理由：快树的纠错闭环（§7.4.2 的事件 → 下一批反思 → 修改或删除 arm）里只要有一步要人点头，进化就会卡在人身上。安全网改由**版本回滚**承担（下面第 5 条）。代价：一个改坏的 arm 会一直生效到下一批反思发现它，或人手动回滚。

4. **生效时机**：新版本在下一个 tick 边界换上；**快树正在一个情节里（命中真实 arm 且 `RUNNING`）时不换**，等情节结束
5. 每个版本都可回滚：`/bt fast rollback <version>`

| 命令 | 作用 |
|---|---|
| `/bt fast status` | 当前版本、最近的补丁、排队的批次 |
| `/bt fast log` | 版本链：每一版的补丁内容、理由、来自哪一批事件 |
| `/bt fast rollback <version>` | 回滚到指定版本 |

**【审阅点 2，已定 2026-10-23】`add-arm` 的插入位置**：由大模型在补丁里**指定位置并写明理由**，不论插在哪里都**自动落盘**，不因"插在已有 arm 之前"而另设门槛。

`Match` 是"第一个为真者胜出"，新 arm 插在前面可能抢走已有 arm 的命中。这不在落盘时防，而交给**后续的快树反思自己迭代纠正**：被抢走命中的局面若处理得更差，会以"命中真实 arm 但 `FAILURE`"或"情节中受伤 / 死亡"的事件出现在之后的批次里（§7.4.2），由大模型判断要不要调整 arm 的 `when` 或位置。为了让它看得出"抢占"，`fast_view` 的命中统计按**快树版本**分列：同一个 arm 在新版本里命中数骤降，就是被前面的 arm 抢了。

**【审阅点 9，已定 2026-10-23】** 自动落盘的 `add-arm` **不先跑回归测试**。效果不好的 arm 同样由**后续的快树反思**发现并改进或删除；严重时人用 `/bt fast rollback` 回滚。

### 7.5 崩溃与重启

第一版**不恢复中断的任务**（[行为树](行为树节点设计方案.md) §11"黑板持久化暂不涉及"）。宿主进程重启后：执行器起来是 `idle`；上一个任务的事件日志和树版本都在磁盘上，可以查，但不续跑。

## 8. 日志与定位（I7）

### 8.1 两套日志

| 日志 | 记什么 | 谁写 | 在哪 |
|---|---|---|---|
| **DSH 会话日志** | 大模型看到的每条消息、每次工具调用与结果 | DSH（原生） | `~/.dsh/sessions/` |
| **任务事件日志** | tick 级事件：节点进入 / 返回码、抢占、恢复、依赖失效、请求发出 / 被回答 / 过期、提交通过 / 被拒 | `bt` | `steveX/runtime/tasks/<taskId>/events.jsonl` |
| **快树事件流** | 快树情节与 `otherwise` 下的受伤 / 死亡（§7.4.2）；每条带快树版本号与当时的 `taskId` | `bt` | `steveX/runtime/fast/events.jsonl`（跨任务累积） |
| **树版本链** | 每次提交后的完整执行格式树（[src/bt/README.md](../src/bt/README.md) T4 的流式写入） | `bt` | `steveX/runtime/tasks/<taskId>/trees/v<N>.json` |

### 8.2 互相定位

| 从 | 到 | 靠什么 |
|---|---|---|
| 会话日志里的一次提交 | 对应任务的哪一版树 | 提交工具结果里的 `taskId` + 树版本号（§5.2） |
| 会话日志里执行器发来的消息 | 触发它的任务事件 | 消息来源里的 `taskId` + `requestId`；正文附事件序号 |
| 任务事件日志里的一条"请求发出 / 提交" | 会话日志里的那一轮 | 事件记录 `sessionId` + DSH 的 turn 号 + `toolCallId` |

这就是 [mc_agent.md](../../mc_agent.md)"可根据日志定位到对应的上下文，查清当时发生的问题"的实现：**任何一边都能跳到另一边**。

DSH 另有 `appendPluginRecord`（`plugin:` 前缀的会话记录，[dsh-session/lib/types/index.d.ts](../node_modules/@deepseek-ai/dsh-session/lib/types/index.d.ts)），可以把执行器事件直接写进会话日志。**第一版不用**：上面的 ID 互引已经够用，而且这个接口在上游被门禁限制为实验性包使用，稳定性没保证。

### 8.3 运行时目录

`steveX/runtime/` 加进 `.gitignore`：慢树是任务工件、会无限增长（[src/bt/README.md](../src/bt/README.md)）。**快树版本链与胶囊库是长期资产，留在仓库里**（`src/bt/trees/fast/`、`src/capsules/`），进 git。

**【审阅点 7，已定 2026-10-23】** 慢树实例**先全部保留**，手动清理。保留策略（进过反思的全留、其余滚动删除）等数据量上来后再定（T9）。

## 9. 事实库（只定接口）

[mc_agent.md](../../mc_agent.md) 里事实库只有标题，本方案**只定它在集成层的接口**，格式与压缩机制另写文档：

- 服务：`memory` 子模块的 `facts.search(query)` / `facts.write(entry)`；对大模型暴露为 `fact_search` / `fact_write`
- **写入的硬约束**：每条事实必须附**源码引用**（文件路径 + 行号范围，指向反编译源码），`fact_write` 校验引用的文件与行存在，否则拒绝。这是"与源码一一对应"的执法机制
- 存储：第一版一个条目一个 JSON 文件，放 `steveX/facts/`，进 git（事实是长期资产）

**源码引用基准（审阅点 8，2026-10-23 定）**：**[steveX/1.21.11_src](../1.21.11_src) 是唯一基准**（客户端与服务端合一，约 6600 个 `.java`）。

- 事实库条目的源码引用写**相对于它的路径** + 行号范围，如 `net/minecraft/server/network/ServerGamePacketListenerImpl.java:1851-1862`
- `mc_source_search` / `mc_source_read` 的可读范围就是这个目录
- 仓库外的 `MC_agent/1.21.11_src`、`MC_agent/decompiled_src_vf` 是另外两份反编译产物，**行号与变量名都和基准不同**（例如 `decompiled_src_vf` 里的 `fullResyncNeeded`，在基准中是 `bl`）。旧设计文档里对它们的引用保留为历史记录，不回改；**新文档和事实库一律引用基准**
