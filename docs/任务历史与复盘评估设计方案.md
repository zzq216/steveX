# 任务历史与复盘评估设计方案

> 状态：**已实施**（2026-11-06），H1–H11 全部按建议，单元测试通过，待游戏内验收（§6）。实施说明见 §7。取代已撤回的《优化训练设计方案》：那份只解决训练场里的同题优化，在真实环境里用不上；其中的指标采集并入本方案 H1。
>
> 目标：让行为树在**真实使用中**也能迭代升级。每个任务结束后，复盘时评估这次的树哪里成本高、耗时多，并记下来（允许没有问题）；下次遇到同类任务时，agent 能查到这次的树、指标和评估，在它的基础上继续改进；再下一次复盘时核对上一次记下的问题是否解决。

## 1. 用户原始想法

1. 任务完成后的复盘（提取胶囊的那个回合）里，评估本次生成的行为树，找出成本高、耗时多的地方并记录下来；允许没有问题
2. 下次遇到同类任务时，拿到这个任务的行为树作参考，直接看到它的问题在哪，继续迭代升级
3. 可以查看以往完成任务的历史记录，仿照胶囊写一套淘汰规则

## 2. 已核实的事实与缺口

| # | 事实 | 对方案的影响 |
|---|------|------------|
| H-F1 | 现在的训练只判对错。多份模式下 agent 直接把"合成一次"的胶囊重复 m 次（记录 b20261102120652 #1：要 87 个，逐次做到 75 个被中止）。复盘时只有总用时 | 没有"低效"的证据，就没有改进的理由。评估必须有系统算好的成本数据（H1） |
| H-F2 | 每个任务的事件都在 `runtime/tasks/<taskId>/events.jsonl`：节点 `enter` / `exit` 带 `at`（毫秒时间）、`exit` 带 `status` 和胶囊引用 `ref`；`request` / `expansion/applied` 记着等待展开、修补回合的起止 | 节点耗时、子树耗时、等 LLM 回合的时间都能从现有事件算出 |
| H-F3 | 节点事件里**没有** mod 调用次数。所有 mod 调用都经过 `GameState.env()`（动作）或 `GameState.read()`（读取），叶子节点执行时各自创建 env（`bt/nodes.js`） | 要补采集：每个叶子节点的 `exit` 事件记本次发出的调用次数（H1） |
| H-F4 | `runtime/` 不进 git，会一直增长，可能被清理 | 任务记录不能只引用 `runtime/` 里的文件，要自己存一份最终树（H4） |
| H-F5 | 复盘回合用 `prompts/skills/review.md`，以 `bt_reflect_done` 结束；`bt_inspect` 只能看当前任务或刚结束的任务 | 评估放进复盘；查看以往任务要新工具（H5） |
| H-F6 | 胶囊按内容哈希存，改了说明以外的内容就换哈希；统计放在条目之外的 `stats.json` | 胶囊的"已知问题"也要放在条目之外（H8） |
| H-F7 | 训练产物（胶囊库、快树、事实库、训练记录）约定只留本地、不进 git | 任务历史同样只留本地 |

## 3. 总体设计

```
任务执行  ──→ 事件流（新增：叶子节点的 mod 调用次数）
   │
任务结束 ──→ 系统算"成本画像"（H1）：总指标 + 按节点 / 按胶囊的调用次数与耗时 + 等 LLM 回合的时间
   │
复盘回合（review）
   ├─ 照旧：决定存哪些胶囊
   ├─ 新增：评估本次的树（task_assess，H2、H3）——问题列表，或"未发现问题 + 理由"
   ├─ 新增：核对"前驱"任务记下的问题（H7）——这次规划 / 展开时参考过的历史任务
   └─ bt_reflect_done → 写一条任务记录（H4）；问题挂到对应胶囊的"已知问题"上（H8）

下一个任务
   └─ 规划 / 展开 / 修补时：task_search 找同类任务 → task_get 看它的树、指标、评估（H5、H6）
        被 task_get 看过的记录自动成为本任务的"前驱"（H7）

维护：淘汰规则 + history-gc 脚本（H9）
```

要点：
- **系统给证据，agent 写结论**：成本画像由系统计算；问题和改进设想由 agent 写，系统不生成任何建议，符合"不教写法"
- **评估是待验证的假设**：以下一次同类任务的指标为准，在核对时标为已解决 / 仍存在 / 判断有误
- **真实环境通用**：不依赖训练场，同类任务自然反复出现时就形成"提出问题 → 改进 → 验证"的链条；训练场只是让同类任务出现得更密

## 4. 决策点

### H1　成本画像（证据）

任务结束时系统计算，放进复盘请求，也存进任务记录：

**总指标**

| 指标 | 定义 |
|---|---|
| `outcome` | done / failed / aborted（训练场的轮次另带判定结果） |
| `execMs` | 任务处于 `running` 状态的累计时长，扣掉等待展开 / 修补回合（`suspended`）和暂停（`paused`） |
| `waitMs` | 等 LLM 回合的累计时长（展开、修补各自的次数与时长） |
| `modCalls` | 本任务的树发出的 mod 调用总数，分 `actions`（动作）和 `reads`（读取）；完全确定，同一棵树同一局面每次一样 |
| `nodeRuns` | 节点执行次数总和 |
| `turns`、`tokens` | 规划、展开、修补回合的数量与 token（训练器已有的算法，挪到通用位置） |

**明细**（各取前 10，按 `modCalls` 排）
- **按胶囊**：引用、被调用几次、累计 `modCalls`、累计耗时、占全树的比例
- **按节点**：节点 id、名字、类型、执行次数、`modCalls`、累计耗时（子树按 enter→exit 算，叶子另算自身）
- **重复模式**：同一个胶囊或同一个子树被连续调用 ≥ 3 次时单列一行（"`trees/craft.once-in-inventory-2x2` 连续 29 次，占执行时间 85%"）。这只陈述事实，不下结论

**采集补充**：叶子节点执行时，用它自己的 env 计数，在 `exit` 事件里写 `calls: { actions, reads }`。

**建议**：采用以上内容。

### H2　评估在哪里做

| 方案 | 做法 |
|---|---|
| **A** | 复盘回合里新增工具 `task_assess`，在 `bt_reflect_done` 之前调用 |
| B | 给 `bt_reflect_done` 加 `assessment` 参数 |
| C | 单独开一个评估回合 |

A 让评估和"存胶囊"分开，可以反复修改（同一次复盘里重复调用就覆盖），错误提示也更清楚。C 多一个回合，成本高。

**必填规则**：任务 `done` 时必须先调用 `task_assess`，否则 `bt_reflect_done` 被拒绝并提示；`failed` / `aborted` 时可选（这时复盘的重点是失败原因）。手动 `/bt reflect` 同样适用。

**建议：A**，按上面的必填规则。

### H3　评估的格式

```json
{
  "requestId": "c1",
  "issues": [
    {
      "where": "trees/craft.once-in-inventory-2x2",
      "kind": "cost",
      "problem": "每做一次都重新开关背包、逐个放料、核对，29 次合成重复了 29 遍",
      "evidence": "连续调用 29 次，modCalls 1240 / 1310，执行时间占 85%",
      "idea": "一次把每格放满需要的份数，取一次产物"
    }
  ],
  "none": null,
  "review": [ { "record": "task-…", "issue": 0, "status": "open", "evidence": "…" } ]
}
```

- `issues`：0–5 条。`where` 是节点 id 或胶囊引用（不带哈希的名字或带哈希都可以）；`kind` ∈ `cost`（调用多）、`time`（耗时长）、`turns`（等 LLM 回合多）、`fragile`（容易出错）、`other`；`problem`、`evidence` 必填，`idea` 可选
- `none`：没有问题时写理由（如"每次合成只调用 1 次子树，没有重复，调用次数已经接近下限"），与 `issues` 二选一，不能都空
- `review`：核对前驱的问题（H7）
- `evidence` 要能在成本画像里找到对应的数字。系统不逐条校验数字，但会检查 `where` 是否真的出现在本次的树里，不在就拒绝

**建议**：采用以上格式。

### H4　任务记录：存什么、存在哪

**存哪**：`src/history/`（和胶囊库同级，不进 git），每个任务一个文件 `<taskId>.json`，另有索引 `index.json`（检索用的摘要）。

**存什么**

| 字段 | 内容 |
|---|---|
| `taskId`、`at`、`goal` | 任务 id、结束时间、指令原文 |
| `keywords` | 从指令和最终树里提取的检索词：物品 id、胶囊名、节点名里的词 |
| `outcome`、`metrics` | H1 的总指标 |
| `profile` | H1 的明细 |
| `tree` | 最终树（和 `bt_inspect tree` 同一种文本），以及编写格式的规格 |
| `capsules` | 用到的胶囊引用（带哈希） |
| `assessment` | H3 的 `issues` / `none`，每条问题带 `status`：`open`（待验证）/ `resolved` / `wrong` |
| `predecessors` | 前驱任务 id（H7） |
| `retrieved` | 被 `task_get` 看过的次数、最近一次的时间（淘汰用） |
| `training` | 训练场轮次的场地、种子、n / m（普通任务没有） |

没做复盘的任务（复盘关闭、复盘出错）也写一条记录，只是没有 `assessment`：成本画像本身就有参考价值。

**建议**：采用以上内容。

### H5　检索工具

- `task_search`：参数 `query`（文本，可空）、`outcome?`、`limit?`。按关键词匹配 `goal` 和 `keywords`（和 `capsule_search` 同一种文本匹配），相关度相同时按时间倒序。每条返回：任务 id、时间、指令、结果、`execMs` / `modCalls` / `turns`、待验证问题条数、用到的主要胶囊。已归档的默认不返回
- `task_get`：参数 `taskId`。返回完整记录（树、成本画像、评估），并把这次查看记作本任务的前驱（H7）

**可用的回合**：规划、展开、修补、复盘。快树相关的回合和整理回合不开放。

**找不到同类任务是正常情况**：
- 没有匹配时返回空列表和一句"没有找到匹配的任务记录"，不是错误；agent 照常规划，本任务没有前驱，复盘时也就没有要核对的问题
- 找到了但都不相干：是否相关由 agent 判断。只有 `task_get` 看过的才算前驱，`task_search` 列出来不算，所以不相干的结果不会把问题带进复盘
- 查不查历史由 agent 决定，规划不要求先查；报告统计"有前驱的轮次比例"（H10），用来观察它会不会用

**建议**：采用。

### H6　提示词

只说明有什么能力、里面有什么，不规定怎么用：
- **大纲 skill**（`outline.md`）第 1 步"看有什么可用"补一句：`task_search` 查做过的同类任务，`task_get` 看它的树、指标和复盘时记下的问题
- **展开 / 修补**的请求模板同样补一句
- **复盘 skill**（`review.md`）新增一节"评估这次的树"：成本画像在请求里；用 `task_assess` 记下成本高、耗时多或容易出错的地方，没有就写理由；有前驱时逐条核对它记下的问题
- **复盘请求**（`prompts/requests/reflect.md`）新增"成本画像"和"前驱的待验证问题"两段

**建议**：采用。

### H7　前驱与核对

**前驱怎么定**

| 方案 | 做法 |
|---|---|
| **A** | 本任务的规划、展开、修补回合里用 `task_get` 看过的记录 |
| B | 系统按关键词自动找最相似的一条 |

A 准确：agent 看过、参考过的才算，核对有意义。B 可能配错，把不相干的问题塞给它。A 的缺点是 agent 没查历史时就没有前驱，这本身也是一种信息：报告里统计"同类任务出现时有没有查历史"。

**怎么核对**：复盘请求里列出前驱记录中 `open` 的问题，agent 在 `task_assess` 的 `review` 里逐条写 `resolved` / `open` / `wrong` 和证据（如"这次 modCalls 从 1310 降到 160"）。写进前驱记录的对应问题，并记下是哪个任务核对的。没核对的保持 `open`。

**建议：A。**

### H8　胶囊的"已知问题"

问题的 `where` 是胶囊时，也挂到胶囊上，让不是同类任务、但用到这个胶囊的规划也能看到：

- 存在 `src/capsules/notes.json`（和 `stats.json` 一样在条目之外，不改哈希），按胶囊名字记，每条带版本哈希、来源任务、`status`
- `capsule_search` 的结果多一项"已知问题 N 条（待验证）"；`capsule_get` 给出全文
- 胶囊用 `replaces` 换了新版本：旧版本的问题保留并标注"针对 @旧哈希"，由下一次用到新版本的任务复盘时核对
- 整理回合的清单里也带上已知问题，作为改写或下架的参考
- 问题的状态和任务记录里的是同一份：在任务记录里核对，胶囊上的状态同步变化

**建议**：采用。

### H9　淘汰规则

仿照胶囊整理（下架而不删除，归档可恢复）：

1. **已闭环**：一条记录的所有问题都已核对为 `resolved` / `wrong`，并且之后有同类记录（它是别人的前驱）→ 归档
2. **没人看过**：超过 30 天、从没被 `task_get` 看过 → 归档
3. **总量上限**：活跃记录超过 500 条时，按"没被看过的优先、越旧越先"归档到 500 条
4. **不归档**：还有 `open` 问题、且被看过的记录

- 归档移到 `src/history/archive/`，`task_search` 默认不返回，带 `archived: true` 才返回
- 规则 1 在每次写记录时自动执行；规则 2、3 由脚本 `npm run history-gc` 执行（默认演练，`--apply` 才移动），和 `capsule-gc` 一样
- 胶囊的已知问题跟随：来源记录归档后，问题仍然 `open` 的保留在胶囊上，已闭环的从显示里去掉（文件里保留）

**建议**：采用。阈值做成配置项。

### H10　与训练场的关系

- 训练场的每一轮都是普通任务，照样写记录、做评估；记录带 `training` 字段，训练记录（`runtime/training/*.jsonl`）里也写上 `historyId`
- 训练报告新增几列：评估里提出问题的比例、有前驱的轮次比例、前驱问题被核对为 `resolved` 的比例
- 训练场的作用是让同类任务出现得更密，加快"提出 → 改进 → 验证"的循环；机制本身不依赖训练场

**建议**：采用。

### H11　成本与规模

- 复盘请求变长：成本画像只给前 10 条明细，前驱问题最多列 10 条，合计控制在约 3000 字以内（配置项）
- 每个 `done` 任务多一次工具调用（`task_assess`），不多开回合
- `task_get` 返回的树可能很长：超过上限时只给到第 3 层，下面折叠，并提示用 `task_get` 的 `node` 参数展开某个子树

**建议**：采用以上上限。

## 6. 验收清单（实施后）

1. 任务结束后，复盘请求里有成本画像：总指标、按胶囊和按节点的前 10、重复模式。同一棵树在同一局面下重复执行，`modCalls` 完全一样；有 `expand` 的任务，`execMs` 不含等待展开的时间。
2. `done` 任务的复盘不调用 `task_assess` 就 `bt_reflect_done`，会被拒绝；写"未发现问题 + 理由"可以通过；`where` 不在本次树里的问题被拒绝。
3. 复盘结束后 `src/history/<taskId>.json` 有完整记录；没做复盘的任务也有记录（没有评估）。
4. 下一个同类任务规划时，`task_search` 能找到上一条记录；`task_get` 之后，它成为本任务的前驱；本任务复盘请求里列出前驱的待验证问题，核对结果写回前驱记录。
5. 问题挂在胶囊上时，`capsule_search` 显示"已知问题 N 条"；胶囊被 `replaces` 后，旧问题标注针对旧版本。
6. `npm run history-gc` 演练列出将归档的记录；`--apply` 后它们移到 `archive/`，`task_search` 默认不再返回。
7. 训练报告里有"提出问题比例、有前驱比例、前驱问题解决比例"。

## 7. 实施说明（2026-11-06）

- **采集（H1）**：`bt/nodes.js` 的异步叶子（条件、Compute、Action、Steps）经 `this.game(ctx)` 发 mod 调用，进入节点时清零、退出事件里写 `calls: { actions, reads }`；一次读 N 个来源记 N 次，执行前后的观察读取也算。`Executor.setState` 写 `task/state` 事件。旧的事件流没有 `task/state`：画像退化成"总时长 − 等待请求的时长"，调用次数为 0

### 7.1 补充 H12：效率写进验收标准、复盘时确认改进设想（2026-11-07）

### 7.3 第二批训练后的修正（2026-11-07）

看了 session-68dbb8ab / 2417ef83 / 72c51d6f 三轮后修的三处：

- **`container/slot` 的 clickType 写全**：原说明是"0拾取 1快捷移动 2交换 4丢弃…"、参数提示里 5 还写成"合成"；mod 实际支持 0–6 全部 vanilla ClickType。72c51d6f 复盘为确认 PICKUP_ALL 翻了约 160 s 源码，最后仍写"本 mod 是否暴露未确认"。现在说明逐项列出 0=PICKUP … 6=PICKUP_ALL 与 button 的含义（只列对应关系与参数，效果仍以 vanilla 源码为准）
