# 村民交易训练场设计方案

> 状态：**V-S1–V-S4 已实施**（2026-11-23），单元测试通过，mod 编译通过，待游戏内按 §7 验收。审阅结论：V1–V13 全部按建议执行；任务目标按审阅意见改成"在指定的交易上交易指定次数"（V4）。实施时补充的地方见 §8。
>
> 分析后已经确定的方向（2026-11-23 用户确认）：
> - 村民设成 NoAI 加无敌、成年；排除无职业和傻子；交易项从 1 级逐级生成到 L 级；排除藏宝图；每轮换一只新村民；
> - 名额都用整数：每笔交易的付款物最多 4 格，产物最多 9 格，另有全局格数预算；
> - 付款物多发余量 e，默认 0–16，并保证有一部分轮次的 e 不小于单价，让"多换"成为可能；
> - 判定以服务端的交易次数 `uses` 为准，再检查物品守恒、没有扔出物品、界面已关；
> - 多换或换错是不可逆的，一发生就立即判失败、结束本轮；
> - 任务目标直接写成"在指定的交易上交易指定次数"，不写成"换到这些产物"（2026-11-23 审阅意见），因此选交易时不需要产物方面的约束；
> - 带组件的产物（附魔书、附魔装备等）保留；
> - `container/get` 的 `trades[]` 补上实际价。
>
> 本方案沿用《合成器训练场设计方案》（下称"合成器方案"）、《坐骑训练场设计方案》（下称"坐骑方案"）、《附魔台训练场设计方案》（下称"附魔台方案"）和《村民交易 API 设计方案》（下称"交易 API 方案"）的架构，下面只写不同的部分。

## 1. 用户原始流程

1. agent 传送到对应的训练场地中，正前方有一个随机职业、随机等级的村民，视角对着它，直接右键就能打开交易界面
2. 清空 agent 身上的所有物品
3. 开始计时，发布任务：
   1. 随机选 1–4 笔交易，每笔交易定一个交易次数 n1；
   2. 发放付款物，格数有上限，不可堆叠的产物要特别注意格数；
   3. 要求 agent 换到这些交易 n1 次的产物，放进物品栏，关掉界面
4. 检测到物品栏里正好是目标物品（不多也不少）时，停止计时并记录

原文里几个数量（1/8、1/4 格、m0）的定义落实在 V5，判定按 V6、V7 落实。第 3 步的目标按审阅意见改成"在指定的交易上交易 n1 次"（V4、V9）。

## 2. 已核实的事实

源码位置都在 `1.21.11_src/net/minecraft/world/` 下。

| # | 事实 | 对方案的影响 |
|---|------|------------|
| F1 | 交易项是**惰性生成**的：`AbstractVillager.getOffers()` 第一次调用时才调用 `updateTrades`。`Villager.updateTrades` **只按当前等级**从 `VillagerTrades.TRADES[职业][等级]` 里抽 2 笔（`addOffersFromItemListings`：随机取出一个 listing，`getOffer` 返回 null 就换下一个，直到抽够 2 笔或抽完）。升级时（`increaseMerchantCareer`）再追加新等级的 2 笔 | 直接生成一个 5 级村民只有 5 级的 2 笔交易。要从 1 级逐级生成到 L 级（V2） |
| F2 | 每个 listing 的 `getOffer(level, entity, random)` 只用传进来的 `random`，不用实体自己的随机数（`VillagerTrades` 里没有 `getRandom()`）。`entity` 只被 `TypeSpecificTrade` 用来读村民类型 | 用种子创建的 `RandomSource` 逐级生成，同一种子一定出同一组交易项，可以先预览再出题（V3） |
| F3 | **藏宝图**（`TreasureMapForEmeralds`，制图师 2–5 级，有的包在 `TypeSpecificTrade` 里）在 `getOffer` 时调用 `findNearestMapStructure`，在 100 区块内搜索结构，找不到就返回 null | 很慢，在训练场世界里也可能找不到。抽之前就从池里拿掉（V2） |
| F4 | `TypeSpecificTrade` 按村民类型（平原、沙漠等 7 种）决定给不给这笔、给哪一笔（例如制图师的各色旗帜）；类型对不上时返回 null | 村民类型要随机，也要进种子（V2） |
| F5 | 设了 NoAI 以后，`Mob.isEffectiveAi` 为假，`LivingEntity.aiStep` 不调用 `serverAiStep`，所以 `Villager.customServerAiStep` 整个不跑。下面这些都不会发生：<br>• 走动、转身；<br>• 升级（`updateMerchantTimer` 只在这里倒数，交易后 40 tick 升级并追加交易项）；<br>• 交易口碑（`lastTradedPlayer` 只在这里转成 `ReputationEventType.TRADE`，每次 TRADING +2） | NoAI 以后交易项和价格在一轮内固定不变。右键交易不受影响（`Villager.mobInteract` 不检查 AI）。坐骑场地已经在用 NoAI 加无敌（`MountArena.spawn`） |
| F6 | 实际价 = `MerchantOffer.getCostA()`，等于基础价 + ⌊基础价 × demand × priceMultiplier⌋ + specialPriceDiff，截到 [1, 付款物堆叠上限]：<br>• `specialPriceDiff` 在每次打开界面时由 `updateSpecialPrices` 按口碑和村庄英雄效果重算；<br>• `demand` 只在补货时更新 | 新生成的 NoAI 村民口碑为 0、`demand` 为 0，`prepare` 又会清掉玩家的状态效果，所以实际价等于基础价。在真实世界里两者会不同（V11） |
| F7 | 交易包同步了 `specialPriceDiff`、`priceMultiplier` 和 `demand`（`MerchantOffer.writeToStream`），客户端的 `getCostA()` 算出的是真实价格 | `container/get` 可以直接在客户端读实际价，不用新开同步通道（V11） |
| F8 | `container/get` 的 `trades[]` 现在给的是 `inputA = getBaseCostA()`（基础价），另有 `inputB`、`result`、`uses`、`maxUses`、`xp` | 基础价在真实世界里可能不是实际要付的数（V11） |
| F9 | `MerchantOffers.getRecipeFor`：`selectionHint` 大于 0 时只认这一笔；等于 0 时按顺序找第一笔能被支付格满足的交易 | 付款物相同的两笔交易之间，手动放料会选到排在前面的那笔。`container/select-trade` 已经能选中，不需要新能力，提示词也不提 |
| F10 | Shift 点结算格（QUICK_MOVE）时，`AbstractContainerMenu` 会循环调用 `MerchantMenu.quickMoveStack(2)`，一直交易到付款物不够、交易次数用完或物品栏放不下 | 只发最少的付款物，Shift 一下就一定恰好成功，没有难度；所以要多发余量（V5） |
| F11 | 关界面时（`MerchantMenu.removed`），支付格里的东西用 `placeItemBackInInventory` 放回物品栏；光标上的东西也由 `AbstractContainerMenu.removed` 放回。物品栏满了会掉在地上 | "把产物放进物品栏"在关界面时自动完成，提示词不用单独提；全局格数预算要保证放得下（V5） |
| F12 | 村民不补货：补货要在工作站方块旁边、并且由 AI 触发（`restock`、`shouldRestock`） | 场地里没有工作站，再加上 NoAI，交易次数用掉就回不来。多换不可逆（V7） |
| F13 | `Villager.mobInteract`：幼年村民不能交易；没有交易项（无职业、傻子）时只会摇头 | 只生成成年村民，排除无职业和傻子（V2） |
| F14 | 打村民会通过 `onReputationEventFrom(VILLAGER_HURT)` 加负面口碑，价格上涨。这一步不经过 AI | 必须设无敌（V1） |
| F15 | 交易时村民会在身边生成经验球（`rewardTradeXp`），村民经验也会增加，但 NoAI 下不会升级（F5） | 经验球不是物品，不算进守恒。`prepare` 本来就会清场内的经验球 |
| F16 | 附魔书（`EnchantBookForEmeralds`）的价格是 2 + random(5 + 10 × 级) + 3 × 级，宝藏附魔翻倍，上限 64，另要一本书；附魔装备（`EnchantedItemForEmeralds`）最多交易 3 次；染色皮甲（`DyedArmorForEmeralds`）的颜色随机 | 产物带组件，但同一笔交易每次给出的东西完全一样，判定按交易次数就能确定换到了什么（V6） |
| F17 | 训练器已经有 `task.preview` 钩子（附魔台用来调用 `arena/enchant-preview`），轮询 `arena/status` 时只用来记 `reachedAt`，**没有"不可逆失败，立即结束"的钩子** | 预览直接复用；立即结束要给训练器加一个通用钩子（V7） |

## 3. 总体设计

```
/bt train villager [runs] [seed] [profession=<职业>] [level=k|a-b] [tasks=k|a-b] [n=k|a-b] [extra=k|a-b] [item=<产物>]
  插件 trade 题型：抽职业、等级、村民类型、交易项种子
  → arena/trade-preview（新，只读）：mod 用同一套算法逐级生成交易项，返回列表
  → 插件：选几笔交易（V4）→ 每笔抽 n1 → 每种付款物抽余量 → 拆堆、打乱格位
  → arena/prepare { station: villager, villager: {...}, items, expect: { trade: {...} } }
       mod：换一只新村民、按同一种子生成交易项并和预览核对、发物品、对准视角
  → 发任务 → 轮询 arena/status（mod 在 tick 里记第一次到达的时刻；插件每次轮询检查有没有多换、换错）
  → 任务结束或多换、换错立即结束 → arena/status 拿最终状态 → 判定、写记录 → arena/finish
```

分工同合成器场地：**插件出题、判定；mod 负责场地、生成交易项、计数和到达检测**。新增题型文件 `src/training/trade.js`，其余复用训练器。

## 4. 决策点

### V1　场地、村民、视角

- **场地 `villager` 设在 `(10000, 120, 10390)`**，和合成器场地间隔 30 格。场外平台、告示牌、屏障墙沿用现有逻辑。
- **工作站 `villager`** 对应 `Blocks.AIR`，同坐骑场地；`isVillager(station)` 决定走村民分支。
- **村民的位置**：`(ox + 0.5, oy + 1, oz + 2.5)`，面朝玩家，同坐骑方案 H1。
- **视角**：俯角按"眼睛 → 村民碰撞箱中心"算；准星自检改成服务器端的实体射线检测，命中本轮这只村民就是 `aimOk`。这些都沿用坐骑方案 H1。
- **每轮 `prepare`**：
  1. 先关界面；
  2. 清掉场内所有村民（上一轮记下 UUID 的那只，以及场地范围内的所有 `Villager`）；
  3. 生成本轮的村民，设置：
     - 成年；
     - `NoAI`（F5）；
     - 无敌（F14）；
     - `setPersistenceRequired`；
     - 职业、等级、类型、交易项按 V2；
  4. 记下 UUID。
- **丢失**：本轮这只村民不在了，判 `lost`。
- `opensStation` 认 `MerchantMenu`，并且交易对象是本轮这只村民，记下第一次打开界面的时刻 `openedMs`。

**建议：采用。**

### V2　交易项的生成（mod）

| 方案 | 做法 | 问题 |
|------|------|------|
| 直接设等级 | `setVillagerData(level = L)`，让 `getOffers()` 惰性生成 | 只有 L 级的 2 笔（F1）；随机数来自实体，没法预览 |
| 原版逐级升级 | 从 1 级开始反复调用 `increaseMerchantCareer` | 是 private 方法；随机数还是来自实体，没法预览；也拿不掉藏宝图 |
| **按原版算法自己逐级生成** | **mod 用 `RandomSource.create(offerSeed)`，对 1..L 每一级照抄 `addOffersFromItemListings`：随机取出一个 listing，调用 `getOffer`，非 null 就加入，直到抽够 2 笔或池子抽完；最后 `setOffers`** | 无 |

细节：

- **listing 表**：和 `updateTrades` 一样，世界开了 `TRADE_REBALANCE` 实验特性就用 `EXPERIMENTAL_TRADES`，否则用 `TRADES`。
- **排除藏宝图**（F3）：抽之前从池子里拿掉 `TreasureMapForEmeralds`，以及 `trades()` 里含有它的 `TypeSpecificTrade`。效果等于"这几笔永远生成失败"，原版逻辑会接着换下一个 listing。
- **村民数据**：职业、类型、等级 L 都由插件给出（V3）。`villagerXp` 设成 L 级的最低经验（L < 5 时用 `VillagerData.getMinXpPerLevel(L)`；L = 5 时它返回 0，改设 250，即 5 级的门槛），让界面上的经验条和等级对得上。
- **职业池**：`VillagerProfession` 里除了 `none`、`nitwit` 以外的 13 种，减去场地配置 `exclude.professions`。
- **村民类型**：7 种（平原、沙漠、丛林、热带草原、雪原、沼泽、针叶林）等概率抽（F4）。
- 预览和 `prepare` 共用同一个生成函数（`VillagerArena.offers(level, profession, type, L, seed)`）。预览时用一个**不加入世界**的临时 `Villager` 实体作为 `getOffer` 的 `entity` 参数。

**建议：按原版算法自己逐级生成。**

### V3　出题流程：先预览，再选交易

沿用附魔台方案 N5 的"预览 → 出题 → prepare 核对"：

1. 插件抽职业、等级 L、村民类型、交易项种子 `offerSeed`；
2. **`arena/trade-preview`**（新，只读）：参数是 `{ profession, level, type, offerSeed }`，返回交易列表。每笔交易包含：
   - `index`
   - `level`：它是在第几级生成的
   - `costA: { id, count, maxStack }`
   - `costB: { id, count, maxStack } | null`
   - `result: { id, count, maxStack, components: bool }`
   - `maxUses`
3. 插件按 V4、V5 选交易、定数量。选不出来（例如 `item=` 指定的产物不在这只村民的交易里，或者 `n` 的下限超过了每笔交易的 n0）就用 `offerSeed + 重试次数` 重新预览，最多 10 次，还不行就本轮 `aborted`；
4. **`prepare`** 用同样的参数再生成一次，把每笔交易用 `MerchantOffer.CODEC` 编码后和预览逐笔比对，不一致就报"预览和村民交易项不一致"，本轮 `aborted`。

**随机数的抽取顺序**（同一种子出同一道题）：职业 → 等级 → 类型 → `offerSeed` →（预览后）笔数 k → 交易排列 → 每笔的 n1 → 每种付款物的 e → 拆堆 → 打乱格位。重新预览时，从 `offerSeed` 开始往后的步骤全部重抽。

**建议：采用。**

### V4　任务目标与选交易

**任务目标**（审阅意见）：直接指定"在哪几笔交易上各交易几次"，不写成"换到这些产物"。

| 方案 | 目标 | 问题 |
|------|------|------|
| 按产物 | 换到 X × a、Y × b | 产物和交易次数要一一对应才能判定，需要额外约束：<br>• 选中的产物互不相同；<br>• 产物不能是付款物；<br>• 没选中、但付得起的交易不能给出同样的产物。<br>这些约束会让一些题出不了（例如图书管理员的两本附魔书） |
| **按交易次数** | **在"用 A 换 B"那笔交易上交易 n1 次** | 无。判定直接看 `uses`（V6），不需要上面的约束 |

按交易次数时，下面这些情况都合法，不用排除：

- 两笔选中的交易给出同一种产物（例如都给绿宝石）：各查各的次数；
- 一笔的产物是另一笔的付款物（例如先卖小麦换绿宝石，再用绿宝石买面包）：agent 可以拿换来的绿宝石去付，也可以用发的。结束时物品栏的数目仍然由各笔交易的次数唯一决定（V6 的守恒式），多发的付款物只是剩下；
- 没选中的交易 agent 也付得起：做了就是 `mistrade`（V8）。

代价是 agent 不用再做"从产物反推是哪笔交易、用目标个数除以每次的产物数"这一步。以后要练这一步，再加一个按产物出题的变体（V13）。

**选交易**：笔数 k 在 `tasks` 里抽（缺省 `1-4`），不超过可选的交易数。把交易项随机排列，依次取能选的（满足 V5 的 n 范围，并且 `maxUses > 0`），取满 k 笔就停。不足 k 笔时按实际笔数出题，并记下 `kWanted` 和 `k`。

**文案能否区分**：V9 按内容描述每笔交易。如果两笔交易写出来完全一样（付款物、产物的 id 和数量都相同，例如两本附魔书碰巧同价），描述时在产物后面加上组件说明，例如附魔名（V9）。

- `item=<产物>`：选中的交易里必须有一笔的产物是这个 id，先选它，再选其余的；没有这样的交易就重新预览。
- `profession=<职业>`：固定职业。
- `level=k|a-b`：限定等级（1–5，缺省 `1-5`）。

**建议：采用。**

### V5　数量与格数

把原文的 1/8、1/4 落成整数：

| 名额 | 值 | 说明 |
|------|----|------|
| 每笔交易的付款物 | 最多 **4 格** | 原文"物品栏 1/8"（4.5 格）取整 |
| 每笔交易的产物 | 最多 **9 格** | 原文"单笔交易 1/4"，实际作用是限制不可堆叠的产物 |
| 全局 | 开局占用格数 + 全部产物格数 ≤ **36** | 保证交易过程中物品栏任何时候都放得下（F11）；比之前说的"结束时 ≤ 27 格"更严，也真正防住了中途放不下 |

**每笔交易 i 的次数**：

```
n0_i = min( maxUses_i,
            ⌊4 × stack(A_i) / a_i⌋,
            ⌊4 × stack(B_i) / b_i⌋（有第二种付款物时）,
            ⌊9 × stack(P_i) / c_i⌋ )
n1_i 在 [max(1, n 的下限), min(n0_i, n 的上限)] 里均匀抽
```

其中 a_i、b_i 是单价（实际价，等于基础价，F6），c_i 是每次的产物数，stack 是堆叠上限。`n=k|a-b` 缺省 `1-64`，等于不限制。n 的下限超过 n0_i 时，这笔交易不能选，回到 V4 换下一笔。原文的 m0 就是这里的 4 格名额，n0 就是 n0_i。

**付款物**：同一种付款物（例如两笔交易都要绿宝石）合在一起发：

```
need_g = Σ n1_i × 单价_i,g          （S 里用到 g 的交易）
e_g    在 [extra 下限, max(extra 上限, 2 × p_g)] 里均匀抽，p_g 是 S 里用 g 的交易的最高单价
       再截到：⌈(need_g + e_g) / stack(g)⌉ ≤ 4 × （S 里用 g 的交易笔数）
发放   need_g + e_g
```

- `extra` 缺省 `0-16`，选项名和合成器场地一致。
- 上限取 `max(extra 上限, 2p)`，保证单价较高的付款物（例如 20 个小麦换 1 个绿宝石）也有一部分轮次能"多换一次"。e ≥ 单价时，agent 有多换的可能；同时 `n1 < maxUses` 才真的换得出来。记录里记 `canOvershoot`（V10）。
- 两种付款物里任何一种的 e 都可能抽到 0。
- 串联的交易（一笔的产物是另一笔的付款物）也按 `need_g` 足额发，不扣除能换来的部分。用不用换来的，由 agent 自己决定。

**拆堆**：用 `spreadStacks(random, items, 36 − 产物格数)`（合成器场地抽出来的公共函数），给产物把格子预留出来，全局预算自然满足；再在 36 格里随机摆放。产物格数按 ⌈n1 × c / stack⌉ 计。

**付款物的形态**：用 `ItemCost.itemStack()`（满足 `ItemCost.test`）。原版交易的付款物都是不带组件的普通物品。

**建议：采用。**

### V6　计数、守恒和判定依据

- **交易次数**：mod 直接读本轮村民每笔交易的 `uses`，这是服务端的权威值。目标是 S 里每笔正好 n1_i，其余每笔都是 0。
- **物品计数**：mod 按物品 id 分别统计物品栏、光标、支付格（界面开着时）、场内地上的数量。
- **守恒**：每种物品都要满足下式：

  ```
  物品栏 + 光标 + 支付格 + 地上 = 发放数 − Σ 次数 × 单价 + Σ 次数 × 产物数
  ```

  交易次数按全部交易的 `uses` 算，包括换错的那些。不满足就说明有东西出了场。
- **不需要按组件比较**：交易次数已经确定了换到的是哪件东西（同一笔交易每次给出的完全一样，F16），所以计数按 id 就够了。带组件的产物（附魔书、附魔装备、染色皮甲、迷之炖菜、药箭）照常出题。这一条与上次分析里"判定按组件比较"不同，结论更简单。

**建议：采用。**

### V7　多换、换错：立即结束

多换（S 里某笔 `uses > n1`）和换错（S 以外某笔 `uses > 0`）都拿不回来（F12）。

- **训练器加一个通用钩子** `task.doomed?(ctx, picked, status)`：每次轮询 `arena/status` 后调用，返回原因文字或 null。返回原因时：
  1. 训练器用 `abortRun(..., by: 'arena')` 中止任务，原因写进任务历史，例如"交易次数超过目标：minecraft:bread 那笔交易已经做了 4 次，目标是 3 次，无法挽回"；
  2. 记 `doomedMs`，接着照常走 `settle` → `arena/finish` → 判定。
- 钩子是通用的，以后别的场地也可以用；**现有场地不实现它，行为不变**。
- 判定（V8）按最终状态重新算一遍，不依赖钩子当时的判断。

**建议：采用。**

### V8　判定

任务结束时按最终状态判定，判定顺序同合成器方案 R6，加入两种不可逆的失败：

| 顺序 | 结果 | 条件 |
|------|------|------|
| 1 | `aborted` | 手动停止；预览或 `prepare` 失败（包括 V3 核对不过） |
| 2 | `lost` | 村民不在了；场内地上有物品；或者不守恒（V6） |
| 3 | `overshoot` | S 里某笔 `uses > n1` |
| 4 | `mistrade` | S 以外某笔 `uses > 0` |
| 5 | `timeout` | 超时 |
| 6 | `success` / `false_success` / `failed` | 任务以完成结束时，到达条件（V9）成立就是 `success`，否则是 `false_success`；其余情况是 `failed` |

- `overshoot` 中文沿用"放多"的口径，写成"换多"；`mistrade` 是"换错"。报告的结果列加 `mistrade`。
- **手动停止的轮次也算失败原因**：拿到最终状态时照常算，结果仍是 `aborted`，同 2026-11-23 给合成器、酿造台补的做法。

**失败原因 `faults`**：结果不是 `success` 时，列出最终状态不满足的条件，可以同时有多条：

| 原因 | 条件 |
|------|------|
| `short` | S 里有交易的次数不到 n1 |
| `over` | S 里有交易的次数超过 n1 |
| `wrong` | S 以外有交易做过 |
| `open` | 界面没关，或者光标上还有东西 |

守恒成立、界面已关时，物品栏的数目由交易次数唯一决定，所以不单独设 `leftover`。

**建议：采用。**

### V9　到达条件和文案

**到达条件**：mod 在服务器 tick 里检测，记下第一次到达的时刻 `reachedAtMs`，不打断 agent。`Expect` 增加交易写法：

```
expect: { trade: { uses: [每笔交易的目标次数（S 以外为 0）…], held: { id: 应有个数, … } } }
```

同时满足下面几条就算到达：

1. 容器界面已经关闭，光标为空；
2. 本轮村民每笔交易的 `uses` 都等于 `expect.trade.uses`；
3. 物品栏里每种物品正好是 `held` 里的数，没有别的东西。

`held` 由插件按 V6 的守恒式算好：发放数 − 消耗 + 产物。

**文案**：只写目标状态，不写做法。不提"右键打开""选中交易""Shift 点结算格"，也不写交易的下标（下标是 `container/get` 的编号，写进任务等于把接口细节交给 agent）。

模板 `prompts/training/trade.md`：

```
你正前方有一个村民，视角已经对准它。你的物品栏里有和它交易要用的物品。
请和它交易：
{{trades}}
每笔都正好交易这么多次，不要做别的交易。换完以后关掉交易界面。用不完的物品留在物品栏里，不要动其他物品。
```

`{{trades}}` 每笔交易一行，按内容描述，单价写实际价：

```
- 用 minecraft:emerald × 1 换 minecraft:bread × 6 的那笔，交易 3 次；
- 用 minecraft:emerald × 24 和 minecraft:book × 1 换 minecraft:enchanted_book × 1 的那笔，交易 2 次。
```

- 两笔交易写出来完全一样时（V4），在产物后面加上组件说明：附魔书、附魔装备写附魔和等级，例如"（锋利 III）"；其他带组件的产物如果还分不开，这一组里只选其中一笔；
- agent 可以在 `container/get` 的 `trades[]` 里自己对照是哪一笔。

**建议：采用。**

### V10　记录与报告

记录在工作台场地的公共字段之外增加：

| 字段 | 含义 |

**建议：采用。**

### V11　补观测：`trades[]` 给实际价（agent 的通用能力）

`container/get` 的 `trades[]` 每项增加 `priceA`，值是 `offer.getCostA().getCount()`，即实际要付的 A 物品个数（F6、F7）。`inputA` 保持基础价不变，不改已有字段的含义（交易 API 方案 §2 非目标）。B 物品不受价格调整影响，不加字段。

- 训练场里 `priceA` 和 `inputA.count` 相等，这一项**不影响本场地的判定**；
- 真实世界里，村庄英雄、口碑、需求都会让两者不同，只看 `inputA` 会算错要付多少。这是补证据，不是教做法：玩家在界面上看到的就是实际价（原价被划掉）。
- `methods.js` 的说明同步更新。

**建议：采用。**

### V12　超时、场地安全、胶囊库

- **超时**：场地配置单独设 `timeoutSec`，默认 **900 秒**，和合成器一样。
- **场地安全**：
  - 场内不放工作站方块（F12），也不放床；
  - `prepare` 清掉玩家的状态效果（已有），村庄英雄效果也会被清掉（F6）。
- **村民被推走**：NoAI 的村民不会自己移动；本轮的村民不在场内，判 `lost`（V1）。
- **胶囊库**：不做特殊处理。

**建议：采用。**

### V13　暂不做的部分

- **hidden 模式**（不告诉 agent 要换什么）：没有可以观察的"做出来"这一步，不说目标就没法出题。
- **会升级、会补货、口碑变化的村民**：都要打开 AI，价格和交易项会在一轮内变化。以后要练"养村民"时再另做。
- **流浪商人**：交易表不同（`WANDERING_TRADER_TRADES`），而且会消失，暂不出。
- **藏宝图**：见 V2。
- **按产物出题的变体**（"换到 X × a"）：要 agent 从产物反推是哪笔交易、算出次数。需要 V4 表里列的那几条约束，以后要练这一步时再加。

## 5. 训练命令

```
/bt train villager [runs=…] [seed=…] [profession=<职业>] [level=k|a-b] [tasks=k|a-b] [n=k|a-b] [extra=k|a-b] [item=<产物>]
```

| 参数 | 缺省 | 说明 |
|------|------|------|

## 7. 验收清单（实施后）

1. `/arena villager` 能传送到场外平台；`/bt train villager runs=1` 进场后，第一次右键就能打开交易界面，`aimOk=true`。
2. 村民不走动、不转身，打它不掉血；关掉界面再打开，价格和交易列表都不变，交易后也不升级。
3. 同一个 `seed` 跑两次，村民的职业、等级、交易列表和题目完全一样；L 级村民的交易里有 1..L 级生成的项。
4. 制图师村民的交易里没有藏宝图，生成也没有卡顿。
5. `container/get` 的 `trades[]` 有 `priceA`，训练场里等于 `inputA.count`。
6. 正好换够、关界面，判 `success`。
7. 用 Shift 点结算格换多了，本轮立即结束，判 `overshoot`，任务历史里有原因。
8. 换了没选中的交易，本轮立即结束，判 `mistrade`。
9. 少换一次就宣布完成，判 `false_success`，`faults` 含 `short`。
10. 没关界面就宣布完成，`faults` 含 `open`。
11. 往地上丢一个付款物，判 `lost`。
12. 带附魔书、不可堆叠产物的题能正常出题和判定，物品栏不会满。
12a. 串联的题（先卖东西换绿宝石、再用绿宝石买）：用换来的绿宝石付款也判 `success`，剩下的付款物数目和守恒式一致。
12b. 两笔交易写出来一样时（例如两本同价的附魔书），文案里带上附魔名，能区分。
13. `training-report` 能按 `k` 分组，并列出 `mistrade` 和失败原因计数。
