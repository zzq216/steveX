# skill：慢树大纲

把一条指令写成一棵**马上可以开始执行**的树。

## 步骤

1. **看有什么可用**：`capsule_search` 看有没有做过的同类子树或代码；`command_docs` 查原始命令的名字与参数。要写处理数据的条件代码 / Compute，先用 `data_shapes` 查数据长什么样：`state.*`、`json.recipes`、`nbt.*` 的字段结构与词表。**不要猜字段名**——猜错了，条件代码要么永远不成立，要么像"找不到字段就返回 true"那样形同虚设。你看不到当前状态的值——它们由树去读（见下面"先读后展开"）。
2. **拆任务**：把指令拆成几个子任务（按先后顺序）。
3. **只沿第一条路径拆到底**：只拆**第一个**子任务，得到它的几个子子任务；再只拆其中**第一个**……直到第一个可以直接写成具体节点（`steps` / `act` / `compute` / `cond` / `forEach`）为止。
4. **其余全部留成 `expand`**：同一层的后续兄弟、上面各层的后续子任务，都写成 `{ "expand": 目标 }`。目标写清楚"要达成什么"，不写"怎么做"——展开时你能看到那时的状态，会比现在想得更准。
5. **一次提交**：用 `bt_submit_tree` 交回，`requestId` 用请求里的那个。被拒绝就按错误原文修正后重交。

形状：

    seq 任务
    ├─ seq 子任务1
    │   ├─ 子子任务1          ← 具体节点
    │   ├─ expand 子子任务2
    │   └─ expand 子子任务3
    ├─ expand 子任务2
    └─ expand 子任务3

## 先读后展开

你写大纲时不知道现状（背包里有什么、配方是什么、附近有什么）。不要猜，**把"读"写成第一条路径上的具体节点**，把依赖读取结果的部分留成 `expand`：

    seq 做木镐
    ├─ compute code/core.json.query → recipe.pickaxe   ← 具体节点：查配方
    ├─ expand 按 $recipe.pickaxe 准备材料              ← 展开时黑板里已有 recipe.pickaxe
    └─ expand 合成木镐

- 读状态：条件代码 / Compute 的 `read`（`player` / `inventory` / `f3` / `container`）；查记忆：`code/core.nbt.query`；查配方等数据：`code/core.json.query`
- 读到的结论写进黑板（带前缀的键名），后面用 `$键` 引用，**不要把值抄成字面量**
- 需要按情况分支（有工作台 / 没有），就写成 `sel` + `cond`，让树在执行时判断

## 注意

- 具体节点要有验收：关键的 `steps` / `act` 写 `expect`，让失败有证据。
- 需要算东西（点击计划、坐标、计数）就写 Compute 代码，放在提交的 `code` 字段里。
- 指令不清楚、或者当前做不到（缺前置条件又无从获取）：用 `ask_user_question` 问人，或 `bt_abort_task` 放弃并说明原因。

### 4.6 树的设计要点

1. **胶囊优先**：n1.3 只写了一行 `use trees/craft.in-player-grid`，把“开背包 → 铺料 → 点击 → 验收”整段复用；胶囊的 12 个内部节点在运行时展开，模型不需要重新写点击算法。
2. **读/reason/act 分离**：count-materials 只读背包；planks-need 只做“配方需要多少 vs 手里有什么”的推理；plan-planks-clicks 只算点击；补木板段只负责执行。每段都可以单独复用。
3. **数量判定放在树里**：`sel` + `blackboard/compare` / `task/planks-enough` 决定要不要补、补完够不够，没有把“缺口 4”写死。
4. **省料的点击计划**：`plan-planks-clicks` 用右键逐个放 `ceil(缺口/4)` 根原木，而不是把整堆放进去；产物一次 shift 取完。相比上一局的 `plan-stack-craft` 更省原木。
5. **两层验收**：补木板后有 `count-materials + planks-enough`；合成后有胶囊内部的 `done-in-grid`；收尾还有独立的 `verify-table + compare`。三层都不信任上一层的“成功”回执。
6. **关界面有守卫**：补木板段结束时直接 `container/close`；终验段先用 `ui.menu-open(none)` 判断，已经关了就不重复按。
7. **失败分支最小化**：`retry ×2` 里的 `expand` 是兜底，快乐路径不会展开它；终验失败分支留成 `expand` 描述，未执行。

## 6. 关键观察与问题复盘

### 6.1 胶囊复用的效果

- 上一局的 5 条胶囊在本局开头就能被 `capsule_search` 命中；`trees/craft.in-player-grid` 的契约（输入只有 `recipes`）让模型在规划阶段就敢把它写进 n1.3 的目标里。
- 实际执行时，胶囊的 `ui.menu-open` 条件带了 `read: ["container"]`，所以菜单关闭时返回 FAILURE 是**真实状态**，按 E 打开后 `confirm` 条件再验证；不会再出现上一局“空状态恒 true/false”的问题。
- 上一局的 `done-in-grid` 在胶囊内部负责“产物入包 + 合成格清空”，本局直接受益。

### 6.2 `json.query` 只许字面量 → 自写点击计划

这是本局最有意思的约束冲突：

- 组合 `plan-stack-craft` 需要一份 `recipes` 列表；而“该锯哪种木板”取决于运行时持有的原木（`$need.plankId`）。
- `code/core.json.query` 的参数只许字面量，不能 `filters: {result: "$need.plankId"}`；写死 12 种木板 id 又会在胶囊保存时被字面量检查拒绝。
- 模型的解法：**不查配方**，直接写 `plan-planks-clicks`——用“右键逐个放 1 根 + shift 取产物”的通用点击模式，`perLog = 4`（`bamboo_block` 按 2）作为游戏常量；目标木板 id 由 `planks-need` 从原木 id 反推，并在配方 `key` 的候选表里校验。
- 代价：`perLog` 对非竹子木材是硬编码 4；如果未来遇到产量不同的模组木材，需要靠后续复核发现偏差。

### 6.3 终验口径的弱点

`r6` 要求“数量比合成前多 1”，但 `verify-table` 只检查 `have >= max(1, resultCount)` 且合成格为空——**没有记录合成前的 `crafting_table` 基线**，所以如果背包里本来就有工作台，这个终验不能证明“刚合成了一个”。模型在思考里明确指出了这一点，但接受该口径，理由是胶囊内部 `done-in-grid` 已经验证了“产物入包 + 合成格清空”。如果要把终验做严谨，应该在 n1.3 之前记录一次 `crafting_table` 数量，或用 `done-in-grid` 的同一套事件证据。

### 6.4 其它值得注意的点

1. **本局没有 fail/repair 请求**：4 个 FAILURE 都是 `sel` 的分支试探；没有 `recover` / `escalate` / `failed` / `died`，也没有 `bt_submit_patch`。
2. **`retry ×2` 的 `expand` 未被展开**：木板一次就补够了（4 块），`planks-enough` 直接 SUCCESS；retry 及其 expand 子节点在最终树里保留为未执行，是合理的兜底。
3. **关界面确实执行了**：本局 `n1.4.1.3.1` 真实失败（菜单开着），`container/close` 执行并观测到 `inventory → none`；与上一局“cond 空状态恒真、关闭分支被跳过”形成对比。
4. **思考 token 更省**：本局输出 34,111，上一局 54,782；但本局步骤更多（26 vs 23）。最大的一回合是 turn 4（13,728 输出），花在“要不要复用 plan-stack-craft / 怎么绕过字面量约束”上。
5. **工具结果都很小**：除 `capsule_get`（4 KB）和 `f3`（2 KB）外，其余结果都在 1 KB 上下；提交回执只有“已接受 + 新节点 id”。
6. **`fact_search` 空结果**：`bamboo planks` 0 条，说明事实库还没覆盖这个配方；模型只能靠游戏知识写 `bamboo_block → 2`，并在胶囊里用 `keepLiterals` 固定 `bamboo_planks`。
7. **一个不一致点**：`慢树大纲` 技能提到 `ask_user_question`，但本会话的 19 个工具里没有它；本任务不需要问人，未造成影响。
