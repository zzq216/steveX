## 场景 2：记忆过期走 `failed`（P2-D15 / D17）

**验什么**：树用记忆里的东西做事，途中那样东西被人改掉 → 用到它的节点失败 → `failed` 请求的目录里列出"记忆来源已换代"。执行器不替树盯着记忆（依赖集已删除），过期只通过失败暴露。

**为什么现在碰不到**：需要 agent 能可靠地查到记忆里的箱子、走过去并打开它。目前寻路和开箱还要靠 agent 自己在训练中写出来。

**前提**：agent 能写出"`core.nbt.query` 查箱子 → 走过去 → 打开"的树并跑通（不挖箱子时能成功）。

**步骤**：
1. 在 agent 附近放一个箱子，放几根木棍，让 agent 看到它（确保记忆里有：普通问答里让它 `nbt_query` 查 `containers` 或 `block_entities`，能查到这个箱子）
2. `/bt task 从附近的箱子里拿出木棍`
3. 大纲交上来后看一眼树：应该有 `code/core.nbt.query` 查箱子的节点
4. agent 往箱子走的途中，人把箱子挖掉

**期望**：
- 某个节点失败（打不开界面、`expect` 不成立……），原地重试一次仍失败 → 会话里"修复请求 rN"，skill 是「慢树反思」
- 目录里有一行 **"记忆来源已换代 containers（或 block_entities）（n1.x 读到之后又变过）"**
- 失败后游戏里**没有按着的键**（§11.1 修过的缺口）
- 大模型交补丁或放弃

**events.jsonl 里应有**：`query/version`（查询读到的版本）→ `node`（exit `FAILURE`）→ `task/retry` → `controls/keys-released` → `request`（type `failed`）→ `patch/applied` 或 `task/failed`

**会话日志里观察**（不判对错，作为以后调整目录与提示词的依据）：
- 有没有调 `bt_inspect`，调了哪几种；有没有用 `versions`——目录里那一行被它注意到了没有
- 补丁有没有在树里重新查询；有没有把看到的坐标写成字面量（不该写死）

## 场景 3：reactive 复查（P2-D14 / D16）

**验什么**：reactive 序列按 `every` 复查守卫；守卫现场读状态时不中止正在跑的动作；守卫不成立时约一个间隔内中止动作并松键。

**为什么现在碰不到**：（按你的安排留到以后。手写树与示例条件代码已经备好，不依赖大模型。）

**准备**：启动 DSH **之前**保存示例条件代码（胶囊库在插件启动时装载）：
```bash
cd steveX/dsh-plugins/agent
node scripts/capsule-save.js examples/capsules/example.has-item.json
```
树文件：[examples/reactive_guard.json](../dsh-plugins/agent/examples/reactive_guard.json)——"背包里有木棍就一直往前走 20 秒"，每 1000 ms 复查一次（假 mod 上验证过：拿走木棍后 1022 ms 停下）。

**步骤 A（守卫不成立）**：
1. `/give @s minecraft:stick`，面朝一片空地
2. `/bt run dsh-plugins/agent/examples/reactive_guard.json`
3. 走到一半按 Q 扔掉木棍（或 `/clear @s minecraft:stick`）

**期望 A**：约 1 秒内停下、前进键松开；手写树不属于会话 → 本地应答器放弃任务，`/bt status` 显示 failed，失败节点 `n1.1`（还有木棍）。
events.jsonl：最后是 `n1.1` exit `FAILURE` → `controls/keys-released` → `request`（type `failed`）→ `task/failed`

**步骤 B（守卫一直成立，对照）**：同上但不扔木棍。

**期望 B**：**连续走满 20 秒，中途不停顿**（守卫复查时现场读状态返回"还在读"，不算不成立）。
events.jsonl：`n1.1` 大约每秒进出一次，`n1.2` 只进入一次。

**附带可测**：让大模型写一棵 reactive 树，看校验规则（P2-D16）的报错它能不能照着改——最后一个孩子之前放动作、任务树里用 reactive sel、`every` 小于 200，这三种都应被拒并给出改法。

## 场景 4b：执行中死亡 → `died` 请求（§8.3）

**验什么**：任务树**有叶子在跑**时死亡 → 中止、松键关容器 → 自动重生 → 发 **`died` 请求**（不是让别的请求过期）→ 大模型决定继续 / 补救 / 放弃。

**为什么要补测**：2026-10-25 的场景 4 测试（`task-20261025120908-2`）里，`/kill` 恰好发生在展开请求 r10 等待期间，走的是"请求等待期间死亡 → 让它过期"那条路；`died` 请求本身、死亡恢复模板、`← 死亡时在跑` 标记都还没在游戏里出现过。

**步骤**：
1. `/bt task` 给一个持续时间长、**大纲里第一步就是长时间动作**的任务（比如"一直往前走 30 秒"），减少落在展开等待期间的概率
2. 看到 agent 在走（`/bt status` 显示"正在执行"某个 Steps，且没有在飞请求）时 `/kill`

**期望**：
- 游戏里按键松开、死亡界面出现后**不用点**约 1 秒内自动重生
- 会话里"死亡恢复请求 rN"：错误一行是死亡信息；目录有 `death` / `respawn` 快照；树里死亡时在跑的节点标 `← 死亡时在跑`；skill 是「慢树恢复」
- 大模型交补丁或放弃

**events.jsonl 里应有**：`player/died` → `task/interrupted`（reason `death`）→ `controls/released` → `player/respawned` → `request`（type `died`）
