## 1. 为什么需要这一层

### 1.1 现状：树能表达什么，不能表达什么

- **能**：分支、顺序、循环、失败恢复、抢占、可观测、可 diff
- **不能**：算法。寻路、配方推导、目标选择、成本估算——这些需要真正的计算，不是控制流

### 1.2 三种把算法塞进树里的写法及其代价

| 写法 | 代价 |
|---|---|
| 在树里搭算术子树（`math.sub` → `math.len` → …） | 树变成表达式求值器；每个中间量占一个黑板键；组合本身不是最小任务（D8）；大模型写算术子树的出错率远高于记住一条命令 |
| 在 `params` / `writes` 里写表达式字符串 | 等于给树语言塞进求值器：要定语法、定类型规则、给出错位置；而且它是**没有注册表的第二套 API** |
| 全推给 `PendingExpansion` | 数值处理是高频运行期的事，不是规划。每轮跑一次大模型，代价荒谬 |

### 1.3 结论

**算法必须在树外。** 剩下的问题只是：它在外面长什么样、和树怎么接。

## 2. 三层职责边界（本方案的框架）

```
┌─────────────┐   handle   ┌──────────────┐   params   ┌─────────────┐
│   Compute   │ ─────────► │  Blackboard  │ ─────────► │   Actuate   │
│ 算法 / 策略  │            │  数据流 / 决策 │            │  原语 / 执行 │
└─────────────┘            └──────────────┘            └─────────────┘
       ▲                                                       │
       └─────────────────── 树：控制流 ───────────────────────┘
```

### 2.1 三层各自负责什么

| 层 | 职责 | 典型产物 | 谁写 |
|---|---|---|---|
| **Compute** | 把大输入坍缩成小决策 | 路点列表、目标坐标、评分 | LLM 进化（§3） |
| **Blackboard** | 层间传值、跨迭代累计、恢复证据 | 句柄、候选列表、计数 | 树上声明（§6） |
| **Actuate** | 与游戏世界交互的最小操作 | 按键、注视、点击 | 人手（§5） |

### 2.2 判定表：一个新能力该放哪一层

| 特征 | 归哪层 |
|---|---|
| 需要遍历/排序/搜索大量数据 | Compute |
| 结果是"某一刻的事实"且无回读通道 | Blackboard |
| 需要在多个节点间传递 | Blackboard |
| 一次按键/一次注视/一次点击 | Actuate |
| 需要多 tick 持续、可能被打断 | Actuate（带 abort） |
| 需要"台阶是 0.5 还是 1 格"这类唯象知识 | Actuate，**且必须人手写** |
| 是分支、重试、抢占、恢复 | **树** |

**【审阅点 1】** 这张判定表是本方案的框架。加新能力时先查它，比事后争论便宜。

### 2.3 不属于任何一层的东西

树自己保留的四件事——**分支、失败恢复、抢占、可观测**——是代码写不好、脚本写不出的那部分。本方案不是"给树加能力"，是**把不属于树的划出去，树才站得住**。

## 3. Compute 层

### 3.1 代码即节点

- 新增叶子类型（暂名 `Compute`），等价于"用户自定义命令"
- 与 [行为树](行为树节点设计方案.md) §9.1 命令注册表的关系：**它就是一条命令**，只是实现来自胶囊库而不是手写
- 【审阅点 2】它的 JSON 形态：`{ "type": "Compute", "skill": "...", "params": {...}, "writes": {...} }`？

### 3.2 参数传句柄，不传集合

**硬规矩。** 如果 compute 的参数是一份数据集合，那这份集合必须进黑板（黑板是节点间传值的唯一通道），大数据问题就回来了。

```
ComputePath(goal, grid_handle)     ← 不是 grid
```

对所有 compute 节点成立，不只是寻路。

### 3.3 沙箱：纯函数

- 无文件系统、无网络、无时钟、无随机
- 需要随机必须显式给种子，否则不可复现
- 只能访问声明过的输入

**实现（2026-10-24，`dsh-plugins/agent/src/capsules/sandbox.js`）**：

- body 是 TS（去类型后运行）或 JS，定义同步函数 `main(params, state)`；不能用 `import` / `export`
- 每次调用一个全新的 `node:vm` context：没有 `require` / `process` / 定时器 / `fetch`，`Date`、`Math.random`、`WebAssembly` 被移除，`eval` / `new Function` 被禁用；模块级变量不会跨调用残留
- 参数、状态、返回值都经 JSON 进出，宿主对象不会漏进沙箱；返回值有字节上限（默认 64 KB）
- **"只能访问声明过的输入"扩展为两类（2026-10-24，[行为树](行为树节点设计方案.md) B12）**：`params`（调用点给的），和 `state`（节点 `read` 声明的状态来源，执行时现场读）。状态只进沙箱、不进黑板
- **`node:vm` 不是安全边界**：它防的是生成代码无意中碰到宿主、死循环卡住 tick，不防蓄意逃逸。胶囊代码来自本项目的大模型、存在本地，这个威胁模型下够用；将来要防恶意代码需换 `isolated-vm` 或独立进程

### 3.4 预算：硬超时 + 指令上限

- 超了立刻 `FAILURE`，不是让它跑完
- **实现**：只有硬超时（Compute 默认 1000 ms，条件代码默认 50 ms），**没有指令计数**——`node:vm` 不提供。实测条件代码单次约 0.5 ms（主要是新建 context）
- 沙箱调用是同步的，超时之前会占住事件循环；预算因此要小。若快树条件多到影响 tick，再改为复用 context 或放进 Worker
- 由来是 [行为树](行为树节点设计方案.md) §7.3：tick 中不许大模型调用 / 阻塞等待 / 服务端往返。一段不受约束的 TS 可以一次违反全部三条

### 3.5 档位：默认 `Action`，运行期实测降档

[行为树](行为树节点设计方案.md) §9.1 的 `cost` 三档是**声明式标签**，但一段 LLM 写的代码算什么档取决于它写了什么——一个本该 `local_cached` 的节点里塞个 O(n²) 循环，声明就是骗人。

~~2. 想升格成 `Condition`，必须有人工审核那一关~~
3. 【审阅点 3】运行期实测首次调用耗时，超阈值自动降档

**2026-10-24 改（撤销 A5）**：读世界的条件也由 agent 写（[行为树](行为树节点设计方案.md) §4.1.1），不经人审。代码条目用 `signature.returns: "bool"` 声明自己是条件；"每 tick 重评"的风险由条件代码更小的硬超时（50 ms）兜住，超时 = 条件不成立。

## 4. 契约：Compute ↔ Follower 的接口

### 4.1 为什么契约是进化的单位

**进化的单位不该是"一个 compute 函数"，也不是"一棵 follower 子树"，而是一份契约。** 两侧各自只是这份契约的一个实现。

技能库里存**接口**（名字 + `params` schema + `returns` schema + 语义约束），实现可以有多个版本。这样"进化出更好的 A\*"就是换 compute 那一侧，follower 一动不动。

### 4.2 为什么这是最容易被忽略、也最难查的失败模式

如果契约不冻结，"配对"就是口头约定。而**失败现象是「走路看起来很怪」，不是报错**。

follower 必须知道的事，一件都不能含糊：

- 离散路点还是连续轨迹？
- **相邻两点之间的距离上限是多少？**（follower 会假设"两点之间可以直线走"吗）
- 最后一个点是不是终点本身？
- 世界坐标还是相对坐标？
- 给"站的位置"还是"方块中心"？

### 4.3 契约的承载者：胶囊条目的 `signature`【已定 2026-10-07】

**契约写在胶囊库条目自带的 `signature` 里**，不是另开一段 `contracts:`，也不靠 `SubTree.params` 的类型标注。

```json
"signature": {
  "inputs":  { "route": { "type": "list", "item": "vec3", "required": true } },
  "outputs": { "nav.lastReached": { "type": "vec3" } }
}
```

理由（三条候选的对比）：

| 候选 | 结论 |
|---|---|
| `SubTree.params` 的类型标注 | **否决**。契约必须同时覆盖 compute 侧和 tree 侧（§4.1）——`SubTree.params` 只管调用点，compute 节点没有地方写类型 |
| 独立的 `contracts: {...}` 段 | **否决**。契约和实现会被改漏一处：改了 `signature` 忘了改 `contracts`，两者不一致时谁说了算没有答案 |
| 胶囊条目的 `signature` | **采用**。`code/` 和 `trees/` 两类条目**共用同一套 `signature` 形态**（§8.1），契约因此天然跨两侧成立；和 [行为树](行为树节点设计方案.md) §9.1 命令注册表的 `returns` 合并，不新增第二套 API |

调用点与实现两侧的校验关系：

- **调用点**（`SubTree` / `Compute` 节点的 `params`）按 `signature.inputs` 校验，缺必填项直接是校验错误（[行为树](行为树节点设计方案.md) §5.3 校验器）
- **实现侧**（`body` 里 `$route` 的读、`outputs` 的写）按同一份 `signature` 校验
- 契约变更 = `signature` 变更 = 哈希变更 = 新条目。**老引用不受影响**（§8.4）

## 5. Actuate 层

### 5.1 微操层不交进化

"前方高差 1 就跳、到了就松 W"——这些是**极其容易错的物理细节**：台阶是 0.5 格还是 1 格、跳跃能不能上 1.25、卡在墙角怎么办、被水推了怎么办。

- 它是**唯象的**，需要反复在游戏里试，不是逻辑推演能得出的
- 让 LLM 每次进化一个"怎么上台阶"，是在重复解决上游已经解决的问题
- 不加这条界，胶囊库里会长满"上台阶的 20 种写法"

**分工：LLM 进化策略层，人手负责执行层。**

**2026-10-24 撤销（A7）**：人只提供 mod 的原始命令（[src/mod/methods.js](../src/mod/methods.js)），其上的一切——包括上面说的微操——都由 agent 在训练地图里学，按 §8.8.2 的准入门槛进胶囊库。本节的担忧（微操是唯象的、容易长出"上台阶的 20 种写法"）仍然成立，对策改为训练流程：每张训练图针对一个变量、多图准入、胶囊复用。

### 5.2 现有 51 个命令的现状与缺口

- 现状：全部是**裸按键**（`key/up`、`key/attack`…）+ 感知命令 + 容器槽位级操作，清单在 `src/mod/methods.js`
- 缺口：**没有一条"走一格""注视并前进"级别的原语**。分段寻路的第一步就卡在这里
- 缺口（2026-10-23 补）：**没有 GUI 级的语义原语**（`craft`、`smelt`……）。确定性的 GUI 流程由人封装成原语，见 [行为树](行为树节点设计方案.md) §9.4

### 5.3 原语该有的粒度

**【审阅点 5】** 两条候选判据：

- 一次调用能在有限 tick 内完成，且能被 abort
- 它对应一个"动作语义"（走一格、跳一次、捡起一个），不是一段流程

~~Follower 的循环**不需要新节点类型**：`Repeat until <黑板列表空>` + `blackboard.pop` 就能表达 `ForEach`~~ **2026-10-24**：改用 `ForEach` 节点（[行为树](行为树节点设计方案.md) §3.5.1）——pop 在处理前就拿走元素，被快树打断时那一项会被静默跳过；（[行为树](行为树节点设计方案.md) §3.5 的 `ForEach` 可以继续暂缓，但那条暂缓理由要改——见 §9 待落地表）。

**未受信的实现在 `capsules/` 里，不在 `src/mod/methods.js` 里**：51 个命令是人写的、装进 mod 的；胶囊是进化的产物，装载时才从库里取（§8.5）。两者走同一套命令注册表（[行为树](行为树节点设计方案.md) §9.1），但来源和信任级别不同。

### 5.4 abort

每个持续型原语必须声明自定义 abort（[行为树](行为树节点设计方案.md) §6.4）。`key/up {pressed:true}` 的 abort 是 `key/up {pressed:false}`——松开按键必须挂在中止路径上，否则树一重置 agent 就一直往前走。

## 6. 数据流与黑板

### 6.1 三种数据规模

| 规模 | 去向 | 例子 |
|---|---|---|
| 小 | **黑板** | 句柄、候选列表、计数、上次失败原因 |
| 中 | 命令的 `returns` | 摘要、统计、少量命中 |
| 大 | **`payload` 缓冲区**（不进树、不进黑板、不进上下文） | 全部可见方块表、记忆世界 dump |

**`returns` 给树看，`payload` 给缓冲区。** 树只能看见 `returns`。

### 6.2 句柄与数据集生命周期

- 新增类型 `handle`（[行为树](行为树节点设计方案.md) §5.3 的类型表现缺 `handle` 和 `list`）
- 句柄**进黑板**：它是"我这次任务看的是哪一份快照"，重拉会得到一份新的，**没有回读通道**
- 数据集要带版本戳；查询命令必须能检测自己那份已过期（记忆世界被新快照覆写后）
- 句柄在 D9 恢复时的作用：让大模型知道"我被打断时用的是哪份数据"

### 6.3 黑板的分层：两级作用域【已定 2026-10-07】

**采用两级作用域链**：任务帧 + 胶囊实例帧，见 [行为树](行为树节点设计方案.md) §5.1.1。

```
任务帧     ← 树主体读写；胶囊的 outputs 拷贝到这里
└─ 实例帧  ← 每次 SubTree / Compute 调用创建一个；capsule 内的名字都活在这一层
```

被否决的方案：**键名拼调用点 `id`**。它要求校验器和写树的大模型都理解一套拼接规则，而收益只是省掉一层查找。两级帧的查找规则是"先实例帧、后任务帧"，大模型只需要知道这一条。

三件必须记住的事：

- **形参、胶囊内部变量、回传都在同一帧里**。胶囊里的名字不带前缀（调用点看不见它们），只有**回传的任务帧键**带前缀（[行为树](行为树节点设计方案.md) §5.3）。
- **帧的生命周期挂在调用点上**，不在迭代上。`Repeat` 迭代不重建帧（[行为树](行为树节点设计方案.md) §3.5 规则 3）。
- **中止时帧不清空**——重置的是树的执行状态，不是任务状态（[行为树](行为树节点设计方案.md) §5.1）。D9 恢复时大模型要能读到"我被打断时实例里剩下什么"。

§6.2 的句柄也走这套帧：句柄进实例帧（胶囊内部用），要跨调用点共享的才由 `outputs` 拷进任务帧。

## 7. 分段式寻路（第一个完整实例）

### 7.1 为什么必须分段

**A\* 假设输入地图是完整的、当前的。缺格在 A\* 里不是「未知」，是「可通行」——它会安静地穿过去。**

steveX 给不出完整地图（见 §7.2），所以全局 A\* 的产物是一条穿墙路径，而且**不报错**。

分段解决了这件事：

- 每段 8~16 格，短到"这一段里我确实看得全"
- 走完一段 → 重看 → 重算。遇到意外时，代价是重算一段，不是全部

### 7.2 局部栅格的来源（2026-10-23 已定）

记忆世界"没去过的地方是空的"这个缺陷仍然存在，处理它是寻路设计的一部分：例如只在见过的区域内逐格规划、未知区域边走边看（分段，§7.1）。寻路属于"有变数的策略"，按 §8.8 在训练地图里迭代成胶囊。

### 7.3 一个分段的形状

```
Repeat until 到达终点:
  ├─ Compute  算下一段（8~16 格）  ref: code/nav.path@<hash>
  └─ SubTree  PathFollower 消费 path   ref: trees/nav.follow@<hash>
```

两个节点各自引用**一个胶囊**（§8），同一个调用点上换实现只改 `ref`。

注意 `Compute` 自己把结果写进黑板（`writes`，[行为树](行为树节点设计方案.md) §5.1.1），不需要中间夹一个"写入 path"的 `Action`——§7.3 的早先版本里那一行是多余的：`Compute` 的 `writes` 就是它。

同一份 `nav.follow` 胶囊被每一段复用，而且**每一段新建一个实例帧**（§6.3）：上一段的 `remaining` 不该漏进下一段。

### 7.4 契约：`nav.path` v1

承载者已定（§4.3）——写成胶囊条目的 `signature`：

```json
{
  "name": "nav.path",
  "signature": {
    "inputs": {
      "start":  { "type": "vec3", "required": true },
      "goal":   { "type": "vec3", "required": true },
      "grid":   { "type": "handle", "required": true },
      "limit":  { "type": "number", "required": false }
    },
    "outputs": { "path": { "type": "list", "item": "vec3" } }
  },
  "preconditions": ["grid.version == current_snapshot"]
}
```

**【审阅点 8】** 还差的是**语义条款**——这些不进 `signature` 的类型，但必须写进条目的文档且两侧都遵守（§4.2 的清单）：

| 条款 | 待定的取值 |
|---|---|
| 点的坐标口径 | 方块中心 / 站立点 |
| 相邻两点距离上限 | 1 格 / 可直线到达的任意距离 |
| 末点语义 | 是否等于 `goal` 本身 |
| 坐标系 | 世界绝对坐标 / 相对 `start` |
| `path` 为空 | 是"已经到达"还是"无路可走" |

## 8. 胶囊库【已定 2026-10-07】

### 8.1 技能库和胶囊库是同一个东西

早先的设想里有两套东西：一套"技能库"装进化出来的函数（Voyager 风格），一套"子树模板"装参数化的行为树。**分开是错的**——两者都是"名字 + 契约 + 实现"，而且契约一侧本来就要跨两侧成立（§4.1）。

统一成一个库，**按 kind 分文件夹存放**（2026-10-14 修订；kind 不再写成字段，见 §8.2）：

| 文件夹 | 谁引用它 | `body` 是什么 |
|---|---|---|
| `capsules/trees/` | `SubTree` 节点 | 一棵子树（`{ type, mode, children }`） |
| `capsules/code/` | `Compute` 节点 | 一段 TS 源码（§3.3 沙箱内运行） |

两类条目**共用同一套 `signature`**（§4.3）。这正是统一的意义：换实现不换契约——把实现从代码换成树（条目从 `code/` 挪到 `trees/`）也是换实现（§8.5 的重写路径）。

### 8.2 条目的形状（2026-10-14 修订）

```json
{
  "name": "nav.goto",
  "hash": "a3f9c1",
  "locked": true,
  "signature": {
    "inputs":  { "route": { "type": "list", "item": "vec3", "required": true } },
    "outputs": { "nav.lastReached": { "type": "vec3" } }
  },
  "preconditions": ["agent.on_ground"],
  "body": { "...": "..." }
}
```

- **`name`**：库内逻辑名，稳定标识。调用点写 `文件夹/name@hash`（前缀 `code/` / `trees/`，§8.3）。
- **`hash`**：内容哈希，覆盖 `signature` + `preconditions` + `body`，**不含 `name`**，也不含 `locked`——开关保护标不产生新版本。
- **`locked`**（可选，缺省 `false`）：防止**删除**——§8.6 GC 与 §8.7 淘汰都不碰 `locked` 条目。防修改不需要它：哈希引用天然锁住（§8.4）。
- **`preconditions`**：能被验证的适用条件（§8.7）。写不出可验证条件的，说明这个契约还没想清楚。

**没有 `kind` 字段**（kind = 条目所在的文件夹，§8.1/§8.3），**没有 `origin` 字段**（2026-10-14 删除）：条目的"人手写 / 进化"不再记录——§3.5 的档位规则按**产出路径**执行（进化管线落地的新条目就是 `Action`），§8.7 淘汰不看出处；要追溯出处，git 提交历史就是记录。

### 8.3 存储布局（2026-10-14 修订）

```
capsules/
  code/                       ← kind 由文件夹承载（另有 trees/）
    vision.find-blocks@1c4d.json
  trees/
    nav.goto@a3f9c1.json      ← 一个条目一个文件
    nav.goto@7b2e40.json      ← 同一 name 的旧版本，仍在被某棵树引用
  manifest.json               ← 每个 name 的"当前最新 hash" + 一句话描述
```

- **一个条目一个文件**：`diff` 干净，加载可分片，篡改/冲突能按条目定位。
- **同一个 `name` 的多个版本共存**：树引用的是哈希（§8.4）。
- **`ref` 强制带文件夹前缀**（2026-10-14 定，【审阅点 12】）：`code/name@hash` 或 `trees/name@hash`——**前缀即 kind**，装载时去前缀对应的文件夹里取 `name@hash.json`；`Compute` 的 `ref` 前缀不是 `code/`、`SubTree` 的不是 `trees/` = 装载错误（静态可判，不必解析文件）。名字**允许跨文件夹重名**，在**每个文件夹内唯一**；同一 `name` 的多个 `hash` = 版本共存（下一条）。
- **`manifest.json` 只记最新哈希**，是给大模型选条目用的**提示词材料**（[行为树](行为树节点设计方案.md) §9.2 的"这份表就是提示词"）——不含 `body`，所以它小到可以整体进上下文；以 `文件夹/name` 为键（重名不冲突），kind 由前缀标出。

### 8.4 版本：内容哈希，引用不随库变

树是大模型生成和修改的产物。它不需要"人可读的版本号"，它需要**引用不会在背后变化**——胶囊库更新后，已保存的树必须仍然指向当初那一版。

- 哈希覆盖 `signature` + `preconditions` + `body`，内容相同即同一条目
- **改一个字符 = 新条目**，老条目原样留下
- 装载时按 `文件夹/name@hash` 精确取；取不到**是装载错误**，不是"退回最新版"

**为什么不能"退回最新版"**：胶囊改版恰恰是因为旧版有缺陷，退回最新版等于让一棵历史树悄悄用上没验证过的实现。D9 的证据链、T4 的 diff 全都建立"同一棵保存的树跑出同样结果"上。

**【审阅点 11】**（[行为树](行为树节点设计方案.md) §8.3）哈希的粒度：改一行注释也换哈希。备选是把注释排除在哈希外。

### 8.5 装载时实例化，不是存储时展开

见 [行为树](行为树节点设计方案.md) §8.3。这里只补一条**进化上的后果**：

因为不展开，**换一个胶囊版本 = 换一个哈希 = 只改树文件里一个字符串**。整个"进化出更好的 `nav.path`"的落地动作，就是把调用点的 `ref` 从 `code/nav.path@old` 改成 `code/nav.path@new`。慢树做这个改动只需要改一行，而且 diff 上就只有这一行。

### 8.6 垃圾回收

**保留所有被某棵已保存的树引用过的版本，其余可回收。**

- 扫描 `src/bt/trees/` 下的全部树文件，收集所有 `ref` 里的哈希 → 这就是保留集
- **`locked` 条目永不回收**（§8.2）——否则"还没被任何树引用过的基础条目"会被裸回收
- 不在保留集里的条目可删，**但删之前先归档**：进化史本身是资产（哪些实现试过、为什么被换掉）
- 回收是**离线**动作，不在 tick 里做（[行为树](行为树节点设计方案.md) §7.3）

### 8.7 规模上限、分片加载与淘汰

- [行为树](行为树节点设计方案.md) §9.2 的"这份表就是提示词"对胶囊库同样成立
- 大模型能可靠选择的条目数是有限的。无限制增长会变成"什么都有、什么都选不对"的抽屉
- **按任务类型分片加载**，不是每次全量塞 prompt
- 技能会过拟合：`nav.path` 在平原上好使、在洞穴里废。只记"成功过"的库会攒下一堆只在特定地形成立的实现
- **`locked` 条目永不进淘汰候选**（§8.2），也不被 GC 回收（§8.6）

**【审阅点 9】** 淘汰/合并机制待定。已有的抓手是 `preconditions` + 成功率记录 + 使用次数，但"什么时候该淘汰""两个条目什么时候该合并"还没有可执行的规则。

### 8.8 进化的触发与验证

**触发**（三条并列）：

1. 任务失败
2. 同一节点反复重试后仍失败（重试计数在节点执行状态里，引擎已经记了）
3. 大模型主动提议

**验证**（两道关）：

- 任务完成判定（[目标Agent画像.md](目标Agent画像.md) §2.5 T3）——跑一遍目标任务，过了才算
- 事件流回归（同上 T9）——新版本在**历史任务**上的事件流不能比旧版本差

**通过验证后的落地动作是 §8.5 的那一行 `ref` 改动**，不是重写树。

**新条目的默认档位**（§3.5）：进化产出的新条目一律从 `Action` 起（出处不再是条目字段，按产出路径执行，§8.2）。

#### 8.8.1 ~~技能的两类来源~~（2026-10-23 定；**2026-10-24 改为：全部由训练得到**）

**2026-10-24 用户决定**：确定性协议（合成、熔炼……）也由 agent 训练得到，不再人写原语。人写的 `craft` 等原语、感知条件、配方表已删除；agent 学这些用的工具是条件代码、可读状态的 Compute、`ForEach`、`expect`，以及查配方用的 `code/core.json.query`（白名单里只有处理好的 `recipes.json`，[json查询api设计方案.md](json查询api设计方案.md)）。

下表保留作历史记录。它提出的风险仍然成立：确定性协议"规则全在源码里，靠猜很容易错"——对策是 agent 先查事实库 / 源码再写（事实流程），以及 §8.8.2 的可观测性（`expect` + 前后差异）。

~~不是所有高层动作都该靠训练得到。按技能的性质分两类：~~

| 类型 | 例子 | 怎么得到 | 训练地图的作用 |
|---|---|---|---|
| **确定性协议** | 合成、熔炼、附魔、切石机、村民交易 | 人写成语义原语（[行为树](行为树节点设计方案.md) §9.4），或大模型对照源码写一次、人审阅后 `locked` | 只做**验收测试** |
| **有变数的策略** | 寻路、找资源、挖矿、战斗、搭桥 | 大模型在训练地图里**迭代进化**成胶囊 | **主战场** |

**理由**：确定性协议只有一个正确答案，规则全在源码里（槽位编号、配方形状、Shift 点击的行为），用试错去学等于重新发现源码，而且大模型靠猜很容易错。地形、生物这些变量让人写不出通用解，进化才有意义。

#### 8.8.2 训练流程与胶囊准入（2026-10-23 定）

**先补可观测性，再开始训练。** 每个最小任务结束后，执行器给出**期望与实际的差异**（例如"预期 slot 0 有 3 个铁锭，实际为空"），连同事件流交给反思。原因：[行为树](行为树节点设计方案.md) §9.3.1 已核对过，`waitMs` 赌输时服务端静默覆盖客户端，日志上每一步都显示 ok——没有差异报告，大模型只看到"全部成功，但背包里没东西"，无从定位，只能乱改。

**自底向上训练，每层设准入门槛**：

1. 推荐顺序：注视方块、走到相邻格 → 挖一个方块、拾取 → 寻路 → 采集资源 → 组合任务
2. 一个胶囊要在**多张没见过的测试地图**上达到成功率门槛才能进库，作为下一层的积木。门槛初值 **≥ 95%**，训练时再调
3. **为什么要门槛**：误差逐层累积。成功率 95% 的胶囊串 20 个，整体只剩约 36%；底层不够可靠，上层训练无法收敛

**训练地图的设计**：

- **每张地图针对一个变量**（台阶、水、洞穴、黑暗、敌对生物……）
- **训练图与测试图分开**。准入只看测试图的成绩
- 胶囊的 `params` 不得写死某张图的坐标——"多图准入"会自然逼出这一点，也是 §8.7"技能会过拟合"的直接对策

#### 8.8.3 实现状态（2026-10-24）

`dsh-plugins/agent/src/capsules/`：库（`library.js`，内容哈希 8 位、manifest、磁盘篡改检测）、沙箱（`sandbox.js`）、保存时校验（`save.js`）、内置条目（`builtins.js`：`core.json.query` / `core.nbt.query`，宿主实现、只在内存里、`locked`）。库目录默认 `steveX/src/capsules/`。

- `SubTree` 已实现：装载时实例化，实例帧、outputs 回传、嵌套上限 8、递归检测（[行为树](行为树节点设计方案.md) §5.1.1）
