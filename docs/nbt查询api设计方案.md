## 1. 问题与用途

- **场景**（"事实确认 / 搜索记忆世界"）：记忆世界里某个箱子装了什么、某类实体在哪、某个方块实体的内容。数据已经在 **落盘 NBT 文件**里（采集端 `run/stevex/vision/`：`entities_union.nbt`、`containers/`、`block_entities/`、`biomes/`、`terrain*`），量级从"万条记录"到"百万格"。
- **目标形状**：与 §8.9 `vision.find-blocks` 同款——**大输入在库内部坍缩，只出短列表**（§3.2）。
- **非目标**：写 NBT；任意文件读取；通用 JSONPath/查询语言；把全量数据塞进黑板或模型上下文；跨数据源的联合查询（一次调用 = 一个数据源）。

## 2. 定位

### 2.1 条目与落点（2026-10-14 修订）

```
name:          core.nbt.query
locked:        true            ← 本方案新增字段（§2.2）
signature:     见 §3
body:          TS：纯筛选/投影/截断（沙箱内运行）
```

存放：**`kind` 由文件夹承载**（2026-10-14 修订）——代码条目落 `src/capsules/code/`，行为树逻辑链落 `src/capsules/trees/`；引用**强制带文件夹前缀**：`code/name@hash` / `trees/name@hash`（§8.3，2026-10-14 定）。

`origin` 字段删除：出处（人手写 / 进化）不参与任何已定机制——"不许淘汰"由 `locked` 表达，质量信号将来用使用统计或审查状态更合适；要追溯条目是谁写的，git 提交历史就是记录。（原形状 `name/kind/hash/origin/…` 来自 [算法层与执行层设计方案.md](算法层与执行层设计方案.md) §8.2；已于 2026-10-14 写回，见 §10 审阅点 8。）

裁决细则（**已定 2026-10-14**）：条目**名字允许跨文件夹重名**，在单个文件夹内唯一；`ref` **强制带文件夹前缀**——`code/name@hash` 或 `trees/name@hash`，**前缀即 kind**；`Compute` 的 `ref` 前缀必须是 `code/`、`SubTree` 必须是 `trees/`，不一致 = 装载错误（静态可判，不必解析文件）；`manifest.json` 以 `文件夹/name` 为键（重名因此不冲突），kind 由前缀表达（提示词材料要用）。（历史：2026-10-14 前曾倾向"全局唯一"以避免前缀，已否决——见 §10 审阅点 12。）

### 2.2 `locked`（新字段提案）

§8.4 的哈希引用已经保证**改不了**（改一个字符 = 新条目）。`locked` 解决剩下的一半——**删不了**：

- §8.7 淘汰永不把 `locked` 条目列为候选；
- §8.6 GC 永不回收 `locked` 条目（否则"还没被任何树引用过的基础条目"会被裸回收）；
- 仓库层是最后一道：文件在 `src/capsules/` 由 git 跟踪，删改走 review。

`locked` 管的是"能不能删"，与"谁写的"是两个问题：将来一定有"人写的、但该退役的早期试错条目"，也一定有"进化出来的、但很好用"的条目。（`origin` 字段已删，见 §2.1；将来若代码审查方案需要区分进化产物，用审查状态字段，别复活 `origin`。）

### 2.3 层级核对（§2.2 判定表）

| 特征 | 归类 | 本 API |
|---|---|---|
| 需要遍历/筛选大量数据 | Compute | ✅ 筛选在沙箱（纯函数） |
| 结果是"某一刻的事实"、无回读通道 | Blackboard | ✅ 命中列表进黑板 |
| 一次读盘 → 一份快照 | 句柄 | ✅ `sourceVersion`（§6.2） |
| 与游戏世界交互 | Actuate | ✗ 本 API 不碰游戏，只读盘 |

**`cost` 档位 = `local_scan`**（§9.1）：本地但要扫描。**仅允许在任务树的 Compute 节点中引用；快树禁止引用（因 cost 档位为 local_scan）。**

## 3. 接口

### 3.1 输入（4 个，顺序固定）

| # | 名 | 类型 | 必填 | 语义 |
|---|---|---|---|---|
| 1 | `filters` | object | 否（缺省 `{}` = 全部命中） | 键 = 记录内路径（§4.2），值 = 条件（§4.3）；**多键 = AND** |
| 2 | `fields` | string[] | **是，非空** | 投影：只输出列出的路径（§4.4）。**无默认值**——不给"全字段"兜底，防止意外大结果 |
| 3 | `limit` | int | 否（缺省 64） | 最大返回条数，1..512 |
| 4 | `path` | string | 是 | 目标数据源。**取值域 = 五个数据源标识之一**（`entities` / `containers` / `block_entities` / `biomes` / `terrain`，§4.1）；**不接受任何文件路径**（§6.1） |

**四个参数全部必须是字面量**（v1 不允许任何 `"$键名"` 引用，`limit` 也包括在内）。理由：`path` 字面量 → 数据源与输出 schema 可在**装载期**静态确定（特化见 §3.2）、白名单可静态判定（§6.1）；`filters` / `fields` 字面量 → 语义静态可查，便于人工审阅与 diff。放开动态是后续的事（§10 审阅点 1：`filters` / `fields` 2026-10-14 定，`path` / `limit` 2026-10-17 定）。

（`filters` 在 `signature` 里记作 `object`——这是**校验词汇**，不属于黑板值类型表（§3.2）。）

### 3.2 输出（写黑板）

| 键 | 类型 | 说明 |
|---|---|---|
| `result` | `list<record>` | 命中并投影后的记录，**扁平 KV**（键 = `fields` 里写的路径字符串；"扁平"只约束**顶层键名**，值允许复合结构——整列投影出的 `state` / `items` 就是对象）；顺序 = 记录集原始顺序（v1 不排序） |
| `matchedCount` | number | **截断前**的命中总数（让大模型知道"是差一点还是差很多"） |
| `sourceVersion` | string | 数据源快照版本戳（§5.1），供下游/证据链检测过期（§6.2） |

- 键名（写入哪个黑板键）由**调用点**声明，走 §5.3 校验器的"未声明的写"检查。
- `record` 不在黑板类型集合（行为树 §5.2：number/boolean/string/vec3/itemStack/list）里——**不新增类型**（已定 2026-10-14）：由校验器按 `fields` 字面量**特化**，输出每列的列名与类型在装载期算出。自由形态 NBT 的列（`nbt.*` / `item.components.*`）类型静态不可知，特化对它们只能记"未知列"。**这是本方案唯一触碰类型系统的地方，而它的结论是"不动底层类型表"**（§10 审阅点 2）。**落地时机（2026-10-17）**：特化规则属于校验器，校验器整体暂缓——v1 照常产出结果，只缺这层装载期检查，随校验器一起补。
- **v1 不输出句柄**（2026-10-17，方案 a）：同一任务内的重复查询由宿主缓存命中同一快照（§5.1 / §5.4）；跨调用点共享句柄推迟到 v2。

### 3.3 调用点示例（树文件里的形状）

```json
{
  "type": "Compute",
  "ref": "code/core.nbt.query@9c1a",
  "params": {
    "path": "entities",
    "filters": {
      "id": "minecraft:item",
      "item.id": "minecraft:diamond",
      "pos.x": { "min": -64, "max": 64 }
    },
    "fields": ["uuid", "pos", "item.count"],
    "limit": 32
  },
  "writes": { "nearby.drops": "result", "nearby.count": "matchedCount", "nearby.version": "sourceVersion" }
}
```

语义：在实体快照里找**掉落物**，物品是钻石、x 在 [-64,64]，最多 32 条，每条只带 `uuid / pos / item.count`，结果放 `nearby.drops`。

`writes` 的映射方向：**左 = 黑板键，右 = 返回值字段**（行为树 §8.1）；带前缀的键名（`nearby.*`）写任务帧（行为树 §5.1.1）。

## 4. 语义细则

### 4.1 数据源与记录集

**记录集**（"被筛选的东西"）按数据源定义，不由调用方指定：

| `path` | 记录集 | 记录粒度 | 隐式字段（可筛选/可投影） |
|---|---|---|---|
| `entities` | `entities_union.nbt` 各维桶合并（单文件，不切分） | 每个实体一条 | `uuid`、`dim` |
| `containers` | `containers/` 分片目录（含 `ender.nbt` 全局桶） | 每个容器一条 | `pos`、`dim`、`scope`（**硬编码枚举**：`"container"` / `"ender"`） |
| `block_entities` | `block_entities/` 分片目录 | 每个方块实体一条 | `pos`、`dim` |
| `biomes` | `biomes/` 分片目录 | 每个 quart cell 一条 | `quart`、`dim` |
| `terrain` | `terrain_union/` 分片目录 | 每个方块一条 | `pos`、`dim` |

**载荷字段一览（2026-10-14 逐项核对 mod 写入代码，【审阅点 9】收口）**：`?` = 条件出现；复合体（`item` / `nbt` / `living` / `state`）可继续下钻（§4.2），数组（`items` / `cells`）v1 只能整列投影。

- **`entities`**（源 = `entities_union.nbt`；瞬时 `entities.nbt` 不开放——它多一个 `view` 薄投影、少 `cells`，且不累积）：`id`(number)、`type`(string，**叫 `type` 不是 `typeId`**)、`pos` / `motion`(vec3)、`rotation`(vec2，`x`=yaw、`y`=pitch)、`onGround`(boolean)、`health`(number)；条件键：`item?`（掉落物才有；内含 `id` / `count` / `components`）、`nbt?`（白名单展示实体才有，整份可装载 payload）、`living?`（活体才有、可为空 `{}`——**缺席 = 非活体**，筛 `living.x` 会排除非活体，§4.3；子键 `equipment` / `customName` / `customNameVisible` / `baby` / `pose` / `onFire`）、`cells`（string[]，**union 独有**——AABB 占用格）。
- **`containers`**：`typeId`(string)、`block`(string)、`state`(对象，**值全是 string**)、`items`(list，元素 = `slot`(number) + `item?`(整份物品栈)；空槽不写)。末影箱条目（`ender.nbt`）：只有 `items`，隐式 `scope` = `"ender"`、无 `pos` / `dim`。
- **`block_entities`**：`typeId`(string)、`block`(string)、`state`(对象，string 值)、`nbt`(对象，该 BE 整份存盘 NBT——无内容时为空 `{}`、键恒在)、`timestamp`(long，最后变化毫秒)。
- **`biomes`**：`biome`(string)。
- **`terrain`**：`block`(string)、`state`(对象，string 值)。

- **分片透明**：`containers/`、`block_entities/`、`biomes/`、`terrain_union/` 都是"分片目录 + `_index.nbt`"形态。**宿主装载时按 `_index.nbt`（+ 目录枚举）合并全部片区**，调用方看见的是一个数据源，不是一堆文件。
- **`terrain` 记录 = 一个方块**（2026-10-14 随审阅点 5 入 v1）：载荷 = 区文件 `blocks` 桶值 `{block, state}`，`pos` 由桶键 `"x,y,z"` 解码。这是**体量最大**的数据源——一个片区地表约 26 万格、跨区查询轻易上百万条；`limit` 管输出，扫描耗时靠 §3.4 超时兜底（区裁剪见 §5.1 与 §10 审阅点 13）。瞬时 `terrain.nbt` **不开放**：它不累积，agent 要的是"记忆世界里有什么"（[累积观测文件设计方案.md](累积观测文件设计方案.md) §1.1）。
- **`biomes` 记录 = 一个 quart cell**（同上入 v1）：载荷 = biome id 字符串（区文件 `cells` 桶值），桶键 `"qx,qy,qz"` → 隐式字段 `quart`。坐标是 **quart 口径**（1 quart = 4 格），别与 `pos` 混用；`quart` 是 [qx,qy,qz] 数组，`.x`/`.y`/`.z` 糖见 §4.2。
- **遗留细节（2026-10-14 核对时发现）**：`timestamp` 是 long，**一律降级为 JS number**（这些文件里的 long 全是毫秒时间戳，远小于 2^53；**杜绝 BigInt**，2026-10-17 定）；其余 `living` 子键的类型实施期细核。**实现注记（2026-10-17）**：NBT 没有 boolean——`onGround` 与 `living.customNameVisible` / `baby` / `onFire` 由装载器把 TAG_Byte 归一为 boolean（其余子键原样保留）。提示词注意：entities 用 `type`、block_entities / containers 用 `typeId`；`state.*` 值全是 string（`state.lit` 要写 `"true"` 而非 `true`，§4.3 无隐式转换）。

### 4.2 路径语法

- 键是**记录内**的点分路径：`item.id`、`living.health`、`pos.x`。
- 路径走**嵌套对象**；坐标字段（`pos`、`quart`）是数组，但固定允许 `.x` / `.y` / `.z` 后缀（= 第 0/1/2 个元素）——这是**坐标糖**，不是通用数组下标；**数字下标（`items[0]`）与存在量词（`items[].id`）都不做**（§10 审阅点 4）。容器里的物品数组整列投影出来（`fields: ["items"]`），由后续节点处理。
- 路径不存在 ≠ 错误：见 §4.3。
- **已知限制（v1）**：NBT **键名自身含 `.`** 时（自由形态的 `nbt` / `components` 里可能出现）无法下钻到该键——点号一律按层级分隔符解释，不支持转义。

### 4.3 筛选条件（filters）

值是**按字面量形态**判定的条件，不做隐式转换（`"32"` ≠ `32`）：

| 字段类型 | 允许的写法 | 语义 |
|---|---|---|
| number | `32` | 等于 32 |
| number | `{ "min": 0, "max": 64 }` | 闭区间（两端可省略其一，表示单侧开） |
| number | `[c1, c2, …]`（元素为数字或区间对象） | **并集**，命中任一即匹配 |
| string | `"minecraft:stone"` | 精确匹配（大小写敏感） |
| string | `["a", "b"]` | 枚举并集 |
| boolean | `true` / `false` | 单值，不搞并集（无意义） |

**编码裁决：区间用对象 `{"min","max"}`，数组一律是"并集"，不是区间。** 若用 `[0, 64]` 表示区间，就与"0 或 64（两个单值）"产生**同形歧义**——条件语法里不允许有这种特例。（2026-10-14 已定：不加。）

匹配规则：

- 多键之间 = AND。
- 字段**缺失**、**类型不符**、**路径类型不对**（如对数组取 `.x`）→ **该记录不匹配**（filter 语义，不报错、不中断）。
- 空 `filters` = 全部记录命中（等价于"取前 limit 条"）。

### 4.4 投影（fields）

- 输出记录的键 = `fields` 里写的路径字符串本身（**扁平**，如 `"item.count"`），**不重建嵌套结构**。理由：黑板是扁平 KV；点号路径 → 输出键 1:1 无歧义；嵌套重建会让"字段缺失"与"空对象"难以区分。
- 某条记录缺某个投影字段 → 该键**缺席**（不出现在这条记录里），不写 `null`、不报错（沿用 entities 里 `enchanted`/`equipment` 只在存在时出现的既有口径）。

### 4.5 limit 与大小预算

- `limit` ∈ [1, 512]，缺省 64。超 `limit` → **截断**（取前 N 条），`matchedCount` 报告截断前总数；**截断不是失败**。
- 另设**字节上限**（具体值实测后定，§10 审阅点 7）：投影后仍超字节上限 → 继续截断，直到入界。目的：`limit` 只约束条数，管不住"一条记录里塞了个超大数组"。本 API 用**自我截断**保证永不超限；全系统的兜底是执行器的**写入关卡**（任何黑板写入超限 = 拒绝、节点 FAILURE，2026-10-14 定，见 [行为树节点设计方案.md](行为树节点设计方案.md) §5.3）。
- `terrain` 是唯一会让 `matchedCount` 到**百万级**的数据源：`limit` 保护输出，扫描耗时按 §3.4 硬超时（区裁剪见 §5.1 / §10 审阅点 13）。
- 超时按 §3.4：**硬超时 → FAILURE**，不是"跑完再说"。首次实测后给预算值。

## 5. 执行模型：两段式

### 5.1 装载：静态校验 + 懒装载（2026-10-17 定）

**树装载不读盘。** 分两段：

**① 树装载期（静态校验，零 I/O）**：`path` 必须是五个数据源标识之一（§6.1）；四个参数都是字面量且形态合法（§3.1 / §4.3 / §4.4，`limit` 在 1..512）。不合格 = **装载错误**，树不实例化。

**② 节点首次执行前（宿主装载，有 I/O）**：

1. 读盘、自动识别 gzip/zlib/裸 NBT、解析；分片源按 `_index.nbt` 合并；
2. 结果放进**宿主缓存**（大对象，不进黑板、不进上下文，§6.1），~~按 `(path, 任务)` 钉住——同一任务内所有调用点共享这一份快照，任务结束释放~~ **2026-10-25 改为按 `(path, 版本戳)`**：每次查询先只 stat 取版本戳，没变就复用已解析的结果、变了就重新装载（见 [P2实施细则.md](P2实施细则.md) §6.3）；**v1 不把句柄写黑板**（方案 a，§5.4），重复查询直接命中缓存；
3. 生成**版本戳**写进 `sourceVersion`。逐源规则：单文件源（`entities_union.nbt`）= mtime + 尺寸；分片源 = `_index.nbt` 的 mtime + 尺寸（containers 另并 `ender.nbt` 的 mtime + 尺寸；`block_entities` **不含** `_pose.nbt`——姿态每帧变、且不属于记录集）；
4. **装载实现注记**：区目录只枚举 `r.<rx>.<rz>.nbt`，**跳过 `_index.nbt` / `_pose.nbt` 等非区文件**；**维名以区文件自报的 `dimension` 字段为准**（目录名 `minecraft_overworld` 是不可逆转义）。

**读一致性（为什么需要）**：落盘的**触发**只发生在采集 API 内（没有周期性任务），但读侧仍可能撞上写入，原因有二——① `terrain_union` / `entities_union` 走 `UnionSaveScheduler`：限频（最短 5s）+ 后台 daemon 线程，盘写会**晚于**触发它的 API 调用；② 分片源在采集调用路径内同步 `VisionRegions.commit`，但**跨区文件不是一组原子提交**（区文件先写、`_index.nbt` 最后写）。每个文件本身是原子写（临时文件 + 改名），读到的永远是完整文件；**跨文件可能读到相邻两代**。对策：读前、读后各取一次版本（第 3 条的规则）——不一致就**重读一次**，仍不一致 → FAILURE（`SOURCE_UNSTABLE`）；分片源另逐区核对「区文件自报的 `updatedAt` == 索引条目」，不等说明撞上了 commit 的中间态，同样重读。读到的快照最多比现实旧 5s，那是允许的陈旧，不是不一致。

**区裁剪（优化；规则先定死，v1 全扫——2026-10-14 定：先不考虑启用）**：`terrain` / `biomes` 的片区按 x/z 二维切（terrain：块坐标 `x >> 9`；biomes：quart 坐标 `qx >> 7`——等价于块坐标 `x >> 9`；区覆盖全高，`y` 不参与定位）。若启用：filters 里 `pos.x` / `pos.z`（biomes 是 `quart.x` / `quart.z`）能推出**闭区间并集**时，只读与之相交的片区；`dim` 为单值/枚举时只读相应维桶；**任一项推不出 → 全读**（保守优先）。裁剪只省 I/O、**不参与命中判定**——语义与全读逐条一致。

### 5.2 运行期（沙箱内，纯函数）

`body` 只接收宿主传入的**快照**（内部以句柄指代）+ `filters` + `fields` + `limit`，做筛选 → 投影 → 截断，产出 §3.2 的三个输出。**沙箱内零 I/O**。

### 5.3 被否决的做法（记录）

| 做法 | 否决理由 |
|---|---|
| 沙箱内直接读文件 | 违反 §3.3（无文件系统）；且等于给生成代码开 fs 后门 |
| 每次查询重读文件 | 破坏可复现（同一棵树跑出不同结果，§8.4）；与 §6.2 的"快照句柄"冲突 |
| 每次查询重新解析 | 同一任务多次查询要重复解析 9MB 级文件；缓存按 mtime 生效后不必要 |
| 全量解析结果进黑板 | §6.1：大 → 缓冲区；黑板只放"能进上下文"的量级 |

### 5.4 后续节点怎么继续处理同一份数据

全量进缓冲区、黑板只放短结果（v1 不暴露句柄，见下），**不削减任何能力**。树节点可以挂 TS 代码，遍历几万条是它本来就有的能力——这个 API 本身就是挂在节点上的 TS 代码。能力来自"拿得到数据"，与"数据物理上放在哪"无关：§3.2 的规矩就是**参数传句柄不传集合**。

| 后续节点想要 | 路径 |
|---|---|
| 直接要结论 | 读黑板的 `result` / `matchedCount` |
| 在同一份快照上做另一种计算（排序、分桶、统计） | **v2**：声明一个 `handle` 输入参数，宿主把该快照交给它，在沙箱里遍历全量（v1 不暴露句柄） |
| 换一种筛法 | 再调一次 `core.nbt.query`（第二遍命中**同一份内存快照**，不重读盘、不重解析） |

把全量数组直接当黑板普通变量也能跑，但黑板后面挂着一串机制：校验器类型检查（[行为树节点设计方案.md](行为树节点设计方案.md) §5.3）、任务帧/实例帧两级作用域、任务恢复（D9）要连它一起存取、以及任何把黑板整体序列化/落盘的机制——这些机制面向的是"可声明、可检查、可整体序列化的值"。§6.1 把"大"划给缓冲区，正是为了让它们不必面对 MB 级数据。**放与不放，节点能力一样；放，是让所有碰黑板的机制都变成 size-aware。**

**决策记录（2026-10-14）**：选定方案 A——全量走缓冲区 + 句柄，黑板只放短结果。理由：保住黑板上的值可整体序列化这条系统级不变量，让日志/恢复/调试面等后续机制都不必再关心大小；代价是多一个缓冲区 + 句柄概念。（LLM 通道不受影响：黑板给大模型看的是变量名、变量类型、内容概括，不是完整值。）**补充（2026-10-17，方案 a）**：v1 的句柄只存在于宿主内部，不进黑板；同一任务内重复查询按 `(path, 任务)` 命中缓存。把句柄作为黑板变量暴露是 v2 的事。

## 6. 安全

### 6.1 路径白名单（收紧用户原型里的"任意路径"）

- `path` **只接受五个数据源标识**（§4.1 表），且必须是字面量（§3.1）——**不接受任何文件路径形态**：`..`、绝对路径、`vision/` 相对路径、符号链接一概不认。没有目录可遍历，逃逸面在语法层就被消掉。
- **为什么这不是矫情**：`steveX/configs/environments/` 里是 API 密钥。若 path 无限制，一句 `"path": "../../configs/environments/xxx.json"` 就是任意文件读取；而写树的恰恰是大模型。
- 解析器与 mod 侧 `NbtIo` 的口径差异（modified UTF-8、压缩方式、long→number——**杜绝 BigInt**）需专测（§11）。

### 6.2 解析健壮性

- 只读，永不写回；
- 深度/长度上限，防 zip bomb 与深递归；
- 解析失败 = 明确错误（§7），不产出"看似空的"结果。

---

## 7. 失败模式

**空结果与失败必须可区分**——否则大模型会把"读不到"当成"没有"，这是错误决策的直接来源。

| 情形 | 结果 |
|---|---|
| 无记录命中 | **SUCCESS** + `result: []`、`matchedCount: 0` |
| 文件不存在 / 不可读 | **FAILURE** + `SOURCE_MISSING` |
| 解析失败（半截写、损坏） | **FAILURE** + `SOURCE_CORRUPT`（采集侧既有"半截写"现象；节点可被树重试/反思） |
| 读盘期间被刷盘改写（版本前后不一致，重读一次仍变） | **FAILURE** + `SOURCE_UNSTABLE`（§5.1 读一致性） |
| `path` 越界 / 非白名单 | **装载错误**（校验期拦截，不进运行期） |
| `filters` / `fields` / `limit` 形态或取值非法 | **装载错误**（校验器按 §4.3/§4.4 判形态；`limit` 须在 1..512） |
| 超过字节上限 | SUCCESS + 截断 + `matchedCount` 如实 |
| 硬超时 | **FAILURE**（§3.4） |

## 8. 生命周期与可复现

- 版本戳语义走 §6.2；**v1 不把句柄写黑板**（方案 a，2026-10-17）：同一任务内重复查询命中宿主缓存（§5.1），句柄只在宿主内部存在。
- ~~**快照语义：首次执行时冻结、按任务钉住**（§5.1 懒装载）。任务运行期间文件被 mod 覆写，本任务内的多次查询仍看同一份快照（可复现，对齐 §8.4"同一棵保存的树跑出同样结果"的取向）~~；**2026-10-25 改（P2-D15）：每次查询读当前版本**，一致性只在一次查询之内。按任务钉住会让树里的"复查"永远读到旧数据，记忆过期就只能靠执行器替树盯着（依赖集，已删除）；回放需要的可复现性由事件日志里每次查询的版本记录（`query/version`）提供。`sourceVersion` 仍是"世界已换代"的依据：修复请求的目录用它列出读过之后又变了的数据源（P2-D17）。装载器另有只 stat 的 `version(path)`。
