# 坏工具参数定位设计方案

> 状态：**已实施**（2026-11-24），单元测试通过，待实际出现坏工具参数时按 §6 第 5 条确认。审阅结论：决策点全部按建议执行。实施说明见 §7。
>
> 目标：模型返回的工具参数不是合法 JSON 时，重试消息里告诉 agent **错在哪**：哪个工具调用、解析器报的错（第几行第几列），以及出错位置前后的原文。只给证据，不教怎么改。
>
> 起因：`task-20261124134735-3`（弓箭训练）的规划回合出了一次 `DeepSeek Messages stream: tool input is invalid JSON`，重试消息只有这一句。agent 不知道自己写了什么、错在哪，只能盲目重试；这类不计次的重试一共只有 2 次。

## 1. 现在的流程

1. DeepSeek 适配层收完一条消息，逐个解析工具调用的参数；解析失败就抛 `MALFORMED_RESPONSE`，消息是固定的一句话。
2. DSH 发 `agent/error`，插件的 `index.js` 交给 `fastBridge.onTurnError` 或 `bridge.onTurnError`。
3. 桥判断是"坏工具参数"（`isMalformedError`），前 2 次不计入不合法尝试，按 `retry.md`（复盘用 `reflect_retry.md`，快树用 `fast_retry.md`）发一条重试消息，把那句错误原样贴进去。

## 3. 总体设计

1. 新文件 `src/llm/tool_input_trace.js`：
   - 按会话（agent id）记下**最近一次请求**里各工具调用的名字和参数原文；
   - 出错时对这些原文逐个解析，找出第一个解析失败的，生成出错位置的说明。
2. `index.js`：
   - 听 `agent/assistant-stream`，把块交给它；
   - 在 `agent/error` 里，坏工具参数时取出说明，交给两个桥的 `onTurnError`。
3. 三个重试模板各加一段 `{{detail}}`，放在错误原文后面。
4. 参数原文完整存一份到 `runtime/malformed/`，给人排查用；不全部发给 agent（可能很长）。

## 4. 决策点

### Q1　原文从哪里来

从 `agent/assistant-stream` 的块里拼（F2、F3）。

- 不读 DSH 的会话日志：那是 DSH 的数据，格式也不归我们管。
- 每个会话只留最近一次请求：
  - 收到 `start` 就清空重来（DSH 自己重试时，每次请求各有一个 `start`，留下的就是最后报错的那一次）；
  - `agent/error` 取走后删掉。
- 内存上限：每个会话最多记 2 MB 的参数原文，超出的部分不再记，并在说明里写明"原文太长，只记了前 2 MB"；最多同时记 32 个会话，超出的丢掉最久没动的。

**建议：采用。**

### Q2　告诉 agent 什么

只列事实：

- 出错的是这条消息里的第几个工具调用、工具名、一共几个；
- 参数原文的长度（字符数）；
- 解析器原样的报错（含第几行第几列）；
- 出错位置前后各 80 个字符的原文，出错点用 `⟦✗⟧` 标出。前后截断的地方用 `…` 表示。

**原文里的控制字符显示成可见符号**：换行显示成 `␊`、制表符显示成 `␉`、其他码值 < 32 的字符显示成 `␀` 一类的符号。JSON 字符串里直接出现换行本身就是一种常见错误（`Bad control character in string literal`），原样贴出来就看不见了。

示例：

````
出错的是这条消息里的第 1 个工具调用 `bt_submit_tree`（共 1 个），参数原文 12345 个字符。解析器报错：

```text
Expected ',' or '}' after property value in JSON at position 5210 (line 1 column 5211)
```

出错位置前后的原文（⟦✗⟧ 是解析器停下的位置）：

```text
…"body":"function main(p) { return { ok: p.n > 0 } }"⟦✗⟧ "signature":{"inputs":…
```
````

- 代码块的围栏按原文里最长的一串反引号加长，原文里有 ``` 也不会把格式弄乱。
- **拿不到原文时**（没收到块，或者重新解析都通过了）：这一段写"（拿不到这次工具参数的原文，指不出出错位置）"，其余照旧。
- **不给建议**：不写"应该加逗号""把提交拆小"之类的话。

**建议：采用。**

### Q3　放在哪些重试消息里

三个模板都加：`retry.md`（规划、展开、修补）、`reflect_retry.md`（复盘）、`fast_retry.md`（快树）。

- 位置：紧跟在 `{{error}}` 那个代码块后面，变量名 `{{detail}}`。
- 不是坏工具参数的出错（网络故障、其他错误），`{{detail}}` 为空，消息和现在一样。

**建议：采用。**

### Q4　给人看的记录

- 每次坏工具参数，把出错那次请求的全部工具调用（名字 + 原文）、错误、会话、回合、请求号写成一个文件：`runtime/malformed/<时间>-<会话>.json`。
- 只留最近 50 个文件。`runtime/` 本来就只留本地、不进 git。
- 桥的日志多一行，例如：`[bt] p3: malformed tool input in bt_submit_tree at line 1 column 5211 (12345 chars)`。

**建议：采用。**

### Q5　快树模板里那句猜测

`fast_retry.md` 末尾那句"多半是一次提交太长……"（F7）是在教方法，而且是猜的。有了真实的出错位置，建议**删掉**，换成 `{{detail}}`。

**建议：删掉。**

### Q6　不变的部分

- 重试次数规则不变（F6）。
- 训练记录里的 `malformedTurns` 不变。
- 不改 DSH 的代码，也不改出错时 DSH 怎么处理这个回合。

## 6. 验收清单

单元测试：

1. 按 F2 的形状喂几组块（一个调用、多个调用、第二个坏、参数分很多段），能拼回原文，指出第一个解析失败的调用、报错和位置，片段里出错点、`…`、控制字符的显示都对。
2. 收到新的 `start` 会清空上一次请求；超过 2 MB 的原文会截断并写明；超过 32 个会话会丢掉最久没动的。
3. 坏工具参数时三种重试消息里都有这一段；拿不到原文时是那句"指不出出错位置"；不是坏工具参数时这一段为空，消息和改动前一样。
4. `runtime/malformed/` 只留最近 50 个文件。

实际运行：

5. 下次自然出现坏工具参数时：
   - 重试消息里的位置和片段，和 `runtime/malformed/` 里存的原文对得上；
   - 日志里有那一行。

   F4 的先后顺序也在这时确认：说明不是"指不出出错位置"。

## 7. 实施说明（2026-11-24）

改动：`src/llm/tool_input_trace.js`（新）、`src/index.js`、`src/llm/bridge.js`、`src/llm/fast_bridge.js`、`prompts/requests/retry.md`、`reflect_retry.md`、`fast_retry.md`；测试 `test/tool_input.test.js`（新，5 条，也加进根目录的测试列表）、`test/bridge.test.js`（新增 1 条）。插件 355 条、根目录 354 条通过。

- `ToolInputTrace.onFrame`：`start` 清空重来；只收 `tool-call-delta` 块，按 `index` 拼原文，名字取第一块带的；没有 `start` 的块（插件中途加载）不记。会话按最近有动静排序，超过 32 个丢最前面的。
- `diagnose`：按 `index` 顺序逐个 `JSON.parse`，原文为空的跳过；位置取报错里的 `at position N`，"Unexpected end of JSON input" 取原文长度。
- `report`：返回 `{ detail, summary, file }`。`index.js` 在 `agent/error` 里先取走记录，是坏工具参数（`isMalformedError`）才调用 `report`，把结果作为 `toolInput` 交给两个桥；会话关掉时也丢掉记录。
- 两个桥的 `onTurnError` 新增参数 `toolInput`：只有坏工具参数时把 `detail` 渲染进 `{{detail}}`，日志多一行 `malformed tool input in <工具> at line L column C (N chars)`。
- `runtime/malformed/<时间>-<会话>.json` 存出错那次请求的全部工具调用原文、错误、回合、诊断结果。
- **补充**：用 Edit 工具改 `retry.md`、`reflect_retry.md` 时两个文件变成了 CRLF，已改回 LF；测试里加了"三个模板不含 `\r`"的检查。
