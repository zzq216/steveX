# skill：任务复盘

任务已经结束，树不会再跑。慢树每个任务重新生成、用完即弃；这次任务里值得留下的，只有存进**胶囊库**的部分。

## 胶囊是什么

- 胶囊库里的条目，下一次规划时可以直接引用：子树写 `{ "use": "trees/<name>", "params": { … } }`，代码写 `{ "compute": "code/<name>", … }` 或 `{ "cond": "code/<name>", … }`
- 规划时用 `capsule_search` 找胶囊，结果里每个条目只有**引用、种类、description、输入 / 输出名与使用统计**（用过几次、在几个任务里、成败各几次；没被用过写"尚无记录"）。要不要用、怎么用，看的就是这一行，契约、正文与统计明细再用 `capsule_get` 取——所以 description 要写清楚它做什么、什么时候用
- 胶囊**不能读调用方的任务帧**：子树里用到的外部值都要写成 `signature.inputs`，树里用 `"$名字"` 引用，调用点用 `params` 传进来；子树写出、调用方要用的值写成 `signature.outputs`
- 条目按内容哈希存，改了就是新的一版；已经存下的树钉着旧版，不受影响

## 怎么存

- **看证据**：`bt_inspect` 的 `tree`（版本链：每一版从哪来、两版之差）、`node`、`events`、`snapshot`；`bt_view` 看最终的树
- **存子树**：`capsule_save` `folder: "trees"`，`signature` + `body`（编写格式，和写大纲一样），`from` 写它在任务树里对应的节点 id
- **代码草稿转正**：`capsule_save` `folder: "code"`，`from: "task/<名字>"`；`signature` / `body` 省略就原样沿用，给了就用给的
- 子树里引用的 `task/…` 草稿：本次复盘里已经转正过的会自动换成 `code/…`；没转正的要先转正
- 子树里调用代码的节点，`read` 要和任务树里原来的节点一样：代码里的 `state.<来源>` 靠它。给了 `from` 时会对照检查，少了会被拒绝
- **同名**：库里已经有这个名字时必须写 `replaces`（它当前最新版的 hash），表示有意替换；不是同一个东西就换个名字
- 存不进去会返回逐条错误，按错误原文改了重交，不计次数

## 写死的值

保存时会把条目里的字面量和这次任务里观察到的值（快照里的格子号、物品 id、坐标，查询结果与初始黑板里的值）比对，相同就拒绝：下一次用到这个胶囊时，世界不一定还是这个样子。代码只比字符串。

- 改成参数（`signature.inputs` + `"$名字"`），或者在胶囊里读出来
- 确实是常量，就写进 `keepLiterals`：`{ "<错误里给出的位置>": "为什么是常量" }`。被拒时会附一份模板，键照抄

## 评估这次的树

- 请求里的"成本画像"是这次的树实际花了多少：执行时间（不含等 LLM 回合）、mod 调用次数、按胶囊 / 节点的分布、被重复执行的部分。需要细节用 `bt_inspect`
- 用 `task_assess` 记下成本高、耗时长、等 LLM 回合多或容易出错的地方：位置（节点 id 或胶囊引用）、问题、证据，可以附你设想的改法；**没有值得记的就写 `none` 和理由**，不必硬找问题。任务做成时，结束复盘前必须先评估
- 这条评估和这次的树一起存进任务历史：下次做同类任务时 `task_search` / `task_get` 能查到；问题挂在胶囊上时，用到这个胶囊的规划在 `capsule_search` 里也看得到
- 这次的实测改变了对某个条目"做什么、什么前提下用、大概多贵"的认识时，可以用 `capsule_describe` 改它的说明（只能改这次任务用到的、或本次复盘存下的条目；说明不在哈希里，不产生新版本）
- 请求里有"和参考过的同类任务比"时，看这次比那次多了还是少了，多了的话原因在哪
- 改进设想依赖的游戏机制（一次操作会产生什么效果、边界在哪），先用 `fact_search` 查事实库，库里没有、或引用标了 `stale`，再用 `mc_source_search` / `mc_source_read` 在本回合确认，确认了用 `fact_write` 写成事实，并按确认的结果修正设想；确认不了的，在 `idea` 里写明哪一点还没确认
- 请求里列出了"涉及这次所用版本的待核对判断"时，在 `task_assess` 的 `claims` 里逐条核对：这次的情况印证了（confirmed）、推翻了（refuted），还是说明不了（open），写明依据（这次的条件与指标）
- 存同名新版本（`replaces`）时要写 `versionNote`：改了什么、哪一版在什么情况下更好（实测还是推测）。这些判断以后用到相关版本的任务会核对
- 请求里列出了"以往任务里待验证的问题"时，在 `task_assess` 的 `review` 里逐条核对：这次解决了（resolved）、还在（open）、当时判断错了（wrong），还是受现有能力限制、换写法也改不了（blocked，以后不再核对），写明依据（如这次的指标）

## 结束

`bt_reflect_done`，`summary` 写存了什么、为什么。**什么都不存也是合法的结局**，写明理由。
